# 第5天课堂笔记：软件包、MQTT 与文件系统

> 课程主题：RT-Thread 软件包与组件、MQTT 协议、文件系统（DFS/FAL）
> 实验硬件：星火一号开发板，STM32F407ZG
> 本次作业：AHT10 采集温湿度上传 EMQX、font 分区挂载写入 Data.txt、云端指令控制 LED

## 1. 软件包

软件包是封装了底层驱动、协议栈或通用算法的功能模块。应用程序只需调用软件包提供的 API，就能减少重复开发，快速验证传感器、网络和存储功能。

### 1.1 软件包的价值

- 缩短开发周期，无需从零编写传感器驱动或协议栈。
- 复用经过社区测试的代码，稳定性更高。
- 通过 Kconfig 和 menuconfig 按需裁剪，控制 ROM、RAM 占用。

RT-Thread 软件包中心地址：<https://packages.rt-thread.org/index.html>

### 1.2 在 RT-Thread Studio 中使用软件包

1. 打开工程的 `RT-Thread Settings`。
2. 在 `RT-Thread online packages` 中找到需要的软件包并勾选。
3. 保存配置，Studio 自动执行 `pkgs --update` 下载软件包源码到 `packages` 目录。
4. 编译工程时，软件包代码会被自动加入构建。

本实验用到的软件包：

| 软件包 | 用途 | 类别 |
| --- | --- | --- |
| `aht10` | AHT10/AHT21 温湿度传感器驱动 | peripherals/sensors |
| `kawaii-mqtt` | MQTT 客户端，支持 QoS0/1/2 | iot |
| `rw007` | SPI WiFi 模块驱动 | iot |

## 2. AHT10 温湿度传感器

### 2.1 硬件连接

星火一号开发板上的 AHT21 传感器通过软件模拟 I2C3 总线连接，引脚配置为：

- SCL：PE0（引脚编号 64）
- SDA：PE1（引脚编号 65）

在 Kconfig 中通过 `BSP_USING_AHT21` 选项开启，它会自动选择 I2C3 和 AHT10 软件包。

### 2.2 不使用软件包的驱动方式

直接调用 RT-Thread I2C API 需要完成以下工作：

1. 通过 `rt_i2c_bus_device_find()` 找到 I2C 总线设备。
2. 构造 `struct rt_i2c_msg` 消息结构体，设置从机地址、读写标志和数据缓冲区。
3. 调用 `rt_i2c_transfer()` 发送命令或读取数据。
4. 根据数据手册公式将原始数据转换为温度和湿度。

AHT10 的关键命令和参数：

| 命令 | 含义 | 参数 |
| --- | --- | --- |
| `0xBE` | 校准命令 | `0x08, 0x00` |
| `0xA8` | 正常工作模式 | `0x00, 0x00` |
| `0xAC` | 触发测量 | `0x33, 0x00` |

数据转换公式：

```text
湿度 = (Data[1]<<12 | Data[2]<<4 | (Data[3]&0xf0)>>4) * 100.0 / (1<<20)
温度 = ((Data[3]&0x0f)<<16 | Data[4]<<8 | Data[5]) * 200.0 / (1<<20) - 50
```

### 2.3 使用软件包的驱动方式

启用 AHT10 软件包后，只需要三个 API：

```c
aht10_device_t aht10_init(const char *i2c_bus_name);  // 初始化
float aht10_read_temperature(aht10_device_t dev);     // 读温度
float aht10_read_humidity(aht10_device_t dev);        // 读湿度
```

对比直接操作 I2C 的方式，软件包大幅简化了应用层代码，传感器时序和数据处理都由软件包内部完成。

### 2.4 浮点输出注意事项

RT-Thread 默认的 `rt_kprintf` 不支持 `%f` 格式。如果要打印浮点数，有两种方式：

- 启用 `rt_vsprintf_full` 软件包，直接使用 `%f`。
- 拆分整数和小数部分，用 `%d.%d` 输出。

本次作业采用第二种方式：

```c
rt_kprintf("Temp: %d.%d\n", (int)temp, (int)(temp * 10) % 10);
```

## 3. MQTT 协议

### 3.1 基本模型

MQTT 是一种轻量级的发布/订阅消息协议，适合资源受限的嵌入式设备和带宽有限的网络环境。

| 概念 | 说明 |
| --- | --- |
| Client | 客户端，即设备或应用，可以发布、订阅、连接和断开 |
| Server (Broker) | 服务端，维护连接、接收消息并转发给匹配的订阅者 |
| Topic | 主题名，对消息分层分类，例如 `rsoc/sensor/temperature` |
| Publish | 发布，将消息发送到指定主题 |
| Subscribe | 订阅，声明客户端希望接收哪些主题的消息 |

### 3.2 QoS 等级

| 等级 | 含义 | 典型场景 |
| --- | --- | --- |
| QoS 0 | 最多一次，不确认，可能丢失 | 高频环境数据 |
| QoS 1 | 至少一次，可能重复 | 报警、控制命令 |
| QoS 2 | 恰好一次，开销最高 | 不能重复的关键消息 |

### 3.3 主题设计

主题区分大小写，支持通配符 `+`（匹配单层）和 `#`（匹配多层）。公共 Broker 上的主题对所有用户可见，应避免使用 `test`、`hello` 等常见名称。

本次作业的主题设计：

```text
板卡发布，MQTTX 订阅：rsoc/spark05/device/up
MQTTX 发布，板卡订阅：rsoc/spark05/device/down
```

### 3.4 kawaii-mqtt 软件包

kawaii-mqtt 是基于 socket API 的跨平台 MQTT 客户端，API 简洁，支持 QoS2 和 mbedtls 加密。

核心 API：

```c
mqtt_client_t *mqtt_lease(void);                    // 申请客户端
void mqtt_set_host(mqtt_client_t *c, char *host);   // 设置服务器地址
void mqtt_set_port(mqtt_client_t *c, char *port);   // 设置端口
void mqtt_set_client_id(mqtt_client_t *c, char *id);// 设置客户端ID
int  mqtt_connect(mqtt_client_t *c);                // 连接服务器
int  mqtt_subscribe(mqtt_client_t *c, const char *topic,
                    mqtt_qos_t qos, message_handler_t handler);  // 订阅
int  mqtt_publish(mqtt_client_t *c, const char *topic,
                  mqtt_message_t *msg);             // 发布
```

### 3.5 EMQX 公共 Broker

本实验使用 EMQX 免费公共 MQTT Broker：

| 配置项 | 值 |
| --- | --- |
| Host | `broker.emqx.io` |
| Port | `1883`（TCP，未加密） |
| 用户名 | 留空 |
| 密码 | 留空 |
| MQTT Version | `3.1.1`（kawaii-mqtt 中设为 4） |

公共 Broker 只适合学习和功能验证，不能用于生产环境。

### 3.6 使用 MQTTX 验证

MQTTX 是跨平台 MQTT 客户端工具，可以在电脑上模拟另一个 MQTT 设备，与开发板进行双向收发验证。

验证步骤：

1. MQTTX 订阅 `rsoc/spark05/device/up`，确认能收到板卡发布的温湿度 JSON。
2. MQTTX 向 `rsoc/spark05/device/down` 发送消息，确认板卡回调收到并翻转 LED。

如果 MQTTX 能连接但收不到数据，优先核对主题方向：板卡的发布主题必须等于 MQTTX 的订阅主题。

## 4. 文件系统

### 4.1 DFS 架构

DFS（Device File System）是 RT-Thread 的虚拟文件系统组件，向上提供统一的路径和文件操作接口，向下对接 FatFS、RomFS、DevFS 等不同文件系统以及块设备。

```text
应用层
  open() / read() / write() / close()
        |
DFS 虚拟文件系统层
  dfs_mount() / dfs_mkfs()
        |
具体文件系统（FatFS / RomFS / DevFS）
        |
块设备（FAL 分区 -> W25Q64）
```

### 4.2 常见文件系统类型

| 类型 | 特点 |
| --- | --- |
| FatFS | 兼容 FAT 格式，可读写，适合 SD 卡和 SPI Flash |
| RomFS | 只读，适合固件内置资源 |
| DevFS | 将设备映射到 `/dev` 目录 |
| UFFS | 面向 NAND Flash 的轻量级文件系统 |

### 4.3 POSIX 接口

在 RT-Thread 中，文件操作使用 POSIX 接口：

| API | 说明 |
| --- | --- |
| `open(path, flags, mode)` | 打开/创建文件 |
| `write(fd, buf, len)` | 写入文件 |
| `read(fd, buf, len)` | 读取文件 |
| `close(fd)` | 关闭文件 |
| `mkdir(path, mode)` | 创建目录 |
| `opendir(path)` | 打开目录 |
| `readdir(dirp)` | 读取目录项 |
| `closedir(dirp)` | 关闭目录 |

文件描述符 `fd` 是整数句柄，调用 `open()` 成功后必须在所有退出路径调用 `close()`。

### 4.4 文件系统启动流程

1. DFS 组件初始化：系统启动时初始化文件系统注册表、文件描述符表和锁。
2. 注册文件系统类型：FatFS、RomFS 等通过初始化函数注册到 DFS。
3. 格式化并挂载：块设备首次使用时需要格式化，然后挂载到路径。自动挂载功能可以在启动阶段完成这一步。

## 5. FAL 与 SFUD

### 5.1 SFUD

SFUD（Serial Flash Universal Driver）是串行 Flash 通用驱动库，屏蔽不同 SPI NOR Flash 在命令上的差异，为上层提供统一的设备访问接口。

### 5.2 FAL

FAL（Flash Abstraction Layer）是 Flash 抽象层，管理 Flash 设备和分区，向文件系统、OTA 等上层提供统一的分区访问接口。

两者的职责区分：

- SFUD 负责"如何和具体 Flash 芯片通信"。
- FAL 负责"如何把 Flash 划分成可管理的逻辑分区"。

### 5.3 星火一号的 FAL 分区表

W25Q64（8MB SPI Flash）的分区定义如下（非 bootloader 模式）：

| 分区名 | Flash 设备 | 偏移 | 大小 |
| --- | --- | --- | --- |
| easyflash | W25Q64 | 0 | 512KB |
| download | W25Q64 | 512KB | 1024KB |
| wifi_image | W25Q64 | 1536KB | 512KB |
| font | W25Q64 | 2048KB | 3072KB |
| filesystem | W25Q64 | 5120KB | 3072KB |

本次作业挂载的是 `font` 分区，大小 3MB，足够存储温湿度记录数据。

### 5.4 数据链路

```text
SPI 控制器
  -> spi20 设备
  -> SFUD W25Q64 设备
  -> FAL font 分区
  -> 块设备（fal_blk_device_create）
  -> FatFS (elm)
  -> DFS 挂载点 /fal
  -> POSIX 文件 API（open/write/read/close）
```

### 5.5 挂载 font 分区

代码中的挂载流程：

```c
fal_init();                                    // 初始化 FAL
fal_blk_device_create("font");                 // 为 font 分区创建块设备
dfs_mount("font", "/fal", "elm", 0, 0);        // 挂载 FatFS 到 /fal
```

首次使用时 `dfs_mount` 会失败，需要先格式化：

```c
dfs_mkfs("elm", "font");                       // 格式化为 FatFS
dfs_mount("font", "/fal", "elm", 0, 0);        // 重新挂载
```

也可以用 MSH 命令手动操作：

```text
msh > fal probe
msh > mkfs -t elm font
msh > mount font /fal
msh > ls /fal
```

## 6. 完整作业实现

本次作业将三个要求整合到一个 `main.c` 文件中，通过 MSH 命令 `start_app` 启动。

### 6.1 功能架构

```text
start_app (MSH 命令)
  |
  +-> led_init()          初始化 LED 引脚
  +-> fs_init()           挂载 font 分区到 /fal
  +-> 创建 sensor 线程
        |
        +-> 等待网络就绪（8秒）
        +-> aht10_init("i2c3")          初始化温湿度传感器
        +-> mqtt_app_init()             连接 broker.emqx.io:1883
        +-> 循环采集：
              +-> 读取温湿度
              +-> save_to_file()        写入 /fal/Data.txt（作业2）
              +-> mqtt_publish()        发布 JSON 到云端（作业1）
              +-> mqtt_sub_callback()   收到指令翻转 LED（作业3）
```

### 6.2 MQTT 主题与数据格式

发布主题 `rsoc/spark05/device/up`，Payload 为简短 JSON：

```json
{"temperature":26.1,"humidity":45.2,"count":1}
```

订阅主题 `rsoc/spark05/device/down`，收到任意消息后翻转 LED。

### 6.3 文件内容格式

`/fal/Data.txt` 内容，使用全角冒号匹配作业要求：

```text
Temp：26.1 ; Humi：45.2 ; Count： 1
Temp：26.1 ; Humi：45.3 ; Count： 2
Temp：26.2 ; Humi：45.2 ; Count： 3
```

### 6.4 运行步骤

编译下载后，在 MSH 中操作：

```text
msh > wlan autoconnect enable
msh > wlan connect <WiFi名> <WiFi密码>
msh > ifconfig                # 确认拿到 IP
msh > start_app               # 启动作业应用
```

预期串口输出：

```text
[APP] waiting for network...
[APP] AHT10 init success
[MQTT] connected, subscribed: rsoc/spark05/device/down
[DATA] Temp: 26.1, Humi: 45.2, Count: 1
[DATA] Temp: 26.1, Humi: 45.3, Count: 2
```

用 MQTTX 验证：

1. 订阅 `rsoc/spark05/device/up`，看到温湿度 JSON。
2. 向 `rsoc/spark05/device/down` 发送消息，板卡 LED 翻转并打印 `[LED] ON/OFF`。

用 MSH 验证文件系统：

```text
msh > ls /fal
msh > cat /fal/Data.txt
```

## 7. 需要开启的工程配置

在 `RT-Thread Settings` 中需要勾选的选项：

| 配置路径 | 选项 |
| --- | --- |
| Hardware Drivers -> Onboard | Enable AHT21(i2c3) |
| Hardware Drivers -> Onboard | Enable Rw007 Wlan Base on SPI2 |

| online packages -> IoT | kawaii-mqtt（version 设为 4） |

保存后执行 `pkgs --update` 下载软件包，然后重新编译。

## 8. 故障排查

| 现象 | 检查项 |
| --- | --- |
| AHT10 初始化失败 | Kconfig 是否开启 I2C3、总线名是否为 `i2c3` |
| MQTT 连接失败 | WiFi 是否已连接、`ifconfig` 是否有 IP、Broker 地址和端口是否正确 |
| MQTTX 收不到数据 | 主题方向是否一致、Client ID 是否冲突 |
| 文件系统挂载失败 | font 分区是否已格式化、FAL 分区表是否编译进工程 |
| 重启后文件丢失 | 是否启用自动挂载、写入后是否正确关闭文件 |
| 温湿度一直为零 | 传感器是否完成校准、测量命令后等待时间是否足够 |

## 9. 本节小结

第五天的核心是把软件包、网络通信和文件系统串联起来，形成一个完整的物联网数据采集链路：

1. AHT10 软件包简化了 I2C 传感器驱动开发，应用层只需调用 `aht10_init/read` 三个函数。
2. kawaii-mqtt 提供简洁的 MQTT 客户端 API，通过 EMQX 公共 Broker 实现设备与云端的双向通信。
3. DFS + FAL + FatFS 构成从 SPI Flash 到文件操作的完整链路，font 分区挂载后可用标准 POSIX 接口读写文件。
4. 三者结合后，开发板实现了"采集温湿度 -> 上传云端 -> 本地存储 -> 远程控制 LED"的完整 IoT 应用。
