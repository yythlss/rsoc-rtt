# 第4天课堂笔记：RT-Thread 设备驱动框架与 PIN 设备对接

> 课程主题：RT-Thread 设备驱动框架与 IO 外设开发  
> 核心内容：设备驱动分层架构、`rt_device` 与 ops 回调、PIN 设备对接链路、虚拟设备驱动框架 `test_dev`

## 1. 为什么需要设备驱动框架

不同 MCU 厂商对外设寄存器、库函数和初始化方式定义不同。如果应用层直接调用厂商 API，代码会与具体芯片绑定，换一颗 MCU 后几乎要重写业务逻辑。

RT-Thread 的思路是把外设抽象成统一设备，由驱动层负责对接具体硬件：

- 上层应用只使用 `open / close / read / write / control` 等标准接口。
- 底层驱动负责把标准接口转换为 STM32 HAL 调用。
- 换用不同 MCU 时，通常只需要替换或适配底层驱动，应用代码可以继续复用。

这种“驱动与应用分离”的设计，是嵌入式代码可移植性和可维护性的基础。

## 2. 设备框架的三层结构

| 层级 | 主要工作 | 典型对象或函数 |
| --- | --- | --- |
| 应用层 | 查找、打开并使用设备 | `rt_device_find`、`rt_device_open`、`rt_device_read` |
| IO 设备管理层 | 注册、查找、引用计数和统一访问入口 | `rt_device_create`、`rt_device_register`、`rt_device` |
| 驱动层 | 对接具体硬件，提供真实读写实现 | `init / open / close / read / write / control` |

调用链路可以理解为：

```text
应用层
  -> rt_device_find / rt_device_open
  -> rt_device_read / rt_device_write / rt_device_control
      -> rt_device 中的 ops 函数指针
          -> STM32 HAL 或自定义虚拟设备实现
```

## 3. `rt_device` 与 ops 回调

`rt_device` 是设备框架的核心结构，它把设备属性和操作方法封装在一起，本质上是一种 C 语言中的面向对象设计。

常见成员包括：

- `type`：字符设备或块设备等类型。
- `flag`：设备打开标志，例如 `RT_DEVICE_FLAG_RDWR`。
- `ref_count`：打开引用计数。
- `user_data`：驱动私有数据，用于保存当前设备状态。
- `init / open / close / read / write / control`：指向驱动层实现的操作函数。

驱动注册时的典型流程：

```c
rt_device_t dev = rt_device_create(RT_Device_Class_Char, 0);

dev->init    = test_dev_init;
dev->open    = test_dev_open;
dev->close   = test_dev_close;
dev->read    = test_dev_read;
dev->write   = test_dev_write;
dev->control = test_dev_control;

rt_device_register(dev, "test_dev", RT_DEVICE_FLAG_RDWR);
```

注册完成后，设备会挂载到 IO 设备管理系统的链表中，可在 MSH 中使用 `list_device` 查看。

## 4. 设备生命周期

一次完整的设备访问通常包含以下过程：

1. 驱动初始化时创建并注册设备。
2. 系统通过引用计数管理设备打开状态。
3. 应用层使用 `rt_device_find` 找到设备。
4. 应用层使用 `rt_device_open` 打开设备。
5. 应用层通过 `read / write / control` 操作设备。
6. 应用层使用 `rt_device_close` 关闭设备。

打开和关闭对应引用计数的增减。只有应用层与驱动层都遵守这套生命周期，系统才能在多个任务同时访问设备时正确管理资源。

## 5. PIN 设备如何对接

PIN 设备是理解“统一 API 到具体硬件”的最佳例子。应用层看到的是简洁的 PIN API：

```c
rt_pin_mode(pin, mode);        // 配置输入/输出等模式
rt_pin_read(pin);              // 读取引脚电平
rt_pin_write(pin, value);      // 设置引脚电平
rt_pin_attach_irq(pin, mode, hdr, args); // 注册中断回调
```

底层对接链路大致如下：

| 上层 PIN API | 驱动层动作 | STM32 HAL 层动作 |
| --- | --- | --- |
| `rt_pin_mode` | 把模式转换为 STM32 引脚模式 | `HAL_GPIO_Init` |
| `rt_pin_read` | 读取引脚状态 | `HAL_GPIO_ReadPin` |
| `rt_pin_write` | 设置引脚状态 | `HAL_GPIO_WritePin` |
| `rt_pin_attach_irq` | 配置 EXTI 中断并挂载回调 | `HAL_GPIO_EXTI_IRQHandler`、`EXTI_IRQHandler` |

以 STM32 为例，`GET_PIN(port, pin)` 把逻辑引脚编号映射到具体的 GPIO 端口和引脚；中断触发后，底层中断服务函数再回调到 RT-Thread 的 PIN 驱动，最后通知应用层注册的回调函数。这样应用层就无需关心具体芯片的 GPIO 寄存器地址和 EXTI 编号。

按键实验中出现的“一次按键触发两次中断”，通常是机械抖动造成的。解决方式可以是加入软件延时消抖，也可以使用 RT-Thread 的 `button` 软件包统一处理。

## 6. 虚拟设备驱动框架 `test_dev`

本次作业完成了一个虚拟字符设备 `test_dev`，它不直接操作真实硬件，而是用一个结构体保存状态，用来验证设备框架的注册、查找、打开、读写和控制流程。

`test_dev.c` 的核心分层关系：

```text
应用层 MSH 命令 test_dev_demo
    -> rt_device_find / open / write / read / control / close
        -> test_dev 的 ops 实现
            -> test_dev_data 中的 value
```

设备控制命令定义如下：

```c
#define TEST_DEV_CTRL_GET_VALUE (RT_DEVICE_CTRL_BASE(Char) + 1)
#define TEST_DEV_CTRL_SET_VALUE (RT_DEVICE_CTRL_BASE(Char) + 2)
#define TEST_DEV_CTRL_RESET     (RT_DEVICE_CTRL_BASE(Char) + 3)
```

`test_dev` 在系统启动阶段通过 `INIT_DEVICE_EXPORT(test_dev_register)` 自动注册，同时导出 MSH 命令 `test_dev_demo` 用于验证。

## 7. 在 RT-Thread Studio 中查看运行结果

1. 编译整个工程，确认 `test_dev.c` 被加入构建。
2. 下载程序到星火一号开发板。
3. 打开串口终端，进入 RT-Thread MSH 命令行。
4. 输入 `list_device`，确认列表中包含 `test_dev`。
5. 输入 `test_dev_demo`，观察标准设备接口的执行结果。

输出：

```text
test_dev init
test_dev open
write then read: 1234
control get: 5678
after reset: 0
test_dev close
```

这些输出分别对应初始化、打开、写入后读回、`control` 设置/获取值、复位以及关闭设备，说明虚拟设备已经正确接入 RT-Thread 设备框架。

## 8. 本课小结

RT-Thread 设备框架的价值在于把不同厂商的硬件差异隐藏在驱动层之下，让应用层使用统一的设备 API。`rt_device` 是统一入口，ops 函数指针负责分发到具体实现；PIN 设备通过这套机制把 `rt_pin_*` 接口映射到 STM32 HAL；自定义 `test_dev` 又用相同机制验证了设备框架的完整生命周期。

掌握这一条链路后，后续 I2C、SPI、串口等复杂外设也可以按照“总线控制器或设备驱动层负责硬件细节，应用层调用统一接口”的方式接入。
