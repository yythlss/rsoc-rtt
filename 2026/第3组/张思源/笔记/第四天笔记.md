# 第四天笔记 - PIN 设备驱动框架分析

## 一、设备驱动框架概述

RT-Thread 的设备驱动框架采用**三层架构**，将应用、框架和硬件隔离，实现代码复用与可移植性：

```
应用层          rt_pin_mode() / rt_pin_write() / rt_pin_read()
  |             用户直接调用的 API，无需关心底层硬件
  v
框架层          pin.c / pin.h
  |             定义 ops 接口表，提供注册函数和用户 API
  |             连接应用层与 BSP 层
  v
BSP层           drv_gpio.c
                实现具体芯片的 ops，启动时注册设备
```

**核心思想**：框架层定义"接口"（`rt_pin_ops`），BSP 层"实现"接口，应用层通过框架层提供的 API 间接调用。只要 BSP 层实现了 ops 接口，应用层代码无需任何修改即可在不同芯片上运行。

## 二、关键数据结构

### 1. PIN 设备结构体（pin.h:22-26）

```c
struct rt_device_pin
{
    struct rt_device parent;      // 继承 RT-Thread 通用设备（包含 type、open、read 等标准字段）
    const struct rt_pin_ops *ops; // PIN 设备专属的操作接口表
};
```

`parent` 是 RT-Thread 通用设备基类，通过 `rt_device_register()` 注册到设备管理器后，可以用 `rt_device_find("pin")` 查找到。`ops` 是框架层自定义的接口表，存放 BSP 层实现的硬件操作函数。

### 2. PIN 操作接口表（pin.h:65-75）

```c
struct rt_pin_ops
{
    void (*pin_mode)(struct rt_device *device, rt_base_t pin, rt_base_t mode);
    void (*pin_write)(struct rt_device *device, rt_base_t pin, rt_base_t value);
    int (*pin_read)(struct rt_device *device, rt_base_t pin);
    rt_err_t (*pin_attach_irq)(struct rt_device *device, rt_int32_t pin,
                               rt_uint32_t mode, void (*hdr)(void *args), void *args);
    rt_err_t (*pin_detach_irq)(struct rt_device *device, rt_int32_t pin);
    rt_err_t (*pin_irq_enable)(struct rt_device *device, rt_base_t pin, rt_uint32_t enabled);
    rt_base_t (*pin_get)(const char *name);
};
```

7 个函数指针的含义：

| 函数指针 | 作用 |
| --- | --- |
| `pin_mode` | 配置引脚工作模式（输出/输入/上拉/下拉/开漏） |
| `pin_write` | 写引脚电平（高/低） |
| `pin_read` | 读引脚电平 |
| `pin_attach_irq` | 挂载中断回调函数 |
| `pin_detach_irq` | 解除中断回调函数 |
| `pin_irq_enable` | 使能/失能引脚中断 |
| `pin_get` | 从引脚名（如 "PA.0"）解析出引脚编号 |

### 3. 引脚模式与电平宏定义（pin.h:28-44）

```c
#define PIN_LOW                 0x00
#define PIN_HIGH                0x01

#define PIN_MODE_OUTPUT         0x00    // 推挽输出
#define PIN_MODE_INPUT          0x01    // 浮空输入
#define PIN_MODE_INPUT_PULLUP   0x02    // 上拉输入
#define PIN_MODE_INPUT_PULLDOWN 0x03    // 下拉输入
#define PIN_MODE_OUTPUT_OD      0x04    // 开漏输出

#define PIN_IRQ_MODE_RISING         0x00    // 上升沿触发
#define PIN_IRQ_MODE_FALLING        0x01    // 下降沿触发
#define PIN_IRQ_MODE_RISING_FALLING 0x02    // 双沿触发
```

## 三、注册流程

### 1. BSP 层入口（drv_gpio.c:749-799）

```c
int rt_hw_pin_init(void)
{
    /* 使能 GPIOA ~ GPIOK 时钟 */
    __HAL_RCC_GPIOA_CLK_ENABLE();
    __HAL_RCC_GPIOB_CLK_ENABLE();
    // ...

    return rt_device_pin_register("pin", &_stm32_pin_ops, RT_NULL);
}
```

`rt_hw_pin_init()` 在系统启动阶段（`rt_hw_board_init()` 内）被调用，先使能 GPIO 时钟，再将 BSP 层实现的 `_stm32_pin_ops` 传给框架层进行注册。

### 2. 框架层注册（pin.c:78-102）

```c
static struct rt_device_pin _hw_pin;  // 全局唯一的 PIN 设备实例

int rt_device_pin_register(const char *name, const struct rt_pin_ops *ops, void *user_data)
{
    _hw_pin.parent.type    = RT_Device_Class_Pin;
    _hw_pin.parent.rx_indicate = RT_NULL;
    _hw_pin.parent.tx_complete = RT_NULL;

    /* 挂载框架层的中间层函数到通用设备的 read/write/control */
    _hw_pin.parent.read    = _pin_read;
    _hw_pin.parent.write   = _pin_write;
    _hw_pin.parent.control = _pin_control;

    /* 关键：保存 BSP 层传入的 ops 接口表 */
    _hw_pin.ops             = ops;
    _hw_pin.parent.user_data = user_data;

    /* 注册到 RT-Thread 设备管理器 */
    rt_device_register(&_hw_pin.parent, name, RT_DEVICE_FLAG_RDWR);
    return 0;
}
```

注册过程做了两件事：
1. 将框架层的 `_pin_read/_pin_write/_pin_control` 挂到通用设备的 `read/write/control` 上（这样通过 `rt_device_find("pin")` + `rt_device_read()` 也能用）
2. 将 BSP 层的 `ops` 存入 `_hw_pin.ops`，供 `rt_pin_mode/write/read` 等专用 API 直接调用

### 3. BSP 层的 ops 实现（drv_gpio.c:505-514）

```c
const static struct rt_pin_ops _stm32_pin_ops =
{
    stm32_pin_mode,
    stm32_pin_write,
    stm32_pin_read,
    stm32_pin_attach_irq,
    stm32_pin_dettach_irq,
    stm32_pin_irq_enable,
    stm32_pin_get,
};
```

BSP 层将所有硬件操作函数填充到 `rt_pin_ops` 结构体中，形成一张函数指针表。

## 四、用户 API 调用链

以 `rt_pin_write()` 为例，分析从应用层到硬件寄存器的完整调用链：

### 第一步：应用层 API（pin.c:142-146）

```c
void rt_pin_write(rt_base_t pin, rt_base_t value)
{
    RT_ASSERT(_hw_pin.ops != RT_NULL);
    _hw_pin.ops->pin_write(&_hw_pin.parent, pin, value);
}
```

应用层 API 直接访问全局变量 `_hw_pin`，通过 `ops->pin_write` 函数指针跳转到 BSP 层实现。

### 第二步：BSP 层实现（drv_gpio.c:206-218）

```c
static void stm32_pin_write(rt_device_t dev, rt_base_t pin, rt_base_t value)
{
    GPIO_TypeDef *gpio_port;
    uint16_t gpio_pin;

    if (PIN_PORT(pin) < PIN_STPORT_MAX)
    {
        gpio_port = PIN_STPORT(pin);   // 从 pin 编码解码出 GPIO 端口地址
        gpio_pin = PIN_STPIN(pin);     // 从 pin 编码解码出引脚位掩码
        HAL_GPIO_WritePin(gpio_port, gpio_pin, (GPIO_PinState)value);  // 调用 STM32 HAL 库
    }
}
```

### 第三步：HAL 库

`HAL_GPIO_WritePin()` 最终操作 STM32 的 GPIO 寄存器（BSRR/ODR），完成电平输出。

**完整调用链**：

```
rt_pin_write(pin, value)                        [应用层, pin.c:142]
  -> _hw_pin.ops->pin_write(&_hw_pin.parent, pin, value)  [框架层, 通过函数指针跳转]
    -> stm32_pin_write(dev, pin, value)         [BSP层, drv_gpio.c:206]
      -> HAL_GPIO_WritePin(gpio_port, gpio_pin, value)  [HAL库]
        -> 写 GPIO->BSRR 寄存器                  [硬件寄存器]
```

其他 API（`rt_pin_mode`、`rt_pin_read`、`rt_pin_attach_irq`、`rt_pin_irq_enable`）的调用链结构完全相同。

## 五、GET_PIN 宏与引脚编码

### 1. 编码方式（drv_gpio.c:19-21）

```c
#define PIN_NUM(port, no)  ((((port) & 0xFu) << 4) | ((no) & 0xFu))
#define PIN_PORT(pin)      ((uint8_t)(((pin) >> 4) & 0xFu))
#define PIN_NO(pin)         ((uint8_t)((pin) & 0xFu))
```

引脚编号是一个 `rt_base_t`（32 位整数），高 4 位存储端口号，低 4 位存储引脚号：

```
  bit 7  6  5  4 | 3  2  1  0
 [  端口号 port ] | [ 引脚号 no ]
```

例如 `GET_PIN(C, 5)`：端口 C 是第 2 个端口（A=0, B=1, C=2），引脚号 5，编码结果 = `(2 << 4) | 5` = `0x25` = 37。

### 2. 端口地址解码（drv_gpio.c:31）

```c
#define PIN_STPORT(pin) ((GPIO_TypeDef *)(GPIOA_BASE + (0x400u * PIN_PORT(pin))))
```

STM32 各 GPIO 端口基地址以 0x400 递增（GPIOA_BASE=0x40020000, GPIOB_BASE=0x40020400, ...），通过端口号乘以 0x400 即可计算出对应端口的寄存器基地址。

### 3. 引脚位掩码解码（drv_gpio.c:34）

```c
#define PIN_STPIN(pin) ((uint16_t)(1u << PIN_NO(pin)))
```

将引脚号转换为 16 位掩码，例如引脚 5 对应 `0x0020`（bit 5 置 1）。

## 六、框架层的中间层函数

框架层在 `rt_device_pin_register()` 中还挂载了三个中间层函数到通用设备的 `read/write/control` 上，用于支持通过 `rt_device_find()` + `rt_device_read/write/control()` 的方式访问：

### _pin_write（pin.c:32-47）

```c
static rt_size_t _pin_write(rt_device_t dev, rt_off_t pos, const void *buffer, rt_size_t size)
{
    struct rt_device_pin_status *status;
    struct rt_device_pin *pin = (struct rt_device_pin *)dev;

    status = (struct rt_device_pin_status *)buffer;
    if (status == RT_NULL || size != sizeof(*status))
        return 0;

    pin->ops->pin_write(dev, (rt_base_t)status->pin, (rt_base_t)status->status);
    return size;
}
```

通用设备的 `write` 接口参数是 `(dev, pos, buffer, size)`，而 PIN 的 `pin_write` 参数是 `(dev, pin, value)`。中间层函数负责将 `buffer`（`rt_device_pin_status` 结构体）拆包，转换成 `pin_write` 需要的参数格式，再调用 `ops->pin_write`。

### _pin_control（pin.c:49-64）

```c
static rt_err_t _pin_control(rt_device_t dev, int cmd, void *args)
{
    struct rt_device_pin_mode *mode;
    struct rt_device_pin *pin = (struct rt_device_pin *)dev;

    mode = (struct rt_device_pin_mode *)args;
    if (mode == RT_NULL)
        return -RT_ERROR;

    pin->ops->pin_mode(dev, (rt_base_t)mode->pin, (rt_base_t)mode->mode);
    return 0;
}
```

`_pin_control` 将通用 `control(dev, cmd, args)` 的 `args` 解释为 `rt_device_pin_mode` 结构体，从中取出 `pin` 和 `mode`，调用 `ops->pin_mode`。

**两种访问方式的对比**：

| 方式 | API | 说明 |
| --- | --- | --- |
| 专用 API（推荐） | `rt_pin_write(pin, value)` | 参数语义清晰，直接调用 ops |
| 通用设备 API | `rt_device_find("pin")` + `rt_device_write(dev, 0, &status, sizeof(status))` | 需要构造结构体，参数不直观 |

## 七、中断机制

### 1. 挂载中断回调（pin.c:104-113）

```c
rt_err_t rt_pin_attach_irq(rt_int32_t pin, rt_uint32_t mode,
                           void (*hdr)(void *args), void *args)
{
    RT_ASSERT(_hw_pin.ops != RT_NULL);
    if (_hw_pin.ops->pin_attach_irq)
    {
        return _hw_pin.ops->pin_attach_irq(&_hw_pin.parent, pin, mode, hdr, args);
    }
    return -RT_ENOSYS;
}
```

### 2. BSP 层中断回调表（drv_gpio.c:146-164）

BSP 层维护一个全局数组 `pin_irq_hdr_tab[]`，16 个表项对应 16 个引脚位（GPIO_PIN_0 ~ GPIO_PIN_15），每个表项记录该引脚的中断回调函数、触发模式和参数。

```c
static struct rt_pin_irq_hdr pin_irq_hdr_tab[] =
{
    {-1, 0, RT_NULL, RT_NULL},  // pin=-1 表示未使用
    // ... 共 16 项
};
```

### 3. 中断使能流程

```
rt_pin_irq_enable(pin, PIN_IRQ_ENABLE)
  -> stm32_pin_irq_enable()
    -> 根据 pin_irq_hdr_tab 中的 mode 配置 GPIO 为中断模式
    -> HAL_NVIC_SetPriority() 设置优先级
    -> HAL_NVIC_EnableIRQ() 使能 NVIC 中断
```

### 4. 中断响应流程

```
硬件产生 EXTI 中断
  -> EXTIx_IRQHandler()           [drv_gpio.c:690, ISR 入口]
    -> rt_interrupt_enter()        [进入中断上下文]
    -> HAL_GPIO_EXTI_IRQHandler()  [HAL 库清中断标志]
      -> HAL_GPIO_EXTI_Callback() [HAL 库弱函数回调]
        -> pin_irq_hdr(irqno)      [drv_gpio.c:516, 查表调回调]
          -> pin_irq_hdr_tab[irqno].hdr(args)  [执行用户回调]
    -> rt_interrupt_leave()        [退出中断上下文]
```

## 八、为什么用 ops 模式（函数指针表）

### 对比：如果不用 ops 会怎样？

假设不使用 ops 模式，框架层直接调用 BSP 层函数：

```c
void rt_pin_write(rt_base_t pin, rt_base_t value)
{
    stm32_pin_write(pin, value);  // 直接调用 STM32 实现
}
```

问题：
1. **不可移植**：换芯片（如从 STM32 换到 GD32）必须修改框架层代码
2. **框架层依赖 BSP 层**：违反分层原则，框架层不应该知道具体芯片实现
3. **无法替换**：运行时无法切换不同实现

### 使用 ops 的优势

```c
void rt_pin_write(rt_base_t pin, rt_base_t value)
{
    _hw_pin.ops->pin_write(&_hw_pin.parent, pin, value);  // 通过函数指针间接调用
}
```

1. **解耦**：框架层只依赖 `rt_pin_ops` 接口定义，不依赖任何具体芯片实现
2. **可移植**：换芯片只需实现新的 `rt_pin_ops` 并注册，框架层和应用层零修改
3. **符合面向对象思想**：ops 本质是"虚函数表"，`rt_pin_ops` 是接口，`_stm32_pin_ops` 是实现

## 九、PIN 框架 vs 通用 rt_device 框架

| 对比项 | PIN 框架 | 通用 rt_device |
| --- | --- | --- |
| 设备结构体 | `struct rt_device_pin`（继承 rt_device + 自定义 ops） | `struct rt_device` |
| ops 定义 | `struct rt_pin_ops`（pin_mode/pin_write/pin_read...） | 无自定义 ops，直接用 rt_device 的 init/open/read/write/control |
| 用户 API | `rt_pin_write(pin, value)` 语义化 | `rt_device_write(dev, pos, buf, size)` 通用 |
| 参数传递 | 直接传 pin 号和值 | 通过结构体包装（rt_device_pin_status） |
| 适用场景 | 引脚操作，语义明确 | 通用字符/块设备，接口统一 |

PIN 框架在通用 `rt_device` 基础上**增加了一层语义化封装**：自定义 ops 提供更贴合引脚操作的接口，用户 API 参数更直观（直接传引脚号和电平值，而非 buffer+offset）。

## 十、总结

PIN 设备驱动框架的核心设计：

1. **分层**：应用层 -> 框架层(pin.c) -> BSP层(drv_gpio.c)，各层职责清晰
2. **接口隔离**：框架层定义 `rt_pin_ops` 接口，BSP 层实现，通过函数指针表连接
3. **注册机制**：BSP 层在启动时调用 `rt_device_pin_register()` 将 ops 注入框架层，再注册到设备管理器
4. **双通道访问**：既支持专用 API（`rt_pin_write`，推荐），也支持通用设备 API（`rt_device_find` + `rt_device_write`）
5. **可移植性**：换芯片只需实现新的 `rt_pin_ops` 并在 `rt_hw_pin_init()` 中注册，框架和应用代码无需修改
