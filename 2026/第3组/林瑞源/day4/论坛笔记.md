## 为什么要分层？

写裸机的时候，换个芯片就要重写一堆业务代码——因为应用逻辑和硬件操作搅在一起了。RT-Thread 的设备框架把这层剥开：上层应用用 `open/read/write/close` 操作设备，底层驱动只管对接硬件寄存器，中间靠 IO 管理层分发。

换芯片时上层代码不用动，只要适配底层驱动就行。

## 设备驱动的核心：ops 函数指针

所有设备都有一个 `rt_device` 结构体，里面挂着一组函数指针（ops）：

```
init / open / close / read / write / control
```

驱动层的活儿就是实现这些函数，然后赋值到设备对象上。应用层调用 `rt_device_read()` 时，IO 管理层帮你转发到驱动层的 `read` 函数——应用代码完全不知道底下是 GPIO 还是 SPI 还是虚拟设备。

## PIN 设备对接链路

以 `rt_pin_write(GET_PIN(B, 5), PIN_HIGH)` 为例，完整调用链：

```
应用层:  rt_pin_write(21, PIN_HIGH)
  ↓
PIN 抽象层: _pin_ops->pin_write()
  ↓
BSP 驱动层: stm32_pin_write() → HAL_GPIO_WritePin()
  ↓
硬件层: GPIOB->BSRR = GPIO_PIN_5
```

关键设计：
- **GET_PIN(port, pin)** 把物理引脚转成逻辑编号（`16*(port-'A') + pin`），上层不碰寄存器
- **pins[] 数组** 在 BSP 驱动层做逻辑号 → `{GPIOx, GPIO_PIN_x}` 映射
- **中断回调** 用 `pin_irq_hdr_tab[]` 表管理，硬件 EXTI 触发后查表调回调

## 虚拟设备 test_dev

作业要求设计一个虚拟设备驱动框架层。我做了个纯内存的字符设备 `test_dev`——不接真实硬件，数据在缓冲区里读写，但完整走了一遍框架流程：

**驱动层（test_drv.c）**：
1. `rt_device_create(RT_Device_Class_Char, sizeof(私有结构))` 创建设备对象
2. 绑定 6 个 ops（init/open/close/read/write/control）
3. `rt_device_register()` 挂入内核设备链表
4. `INIT_DEVICE_EXPORT` 开机自动注册

**应用层（test_dev.c）**：
MSH 命令 `test_dev_demo` 走完整生命周期：
```
find("test_dev") → open → write("Hello...") → read
→ control(GET_VERSION) → control(ECHO) → control(CLEAR) → read(验证清空) → close
```

踩了个坑：本版 RT-Thread 没有 `RT_DEVICE_CTRL_USER_ALLOC` 宏，自定义控制命令直接用十六进制值（0x20/0x21/0x22），避开内核已用的 0x01~0x04 / 0x10~0x12。

## 小结

设备框架的本质是**用 ops 函数指针做接口约定**：上层调标准 API，底层实现具体函数，中间靠 IO 管理层分发。设计 test_dev 让我直观感受到这套机制的解耦能力——应用代码和驱动代码完全独立，换底层实现上层不用改一行。

PIN 设备的对接分析则让我看到了从 API 到寄存器的完整路径，理解了逻辑编号、ops 挂载、中断回调表这些关键设计。
