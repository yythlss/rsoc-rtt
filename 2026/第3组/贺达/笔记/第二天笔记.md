# RT-Thread 第二天学习笔记：内核启动、对象管理与线程调度

## 一、启动过程的核心认识

在裸机程序中，通常将 `main()` 视为应用起点；在 RT-Thread 完整系统中，复位后还需要先建立内核运行环境。GCC 工程的启动顺序为 `Reset_Handler → entry → rtthread_startup → 调度器 → main 线程 → main()`。

`Reset_Handler` 负责建立 C 语言运行环境，包括设置栈、初始化时钟、复制 `.data`、清零 `.bss` 和调用运行库构造函数。随后进入 RT-Thread 的 `entry()`，由 `rtthread_startup()` 初始化板级环境、定时器系统、调度器、系统线程和用户主线程。调度器启动后，`main_thread_entry()` 才在普通线程上下文中执行组件初始化和用户 `main()`。

这一过程解释了两个常见现象：

- `main()` 中可以使用 `rt_thread_mdelay()`，因为调度器此时已经运行；
- 使用 `INIT_APP_EXPORT()` 注册的函数会在 `main()` 之前执行，因为 `main_thread_entry()` 先调用 `rt_components_init()`。

## 二、自动初始化机制

自动初始化的本质是“编译期登记，运行期遍历”。`INIT_EXPORT(fn, level)` 将函数指针放入特定链接段，而不是在宏展开处直接调用函数。不同宏对应不同等级：

| 宏 | 等级 | 典型用途 |
| --- | --- | --- |
| `INIT_BOARD_EXPORT` | 1 | 板级基础设施和早期硬件初始化 |
| `INIT_PREV_EXPORT` | 2 | 纯软件预初始化 |
| `INIT_DEVICE_EXPORT` | 3 | 设备驱动初始化 |
| `INIT_COMPONENT_EXPORT` | 4 | 中间件与组件初始化 |
| `INIT_ENV_EXPORT` | 5 | 系统环境初始化 |
| `INIT_APP_EXPORT` | 6 | 应用模块初始化 |

链接脚本把 `.rti_fn.*` 按等级排列，内核根据起止符号逐项调用。使用自动初始化可以降低应用模块之间的直接耦合，但初始化函数仍应满足以下约束：

1. 返回明确的错误码；
2. 不依赖尚未完成初始化的低等级模块；
3. 避免同时在 `main()` 中重复调用；
4. 初始化失败时输出足够的诊断信息。

## 三、内核对象模型

线程、信号量、互斥量、事件和消息队列都从 `rt_object` 派生。统一对象头使内核可以完成名称管理、类型识别和链表组织，也使 shell 调试命令能够遍历系统对象。

静态对象和动态对象使用不同的生命周期接口：

| 类型 | 建立 | 启动或使用 | 结束 |
| --- | --- | --- | --- |
| 动态线程 | `rt_thread_create()` | `rt_thread_startup()` | `rt_thread_delete()` |
| 静态线程 | `rt_thread_init()` | `rt_thread_startup()` | `rt_thread_detach()` |

动态对象适合数量或生命周期在运行期变化的场景；静态对象适合长期存在、内存预算固定的关键任务。静态分配能够避免堆碎片和运行期分配失败，但必须在编译期预留足够容量。

## 四、线程控制块要点

线程控制块保存线程执行和调度所需的全部上下文。

- `sp` 指向保存后的线程栈位置，是上下文切换恢复现场的依据。
- `stack_addr` 与 `stack_size` 描述栈空间。
- `stat` 表示 INIT、READY、RUNNING、SUSPEND 或 CLOSE 等状态。
- `current_priority` 是当前有效优先级，可能受优先级继承影响。
- `init_tick` 是创建线程时设置的时间片。
- `remaining_tick` 是尚未消耗的时间片。
- `thread_timer` 支持线程延时和超时等待。

新版内核把部分调度字段封装进调度上下文。读取内部字段时应保持临界区，并且应用代码不应直接修改它们。日常状态查询优先使用系统已有命令；直接读取主要用于理解源码和受控实验。

## 五、线程状态转换

```text
        startup/resume/条件满足
INIT ───────────────────────→ READY
                                │  调度器选中
                                ↓
                             RUNNING
                                │
             delay/等待IPC/主动挂起
                                ↓
                             SUSPEND
                                │
                    超时/唤醒/resume
                                └────────→ READY

线程入口返回或被删除 ─────────────→ CLOSE
```

`SUSPEND` 是“当前不可运行”的统一状态，不只代表人为暂停。调用 `rt_thread_mdelay()` 后，线程也会进入挂起态，等待内置定时器超时后重新进入就绪队列。

## 六、优先级抢占和同优先级轮转

RT-Thread 的优先级数值越小，优先级越高。高优先级线程进入就绪状态后，可以抢占正在运行的低优先级线程。本次实验中监控线程优先级为 10，因此每次 2 秒延时结束后都会优先于两个优先级为 16 的 LED 线程运行。

同一优先级存在多个就绪线程时使用时间片轮转。两个 LED 线程都设置为 5 tick；如果二者持续占用 CPU，时间片耗尽会触发同级切换。本实验中的线程还会主动延时，所以实际切换通常由延时阻塞先触发。由此可知，时间片只解决同优先级线程之间的 CPU 分配，不能替代合理的优先级和阻塞设计。

## 七、线程挂起的安全性

内核允许一个线程挂起另一个线程，但目标线程可能正持有互斥量或处于关键操作中，强制挂起可能导致死锁或资源长期得不到释放。更稳妥的做法是：

1. 控制线程只发布挂起请求；
2. 目标线程在明确的安全点检查请求；
3. 目标线程调用 `rt_thread_suspend(rt_thread_self())` 主动挂起；
4. 控制线程在需要时调用 `rt_thread_resume()`。

本次实验采用这种协作方式。它比在按键中断中直接操作线程更安全，也避免在中断服务函数中执行复杂调度逻辑。

## 八、栈使用量观察

线程初始化时，RT-Thread 使用固定字节填充栈。运行后扫描仍未被覆盖的连续区域，可以估算剩余栈空间。该值的意义是“截至当前观察时刻的高水位”，不等于未来一定安全。

评估栈大小时还应覆盖：

- 最深函数调用层级；
- 局部数组和格式化输出开销；
- 中断嵌套和异常路径；
- 组件库在极端输入下的调用路径；
- 足够长时间的压力运行。

若剩余空间长期过大，可以在验证后适度缩减；若余量接近安全阈值，应优先增大栈并排查大对象和深层调用。

## 九、实验程序摘要

实验包含三个线程：

- `th_led1`：动态创建，优先级 16，时间片 5，1024 B 栈，每 500 ms 翻转红色 LED；
- `th_led2`：静态初始化，参数与 `th_led1` 相同，每 1000 ms 翻转蓝色 LED；
- `th_monitor`：动态创建，优先级 10，每 2000 ms 输出线程状态和栈余量，并处理 KEY_UP 事件。

模块通过 `INIT_APP_EXPORT()` 自动加载，并通过 `MSH_CMD_EXPORT()` 提供 `thread_dump` 命令。编译后的符号表中已确认两个导出项存在。

## 十一、学习总结

本次学习将处理器复位入口、RT-Thread 内核启动、组件自动初始化和用户线程运行串联起来，并通过动态与静态线程的对照理解了对象生命周期和内存分配方式。实测日志进一步说明，线程状态必须结合阻塞原因分析，优先级决定抢占关系，时间片负责同优先级线程之间的轮转，而栈高水位能够为线程容量调整提供依据。实验程序还将按键中断、线程自挂起与恢复、MSH 命令导出结合起来，为后续学习线程同步和设备框架奠定了基础。
