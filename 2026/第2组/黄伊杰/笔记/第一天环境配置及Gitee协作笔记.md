## 一、RT-Thread 系统介绍

### 1. 基本定位
- RT-Thread 是**国产自研 RTOS**，发展近 20 年，主打**"小而美、高可靠"**
- 100% 国产自主可控 + 第三方中立，社区活跃，GitHub 已迭代至 **v5.3.0**
- 后续 5 天课程**基于标准版**展开，第 5 天安排文件系统与云服务 Demo

### 2. 三条产品线对比

| 产品线 | 定位 | 核心特点 | 适用场景 |
|---|---|---|---|
| **Nano** | 极简版 | 硬实时内核、线程管理，Apache 协议开源 | 资源极度受限的裸机替代 |
| **标准版**（RT-Thread） | 主力教学版 | 内核丰富、全面兼容 POSIX API，集成日志/网络/IoT 协议栈，高度可定制 | 通用物联网设备 |
| **Smart** | 混合微内核版 | 内核轻量、用户态/内核态隔离（高安全），API 风格与标准版一致 | 需要安全隔离的复杂场景 |

## 二、开发环境搭建

### 1. RT-Thread Studio
- 基于 **Eclipse 内核**，集成工具链、编译环境与图形化工程菜单，**开箱即用**
- 新建工程模式：统一采用 **"基于芯片"**（纯净 BSP），不用"基于开发板"（自带 Demo）
- 统一配置：芯片选 **STM32F407**（星火 1 号），调试器选 **ST-Link**，内核版本 **4.0.3 / 4.1.1**

### 2. 芯片支持包
- 通过 **SDK 管理器** 下载 `stm32f4` 芯片知识包（当天实操的核心脚手架）
- 若 SDK 管理器界面渲染异常：尝试"添加更多"按钮进入，或统一用 4.1.1 版本绕过报错

### 3. 硬件连接与驱动排障速查

| 问题现象 | 排查方向 |
|---|---|
| 设备管理器无 ST-Link 设备 | 下载安装 ST-Link 驱动，检查 Type-C 是否接对（板子右侧两个口：供电 / Debug） |
| ST-Link 有感叹号 | 驱动未成功加载，拔插板子重装驱动 |
| 终端无输出 | ① 串口被占用 → 关掉其他串口助手；② 波特率设 **115200**；③ 端口号选带"sta"前缀的 COM 口 |
| ST-Link 固件版本过低 | 用 ST-Link Utility 或 Cube Programmer 升级固件 |
| 下载选错工具 | 必须选 **STM32 ST-Link** 模式，不能选其他 |

### 2. 工程目录核心结构

| 目录 | 作用 |
|---|---|
| `application/` | 用户应用代码（main 所在） |
| `drivers/` | LCD、键鼠、串口、音频等外设驱动 + 统一驱动框架 |
| `components/` | C++ 支持、DFS 文件系统等组件 |
| `libcpu/` | 跨架构底层接口（汇编/上下文切换），支持 ARM M 系列及国产芯片 |
| `libc/` | 多工具链兼容层 |
| `kernel/` | IPC、中断、内存、对象管理、调度器 |

### 3. 驱动框架三层架构（重点）

```
应用程序
    ↓
第一层：统一 IO 设备管理层（管理字符/块/SPI 等外设）
    ↓
第二层：设备驱动框架层（介于硬件与应用之间，屏蔽底层差异）
    ↓
第三层：具体厂商/外设的设备驱动层（针对 STM32、具体模块实现）
```

**核心思想**：上层应用不直接碰硬件，通过分层解耦，换芯片不改应用。

### 4. 调试技巧
- 打断点 → 点 **"小虫子"图标** 启动调试（仿真器环境可直接调试，无需下载到板子）
- 终端窗口：IDE 内置 Terminal 或外部串口助手，波特率 **115200**
- 按**复位键**后终端才输出日志（正常行为）

## 五、RT-Thread 系统启动流程（核心理论）

### 1. 裸机 vs RTOS 启动对比

| | 裸机 | RTOS |
|---|---|---|
| 入口 | 汇编 → `main()` | 汇编 → `system_init` → `entry` → `main()`（**main 被封装为线程**） |
| 执行方式 | 线性顺序执行 | 多线程并发调度 |

### 2. RTOS 完整启动顺序

```
上电 → 复位中断处理函数
  → 设置栈指针
  → Flash 数据拷贝到 SRAM
  → 内存段清零（BSS）
  → system_init（浮点/时钟/开全局中断）
  → entry（关全局中断 → 堆初始化 → 板级外设 → 开中断 → 系统时钟）
  → rtthread_startup()
      → 关中断 → 板级初始化 → 打印版本 Logo
      → 系统时钟初始化 → 调度器初始化 → 信号量初始化
      → 创建 main 线程（动态内存）
      → 创建 timer 线程 / idle 线程
      → 启动调度器（基于优先级的抢占式调度）
  → 调度器提取最高优先级线程 → 上下文切换 → 进入 main()
```

### 3. 工具链入口差异（MDK vs GCC）

| 工具链 | 启动路径 |
|---|---|
| **MDK** | 汇编 → `__main` → `main` |
| **GCC** | 汇编 → 自定义 `entry` → `rtthread_startup` → `main` |

> 底层启动流程逻辑一致，只是"敲门砖"不同；当前工程默认适配 **GCC**。

### 4. 初始化组件注册机制
- 用 `INIT_APP_EXPORT` 等宏将初始化函数绑定为**指针数组元素**，系统启动时按顺序依次调用
- 好处：新增组件不用改启动代码，只需一个宏声明即可自动注册

## 六、Git 协作与 PR 流程

### 1. 本地环境配置

```bash
# 1. 配置身份信息（全局）
git config --global user.name "your_english_name"
git config --global user.email "your_email"
git config --list   # 验证

# 2. 生成 SSH 密钥
ssh-keygen -t rsa   # 一路回车三次
cat ~/.ssh/id_rsa.pub   # 查看公钥，全量复制

# 3. 粘贴到代码托管平台 → SSH 密钥设置 → 新建密钥
# 4. 验证：ssh -T git@xxx（首次输入 yes）
```

### 2. 标准单人提交流程

```bash
git clone <SSH地址>          # 拉取远程仓库到本地
cd 仓库目录
git status                   # 查看文件状态
git add <文件名/路径>        # 加入暂存区（. 代表全部）
git commit -m "初次提交"     # 提交到本地仓库
git push origin master       # 推送到远端
```

### 3. 标准 PR（Pull Request）协作流程（重点）

> **核心原则**：`master` 分支受保护，**永远不直接 push 到 master**，走 PR 审核合并。

```
1. 网页端 Fork 上游仓库到自己账号（"大树与分支"比喻：主树干=主仓库，你的仓库=分支）
2. git clone 自己的 Fork 仓库到本地
3. git checkout -b day1      # 基于 master 新建并切换到 day1 分支
4. 修改/新建文件（在对应组目录下建个人文件夹，套用模板）
5. git add . → git commit -m "day1: xxx" → git push origin day1
6. 网页端 → 自己仓库 → 新建 PR → 源分支 day1 → 目标分支 master（上游仓库）
7. 填写标题 + 描述 → 指定 Reviewer 为小组长
8. 小组长审核（评论→修改→标记解决）→ 导师合并
9. 合并后删除分支，下次提交前先同步上游最新代码
```

### 5. 冲突产生原因与解决思路

- **原因**：Fork 时基于 T1 状态，别人先合了代码（master 变成 T2），你的 Fork 还停留在 T1，提交 PR 时内容不一致 → 冲突
- **解决 SOP**：
  1. 本地 `git remote add upstream <上游地址>`（首次）
  2. `git checkout master` → `git pull upstream master`（同步上游最新）
  3. `git checkout day1` → 手动解决冲突文件中的 `<<<<<<<` 标记
  4. `git add .` → `git commit` → `git push origin day1` → PR 自动更新

## 七、当日核心收获总结

1. **RT-Thread 不是"一个内核"**，是覆盖 Nano→标准版→Smart 的完整产品矩阵，标准版是学习主线
2. **驱动框架分层设计**是 RT-Thread 的灵魂——上层应用与底层硬件解耦，换芯片不改业务代码
3. **RTOS 的 main() 是线程**，启动流程从汇编到调度器启动有一套严格顺序，理解这个就理解了"系统怎么活起来的"
4. **MDK 和 GCC 启动入口不同**但逻辑等价，看源码时要先定位工具链再追代码
5. **Git 协作的本质是分支管理**——Fork + 分支 + PR + 审核，这是参与开源的通用工作流，比命令本身更重要
