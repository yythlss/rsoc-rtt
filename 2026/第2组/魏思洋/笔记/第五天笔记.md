# 第五天：AHT10、RW007、MQTT 与 FAL/DFS 文件系统

## 一、AHT10 配置与线程采集

AHT10 是通过 I²C 读取温度和湿度的数字传感器。工程中先确认传感器连接的 I²C 总线名称，再调用软件包提供的初始化接口获得设备对象，随后在独立线程中周期性读取温湿度数据。

典型流程如下：

```text
确认 I2C 总线名称
    -> aht10_init("i2c3")
    -> 检查设备指针
    -> aht10_read_humidity()
    -> aht10_read_temperature()
    -> 延时 1 秒后再次采集
```

作业中的 `AHT10_Test` 线程每秒采集一次数据，并通过 `aht_count` 记录采集次数。若工程没有启用完整浮点格式化支持，可以将浮点数拆成整数部分和一位小数打印，避免直接使用 `%f` 带来的代码体积和格式化支持问题。

## 二、RW007 配置

RW007 属于通过串口与主控通信的 Wi-Fi 模块。配置时需要确认模块对应的 UART 设备、波特率、RT-Thread 设备驱动以及网络协议栈配置。基本检查思路是：

1. 在 Menuconfig 中启用 RW007 驱动和网络组件；
2. 配置模块使用的串口设备名及串口参数；
3. 连接模块并通过 FinSH/msh 查看设备是否注册成功；
4. 确认网卡已初始化，再进行扫描、连接热点和 IP 配置；
5. 使用网络命令或应用程序验证连通性。

排查问题时应先确认串口收发正常，再检查模块固件、天线和供电，最后检查 DHCP、路由和应用层连接，避免把硬件通信问题误判为 MQTT 问题。

## 三、MQTT 软件包解析

MQTT 是基于发布/订阅模型的轻量级消息协议。设备作为客户端连接 Broker 后，可以向主题发布消息，也可以订阅主题接收消息。

一次典型 MQTT 使用流程为：

```text
初始化客户端
    -> 配置 Broker 地址、端口和认证信息
    -> 建立 TCP/TLS 连接
    -> CONNECT/CONNACK
    -> SUBSCRIBE 订阅主题
    -> PUBLISH 发布温湿度数据
    -> 循环处理网络事件和接收回调
    -> 断开连接并释放资源
```

MQTT 主题应按设备和数据类型进行规划，例如 `device/<id>/sensor/aht10`。实际工程中需要关注客户端是否持续处理网络事件、连接断开后的重连策略、消息 QoS、保活时间以及回调线程中的阻塞操作。传感器采集线程与 MQTT 网络线程可以通过消息队列或环形缓冲区传递数据，避免在传感器线程中直接执行较慢的网络操作。

## 四、FAL 组件和 DFS

### 4.1 FAL 组件

FAL（Flash Abstraction Layer，Flash 抽象层）用于统一管理片内 Flash、SPI NOR Flash 等 Flash 设备及其分区。它向上层提供统一的查找、读、写、擦除接口，使文件系统、OTA、FlashDB 等功能不必直接依赖某一种 Flash 驱动。

FAL 的主要特点：

- 可以同时管理多个 Flash 设备；
- 支持静态配置和可配置的 Flash 分区表；
- 为不同 Flash 提供统一的设备和分区操作接口；
- 本身对 RT-Thread 内核依赖较少，也可以在裸机或 Bootloader 中使用；
- 启用 FinSH/msh 后，可直接使用命令测试 Flash 或分区。

#### 1. FAL 的层次关系

```text
应用、OTA、FlashDB、文件系统
            |
       FAL 分区接口
            |
       FAL Flash 设备表
            |
片内 Flash 驱动 / SFUD SPI Flash 驱动
            |
          实际硬件
```

#### 2. FAL 移植步骤

**第一步：实现 Flash 设备。**

在端口文件中定义 `struct fal_flash_dev`，至少需要根据硬件实现设备初始化、读取、写入和擦除操作。通常包括：

- `init`：可选的设备初始化函数；
- `read`：从 Flash 偏移地址读取数据；
- `write`：向 Flash 偏移地址写入数据；
- `erase`：按芯片要求擦除指定区域；
- 设备名称、起始地址、容量和最小擦除块大小。

写入 Flash 前必须确认芯片的写入粒度、擦除粒度和写保护要求。Flash 通常不能像 RAM 一样任意覆盖写入，更新数据前可能需要先擦除对应扇区。

**第二步：配置 Flash 设备表。**

在 `fal_cfg.h` 中通过 `FAL_FLASH_DEV_TABLE` 将设备加入 FAL 管理范围。例如片内 Flash 和外部 NOR Flash 可以同时放进设备表。设备名必须与驱动注册名、SFUD 探测得到的名称保持一致，否则 FAL 可能找不到目标设备。

**第三步：配置分区表。**

通过分区表为同一 Flash 划分不同用途，例如：

| 分区 | 用途 |
| --- | --- |
| `bl` | Bootloader |
| `app` | 应用固件 |
| `filesystem` | 文件系统数据 |
| `font` | 字库或资源文件 |
| `download` | OTA 下载暂存区 |

分区记录通常包含分区名、所属 Flash 设备、相对于该 Flash 的偏移地址和长度。分区之间不能重叠，偏移和长度还必须满足底层 Flash 的擦除块对齐要求。

**第四步：初始化并使用 FAL。**

移植完成后在应用中调用 `fal_init()`。之后可以根据设备名或分区名查找对象，再使用统一接口完成读、写和擦除。对于文件系统场景，还可以使用 `fal_blk_device_create("filesystem")` 把某个 FAL 分区包装成 RT-Thread 块设备。

#### 3. FAL 命令行调试

启用 FinSH/msh 后，可以使用类似下面的命令检查分区和 Flash 驱动：

```text
fal probe                         查看设备或分区信息
fal probe filesystem              选择并查看 filesystem 分区
fal read addr size                从当前对象读取数据
fal write addr data1 ... dataN    写入测试数据
fal erase addr size               擦除指定范围
fal bench <blk_size>              测试读写性能
```

实际使用时应先执行 `fal probe` 确认分区表，再进行写入和擦除测试。测试命令会真实修改 Flash，不能在存放 Bootloader、应用固件或重要数据的分区上随意执行。

### 4.2 DFS 文件系统

DFS（Device File System，设备文件系统）是 RT-Thread 的虚拟文件系统层。它向上提供统一的文件和目录访问接口，向下对接不同存储设备及文件系统实现，例如 ROMFS、FatFs/ELM、LittleFS 等。

DFS 的作用是把“设备名、挂载路径、文件系统类型”关联起来。应用不必直接调用 SD 卡或 Flash 的底层读写函数，而是通过 POSIX 风格接口访问路径：

```text
open -> read/write -> fsync -> close
```

常见初始化和管理接口：

- `dfs_init()`：初始化 DFS；
- `dfs_register()`：注册一种文件系统操作实现；
- `dfs_mount(device_name, path, filesystemtype, rwflag, data)`：将设备上的文件系统挂载到路径；
- `dfs_unmount(path)`：卸载挂载点；
- `dfs_mkfs(fs_name, device_name)`：在设备上创建指定类型的文件系统；
- `open`、`close`、`read`、`write`、`fsync`：文件读写；
- `mkdir`、`opendir`、`readdir`、`closedir`：目录操作。

`dfs_mount` 成功返回 0，失败返回负值。挂载前必须保证底层设备已经注册、文件系统类型已经启用，并且存储区域已经格式化；对于首次使用的空白分区，通常需要先执行格式化操作。

#### 1. ROMFS、FatFs 与 LittleFS

- **ROMFS：** 适合固件内置的只读资源，通常作为根文件系统或资源目录使用；
- **FatFs/ELM：** 适合 SD 卡、U 盘等常见 FAT 存储介质，兼容性较好；
- **LittleFS：** 面向微控制器和 Flash，关注掉电安全和磨损均衡，适合片外 NOR Flash 等场景。

不同文件系统的配置宏、格式化方式和存储介质要求不同，不能只修改 `dfs_mount` 的字符串就认为已经完成移植。

#### 2. 作业代码的完整链路

`drv_filesystem.c` 中的 Flash 文件系统挂载过程如下：

```text
fal_init()
    -> fal_blk_device_create("filesystem")
    -> 创建 FAL 分区对应的块设备
    -> dfs_mount(块设备名, "/fal", "elm", 0, 0)
    -> 通过 /fal 访问 FatFs 文件
```

SD 卡的挂载则是：

```c
dfs_mount("sd0", "/sdcard", "elm", 0, 0);
```

其中 `sd0` 是设备名，`/sdcard` 是挂载点，`elm` 是 FatFs 在 RT-Thread 中使用的文件系统类型名。`romfs_root` 负责构造只读根目录，代码中把 `/sdcard`、`/fal` 和 `/font` 作为可见目录加入 ROMFS 根目录。

`file.c` 中的文件记录线程使用：

```c
fd = open("/fal/Data.txt", O_RDWR | O_CREAT | O_APPEND, 0666);
write(fd, str, strlen(str));
fsync(fd);
```

`O_APPEND` 使新数据写到文件末尾，`fsync` 请求把缓存中的数据同步到底层存储。温湿度线程每秒更新数据，文件系统线程每秒把当前温度、湿度和采集次数追加到 `Data.txt`，实现了“传感器采集—文件持久化”的实操闭环。

#### 3. 代码检查与改进建议

1. `fal_blk_device_create` 返回 `NULL` 时应立即返回，不能继续访问 `flash_dev->parent.name`，否则会发生空指针解引用；
2. 文件打开、写入和同步都应检查返回值，特别是 Flash 空间不足、设备掉线或文件系统损坏时；
3. 文件描述符应在不再使用时 `close`，长期运行的线程不应重复打开文件而不释放；
4. `sprintf` 建议改为带长度限制的格式化方式，并确认缓冲区足够；
5. 使用 `strlen`、字符串格式化函数时应包含对应的字符串头文件；
6. 写入 Flash 时要考虑擦写次数、掉电保护、文件系统一致性和数据备份；
7. 采集线程和文件线程共享 `Temp`、`Humi`、`aht_count`，如果要求严格的一致性，应使用互斥量或消息队列传递一份完整采样结构体，而不是让文件线程直接读取多个全局变量。

## 五、调试命令与排查顺序

```text
list_device       查看设备是否已经注册
list              查看系统对象和线程
mount             查看或挂载文件系统（以当前版本命令为准）
df                查看文件系统空间（以当前版本命令为准）
mkfs              格式化存储设备（执行前确认目标设备）
```

建议按以下顺序排查文件系统问题：

1. 确认 Flash/SD 驱动已初始化；
2. 使用 `list_device` 确认块设备名称；
3. 使用 `fal probe` 确认 FAL 设备和分区表；
4. 确认分区未越界、分区已格式化且文件系统类型匹配；
5. 调用 `dfs_mount` 并检查返回值；
6. 先用小文件测试 `open`、`write`、`read`、`close`，再运行传感器长期记录程序。

## 六、学习总结

FAL 解决的是 Flash 设备和分区的统一管理问题，DFS 解决的是不同存储设备和文件系统的统一访问问题。两者结合后，可以把 Flash 的某个分区转换为块设备，再挂载到 `/fal` 等路径，应用即可使用统一的文件 API 保存传感器数据。实际开发中，设备注册、FAL 分区、块设备、文件系统格式化和 DFS 挂载必须逐层验证，任何一层名称或配置不匹配都会导致上层文件操作失败。
