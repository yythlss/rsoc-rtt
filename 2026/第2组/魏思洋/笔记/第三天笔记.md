# 第三天：RT-Thread IPC 机制与线程同步通信

## 一、课程背景与基础概念

前两天学习了 RT-Thread 工程创建、启动流程和线程调度。本次课程进一步讨论多线程之间如何同步和交换数据。IPC（Inter-Process Communication）在 RT-Thread 中主要用于线程同步与线程间通信，常见对象包括信号量、互斥量、事件集、邮箱和消息队列。

**对于所有的线程，只要优先级更高，即使其他线程正常运行，也可以强制抢占，除非进入临界区或者关闭中断**

### 1. 临界区、阻塞与挂起

- **临界区：** 访问共享变量、外设寄存器或其他共享资源的一段代码，同一时刻通常只允许一个线程进入。
- **阻塞：** 线程暂时无法获得所需资源时等待。阻塞期间线程不占用 CPU，调度器可以运行其他就绪线程。
- **非阻塞：** 不等待资源，立即返回成功或错误结果，适合不能长时间等待的场景。
- **线程挂起：** 线程因等待资源、延时或主动挂起而进入 `RT_THREAD_SUSPEND` 状态，资源可用或延时结束后再恢复为就绪态。

IPC 的选择要同时考虑资源保护、数据传递、等待时间、优先级和是否运行在中断上下文中，不能简单地用一种对象替代所有同步需求。

## 二、线程同步机制

### 1. 信号量 Semaphore

信号量本质上是一个可计数的资源数量，线程通过“获取”和“释放”来协调执行。

- **二值信号量：** 计数通常为 0 或 1，适合表示“事件是否发生”或“某项资源是否可用”。例如线程一完成计数后调用 `rt_sem_release()`，线程二使用 `rt_sem_take()` 等待并执行 LED 操作。
- **计数信号量：** 初始值表示可用资源实例数量，适合管理多个相同资源，例如生产者—消费者模型中的空闲槽位和已有数据数量。
- **动态创建：** `rt_sem_create(name, value, flag)` 从系统对象/堆资源中创建信号量。
- **静态初始化：** `rt_sem_init(sem, name, value, flag)` 使用用户预先分配的控制块。
- **核心操作：** `rt_sem_take(sem, timeout)` 获取信号量，`rt_sem_trytake(sem)` 不等待地获取，`rt_sem_release(sem)` 释放信号量。

`timeout` 决定等待策略：可以立即返回、等待指定 tick，或使用 `RT_WAITING_FOREVER` 永久等待。多个线程等待同一个信号量时，`flag` 可选 `RT_IPC_FLAG_FIFO` 或 `RT_IPC_FLAG_PRIO`。实时性要求较高时通常使用优先级等待；只有确实需要先来先服务时才选择 FIFO。

信号量没有线程所有权，释放操作不要求由最后获取它的线程执行，因此它适合“通知”和“资源计数”，但不适合作为严格的临界区所有权锁。

### 2. 互斥量 Mutex

互斥量是带有所有权的互斥锁，适合保护共享数据和临界区。它与普通信号量的主要区别如下：

| 对比项 | 信号量 | 互斥量 |
| --- | --- | --- |
| 主要用途 | 同步、事件通知、资源计数 | 保护临界区和共享资源 |
| 所有权 | 无所有权 | 有 owner，通常只有持有者可以释放 |
| 递归获取 | 不支持，重复获取可能导致阻塞 | 支持同一线程递归获取，使用次数由内核记录 |
| 优先级继承 | 不提供互斥量式的优先级继承 | 支持优先级继承，用于缓解优先级反转 |
| 中断中使用 | 按具体 API 和上下文限制使用 | 不能在中断服务程序中使用需要阻塞/所有权的互斥操作 |

互斥量的典型 API 是 `rt_mutex_create`/`rt_mutex_init`、`rt_mutex_take`、`rt_mutex_release` 以及对应的 `delete`/`detach`。动态创建的对象使用 `delete`，静态初始化的对象使用 `detach`，两者不要混用。

#### 优先级反转

假设低优先级线程 L 持有共享资源，高优先级线程 H 等待该资源，此时中优先级线程 M 持续运行并抢占 L，H 就会间接地被 M 阻塞，这就是优先级反转。

RT-Thread 互斥量使用优先级继承：当 H 因等待资源而阻塞时，暂时提升持有者 L 的有效优先级，使 L 尽快运行并释放互斥量；释放后，L 恢复原来的优先级。课程中通过比较有无互斥量保护时 `number1`、`number2` 的变化，验证了临界区保护和优先级继承效果。

使用互斥量时应尽快完成临界区操作并释放锁，避免在持锁期间执行长时间延时、复杂计算或改变持有者优先级。

### 3. 事件集 Event Set

事件集使用一个 32 位无符号值表示多个事件标志位，适合一对多或多对多同步。例如：

```c
#define EVENT3 (1u << 3)
#define EVENT5 (1u << 5)
```

线程可以使用 `rt_event_recv()` 等待事件，发送方使用 `rt_event_send()` 设置事件标志。

- `RT_EVENT_FLAG_OR`：等待的标志中任意一个发生即可唤醒；
- `RT_EVENT_FLAG_AND`：等待的所有标志同时满足后才唤醒；
- `RT_EVENT_FLAG_CLEAR`：接收成功后清除已匹配的事件标志，避免旧事件重复触发。

课程示例先以 OR 模式等待事件 3 或事件 5，再以 AND 模式等待事件 3 和事件 5 同时到达。事件集传递的是标志，不携带具体数据；如果需要传递数据，应配合邮箱或消息队列使用。

## 三、线程间通信机制

### 1. 邮箱 Mailbox

邮箱适合传递轻量、固定大小的消息。官方实现中，每封邮件最多保存一个 32 位值；在 32 位 MCU 上通常是 4 字节，因此常用来传递整数、状态值或指针，而不是直接复制一段较大的字符串。

常用 API 包括：

- `rt_mb_create` / `rt_mb_init`：动态创建或静态初始化邮箱；
- `rt_mb_send`：发送邮件，邮箱满时立即返回 `-RT_EFULL`；
- `rt_mb_send_wait`：邮箱满时按照 timeout 等待空间；
- `rt_mb_recv`：接收邮件，可设置立即返回、限时等待或永久等待；
- `rt_mb_delete` / `rt_mb_detach`：分别删除动态邮箱或脱离静态邮箱。

邮箱可以由线程或 ISR 发送，因此适合中断向线程传递“发生了某事件”或一个指针。但传递指针时必须保证指针指向的内存在线程处理完成前仍然有效，并明确由谁负责释放，避免悬空指针和内存泄漏。

课程示例中，线程二交替发送字符串指针，线程一接收并打印；收到特殊字符串 `"over"` 后，接收线程退出，演示了使用邮箱传递控制信息的过程。

### 2. 消息队列 Message Queue

消息队列用于复制传递消息内容，比邮箱更适合传输结构体或多字节数据。需要注意：RT-Thread 的一个消息队列在创建/初始化时配置固定的 `msg_size`，队列中的每条消息都按这个大小处理，因此这里的“变长”应理解为消息队列不受邮箱 4 字节限制，而不是同一个队列中每条消息都可以任意长度。

常用 API 包括：

- `rt_mq_create(name, msg_size, max_msgs, flag)`：动态创建消息队列；
- `rt_mq_init(mq, name, msg_pool, msg_size, pool_size, flag)`：使用消息池静态初始化；
- `rt_mq_send`：将数据复制到队列消息块；
- `rt_mq_recv`：从队列取出消息并复制到接收缓冲区；
- `rt_mq_urgent`：将紧急消息插入队头；
- `rt_mq_delete` / `rt_mq_detach`：删除动态队列或脱离静态队列。

普通消息通常排在队尾。例如依次发送 `a` 到 `h`，再用 `rt_mq_urgent` 发送 `i`，接收顺序会体现 `i` 被插入队头的效果。紧急消息只改变队列位置，不会突破队列容量限制；队列满时仍需检查返回值。

消息队列直接复制数据内容，因此接收方可以使用自己的局部结构体接收消息，不必像邮箱传递指针那样额外管理动态内存。若发送和处理需要确认，可组合使用“消息队列 + 信号量”或“消息队列 + 邮箱”实现应答。

## 四、五种 IPC 机制的选型总结

| 需求 | 推荐机制 | 选择理由 |
| --- | --- | --- |
| 通知某个事件发生 | 二值信号量 | 使用简单，可阻塞等待和释放通知 |
| 管理多个相同资源 | 计数信号量 | 计数值表示可用资源数量 |
| 保护共享变量或外设 | 互斥量 | 有所有权、支持递归、可进行优先级继承 |
| 等待多个条件组合 | 事件集 | 支持 OR/AND 标志匹配，不负责携带数据 |
| 传递一个整数或指针 | 邮箱 | 单条消息固定 32 位，开销小 |
| 传递结构体或多字节数据 | 消息队列 | 按固定消息大小复制数据，并支持紧急消息插队 |

***<u>在使用API的时候，一定注意API返回值，尤其是创建create或者初始化init的时候，</u>***

***<u>例如create的时候，句柄在函数内；而使用init的时候，句柄作为返回值返回。如下面代码所示</u>***

```c
rt_mq_t rt_mq_create(const char* name, rt_size_t msg_size,
            rt_size_t max_msgs, rt_uint8_t flag);
rt_err_t rt_mq_init(rt_mq_t mq, const char* name,
                        void *msgpool, rt_size_t msg_size,
                        rt_size_t pool_size, rt_uint8_t flag);
```

设计 IPC 时还要注意以下原则：

1. 明确每个对象的创建方式，动态对象用 `delete`，静态对象用 `detach`；
2. 所有 `take`、`recv`、`send` 操作都检查返回值和超时情况；
3. 临界区尽量短，持有互斥量时不要执行长时间阻塞操作；
4. 中断服务程序只能使用允许在 ISR 上下文调用的 API，不能调用会让中断阻塞的操作；
5. 使用优先级等待时要确认优先级数值含义：RT-Thread 中优先级数字越小，优先级越高；
6. 传递指针前确认对象生命周期，使用消息队列复制数据时确认接收缓冲区大小不小于队列的消息大小。

## 五、课程实操与调试思路

调试同步问题时，可以按照以下顺序检查：

1. 确认 IPC 对象已经创建或初始化，并且初始化值正确；
2. 确认线程在使用前已经通过 `rt_thread_startup` 启动；
3. 在 `take`、`release`、`send`、`recv` 前后打印线程名、返回值和关键变量；
4. 使用 `list_thread` 观察线程是否处于 READY、RUNNING 或 SUSPEND 状态；
5. 检查是否忘记释放信号量/互斥量，是否出现重复释放、超时未处理或消息队列满；
6. 对优先级反转问题，比较使用信号量和互斥量时持有资源线程的有效优先级变化。

## 七、学习总结

线程同步解决“谁可以继续执行”和“谁可以访问资源”的问题，线程通信解决“数据如何安全传递”的问题。信号量偏向计数和通知，互斥量偏向资源保护，事件集偏向多条件同步，邮箱偏向轻量消息，消息队列偏向结构化数据传递。掌握这些机制后，可以把多个线程组织成清晰的生产者—消费者、事件驱动和资源互斥模型，减少共享变量直接读写造成的竞态条件。
