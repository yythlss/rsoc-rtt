## 二、RTOS 与 RT-Thread 基础认识

RTOS 即 **Real-Time Operating System，实时操作系统**。

在简单的裸机程序中，通常会在 `main()` 中循环执行不同任务：

```c
int main(void)
{
    while (1)
    {
        task_a();
        task_b();
        task_c();
    }
}
```

这种方式在功能较少时比较简单，但随着系统复杂度提高，会出现不同任务周期不同、某个任务阻塞影响其他任务、程序耦合越来越严重等问题。

RTOS 的思路则是：

```text
不同功能
   ↓
拆分成多个线程
   ↓
由操作系统调度运行
```

其中几个核心概念包括：

| 概念 | 含义 |
|---|---|
| Thread / Task | 系统中的基本运行实体 |
| Scheduler | 根据优先级和线程状态决定 CPU 当前运行哪个线程 |
| Tick | RTOS 的基本时间节拍 |
| IPC | 线程之间进行通信与同步的机制 |

常见 IPC 包括：

- Semaphore：信号量；
- Mutex：互斥量；
- Event：事件；
- Mailbox：邮箱；
- Message Queue：消息队列。

RT-Thread 则是在 RTOS 内核基础上进一步提供组件、设备框架和软件包生态，可以简单理解为：

```text
Application
    ↓
Components / Packages
    ↓
RT-Thread Kernel
    ↓
Device Driver Framework
    ↓
BSP / Hardware
```

## 三、RT-Thread 三条产品线

课程重点介绍了 RT-Thread 的三条产品线：

```text
Nano
Standard
Smart
```

### 1. RT-Thread Nano

Nano 是精简版本，主要保留实时操作系统最核心的能力：

- 线程管理；
- 实时调度；
- 时钟；
- 中断；
- 内存管理；
- 线程同步；
- 线程通信。

其特点是资源占用较低，适合 Flash、RAM 较小或者只需要基础 RTOS 功能的 MCU。

可以简单理解为：

```text
RT-Thread Nano

RTOS Kernel
├── Thread
├── Scheduler
├── Timer
├── IPC
├── Interrupt
└── Memory
```

### 2. RT-Thread Standard

Standard 是更加完整的 MCU RTOS 版本。

除了 Kernel，还拥有：

- Device Framework；
- FinSH / MSH；
- DFS 文件系统；
- 网络协议栈；
- POSIX 接口；
- 日志系统；
- IoT 组件；
- 软件包；
- 各类中间件。

结构上可以理解为：

```text
+--------------------------------+
|          Application           |
+--------------------------------+
| Components / Packages / IoT    |
+--------------------------------+
|        RT-Thread Kernel        |
+--------------------------------+
|       Device Framework         |
+--------------------------------+
|       BSP / MCU Hardware       |
+--------------------------------+
```

### 3. RT-Thread Smart

Smart 主要面向具有 **MMU** 的高性能处理器。

它能够利用 MMU 实现：

```text
Application
      │
      ▼
+------------------+
|    User Space    |
+------------------+
         │
   System Call
         │
         ▼
+------------------+
|   Kernel Space   |
+------------------+
```

与普通 MCU RTOS 相比，最大的特点是用户态与内核态隔离，可以提高系统的安全性和应用隔离能力。

### 三者对比

| 产品 | 面向硬件 | 主要特点 | 典型场景 |
|---|---|---|---|
| Nano | 资源受限 MCU | 精简、资源占用低 | 小型嵌入式设备 |
| Standard | 通用 MCU | 组件丰富、生态完整 | 常规复杂嵌入式系统 |
| Smart | 带 MMU 的处理器 | 用户态 / 内核态隔离 | 高性能嵌入式设备 |

可以简单记忆：

```text
Nano      → 小而够用
Standard  → 完整 MCU RTOS
Smart     → 面向 MMU 的操作系统形态
```

## 四、RT-Thread 工程结构与设备框架

RT-Thread 工程中常见的几个目录包括：

| 目录 | 主要作用 |
|---|---|
| `applications/` | 用户应用代码 |
| `drivers/` | BSP 与外设驱动 |
| `components/` | 文件系统、Shell、网络等系统组件 |
| `src/` | RT-Thread 内核源码 |
| `libc/` | C 库兼容相关内容 |

应用开发中最常接触的是：

```text
applications/main.c
```

它通常作为用户应用程序入口。

RT-Thread 还提供了统一的 Device Driver Framework：

```text
Application
     ↓
RT-Thread Device API
     ↓
Device Framework
     ↓
UART / SPI / I2C / GPIO Driver
     ↓
MCU HAL / Hardware
```

这样上层应用不需要直接操作每一种芯片的底层寄存器，而是可以通过统一的设备接口访问硬件。

## 五、RT-Thread Studio 与 SDK Manager

RT-Thread Studio 将 RT-Thread 项目创建、SDK 管理、编译、下载和调试等功能集成到一个 IDE 中。

整体开发环境可以理解为：

```text
RT-Thread Studio
│
├── RT-Thread Source Code
├── Chip Support Package
├── Toolchain
├── BSP
├── Build
├── Download
└── Debug
```

其中 **SDK Manager** 主要负责管理开发所需的软件资源，例如：

- RT-Thread Source Code；
- STM32F4 芯片支持包；
- Toolchain；
- 相关 SDK 与开发资源。

因此 SDK Manager 可以理解为 RT-Thread Studio 中统一管理开发依赖的工具。

## 七、Build、Download、Run 与 Debug

这几个概念在嵌入式开发中经常一起出现，但作用并不相同。

### Build

Build 是将源代码转换为 MCU 可以执行的程序：

```text
Source Code
    ↓
Preprocess
    ↓
Compile
    ↓
Assemble
    ↓
Link
    ↓
Executable Image
```

常见输出文件包括：

- `.elf`
- `.bin`

其中 ELF 通常还包含符号和调试信息，因此 Debug 时经常使用 ELF 文件；BIN 更接近纯二进制程序镜像，可以直接用于烧写。

### Download

Download 是将已经编译完成的程序写入 MCU：

```text
PC
 ↓
RT-Thread Studio
 ↓
ST-Link
 ↓
STM32F407
```

### Run

Run 表示 MCU 正常执行已经烧写的程序。

### Debug

Debug 则通过 ST-Link 等调试工具进行：

- 设置断点；
- 单步执行；
- 查看变量；
- 查看寄存器；
- 查看调用栈。

| 操作 | 作用 |
|---|---|
| Build | 编译程序 |
| Download | 烧写程序 |
| Run | 正常运行 |
| Debug | 调试程序 |

## 八、FinSH / MSH 与系统调试

RT-Thread Standard 中提供 FinSH / MSH Shell，可以通过串口直接与系统交互。

Shell 可以用于：

- 查看系统线程；
- 查看内存；
- 查看 IPC 对象；
- 查看 Timer；
- 执行系统命令。

与单纯打印日志相比，Shell 的优势在于：

> 不需要反复修改程序并重新编译，就可以直接查看 RTOS 当前的运行状态。

因此在后续学习线程、IPC 和设备驱动时，MSH 会成为非常实用的调试工具。

## 十、Git 基础与版本控制模型

Git 是一个**分布式版本控制系统**，主要用于：

- 保存文件历史版本；
- 跟踪修改；
- 多人协作；
- 分支开发；
- 代码回退；
- 开源项目贡献。

理解 Git 最重要的是理解几个区域之间的数据流：

```text
Working Tree
     │
     │ git add
     ▼
Staging Area
     │
     │ git commit
     ▼
Local Repository
     │
     │ git push
     ▼
Remote Repository
```

分别对应：

### 工作区

平时正在编辑的文件。

### 暂存区

使用：

```bash
git add <file>
```

选择本次 Commit 准备包含哪些修改。

### 本地仓库

使用：

```bash
git commit -m "message"
```

把暂存区内容保存成一次正式版本记录。

### 远程仓库

使用：

```bash
git push
```

将本地 Commit 上传到 Gitee 等远程平台。

因此最基本的数据流就是：

```text
编辑
 ↓
git add
 ↓
git commit
 ↓
git push
```

## 十一、Git 常用命令与分支管理

### 初始配置

```bash
git config --global user.name "你的用户名"
git config --global user.email "你的邮箱"
```

### 仓库操作

```bash
git init
git clone <url>
```

### 查看状态与历史

```bash
git status
git diff
git diff --cached
git log --oneline
```

### 添加与提交

```bash
git add <file>
git add .
git commit -m "提交说明"
```

### 远程仓库

```bash
git remote -v
git remote add origin <url>
git remote add upstream <url>
git remote set-url origin <url>
```

### Push / Fetch / Pull

```bash
git push origin <branch>
git fetch upstream
git pull origin master
```

三者的区别：

```text
push
Local → Remote

fetch
Remote → 获取最新信息
但不自动修改当前工作分支

pull
fetch + merge
```

### 分支

查看分支：

```bash
git branch
```

创建并切换：

```bash
git checkout -b day1
```

或者：

```bash
git switch -c day1
```

不同任务放在不同分支，可以减少相互影响：

```text
master
  │
  ├── day1
  ├── day2
  └── feature-x
```

### Stash

临时保存尚未完成的修改：

```bash
git stash
```

恢复：

```bash
git stash pop
```

### 撤销修改

现代 Git 可以使用：

```bash
git restore <file>
git restore --staged <file>
```

而：

```bash
git reset --hard <commit>
```

可能直接丢失未保存修改，因此需要谨慎使用。

## 十二、Fork、PR 与开源协作流程

夏令营使用的是典型的 **Fork + Pull Request** 开源协作模式。

整体关系为：

```text
RT-Thread 官方仓库
      upstream
          │
          │ Fork
          ▼
个人 Gitee Fork
       origin
          │
          │ Clone
          ▼
       本地仓库
          │
          │ Edit
          ▼
       git add
          ↓
      git commit
          ↓
       git push
          ↓
个人 Fork 功能分支
          │
          │ Pull Request
          ▼
RT-Thread 官方仓库
          │
          ▼
        Review
          │
          ▼
         Merge
```

### Fork 与 Clone

Fork：

```text
官方远程仓库
      ↓
个人远程仓库
```

发生在 Gitee 等 Git 托管平台。

Clone：

```text
远程仓库
   ↓
本地电脑
```

是把仓库完整下载到本地。

### origin 与 upstream

Fork 工作流中：

```text
origin
=
自己的 Fork

upstream
=
官方原始仓库
```

例如：

```text
upstream
RT-Thread/rsoc-rtt
       ▲
       │ Pull Request
       │
origin
个人/rsoc-rtt
       ▲
       │ push
       │
      本地
```

### Pull Request

PR 并不是直接把代码强制合入官方仓库，而是：

> 请求维护者审核自己的修改，在审核通过后再 Merge。

基本过程是：

```text
Fork
 ↓
Clone
 ↓
Branch
 ↓
Edit
 ↓
git add
 ↓
git commit
 ↓
git push
 ↓
Pull Request
 ↓
Review
 ↓
Merge
```

### 同步 upstream

官方仓库持续更新时，可以：

```bash
git fetch upstream
```

再根据需要把官方最新内容合入自己的分支。

例如：

```bash
git switch master
git fetch upstream
git merge upstream/master
git push origin master
```

## 十三、Git 冲突、Merge 与 Rebase

多人协作时，如果两个分支修改了同一个文件中的同一部分内容，Git 无法自动判断应该保留哪个版本，就会产生冲突。

例如：

```text
共同版本 A
   │
   ├── Branch 1 修改 README
   │
   └── Branch 2 同样修改 README
```

冲突文件中通常会出现：

```text
 <<<<<<< HEAD
当前分支内容
 =======
另一侧内容
 >>>>>>> branch
```

解决流程：

1. 阅读两侧修改；
2. 决定最终内容；
3. 删除冲突标记；
4. 保存文件；
5. `git add`；
6. 继续 Merge 或 Rebase。

### Merge

```bash
git merge upstream/master
```

Merge 会保留分支之间的合并关系。

### Rebase

```bash
git rebase master
```

Rebase 会把当前分支的 Commit 重新放到新的基线上，使历史更加线性。

可以简单理解：

```text
原来：

A---B---C
     \
      D---E

Rebase 后：

A---B---C---D'---E'
```

因为 Rebase 会改写提交历史，所以对于已经共享的分支需要谨慎使用。

## 十四、几个容易混淆的 Git 概念

### Commit 不等于 Push

```text
Commit
工作区 → 本地仓库

Push
本地仓库 → 远程仓库
```

因此本地 Commit 完成，并不代表代码已经上传。

### Fetch 不等于 Pull

```text
Fetch
只获取远端变化

Pull
获取远端变化
+
合并到当前分支
```

### Fork 不等于 Clone

```text
Fork
官方远程 → 我的远程

Clone
远程 → 我的电脑
```

### origin 不等于 upstream

```text
origin
自己的 Fork

upstream
官方仓库
```

这几个概念弄清楚以后，Git 的整体逻辑就会清晰很多。
