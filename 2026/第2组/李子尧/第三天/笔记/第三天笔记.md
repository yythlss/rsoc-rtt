# RT-Thread 夏令营 Day3 学习笔记

> 主题：RT-Thread 线程间同步与通信  
> 核心内容：临界区、信号量、互斥量、事件集、消息邮箱、消息队列

---

## 一、线程间同步与通信概述

进入多线程程序后，不同线程之间不仅需要被调度，还需要解决同步与通信问题：

- **线程同步**：控制多个线程之间的执行顺序或共享资源访问关系；
- **线程通信**：在线程之间传递状态或实际数据。

本节主要涉及：

```text
线程间同步
├── 信号量 Semaphore
├── 互斥量 Mutex
└── 事件集 Event

线程间通信
├── 消息邮箱 Mailbox
└── 消息队列 Message Queue
```

---

## 二、临界区与阻塞

### 2.1 临界区

当某个资源在同一时刻只能被一个执行主体访问时，访问该资源的代码区域称为**临界区**。

例如多个线程同时修改：

```c
ticket_count--;
```

如果没有同步保护，多个线程可能在同一时刻读取、修改并写回共享变量，从而产生竞态条件。

### 2.2 阻塞

线程请求暂时不可用的资源时，如果该操作允许等待，线程会进入阻塞状态：

```text
RUNNING
   ↓
请求资源
   ↓
资源不可用
   ↓
SUSPEND
   ↓
资源可用
   ↓
READY
   ↓
重新参与调度
```

阻塞期间线程不会持续占用 CPU。

### 2.3 非阻塞

非阻塞操作在资源不可用时立即返回，由线程自行处理返回结果：

```text
阻塞：
资源没有 → 等待

非阻塞：
资源没有 → 立即返回
```

---

## 三、信号量 Semaphore

信号量用于线程同步和资源计数。

基本操作：

```text
take
 ↓
value - 1

release
 ↓
value + 1
```

当信号量不可获得时，请求线程可依据 timeout 参数等待。

---

## 四、二值信号量

二值信号量主要用于表示某个同步事件是否已经发生。

```text
Semaphore = 0
→ 事件尚未发生

release
→ 事件发生

等待线程被唤醒
```

典型模型：

```text
事件线程 / ISR
      ↓
release semaphore
      ↓
等待线程 READY
      ↓
执行后续处理
```

---

## 五、计数信号量

计数信号量适合管理多个同类有限资源。

若系统共有 N 个资源：

```text
Semaphore Initial Value = N
```

获得资源：

```text
value--
```

释放资源：

```text
value++
```

当 `value = 0` 时，表示资源已全部占用。

典型场景：

```text
停车位数量
     ↓
信号量初始值

车辆
     ↓
线程
```

因此：

> **计数信号量适合描述“有多少个资源可以同时被使用”。**

## 六、信号量等待方式与生命周期

IPC 等待策略主要包括：

```text
FIFO
PRIO
```

### FIFO

按照进入等待队列的先后顺序获得资源。

### PRIO

按照线程优先级决定等待顺序，高优先级线程更早获得资源。

IPC 对象还常见两套生命周期接口：

```text
动态创建：
create → delete

静态初始化：
init → detach
```

两套生命周期接口应成对使用。

---

## 七、互斥量 Mutex

互斥量主要用于保护只能由一个线程访问的共享临界资源。

```text
Thread A
   ↓
take Mutex
   ↓
进入临界区
   ↓
操作共享数据
   ↓
release Mutex
```

若 Thread B 同时申请该 Mutex：

```text
Mutex 已被 A 持有
       ↓
Thread B 阻塞
```

直到 A 释放互斥量后，B 才能继续运行。

---

## 八、Mutex 与 Semaphore 的区别

虽然 Mutex 和二值信号量都可表现为两种状态，但语义不同。

### Semaphore

核心是：

```text
信号 / 资源数量
```

### Mutex

核心是：

```text
Ownership
```

哪个线程获得 Mutex，哪个线程就是当前 Owner。只有持有者才能正确释放 Mutex。

因此：

```text
Semaphore
→ 同步、资源数量

Mutex
→ 保护共享变量、结构体和完整临界操作
```

---

## 九、为什么不能只保护一条语句

售票过程是一个完整事务：

```text
检查是否有票
      ↓
读取当前票号
      ↓
修改剩余票数
      ↓
记录售出票号
```

若只保护：

```c
ticket_count--;
```

而把：

```c
if (ticket_count > 0)
```

放在锁外，则两个线程仍可能同时判断“还有票”，造成竞态。

因此 Mutex 应保护完整的：

```text
check → read → modify → record
```

而不是只保护单条赋值语句。

## 十、优先级反转与优先级继承

假设：

```text
A：高优先级
B：中优先级
C：低优先级
```

C 先持有 Mutex，随后 A 需要该 Mutex，因此 A 被阻塞。如果此时 B 抢占 C，则：

```text
A 等 C
C 被 B 抢占
```

实际形成中优先级 B 间接阻塞高优先级 A，即**优先级反转**。

优先级继承机制可使 C 临时继承 A 的高优先级：

```text
A 等待 C 的 Mutex
      ↓
C 临时提高优先级
      ↓
C 完成临界区
      ↓
release Mutex
      ↓
A 获得 Mutex
```

---

## 十一、系统临界区与 Mutex

系统临界区应尽可能短，因为它会影响系统调度甚至中断响应。

一般原则：

```text
极短的变量更新
→ 可使用短临界区

较完整的线程级共享资源操作
→ Mutex
```

不应在临界区中执行：

```text
长时间循环
阻塞等待
线程延时
复杂打印
```

---

## 十二、事件集 Event

事件集用于表示多个独立同步条件。

RT-Thread 使用一个 32 位无符号值表示事件集合：

```text
Bit 0 → Event 0
Bit 1 → Event 1
Bit 2 → Event 2
...
```

例如：

```c
#define EVENT_NET_READY      (1U << 0)
#define EVENT_SENSOR_READY   (1U << 1)
#define EVENT_STORAGE_READY  (1U << 2)
```

---

## 十三、Event OR 与 AND

### OR

任意一个指定事件发生即可满足条件：

```text
Event A ─┐
         ├── OR → Wake Thread
Event B ─┘
```

### AND

必须等待所有指定事件都发生：

```text
Event A ─┐
Event B ─┼── AND → Wake Thread
Event C ─┘
```

系统启动场景：

```text
Network Ready
      +
Sensor Ready
      +
Storage Ready
      ↓
Business Task Start
```

---

## 十四、Event CLEAR

事件接收后可以根据需要清除对应事件位：

```text
Event Bits
00101100
   ↓
Receive + CLEAR
   ↓
对应事件位清零
```

事件集主要用于同步，不负责传递实际业务数据。

同一事件位被多次置位，并不会像消息队列那样形成多条排队消息。

---

## 十五、同步与通信的区别

同步类 IPC：

```text
Semaphore
Mutex
Event
```

主要解决：

```text
什么时候运行？
谁能访问资源？
某些条件是否满足？
```

通信类 IPC：

```text
Mailbox
Message Queue
```

主要解决实际数据在线程间的传递问题。

---

## 十六、消息邮箱 Mailbox

Mailbox 是一种轻量线程通信机制。

在 32 位系统中，一封邮件可用于携带一个机器字大小的数据，因此可以保存整数值或指针。

典型模型：

```text
Producer Thread
      ↓
    Mailbox
      ↓
Consumer Thread
```

例如：

```text
Sensor Thread
      ↓
数据值 / 指针
      ↓
Mailbox
      ↓
Display Thread
```

---

## 十七、Mailbox 的发送与接收

发送时：

```text
Mailbox 有空间
      ↓
send
      ↓
Message Stored
```

接收时：

```text
Mailbox 有邮件
      ↓
recv
      ↓
立即取得
```

如果邮箱为空：

```text
recv
 ↓
按照 timeout 等待
 ↓
线程阻塞
```

---

## 十八、消息队列 Message Queue

Message Queue 比 Mailbox 更适合传递结构化数据。

```text
Mailbox
→ 单个邮件数据尺寸固定

Message Queue
→ 消息尺寸可配置
```

例如：

```c
struct package_msg
{
    rt_uint32_t id;
    rt_uint8_t region;
    rt_uint16_t weight;
};
```

因此消息队列适合：

```text
传感器数据
通信帧
结构体消息
生产者 / 消费者模型
```

---

## 十九、消息队列的数据组织

消息队列通常包含：

```text
消息缓冲区
消息最大长度
最大消息数量
当前消息数量
消息链表
空闲消息链表
等待线程队列
```

发送时：

```text
Producer
   ↓
复制消息内容
   ↓
Queue Node
   ↓
加入消息队列
```

接收时：

```text
Message Queue
   ↓
取出消息
   ↓
复制到接收 buffer
   ↓
Consumer
```

因此 Message Queue 传输的是消息内容的副本。

---

## 二十、普通消息与紧急消息

普通消息按照队列顺序处理：

```text
A
B
C
D
```

紧急消息可以插入队列前部：

```text
A
URGENT
B
C
D
```

消费者下一次接收时会优先取得紧急消息。

## 二十一、五类 IPC 对比

| IPC | 主要功能 | 是否传输数据 | 典型应用 |
|---|---|---:|---|
| Semaphore | 同步 / 资源计数 | 否 | 按键同步、停车位 |
| Mutex | 共享资源互斥 | 否 | 共享变量、设备访问 |
| Event | 多条件组合同步 | 否 | 多模块 Ready |
| Mailbox | 轻量消息传递 | 是 | 状态值、指针 |
| Message Queue | 结构化消息传递 | 是 | 数据结构、生产者/消费者 |

选择关系可以概括为：

```text
有多个同类有限资源？
       ↓
Counting Semaphore

单个共享临界资源？
       ↓
Mutex

等待多个布尔条件？
       ↓
Event

轻量固定字长消息？
       ↓
Mailbox

结构化数据？
       ↓
Message Queue
```

## 二十二、动态创建与静态初始化

RT-Thread IPC 对象普遍支持：

```text
动态方式：

create
  ↓
使用
  ↓
delete
```

以及：

```text
静态方式：

init
 ↓
使用
 ↓
detach
```

即：

```text
create ↔ delete
init   ↔ detach
```

## 二十三、IPC 与线程调度的关系

IPC 的阻塞机制本质上仍建立在线程状态与调度器之上。

例如等待信号量：

```text
RUNNING
   ↓
sem take
   ↓
资源不可用
   ↓
SUSPEND
   ↓
其他线程 release
   ↓
READY
   ↓
Scheduler
   ↓
RUNNING
```

Mutex、Event、Mailbox 和 Message Queue 的阻塞接收也遵循类似状态变化。

因此 Day2 的：

```text
READY
RUNNING
SUSPEND
Priority
Scheduler
```

是理解 Day3 IPC 的基础。

## 二十五、本节内容总结

Day3 的核心是线程之间的**协作机制**。

```text
Semaphore
→ 同步和资源数量

Mutex
→ 共享资源互斥

Event
→ 多条件组合

Mailbox
→ 轻量消息

Message Queue
→ 结构化消息
```

信号量重点在资源数量和同步；互斥量重点在所有权和临界区；事件集重点在多个条件的逻辑组合；Mailbox 和 Message Queue 则用于真正的数据通信。

理解这些 IPC 的差异后，可以根据实际资源模型和数据流选择合适的同步与通信机制，而不是简单依赖全局变量在多个线程之间共享状态。
