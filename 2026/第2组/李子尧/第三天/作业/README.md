# RSOC 2026 Day3：RT-Thread 线程间同步与通信实验

## 1. 环境与任务

工程使用 RT-Thread 4.1.1、STM32F407ZG、ST-LINK SWD 和 USART1（PA9/PA10，115200 baud）。四个实验由 MSH 命令启动：`parking_demo`、`ticket_demo`、`startup_demo`、`package_demo`。每个命令由管理线程创建工作线程，完成后释放动态 IPC 对象并清除运行标志；运行中再次调用会报告 `demo already running`。

## 2. IPC 要点

| 对象 | 适用场景 | 本实验使用 |
|---|---|---|
| 计数信号量 | 可用资源数量 | 3 个停车位 |
| 互斥量 | 互斥访问且有所有权 | 完整售票读改写过程 |
| 事件集 | 多个条件的位组合 | 三个模块全部就绪 |
| 邮箱 | 固定宽度消息 | 本次仅作 API 对比 |
| 消息队列 | 定长结构体消息 | 快递消息与结束消息 |

常用 API：`rt_sem_create/take/release/delete`，`rt_mutex_create/take/release/delete`，`rt_event_create/send/recv/delete`，`rt_mb_create/send/recv/delete`，`rt_mq_create/send/recv/delete`。阻塞等待会让出 CPU；共享统计量的短更新采用临界区，不能替代所需 IPC。

## 3. 停车场计数信号量

5 个车辆线程竞争初值为 3 的信号量。车辆以 `rt_tick_from_millisecond(2000)` 为等待上限，失败后打印并延迟重试；进入后更新最大占用量，离开后释放信号量。实机结果为 5/5 完成、最大占用 3、无容量越界。互斥量只能表示一把锁，不能记录三个可同时分配的车位，故应使用计数信号量。

## 4. 双窗口售票

无锁阶段刻意把“读取余票—短延时—写回”拆开，实机观察到 40 次售出记录和 20 个重复票号，说明仅锁住 `ticket_count--` 仍不能保护检查、读取、票号记录构成的完整事务。安全阶段用互斥量覆盖检查、读、修改和记录；互斥量具备所有权语义，并可支持优先级继承，实机结果为售出 20、剩余 0、重复 0。

## 5. 启动条件事件集

网络、传感器、存储线程分别发送 `EVENT_NET_READY`、`EVENT_SENSOR_READY`、`EVENT_STORAGE_READY`。业务线程用 `RT_EVENT_FLAG_AND` 等待全部事件。正常场景延时 500/1000/1500 ms；超时场景把存储延时设为 5000 ms，业务线程先在 3000 ms 后报告存储未就绪，再次等待后启动。三个信号量可以实现，但需要分别等待、维护组合状态；事件位直接表达“全部条件成立”。

## 6. 快递消息队列

两个生产者各发送 5 条确定编号的 `struct package_msg`，队列容量为 5，分拣线程故意较慢。队满时发送线程记录失败次数并重试同一消息；最后完成的生产者发送唯一 `0xFFFFFFFFU` 结束消息。分拣线程独占统计，实机得到总件数 10、华东 4、华南 3、华北 3、总重 10250 g、重复编号 0。

## 7. 构建与实机验证

SCons 使用 `scons -Q -j1` 链接成功；镜像大小为 text 68292、data 1904、bss 3448。ST-LINK 识别到 Device ID `0x413`，通过 SWD 下载、校验并复位成功。完整串口记录见 `day3_serial.log`；其中包含四个命令的真实输出与结果块。

## 8. 结论

本次实验把“资源数量、互斥事务、条件组合、结构化数据传递”分别映射到计数信号量、互斥量、事件集和消息队列。通过无锁售票与满队列重试，验证了 IPC 的必要性及资源回收、重复运行处理的重要性。
