# RT-Thread 线程间同步与通信

> 对应《RT-Thread 内核学习手册》第 5 章「线程间同步」与第 6 章「线程间通信」，也是第三天作业的主题。
> 环境：RT-Thread 4.1.1　日期：2026-08-20

## 一、为什么需要同步与通信

多线程共享内存时，会出现两类问题：

1. **竞态（Race Condition）**：多个线程同时读写同一变量，结果取决于调度顺序，可能出错。
2. **协调问题**：线程之间需要互相等待（同步）、交换数据（通信）。

内核提供两类机制：

| 类型 | 机制 | 解决什么问题 |
| --- | --- | --- |
| 同步 | 信号量、互斥量、事件集 | 多个线程访问共享资源的先后/互斥关系 |
| 通信 | 消息队列、邮箱 | 线程之间传递数据 |

## 二、信号量（Semaphore）

### 概念

- 维护一个**计数值** `value`：
  - `rt_sem_take` 成功 → 计数减 1；计数为 0 时 `take` 阻塞（或超时返回）。
  - `rt_sem_release` → 计数加 1，并唤醒一个等待线程。
- **计数信号量**：初始值 > 1，表示"可用资源的数量"（如 3 个车位）。
- **二值信号量**：初始值 0/1，可当作简单的"锁"或"事件通知"。

### API（4.1.1）

```c
rt_sem_t rt_sem_create(const char *name, rt_uint32_t value, rt_uint8_t flag);
rt_err_t rt_sem_delete(rt_sem_t sem);
rt_err_t rt_sem_take(rt_sem_t sem, rt_int32_t timeout);  /* RT_WAITING_FOREVER 或 0/毫秒 */
rt_err_t rt_sem_trytake(rt_sem_t sem);                   /* 不等待，拿不到立即返回 */
rt_err_t rt_sem_release(rt_sem_t sem);
```

- 超时用 `rt_tick_from_millisecond(ms)` 转换；超时返回 `-RT_ETIMEOUT`。
- `flag` 一般用 `RT_IPC_FLAG_PRIO`（按优先级唤醒）。

### 典型场景（作业练习一：停车场）

初始值 3（3 个车位），5 辆车 `take`，最多 3 辆进入；车离开时 `release`。**任意时刻场内车辆 ≤ 3** 由信号量保证。

### 易错点：优先级反转

低优先级线程持有信号量时，高优先级线程 `take` 阻塞；若中优先级线程抢占了低优先级线程，高优先级线程会一直等不到——即"优先级反转"。信号量本身**不会**处理它，需要靠**互斥量**的优先级继承机制。

## 三、互斥量（Mutex）

### 概念

- 同一时刻**只能被一个线程持有**，本质是二值锁。
- **有所有权**：只能由持有它的线程 `release`；支持**递归**（同一线程可重复 take）。
- **优先级继承**：当高优先级线程被低优先级持有者阻塞时，系统临时提升持有者优先级，缓解优先级反转。

### 与二值信号量的区别

| | 互斥量 | 二值信号量 |
| --- | --- | --- |
| 所有权 | 有，只能持有者释放 | 无，任何线程可 release |
| 优先级继承 | 有 | 无 |
| 用途 | 保护临界区（互斥访问） | 资源计数 / 事件通知 |

### API

```c
rt_mutex_t rt_mutex_create(const char *name, rt_uint8_t flag);
rt_err_t   rt_mutex_delete(rt_mutex_t mutex);
rt_err_t   rt_mutex_take(rt_mutex_t mutex, rt_int32_t timeout);
rt_err_t   rt_mutex_release(rt_mutex_t mutex);
```

### 关键：临界区要"整体加锁"（作业练习二）

"检查余票 + 减票 + 记录 + 打印"必须作为一个临界区，用同一把互斥量包住。只给 `ticket_count--` 加锁不安全：两个线程可能同时通过 `if (count > 0)` 检查，导致重复票号或余票变负。对比实验（`ticket_demo_race`）用"不加锁 + 检查与修改间插 5ms 延时"制造了竞态。

## 四、事件集（Event Set）

### 概念

- 用 32 位整数的每一位表示一个事件，一次性**同时等待多个条件**。
- 三种模式：
  - `RT_EVENT_FLAG_AND`：所有指定位都置 1 才返回；
  - `RT_EVENT_FLAG_OR`：任一位置 1 即返回；
  - `RT_EVENT_FLAG_CLEAR`：满足条件返回时自动清零（可叠加到 AND/OR 上）。

### API

```c
rt_event_t rt_event_create(const char *name, rt_uint8_t flag);
rt_err_t   rt_event_delete(rt_event_t event);
rt_err_t   rt_event_send(rt_event_t event, rt_uint32_t set);
rt_err_t   rt_event_recv(rt_event_t event, rt_uint32_t set, rt_uint8_t opt,
                         rt_int32_t timeout, rt_uint32_t *recved);
```

### 典型场景（作业练习三：系统启动检查）

网络/传感器/存储三个初始化线程各自完成后 `rt_event_send` 对应位；主业务线程用 `RT_EVENT_FLAG_AND | RT_EVENT_FLAG_CLEAR` 一次等齐三个位再启动。超时测试：storage 5s、业务线程只等 3s → 超时返回 `-RT_ETIMEOUT`，定位"谁没就绪"后继续等。

### 4.1.1 的坑

`rt_event_recv` **超时返回时不会回填 `recved`**（`recved` 只在成功路径被写入）。所以超时后想判断"哪个模块没就绪"，要用 `timeout = 0` 对每个位单独 `recv`（AND、不加 CLEAR）轮询。超时时已置位的事件不会被清除，可继续等待。

## 五、消息队列（Message Queue）

### 概念

- 以**消息**为单位（每条固定大小 `msg_size`）传递数据，先进先出。
- 适合生产者-消费者模型：生产线程 `send`，消费线程 `recv`，队列自带互斥与阻塞等待。

### API

```c
rt_mq_t rt_mq_create(const char *name, rt_size_t msg_size,
                     rt_size_t max_msgs, rt_uint8_t flag);
rt_err_t rt_mq_delete(rt_mq_t mq);
rt_err_t rt_mq_send(rt_mq_t mq, const void *buffer, rt_size_t size);
rt_err_t rt_mq_recv(rt_mq_t mq, void *buffer, rt_size_t size, rt_int32_t timeout);
```

- 队列满时 `rt_mq_send` 返回 `-RT_EFULL`（不阻塞）；可用 `rt_mq_send_wait` 阻塞发送。
- 队列空时 `rt_mq_recv` 阻塞（或超时）。

### 典型场景（作业练习四：快递分拣）

两个发件线程各发 5 条 `struct package_msg`，分拣线程 `rt_mq_recv` 分类统计。队列满时记录失败并延时重发；发件完成后发特殊"结束消息"（约定 `region = 0xFF`），分拣线程收到 2 条结束消息后打印统计退出。

## 六、邮箱（Mailbox，了解）

- 比消息队列更轻量：每条消息是一个 **4 字节**字（可放整数或指针），邮箱中每个格子只占 4 字节。
- API：`rt_mb_create` / `rt_mb_send` / `rt_mb_recv`。
- 需要传结构体/多字节数据时用消息队列，传小数据/句柄时用邮箱。

## 七、API 汇总

| 机制 | 创建 | 删除 | 获取/发送 | 释放/接收 |
| --- | --- | --- | --- | --- |
| 信号量 | `rt_sem_create` | `rt_sem_delete` | `rt_sem_take` | `rt_sem_release` |
| 互斥量 | `rt_mutex_create` | `rt_mutex_delete` | `rt_mutex_take` | `rt_mutex_release` |
| 事件集 | `rt_event_create` | `rt_event_delete` | `rt_event_recv` | `rt_event_send` |
| 消息队列 | `rt_mq_create` | `rt_mq_delete` | `rt_mq_recv` | `rt_mq_send` |
| 邮箱 | `rt_mb_create` | `rt_mb_delete` | `rt_mb_recv` | `rt_mb_send` |

> 说明：事件集用 `send` 置位、`recv` 等待，方向与"发送者/接收者"对应；其余四个都是 take/recv 获取、release/send 释放。

## 八、与今天作业的对应

| 作业练习 | 用到的机制 | 要点 |
| --- | --- | --- |
| 练习一 停车场 | 计数信号量 | 有限资源计数，任意时刻 ≤ 3 |
| 练习二 售票 | 互斥量 | 临界区整体加锁；对比实验演示竞态 |
| 练习三 启动检查 | 事件集 | AND 等待多条件 + 超时定位未就绪模块 |

## 九、使用建议

- 线程与 IPC 对象**创建后都要检查返回值**（`RT_NULL` / 非 `RT_EOK`）。
- 动态线程（`rt_thread_create`）入口函数返回后由系统自动回收；静态线程（`rt_thread_init`）不会。
- MSH 命令重复执行时，要处理同名线程/IPC 对象残留（运行标志 + 结束后主动删除对象）。
- 选择原则：资源计数 → 信号量；保护临界区 → 互斥量；多条件等待 → 事件集；传数据 → 消息队列/邮箱。
