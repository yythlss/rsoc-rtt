# RT-Thread 夏令营 Day4 学习笔记：IO 设备和 PIN 设备

- 姓名：王童乐
- 组别：第 2 组
- 开发板：STM32F407 星火一号（STM32F407ZG）
- 今天的主题：IO 设备驱动框架、PIN 设备、按键中断、I2C 和 SPI

## 一、今天主要讲了什么

今天老师讲的是 RT-Thread 的 IO 设备驱动框架。刚开始听到“分层”和“ops”时，我觉得有点抽象。结合代码和实验后，我的理解是：应用程序不直接操作 STM32 的寄存器，而是先调用 RT-Thread 提供的接口，再由不同层的驱动代码去完成真正的硬件操作。

我目前理解的调用关系大概是这样：

```text
应用程序
  -> RT-Thread 通用设备接口
IO 设备管理层
  -> open / read / write / control / close
PIN、SPI、I2C 等专用框架
  -> 对外提供各自的 API
BSP 驱动层
  -> 调用 STM32 HAL
硬件外设
```

这样做的好处是，应用代码不用跟某一个 MCU 的底层函数绑死。以后如果更换芯片，很多时候只需要修改 BSP 驱动层，上面的应用代码还可以继续使用。当然，分层也会带来一些额外代码，占用一点 Flash，这是抽象带来的代价。

## 二、我对 PIN 设备的理解

GPIO 就是我们平时说的普通引脚，可以用来输出高低电平，也可以读取输入电平。在 RT-Thread 里，GPIO 被统一叫作 PIN 设备。

PIN 设备常见的工作模式有：

- 输出
- 输入上拉
- 输入下拉
- 输入浮空
- 开漏

PIN 还可以配置上升沿、下降沿、高电平、低电平和双边沿中断。

我觉得 PIN 设备比较方便的一点是，它有专门的 `rt_pin_xxx` API，比如 `rt_pin_write()` 和 `rt_pin_read()`。同时，它也可以按照普通字符设备的方式使用 `open/read/write/control/close`。也就是说，同一个设备有比较简单的用法，也有比较通用的用法。

## 三、PIN 设备是怎样一层层接起来的

老师讲到 PIN 设备时，我最开始不太明白 `rt_pin_write()` 最后是怎么控制到某个引脚的。现在我先按照自己的理解，把它简化成下面这条链：

```text
应用调用 rt_pin_write(37, 1)
  -> PIN 框架里的 rt_pin_write()
  -> PIN 设备的 ops
  -> STM32 BSP 里的 stm32_pin_write()
  -> HAL_GPIO_WritePin()
  -> STM32 的 PC5 引脚
```

### 1. BSP 驱动层：真正对接芯片

在 STM32 的 BSP 代码中，会有类似 `stm32xxxx_pin.c` 的文件。这个文件需要实现 `struct rt_pin_ops` 里的函数，例如：

```c
pin_mode
pin_write
pin_read
pin_attach_irq
pin_detach_irq
pin_irq_enable
```

这些函数里面再去调用 STM32 HAL 的函数，比如 `HAL_GPIO_Init()`、`HAL_GPIO_WritePin()` 和 `HAL_GPIO_ReadPin()`。我现在的理解是，这一层主要负责把 RT-Thread 的说法翻译成 STM32 能看懂的说法。

课堂上还讲到了引脚编号。例如 `PC5` 可以按照端口编号换算成 37：

```text
32 * (C - A) + 5 = 37
```

这个公式是为了方便框架统一管理引脚，但具体项目还是要以当前 BSP 的宏定义为准，不能只靠记公式。

底层 ops 准备好后，BSP 会注册 PIN 设备，形式类似：

```c
rt_device_pin_register("pin", &stm32_pin_ops, RT_NULL);
```

### 2. PIN 框架层：把底层函数包装起来

在 `components/drivers/pin/pin.c` 中，RT-Thread 会定义 PIN 设备对象，并提供 `rt_pin_mode()`、`rt_pin_write()`、`rt_pin_read()` 和中断相关接口。

我把这一层理解成中间翻译层：上面给应用提供统一函数，下面再去调用 BSP 的 `pin_write`、`pin_read` 等函数。这样应用代码就不需要知道 STM32 HAL 的细节。

### 3. IO 管理层：把设备放进系统

板级初始化时会调用 `rt_hw_pin_init()`，并通过 `INIT_BOARD_EXPORT` 这样的自动初始化机制运行。PIN 设备注册成功后，可以在 FinSH 中输入：

```text
list_device
```

如果能看到 `pin`，说明 PIN 设备已经进入 RT-Thread 的设备列表。

我对这部分的记忆口诀是：

> 应用调用 PIN API，PIN 框架调用 BSP ops，BSP ops 再调用 STM32 HAL。

## 四、上午做的三个实验

### 实验 1：创建一个字符设备

我们用 `rt_device_create()` 创建了一个叫 `test_dev` 的设备，再用 `rt_device_register()` 把它注册到系统里。注册后输入 `list_device`，可以看到这个设备。这个实验让我第一次看到自己写的设备也能进入 RT-Thread 设备列表，比只看源码直观很多。

### 实验 2：给设备补上 ops

接着给 `test_dev` 写了 `init`、`open`、`read`、`close` 和 `control` 等回调函数，并在函数里用 ulog 打印信息。调用上层设备接口时，可以从日志里看到对应的 ops 被执行了。

这里有一个容易踩的坑：如果没有先执行 `rt_device_open()`，就直接调用 `read`，设备框架可能会拒绝这次操作。所以设备的使用顺序也很重要。

### 实验 3：四个方向键的中断

开发板上的四个按键使用了 `PC0`、`PC1`、`PC4` 和 `PC5`。我们把它们设置成上拉输入，再用 `rt_pin_attach_irq()` 绑定下降沿中断。按下按键后，回调函数会打印按键事件。

按键实验中我注意到，机械按键按一次不一定只产生一个边沿，这就是按键抖动。如果不处理，可能按一次却打印多次。因此实际项目中要做软件消抖，也可以使用 button 软件包。

另外，中断回调里不适合做太多耗时工作。课堂上还提醒了，如果想在中断中使用 ulog，需要打开异步日志，并确认当前日志配置支持这种用法。

## 五、下午简单了解的 I2C 和 SPI

下午还快速看了 I2C 和 SPI。它们和 PIN 的思路是一样的：底层 BSP 先实现 ops，框架层再把这些函数整理成应用可以使用的接口。

| 总线 | 我的理解 | 课堂上记住的 API |
| --- | --- | --- |
| I2C | 先找到总线 `i2c1`，再把设备挂上去，例如 `i2c10` | `rt_i2c_transfer` |
| SPI | 先找到 `spi1`，再配置片选设备，例如 `spi10` | `rt_spi_configure`、`rt_spi_send`、`rt_spi_recv` |

I2C 传输时会使用 `struct rt_i2c_msg`。老师特别提醒了地址通常是 7 位地址，实际传输时要按照接口要求处理地址位。SPI 使用前需要配置模式、数据宽度和通信速率，发送和接收通常可以同时进行。

我现在还不能完全独立写出 I2C 或 SPI 驱动，但已经能看懂它们和 PIN 框架之间的共同思路了。

## 六、今天我的收获

1. 我知道了为什么 RT-Thread 要把设备驱动分成好几层。
2. 我大概理解了 `rt_pin_write()` 从应用到 HAL 的调用过程。
3. 我知道了 PIN 设备既可以调用 `rt_pin_xxx`，也可以当字符设备使用。
4. 通过 `test_dev` 实验，我看到了 `rt_device_ops` 是怎样被调用的。
5. 我知道按键中断需要考虑消抖，中断回调也不能写得太复杂。
6. 我开始把 PIN、I2C 和 SPI 看成同一套驱动框架思路，而不是三个完全独立的知识点。

## 七、我还没完全弄懂的地方

1. 不同 STM32 BSP 的 Pin 编号宏具体是怎么定义的，我还需要继续查源码。
2. `rt_device_pin_register()` 内部的 ops 包装过程，我目前只理解了大概。
3. 中断触发后，底层 IRQ 是怎样一路传到回调函数的，还需要结合源码和断点再看。
4. I2C 的 7 位地址和实际发送地址之间的关系，我还需要多做几次实验。

## 八、今天的简单总结

今天的内容比前几天更偏源码，所以一开始有些绕。现在我还不能说自己完全掌握了驱动框架，但至少知道应该从哪里开始看：先看应用调用的 API，再顺着 ops 找到 PIN 框架和 BSP，最后看到 STM32 HAL。

我觉得今天最重要的收获不是记住所有函数名，而是明白了应用代码和硬件之间还有一层层驱动框架。这也是 RT-Thread 能够跨不同 MCU 复用应用代码的原因。
