## 加入工程

将四个 `.c` 文件复制到 RT-Thread Studio 工程的 `applications` 目录，确认工程启用了 FinSH/MSH、线程、信号量、互斥量、事件和消息队列组件，然后重新生成并编译工程。

```c
#include <rtthread.h>
#include <finsh.h>
```

每个文件都能单独编译。如果把四个文件同时加入工程，命令名和全局符号不会冲突。

## 运行方法

通过串口终端依次输入：

```text
parking_demo
ticket_demo
ticket_demo unsafe
startup_demo
package_demo
```

每条命令立即返回，工作线程在后台运行。示例结束后会删除本次创建的 IPC 对象和线程，因此同一命令可以再次执行；运行期间重复输入会得到 `is already running` 提示。

## 练习一：停车场

`park_sem` 的初始值为 3，5 个车辆线程必须先获取车位信号量才能进入。获取操作等待 2 秒，超时会打印等待信息并重新申请。进入和离开时使用 `park_lock` 保护 `used` 计数，因此任何时刻不会超过 3 个车位。

这里使用计数信号量而不是互斥量，是因为资源有 3 个可用实例；互斥量只能表示“有/无”一个临界资源，不能直接表示剩余数量。

## 练习二：售票

默认执行 `ticket_demo` 时，窗口线程在同一个互斥量临界区内完成“检查余票、分配票号、减少余票、记录售出数量”四步。这样两个窗口不会拿到相同票号，最终余票为 0、售出票数为 20。

执行 `ticket_demo unsafe` 会运行故意不保护售票过程的对比模式。代码在读取余票和写回余票之间延时 10 ms，使两个窗口容易读取同一个票号，从而观察重复售票和统计错误。只给 `ticket_count--` 加锁也不够，因为“检查是否有票”和“递减”必须作为一个不可分割的操作。

## 练习三：启动条件

网络、传感器和存储线程分别在 1 秒、2 秒和 5 秒后发送事件位。业务线程先用 AND 模式等待 3 秒，预期先打印存储模块未就绪；随后无限等待，三个事件全部到达后打印：

```text
all modules are ready
business task started
```

事件集适合表达多个独立条件的组合等待；若使用三个信号量，业务线程需要分别获取并自行维护已经完成的条件，清除和重复等待也更繁琐。

## 练习四：快递分拣

消息队列容量为 5。两个发送线程各生成 5 条唯一编号的消息，分拣线程按区域统计数量和总重量。发送使用非阻塞 `rt_mq_send`，队列满时累计对应发送线程的失败次数并稍后重试，所以不会因队列暂满而丢失消息或崩溃。两个发送线程各发送一个结束标记，分拣线程收到两个结束标记后输出统计并退出。

预期总数为 10，区域数量之和为 10，编号范围为 `1001~1005` 和 `2001~2005`，且不会重复。

## 资源检查与生命周期

- 所有信号量、互斥量、事件、消息队列和动态线程都检查了创建返回值。
- 创建线程失败时，命令会删除已经创建的线程和 IPC 对象。
- 正常完成时，由最后一个工作线程或分拣线程删除 IPC 对象，并清除运行标志。
- 线程入口只在普通线程环境中执行阻塞 IPC 操作，没有在中断中调用这些 API。
