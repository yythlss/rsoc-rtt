# 练习一：停车场车位管理

本实验通过模拟停车场车位管理场景，学习计数信号量的使用方法，理解线程在竞争有限资源时的同步控制过程

停车场共有三个车位，同时有五辆车尝试进入，车辆只有成功申请到车位后才能进入停车场，离开时释放车位。该实验验证计数信号量可以用于管理多个同类有限资源，并保证任意时刻进入停车场的车辆数不超过资源总数

### 实验原理

停车场车位属于有限资源。由于本实验中共有 3 个车位，因此使用初始值为 3 的计数信号量表示当前可用车位数量

当车辆线程申请车位时，实际是对信号量执行获取操作：

如果信号量值大于 0，表示还有空车位，车辆可以进入，信号量值减 1

如果信号量值为 0，表示车位已满，车辆线程需要等待；

如果车辆在 2 秒内没有获得车位，则打印等待超时信息，并稍后重新申请

车辆离开停车场时释放信号量，表示空出一个车位

为了正确统计当前已使用车位数量，程序中使用互斥量保护 used_spaces变量，避免多个线程同时修改该变量导致统计结果错误

### 实验过程

**编写MSH命令入口**

在程序中定义 parking_demo函数作为实验入口，并使用 MSH_CMD_EXPORT 将其导出为 MSH 命令

```
int parking_demo(int argc, char **argv)
{
    ...
}

MSH_CMD_EXPORT(parking_demo, parking lot semaphore demo);
```

**创建IPC对象**

程序运行后，首先创建计数信号量和互斥量，计数信号量 parking_sem的初始值为 3，用于表示停车场可用车位数量。互斥量 count_mutex用于保护 used_spaces、finished_cars 等共享变量，防止多个线程同时修改造成数据错误

**创建车辆线程**

程序创建 5 个车辆线程，每个线程表示一辆车。车辆线程执行流程如下：

1. 延时一段时间，模拟不同车辆到达停车场的时间不同
2. 调用 rt_sem_take申请车位
3. 如果 2 秒内申请成功，则进入停车场
4. 修改并打印当前已使用车位数量
5. 停车一段时间
6. 离开停车场
7. 调用 rt_sem_release释放车位
8. 线程结束前更新完成车辆数量

**创建监控线程**

程序创建一个监控线程，用于判断所有车辆线程是否已经执行结束。所有车辆线程结束后，监控线程释放信号量和互斥量资源，并将运行状态标志清除，保证后续可以再次执行 parking_demo命令

### 思考题

**为什么这里使用计数信号量，而不是互斥量？**

因为本实验要管理的是3个停车位，属于多个同类有限资源，计数信号量可以用计数值表示剩余资源数量。初始值为3，车辆进入时技术值减少1，车辆离开时计数值增加1.

互斥量主要用于保护临界区，适合解决同一时刻只允许一个线程访问共享资源的问题。如果使用互斥量，只能表示“是否有线程正在访问”，不能自然表示“当前还有几个车位”。因此，本实验应使用计数信号量来控制车位数量，同时使用互斥量保护共享变量统计



# 练习二：多窗口售票系统

本实验通过模拟两个售票窗口同时出售同一批车票的场景，学习互斥量的使用方法，理解多线程并发访问共享变量时可能产生的竞态问题

两个售票线程共同出售20张票，每次收票都需要检查余票、记录票号并修改剩余票数，通过对比是否使用互斥量，观察共享变量在并发访问时的安全性差异

### 实验原理

车票数量ticket_count是两个售票线程共同访问的全局变量。每个窗口售票时都需要执行以下操作：

1.判断是否还有余票

2.读取当前票号

3.将剩余票数减少1

4.打印售票结果

这些操作应当作为一个完整的临界区处理，如果没有互斥保护，两个线程可能同时读取到相同的余票值，从而导致重复售票、余票统计错误等问题。因此，实验中使用互斥量ticket_mutex保护完整售票过程，保证同一时刻只有一个窗口线程能够修改ticket_count

### 实验过程

**编写MSH命令入口**

在程序中定义 ticket_demo 函数作为实验入口，并使用 MSH_CMD_EXPORT导出命令：

```
MSH_CMD_EXPORT(ticket_demo, ticket sale demo);
```

程序下载后，在串口 MSH 终端输入以下命令启动实验：

```
ticket_demo
```

**创建互斥量**

正式实验中，将宏设置为：

```

```

程序运行后创建互斥量 ticket_mutex，用于保护售票临界区

**创建售票线程**

程序创建两个售票线程：window A，window B

两个线程共同访问全局变量ticket_count，模拟两个窗口同时售票

**执行售票过程**

每个售票线程循环执行以下流程：

1.获取互斥量

2.判断是否还有余票

3.读取当前票号

4.将ticket_count减少1

5.打印售票窗口和票号

6.释放互斥量

7.延时后继续下一轮售票

当ticket_count<=0时，线程退出

**等待线程结束**

程序中使用完成信号量等待两个售票线程结束，两个窗口线程都退出后，主命令函数删除互斥量和完成信号量，并打印最终结果

在不适用互斥量的对比实验中，虽然本次运行没有出现模型错误，但从程序逻辑上看，ticket_count的读取、判断和修改并不是一个原子操作。如果两个线程在相近时间读取到同一个票数，就可能出现重复售票或余票统计错误。因此，不加互斥量的程序存在竞争条件，只是本次运行没有复现

### 思考题

**为什么只给 `ticket_count--` 加锁仍可能不安全？**

因为售票过程不只是 ticket_count--这一条语句，还包括检查是否有票、读取当前票号、修改剩余票数和打印售票结果

如果只对 ticket_count-- 加锁，而没有保护完整流程，可能出现以下情况：

1. 线程 A 判断还有余票
2. 线程 B 也判断还有余票
3. 两个线程读取到相同票号
4. 虽然后续减票操作加锁了，但重复票号已经产生

因此，必须将“检查余票、读取票号、修改余票”作为一个完整临界区进行保护，而不是只保护单独的减 1 操作



# 练习三：系统启动条件检查

本实验通过模拟设备启动前的模块初始化过程，学习事件集的使用方法，理解多个线程分别完成不同任务后，如何由主业务线程统一等待全部条件满足

要求网络模块、传感器模块和存储模块分别完成初始化，只有三个模块全部就绪后，主业务线程才能启动。通过该实验验证事件集适合用于多个事件条件的同步等待

### 实验原理

事件集是一种线程间同步机制，可以用若干个事件位表示不同状态。每个初始化线程完成后，向事件集发送对应的就绪事件；主业务线程则等待多个事件全部到达

本实验定义三个事件位：EVENT_NET_READY/EVENT_SENSOR_READY/EVENT_STORAGE_READY

主业务线程使用AND模式等待三个事件位全部置位。这样只有当网络、传感器和存储模块都准备完成后，业务线程才会继续执行。为了实现超时检测，主业务线程设置3秒等待时间。如果存储模块初始化时间过长，主业务线程会先超时返回，并打印尚未完成的模块；随后继续等待，直到所有模块全部就绪

### 实验过程

**编写MSH命令入口**

在程序中定义startup_demo函数作为实验入口，并使用MSH_CMD_EXPORT到处命令：

```
MSH_CMD_EXPORT(startup_demo,startup confition check demo);
```

程序下载后，在串口MSH终端输入以下命令启动实验：

```
startup_demo
```

**创建事件集和互斥量**

程序启动后先创建事件集startup_event，用于保护各模块的就绪状态。同时创建互斥量state_mutex，用于保护共享变量ready_flags，避免多个线程同时读写状态时出现错误

**创建初始化线程**

程序创建三个初始化线程，分别模拟三个独立模块的初始化过程：
网络初始化线程：延时1秒后发送网络就绪事件

传感器初始化线程：延时2秒后发送传感器就绪事件

存储初始化线程：延时5秒后发送存储就绪事件

每个线程在完成初始化后，先记录本模块就绪状态，再向事件集发送对应事件位

**创建主业务线程**

主业务线程使用rt_event_recv的AND模块等待三个事件全部到达，并设置3秒超时。当等待超时时，主业务线程会检查当前已完成的模块，并打印尚未完成的模块名称，当三个事件全部到达时，主业务线程打印：

```
all modules are ready
business task strated
```

### 思考题

**如果用三个独立信号实现这个功能，与使用事件集相比有什么区别**

如果使用三个独立信号量，也可以实现等待三个模块完成初始化，但实现方式更复杂。

区别主要有：

**1.表达能力不同**

事件集可以用一个对象同时表示多个事件状态，适合“多个条件同时满足”的等待场景；信号量更适合表示资源数量或单一同步事件

**2.状态查询不同**

事件集支持按位组合，可以直接判断哪些模块已就绪；独立信号量只能一个一个等待，难以直接统一判断整体状态

**3.使用方式不同**

事件集更适合本实验这种“多个模块全部完成后再启动业务”的场景；三个信号量虽然也能实现，但代码更分散，逻辑不如事件集集中



# 四、快递分拣中心

本实验通过模拟快递分拣中心的收件和分拣过程，学习消息队列的使用方法，理解线程之间如何传递结构体类型的数据

实验要求两个发件线程不断产生快递信息，一个分拣线程从消息队列中接收快递消息，并按照目的地区域进行统计。通过实验验证消息队列适合用于线程间传递数据信息

### 实验原理

消息队列是一种线程间通信机制，可以在线程之间传递固定大小的数据块。本实验中，每条快递信息使用结构体package_msg表示：

```
struct package_msg
{
    rt_uint32_t id;
    rt_uint8_t region;
    rt_uint16_t weight;
};
```

其中，id表示快递编号，region表示目的地区域，weight表示快递重量

两个发送线程分别产生快递消息，并通过rt_mg_send将消息发送到消息队列中。分拣线程通过rt_mg_recv从消息队列中接收消息，根据区域统计数量，并累计总重量

为了同质分拣线程停止接收，发送线程收到结束消息后，打印统计结果并退出

### 实验过程

**定义消息结构体**

在程序中定义快递消息结构体：

```
struct package_msg
{
    rt_uint32_t id;
    rt_uint8_t region;
    rt_uint16_t weight;
};
```

**创建消息队列**

重新创建两个发件线程：

发送线程A：产生编号1001到1005的快递

发送线程B：产生编号2001到2005的快递

每个发件线程产生5条消息，并调用rt_mg_send发送到消息队列；如果队列已满，rt_mg_send会返回失败，程序记录发送失败次数，并打印发送失败信息

**创建分拣线程**

程序创建一个分拣线程，分拣线程不断调用rt_mg_recv接收消息队列中的快递消息。每收到一条普通快递消息，分拣线程就打印快递编号、区域和重量，并更新统计数据

区域对应关系如下：

region=1：east

region=2：south

region=3：north

**发送结束消息**

两个发件线程都完成后，程序向消息队列发送一条结束消息。结束消息的编号为0，区域标志为PACKAGE_END_REGION。分拣线程收到该结束消息后不再继续接收快递，转而打印统计结果并退出

**实验结果**

![image-20260819165949131](D:\TYPORA\figures\image-20260819165949131.png)

从结果可以看出：

1.共接收到10条快递消息

2.快递编号从1001到1005、2001到2005，没有重复

3.华东区域3件，华南区域4件，华北区域3件

4.总重量为9780g

5.本次运行中消息发送失败次数为0

6.分拣线程完成统计后正常退出

**结果分析**

本实验中，两个发件线程同时向消息队列发送快递信息，分拣线程从消息队列中接收并处理。消息队列在这里起到了线程间数据传递的作用，使发件线程和分拣线程之间不需要直接共享复杂数据

由于消息队列容量为 5，当发送速度快于接收速度时，理论上可能出现队列已满导致发送失败的情况。因此程序中对 rt_mq_send 的返回值进行了判断，并统计发送失败次数。本次运行中 send failed为 0，说明消息队列在本次调度下没有发生满队列发送失败

实验结果中，快递消息的输出顺序可能与发送顺序不完全一致，这是因为两个发件线程并发运行，线程调度顺序会影响消息进入队列的先后顺序。但最终统计总数、区域数量和总重量均正确，说明分拣线程正确接收并处理了消息队列中的数据
