## 一、 线程的本质：深入 `struct rt_thread` 源码

线程在 RT-Thread 内部并不是一个神秘的黑盒，其全部状态与上下文都承载在 `rtdef.h` 中定义的 **`struct rt_thread`** 结构体中：

```c
struct rt_thread {
    char        name[RT_NAME_MAX];       /* 线程名称（RT_NAME_MAX 默认为 8 字节，超长截断） */
    rt_uint8_t  type;                    /* 对象类型（RT_Object_Class_Thread） */
    rt_uint8_t  flags;                   /* 对象标志位 */
    rt_list_t   list;                    /* 【关键】就绪队列 / 挂起队列挂载点，参与调度 */
    rt_list_t   tlist;                   /* 【关键】调试与容器遍历链表（供 list_thread 使用） */

    void       *sp;                      /* 线程栈顶指针：上下文切换时保存/恢复 CPU 寄存器 */
    void       *entry;                   /* 线程入口函数指针 */
    void       *parameter;               /* 传给 entry 的形参指针 */
    void       *stack_addr;              /* 栈内存起始地址（低地址，栈底） */
    rt_uint32_t stack_size;              /* 栈总容量（字节数） */

    rt_uint8_t  stat;                    /* 线程当前状态 + 附加属性（紧凑位编码） */
    rt_uint8_t  current_priority;        /* 当前实际优先级（0~31，支持优先级继承） */
    rt_uint8_t  init_priority;           /* 初始分配的固有优先级 */

    rt_uint32_t init_tick;               /* 初始化分配的时间片（tick 计数值） */
    rt_uint32_t remaining_tick;          /* 当前轮次剩余时间片 */

    struct rt_timer thread_timer;        /* 内嵌软件定时器：用于延时唤醒与时间片监控 */

    void (*cleanup)(struct rt_thread *); /* 线程退出时的自定义清理回调 */
    rt_ubase_t  user_data;              /* 用户自定义拓展数据 */
};
```

### 核心设计亮点：两个 `list` 的妙用
* **`list`（调度链表）**：线程在不同状态之间流转时，该节点会在 `rt_thread_ready_table[]`（就绪队列）、信号量等待队列或挂起队列之间移动。
* **`tlist`（对象容器链表）**：创建线程后即挂入内核对象容器，调度器不碰它，仅供 `list_thread` 命令遍历。即便线程被 `delete` 但尚未被回收，在从 `tlist` 移除前依然能被调试命令探查到。

## 二、 线程状态 `stat` 的紧凑编码与五态流转

`stat` 字段采用**位掩码（Bitmask）**紧凑编码，既记录主状态，又支持叠加修饰位：

```c
#define RT_THREAD_INIT       0x00   /* 初始态：已分配内存但未加入就绪队列 */
#define RT_THREAD_READY      0x01   /* 就绪态：在就绪队列中等待分配 CPU */
#define RT_THREAD_SUSPEND    0x02   /* 挂起态：主动延时或等待资源不满足 */
#define RT_THREAD_RUNNING    0x03   /* 运行态：当前正在独占 CPU 执行代码 */
#define RT_THREAD_CLOSE      0x04   /* 关闭态：线程已退出/删除，等待垃圾回收 */
#define RT_THREAD_STAT_MASK  0x07   /* 取主状态的三位掩码 (0b00000111) */
#define RT_THREAD_STAT_YIELD 0x08   /* 发生过主动让位附加标志 */
```

> ⚠️ **读状态避坑指南**：读取线程状态必须使用 `thread->stat & RT_THREAD_STAT_MASK`，直接用 `== RT_THREAD_READY` 可能会因 `RUNNING (3)` 或带有 `YIELD (0x08)` 标志导致逻辑漏判。

```text
       [ INIT 初始态 ]
              │
              │ rt_thread_startup()
              ▼
   ┌────> [ READY 就绪态 ] <──────────────────────┐
   │          │                                   │
   │          │ 调度器选中 (Schedule)              │
   │          ▼                                   │
   │      [ RUNNING 运行态 ]                      │
   │          │                                   │
   │          │ rt_thread_delay() /               │ 超时 / IPC 条件满足 /
   │          │ rt_thread_suspend() / 等待信号量  │ rt_thread_resume()
   │          ▼                                   │
   │      [ SUSPEND 挂起态 ] ─────────────────────┘
   │          │
   │ 自然退出 │ rt_thread_delete() / rt_thread_detach()
   └─────────>▼
          [ CLOSE 关闭态 ] (挂入 _rt_thread_defunct 等待 Idle 回收)
```

## 三、 $O(1)$ 抢占式调度与时间片轮转核心

### 1. 优先级查找：`__rt_ffs` 位图查找算法
RT-Thread 在 32 级优先级模式下，使用一个 32 位的整型变量 `rt_thread_ready_priority_group` 作为优先级就绪位图（Bit 0 代表 Priority 0）。
调度器通过内置的汇编/快速查找函数 `__rt_ffs()`，能够在 **几个 CPU 指令周期内瞬间找到最低置位（即当前系统中就绪的最高优先级）**，时间复杂度严格保持在 $O(1)$，与系统任务数量完全无关。

### 2. 同优先级时间片轮转
* 当多个就绪线程处于相同优先级时，调度器按就绪链表先后顺序调度。
* 每个线程消耗自身的时间片 `remaining_tick`，当减到 0 时，触发上下文切换，该线程被移到该优先级链表末尾并重置时间片，让出 CPU 给同优先级的下一个就绪线程。

## 四、 栈安全机制：`'#'` 填充、栈水印与溢出检测

### 1. 为什么栈初始化要用 `'#'` (0x23)？
在 `rt_thread_init` 中，内核会执行：
```c
rt_memset(thread->stack_addr, '#', thread->stack_size);
```
在 ARM Cortex-M 架构中，栈是**从高地址向低地址向下生长**的。整个栈底初始全部填充为 `'#'`，当程序运行压栈时，高地址的 `'#'` 会被逐步覆写为局部变量和调用寄存器。
* **栈水印（Stack Watermark）**：从栈底（`stack_addr`）向高地址扫描连续未被破坏的 `'#'` 字节数，就是该线程运行至今**绝对安全的剩余栈深度（Stack Free）**。

### 2. 调度器栈溢出检测 (`_scheduler_stack_check`)
在开启 `RT_USING_OVERFLOW_CHECK` 时，每次触发调度都会执行防御检查：
1. **栈底魔数破坏**：`*(rt_uint8_t *)thread->stack_addr != '#'` $\rightarrow$ 说明栈已经写穿到底部，发生确凿的栈溢出！
2. **栈指针越界**：`sp <= thread->stack_addr` 或 `sp > thread->stack_addr + stack_size`。
3. **安全警报**：当检测到溢出时，系统将直接调用 `rt_hw_interrupt_disable()` 关中断并进入死循环，防止脏数据写坏其他内核数据区。

> ⚠️ **关键认知**：栈溢出检测是在**调度点**触发的。如果一个死循环线程在单次运行期间把栈写爆且从未让出 CPU，溢出可能在触发调度前就造成内存破坏。因此合理的栈大小估算与静态安全分析至关重要。

## 五、 内存回收机制：空闲线程（Idle）与 Defunct 队列

当动态线程调用 `rt_thread_delete()` 时，**内存并不会立即在当前线程被释放**（因为当前线程自身还在使用这块栈执行退出代码）：
1. 线程将自身状态置为 `RT_THREAD_CLOSE`。
2. 将自身从调度就绪链表摘除，挂入全局僵尸队列 **`_rt_thread_defunct`**。
3. 主动触发调度 `rt_schedule()`，让出 CPU。
4. **真正的资源释放由 `tidle0` 空闲线程完成**：`tidle0` 在获得 CPU 时会轮询 `_rt_thread_defunct` 队列，依次调用 `rt_free(thread->stack_addr)` 和 `rt_free(thread)` 彻底归还内存给堆。

> 💡 **陷阱警示**：如果系统中有一个高优先级线程一直死循环占用 CPU 且不调用任何阻塞延时，`tidle0` 将永远无法执行，导致被删除的线程内存一直堆积在 `defunct` 队列中无法释放，造成“伪内存泄漏”。

## 六、 课堂重点：6 大高频“踩坑点”与调试经验

| 序号 | 经典踩坑场景 | 底层根本原因 | 规范化解决方案 / 正确做法 |
| :---: | :--- | :--- | :--- |
| **1** | 线程名称被截断 | `RT_NAME_MAX` 默认为 8 字节 | 线程命名应简短精炼（如 `th_led1`、`th_mon`） |
| **2** | 状态判断失误 | `RUNNING` 值为 3，`READY` 值为 1 | 读取状态必须使用 `stat & RT_THREAD_STAT_MASK` 掩码 |
| **3** | 中断直接操作线程 | 中断上下文执行耗时阻塞操作导致硬死锁 | 中断服务函数中仅置位标志，由高优先级监控线程在线程上下文中处理 |
| **4** | 动态删除堆内存不降 | 高优先级线程死循环饥饿导致 Idle 无法回收 | 任何业务线程中必须加入适度延时（如 `rt_thread_mdelay`）释放 CPU |
| **5** | 软链接在 macOS 失效 | Windows 批处理 `mklinks.bat` 在 Unix 下不运行 | 在 macOS/Linux 下使用 `ln -s` 手动补齐符号链接 |
| **6** | 自动初始化顺序颠倒 | 误在 `INIT_BOARD_EXPORT` 中创建线程 | `INIT_BOARD` 时调度器未就绪，业务线程必须在 `INIT_APP_EXPORT` 导出 |

## 七、 SCons 构建系统命令速查

```bash
# 1. 多核极速编译 (Mac Apple Silicon 推荐)
scons -j$(sysctl -n hw.ncpu)

# 2. 清理所有编译生成的目标与中间文件
scons -c

# 3. 导出编译数据库 (供 VS Code clangd 极速补全跳转)
compiledb -n scons

# 4. 生成最小依赖独立工程发布包
scons --dist
```
