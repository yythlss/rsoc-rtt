## 练习一：停车场车位管理

### 场景

一个停车场只有 3 个车位，同时有 5 辆车尝试进入。车位属于有限资源，车辆只有获得车位后才能进入。

### 功能要求

1. 创建一个初始值为 3 的计数信号量，表示剩余车位。
2. 创建 5 个车辆线程。
3. 每辆车到达后申请一个车位。
4. 获得车位后打印车辆编号和进入信息。
5. 车辆停留一段时间后离开，并释放车位。
6. 未在 2 秒内获得车位的车辆打印等待超时信息，稍后重新申请。
7. 任意时刻进入停车场的车辆数不能超过 3。

### 示例输出

```text
car1 entered, used spaces: 1
car2 entered, used spaces: 2
car3 entered, used spaces: 3
car4 waiting for a space
car2 left
car4 entered, used spaces: 3
```

### 思考题

为什么这里使用计数信号量，而不是互斥量？

**互斥量本质上是一个 0/1 的二值信号量**，只能表达"占用/空闲"两种状态，用于解决多个任务互斥访问**同一个**临界资源的问题：同一时刻最多允许一个任务进入临界区，并且它带有优先级继承机制，用于缓解优先级反转问题。

而停车场有 **3 个等价车位**，属于"数量大于 1 的可复用资源"。计数信号量的计数值恰好可以表达"剩余资源数量"：

- 创建时初值为 3，表示 3 个空车位；
- 每辆车进入时 `take` 一次，计数减 1；离开时 `release` 一次，计数加 1；
- 计数减到 0 后，后来的车辆自动挂起等待，**内核保证任意时刻场内车辆数不超过 3**。

如果改用互斥量：

1. **并发度退化为 1**——互斥量只能放行一辆车，其余 4 辆车全部排队，3 个车位无法同时利用，浪费资源；
2. **语义不符**——互斥量要求"谁获取谁释放"，通常用于同一任务进入/退出临界区；而车位的获取者（进场的车）与"释放后可进入的下一辆车"不是同一主体，这是典型的资源池模型，用计数信号量表达才自然。

**互斥量管"能不能进临界区"，计数信号量管"还剩多少资源"**。资源只有 1 份时两者等价，资源多于 1 份时必须用计数信号量。

## 练习二：多窗口售票系统

### 场景

两个售票窗口同时出售同一批车票。系统初始有 20 张票，每次只能由一个窗口修改剩余票数。

### 功能要求

1. 创建两个售票线程，分别代表窗口 A 和窗口 B。
2. 使用一个全局变量保存剩余票数。
3. 每个窗口循环完成以下操作：
   - 检查是否还有余票；
   - 将余票减 1；
   - 记录售出的票号；
   - 打印售票结果。
4. 使用互斥量保护完整的售票过程。
5. 售完后两个线程自动退出。
6. 最终必须满足：
   - 20 张票全部售出；
   - 不出现相同票号；
   - 剩余票数不能小于 0。

### 示例输出

```text
window A sold ticket 20
window B sold ticket 19
window B sold ticket 18
...
all tickets sold
remaining tickets: 0
```

### 对比实验

先暂时不使用互斥量，并在“读取余票”和“修改余票”之间加入短暂延时，观察是否会出现重复售票或余票错误。

随后加入互斥量并再次运行，对比两次结果。

### 思考题

为什么只给 `ticket_count--` 加锁仍可能不安全？

售票由三步组成：

1. 读取 `remaining_tickets`，判断是否大于 0（还有没有票）；
2. 将余票减 1；
3. 把售出的票号记录下来。

如果只给第 2 步（`ticket_count--`）加锁，第 1 步的判断和第 2 步的修改之间就存在竞态窗口：

```text
窗口 A: 读取 remaining == 1 → 判断有余票
窗口 B: 读取 remaining == 1 → 判断有余票   ← A 还没来得及减 1
窗口 A: remaining-- → 卖出 1 号票
窗口 B: remaining-- → 也卖出 1 号票        ← 重复售票！
```

两个窗口都认为"还剩 1 张票"，各卖出一张、各减一次，结果：

- 同一个票号被卖出两次（**重复售票**，违反"不出现相同票号"）；
- 计数被减了两次，可能变成负数（**超卖**，违反"剩余票数不能小于 0"）。

对比实验正是复现这一现象：去掉互斥量后，在"读取余票"与"修改余票"之间插入 1ms 延时，把竞态窗口拉大，两个窗口就会同时读到相同的余票值，卖出重复票号，最终 `data verification: FAILED!`。

因此**必须把"检查是否有票 → 减 1 → 记录票号"整个事务放进互斥量保护的临界区**，让复合操作成为原子操作，才能保证售票正确性。这也说明：互斥量保护的范围（临界区划分）比"哪一行加锁"更重要。

## 练习三：系统启动条件检查

### 场景

设备启动前需要完成三个独立模块的初始化：

- 网络模块初始化；
- 传感器模块初始化；
- 存储模块初始化。

只有三个模块全部准备完成，主业务线程才能启动。

PS：只是举例，模拟即可。

### 功能要求

定义三个事件位：

```c
#define EVENT_NET_READY      (1U << 0)
#define EVENT_SENSOR_READY   (1U << 1)
#define EVENT_STORAGE_READY  (1U << 2)
```

创建以下线程：

- 网络初始化线程；
- 传感器初始化线程；
- 存储初始化线程；
- 主业务线程。

每个初始化线程经过不同时间的延时后，发送对应的就绪事件。

主业务线程必须使用 AND 模式等待三个事件全部到达，然后打印：

```text
all modules are ready
business task started
```

另外增加一次超时测试：

- 将存储模块初始化时间设置为 5 秒；
- 主业务线程最多等待 3 秒；
- 超时后打印尚未完成的模块，并再次等待。

### 示例输出

```text
network ready
sensor ready
wait modules timeout, storage is not ready
storage ready
all modules are ready
business task started
```

### 思考题

如果用三个独立信号量实现这个功能，与使用事件集相比有什么区别？

事件集（event set）是"状态型"的**，多个条件被编码到 32 个位中：

1. **一次等待多个条件**：主业务线程一条 `rt_event_recv(AND)` 就能原子地等待"三个模块全部就绪"，与模块就绪的先后顺序无关，代码简洁。
2. **超时后状态不丢失**：超时返回时已就绪的事件位仍然保留（不带 CLEAR 标志时），可以继续等待或随时查询，天然适合"启动条件检查"这种场景。
3. **支持多种组合**：AND（全部满足）、OR（任一满足）、CLEAR（取走即清除），还能广播给多个等待者，表达力强。

**信号量是"消耗型"的**，take 一次就少一次。若用三个独立信号量实现：

1. **必须依次 take 三次**：如果先拿到了网络、传感器两个信号量，而存储信号量还没就绪，那么**已经拿到的两个信号量被本任务消耗掉了**，状态被破坏——下次重试时它们"不见了"，必须小心翼翼地归还，逻辑复杂且容易出错。
2. **难以判断"谁没就绪"**：超时后要定位是哪个模块没完成，需要额外的全局状态记录（如本实现中 `g_ready_state` 所做的事），事件集按位查询天然就能做到。
3. **无法被多个任务共享观察**：一个任务取走信号量后，其他任务就感知不到"模块已就绪"这一事实；而事件集的状态可以同时被多个等待者看到。

## 练习四：快递分拣中心

### 场景

两个收件线程不断产生快递信息，一个分拣线程从消息队列中取出快递并按照目的地区域分类。

### 消息结构

```c
struct package_msg
{
    rt_uint32_t id;
    rt_uint8_t region;
    rt_uint16_t weight;
};
```

其中：

```text
region = 1：华东
region = 2：华南
region = 3：华北
```

### 功能要求

1. 创建一个消息队列，队列容量为 5 条消息。
2. 创建两个发件线程，每个线程产生 5 条快递消息。
3. 快递编号不得重复。
4. 分拣线程接收消息，并打印快递编号、区域和重量。
5. 分拣完成后统计：
   - 总快递数量；
   - 各区域快递数量；
   - 所有快递的总重量。
6. 当队列已满时，发送线程不得崩溃，应记录发送失败次数。
7. 两个发送线程完成后，向分拣线程发送一条结束消息。
8. 分拣线程收到结束消息后打印统计结果并退出。

### 示例输出

```text
package 1001 -> east, weight: 1200 g
package 2001 -> south, weight: 850 g
package 1002 -> north, weight: 960 g
...
total packages: 10
east: 4, south: 3, north: 3
total weight: 10250 g
send failed: 0
```

### 重复执行保护

- 各练习均使用运行标志检测任务是否仍在运行，运行中再次执行命令会被拒绝（返回 EBUSY 并提示）。
- 任务结束后主动删除 IPC 对象（信号量/互斥量/事件集/消息队列）。
- 线程退出后由 RT-Thread 空闲线程自动回收线程对象与栈空间，不会因同名线程残留产生异常。
- task1 在启动新练习前会额外检查并清理残留的车辆线程。

### 对比实验操作步骤（练习二）

1. 输入 `ticket_demo nomutex`，观察输出：两个窗口会多次卖出**相同票号**（重复售票），总售票数与剩余票数对不上，`data verification: FAILED!`。
2. 等待监控线程打印汇总后，再输入 `ticket_demo`，观察输出：20 张票全部售出、无重复票号、剩余票数为 0，`data verification: PASSED`。
3. 对比两次结果即可得出结论：互斥量把"检查 → 减 1 → 记录"变成原子事务，是售票正确性的保证。

总结：**信号量适合"计数/互斥"类同步（如练习一、二），事件集适合"多条件状态组合"类同步（如练习三）**。要求三个条件同时满足且超时后要继续等待，事件集是更合适的工具。
