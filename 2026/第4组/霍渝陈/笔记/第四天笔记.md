## 1. 设备驱动框架：分层架构与设计思想

### 1.1 没有框架的世界（痛点）

不同 MCU 厂商的外设操作方式完全不同：ST 用 HAL 库、GD 用固件库、NXP 用 SDK……裸机写法下，业务代码里到处都是 `HAL_GPIO_WritePin`、寄存器操作，**换一颗芯片 = 全部业务代码重写**。这就是嵌入式"碎片化"的根源。

RT-Thread 的解法：**把"业务"和"硬件"之间的所有访问统一收口到一层抽象接口**，上层只认识 `open/read/write/close`，不认识寄存器。

### 1.2 四层架构

```
┌─────────────────────────────────────────────────────────────┐
│ ① 应用层（业务逻辑）                                          │
│   只调 rt_device_find / open / read / write / control / close │
│   完全不关心底层是 STM32 还是 GD32，是 SPI 还是 GPIO           │
├─────────────────────────────────────────────────────────────┤
│ ② IO 设备管理层（框架核心）                                    │
│   rt-thread/src/device.c  +  components/drivers/             │
│   维护设备链表/对象容器；按名字查找设备；把调用分发到驱动 ops    │
│   负责引用计数、自动初始化、回调登记                             │
├─────────────────────────────────────────────────────────────┤
│ ③ 驱动层（BSP 驱动，对接具体硬件）                              │
│   工程 drivers/drv_gpio.c、drv_uart.c ...                      │
│   实现 rt_device_ops / rt_pin_ops 函数指针集，内部调 HAL/寄存器 │
├─────────────────────────────────────────────────────────────┤
│ ④ 硬件层（寄存器 / 芯片厂商 HAL 库）                           │
│   STM32 HAL、CMSIS、GPIO 寄存器                                │
└─────────────────────────────────────────────────────────────┘
```

**分层核心价值一句话**：应用层只依赖 ② 的稳定接口，③④ 可以随便换——**设备驱动分离，应用代码复用**。换芯片时只重写 ③（驱动层），① 一行不改。

### 1.3 「设备驱动分离」在 C 语言里怎么落地：面向对象三板斧

RT-Thread 是 C 写的，但用三个手法实现了 OOP：

| 手法 | 实现 | 说明 |
|---|---|---|
| **继承** | 自定义设备结构体**首成员放 `struct rt_device`** | 驱动私有结构 = 基类 + 私有字段，指针强转即可访问基类（`struct test_device { struct rt_device parent; rt_uint8_t buf[64]; ... }`） |
| **多态** | 函数指针集（`dev->read/write/control...`） | 框架只调函数指针，具体实现由驱动填。同一套 `rt_device_read`，对串口是读 FIFO、对 Flash 是读扇区、对虚拟设备是读内存 |
| **封装** | `rt_device_find` 按名字拿句柄 | 应用层拿到的只是 `rt_device_t` 句柄，看不到内部结构，驱动细节完全隐藏 |

### 1.4 设备分类

`struct rt_device.type`（`enum rt_device_class_type`）决定设备种类：`RT_Device_Class_Char`（字符：串口/键盘，字节流）、`RT_Device_Class_Block`（块：Flash/磁盘，随机寻址）、`RT_Device_Class_SPIBUS`、`RT_Device_Class_I2CBUS`、`RT_Device_Class_Graphic`、`RT_Device_Class_NetIf` 等。分类的意义：同类的设备可以用统一的框架接口（如块设备有统一的 blk 读写/擦除协议）。

## 2. IO 设备管理层：生命周期 API 与回调机制

### 2.1 生命周期总览（本作业的核心主线）

```
 rt_device_create(type, size)      ① 动态分配设备对象（含私有结构空间）
        │
 绑定 ops 函数指针                  ② 把驱动实现挂到对象上（dev->init/open/...）
        │
 rt_device_register(dev, name, fl) ③ 挂入内核设备对象容器（重名检查）
        │
 rt_device_find("xxx")             ④ 应用层按名字查句柄
        │
 rt_device_open(dev, oflag)        ⑤ 首次 open 自动调 init（懒初始化）→ 调 open，ref_count++
        │
 rt_device_read/write/control()    ⑥ 框架分发到对应 ops 函数
        │
 rt_device_close(dev)              ⑦ ref_count--，归零才真正调 close
        │
 rt_device_destroy(dev)            ⑧ 释放内存（一般驱动生命周期内不调用）
```

### 2.2 创建与注册（`rt-thread/src/device.c`，行号可核对）

**`rt_device_create(int type, int attach_size)`**（L119）：

```c
size = RT_ALIGN(sizeof(struct rt_device), RT_ALIGN_SIZE);   /* 基类大小 */
attach_size = RT_ALIGN(attach_size, RT_ALIGN_SIZE);          /* 私有结构大小 */
size += attach_size;
device = (rt_device_t)rt_malloc(size);                       /* 一块连续内存 */
rt_memset(device, 0x0, sizeof(struct rt_device));            /* 只清了基类！ */
device->type = (enum rt_device_class_type)type;
```

> ⚠️ **关键细节**：`rt_memset` 只清零基类部分，**私有结构（attach_size 那部分）是未初始化内存**——驱动注册时必须自己初始化私有字段（buf、标志位等），否则读到垃圾值。这是本次作业 test_drv.c 的一个注意点。

**`rt_device_register(dev, name, flags)`**（L52）：

```c
if (rt_device_find(name) != RT_NULL) return -RT_ERROR;   /* 重名拒绝 */
rt_object_init(&(dev->parent), RT_Object_Class_Device, name); /* 挂进设备对象容器 */
dev->flag = flags;        /* 如 RT_DEVICE_FLAG_RDWR */
dev->ref_count = 0;       /* 引用计数清零 */
dev->open_flag = 0;
```

### 2.3 查找与打开（find / open）

**`rt_device_find(name)`**（L103）＝ `rt_object_find(name, RT_Object_Class_Device)`——在设备对象容器链表里按名字做字符串匹配，返回句柄或 `RT_NULL`。

**`rt_device_open(dev, oflag)`**（L203）的完整逻辑：

1. **懒初始化**：若 `dev->flag` 没有 `RT_DEVICE_FLAG_ACTIVATED` 标志 → 自动调用 `dev->init(dev)`（如果驱动填了 init），成功后再置 ACTIVATED。**也就是说：驱动在第一次 open 时才被初始化**，不是注册时就 init。
2. **独占检查**：若设备带 `RT_DEVICE_FLAG_STANDALONE` 且已被打开过 → 返回 `-RT_EBUSY`（独占设备不可二次打开）。
3. 调用 `dev->open(dev, oflag)`。
4. 成功 → `dev->ref_count++`，`open_flag |= RT_DEVICE_OFLAG_OPEN`。

> 框架里 `device_init` / `device_open` 这些名字其实是宏（device.c L25-39）：
> `#define device_init (dev->init)`（未开 RT_USING_DEVICE_OPS 时）。开/关 `RT_USING_DEVICE_OPS` 只是"函数指针直接放结构体里"还是"收进一个 ops 结构体"的区别，调用逻辑完全一样。

### 2.4 读写与控制（read / write / control）

| API | 框架行为（device.c） |
|---|---|
| `rt_device_read(dev, pos, buf, size)`（L314） | `ref_count == 0` → 置 errno 返回 0（没 open 不能读）；否则分发 `dev->read`；驱动没实现 → `-RT_ENOSYS` |
| `rt_device_write(dev, pos, buf, size)`（L357） | 同上，分发 `dev->write` |
| `rt_device_control(dev, cmd, args)`（L396） | 分发 `dev->control`。`cmd` 是驱动自定义的"命令字"：内核保留 `RT_DEVICE_CTRL_RESUME 0x01 / SUSPEND 0x02 / CONFIG 0x03 / CLOSE 0x04`、`SET_INT 0x10 / CLR_INT 0x11 / GET_INT 0x12`，**自定义命令从 0x20 起避免冲突** |

`pos` 参数对字符设备一般忽略（或作偏移），对块设备是块号——由驱动自己解释。

### 2.5 关闭（close）

`rt_device_close`（L269）：`ref_count == 0` → 返回错误（没打开不能关）；否则 `ref_count--`；**只有减到 0 才调用 `dev->close`** 并置 `open_flag = RT_DEVICE_OFLAG_CLOSE`。

> **引用计数语义**：`open` 多少次就要 `close` 多少次，计数归零才真正"关闭设备"。这样多个模块可以同时持有一个设备而不互相干扰。

### 2.6 回调机制（rx_indicate / tx_complete）

设备结构体里内置两个回调指针（rtdef.h L1086-1087）：

```c
rt_err_t (*rx_indicate)(rt_device_t dev, rt_size_t size);   /* 有数据可读 */
rt_err_t (*tx_complete)(rt_device_t dev, void *buffer);     /* 发送完成 */
```

应用用 `rt_device_set_rx_indicate(dev, callback)` / `rt_device_set_tx_complete(dev, callback)` 登记回调。**回调的完整链路**：

```
硬件中断（如串口收到一个字节，EXIT/USART 中断）
   → 驱动中断服务函数（drv_uart.c ISR）
   → 驱动调 dev->rx_indicate（框架层的回调，实际是应用登记的）
   → 应用回调里发信号量/消息队列通知业务线程
   → 业务线程醒来处理数据
```

**设计要点**：回调运行在**中断上下文**，必须短小快速——只做"通知"（发信号量/置标志），真正处理放到线程里。

## 3. GPIO（Pin）外设开发

RT-Thread 把 GPIO 抽象成 **PIN 设备**：不走 `rt_device_open/read/write` 那套流程，而是提供一组精简的 C 风格 API（`components/drivers/misc/pin.c` 实现，通过内部 `_pin_ops` 函数指针集分发到 BSP 驱动）。

### 3.1 PIN 设备 API（`drivers/pin.h`，值可核对）

| API | 功能 |
|---|---|
| `rt_pin_mode(pin, mode)` | 配置引脚模式 |
| `rt_pin_write(pin, value)` | 输出电平（`PIN_HIGH` / `PIN_LOW`） |
| `rt_pin_read(pin)` | 读引脚电平 |
| `rt_pin_attach_irq(pin, mode, hdr, args)` | 绑定中断回调（可重复绑定换回调） |
| `rt_pin_irq_enable(pin, enabled)` | 使能/失能引脚中断 |

**引脚模式**（pin.h L31-35）：

```c
#define PIN_MODE_OUTPUT         0x00   /* 推挽输出 */
#define PIN_MODE_INPUT          0x01   /* 浮空输入 */
#define PIN_MODE_INPUT_PULLUP   0x02   /* 上拉输入 */
#define PIN_MODE_INPUT_PULLDOWN 0x03   /* 下拉输入 */
#define PIN_MODE_OUTPUT_OD      0x04   /* 开漏输出 */
```

**中断触发模式**（pin.h L37-41）：

```c
#define PIN_IRQ_MODE_RISING          0x00   /* 上升沿触发 */
#define PIN_IRQ_MODE_FALLING         0x01   /* 下降沿触发 */
#define PIN_IRQ_MODE_RISING_FALLING  0x02   /* 双边沿触发 */
#define PIN_IRQ_MODE_HIGH_LEVEL      0x03   /* 高电平触发 */
#define PIN_IRQ_MODE_LOW_LEVEL       0x04   /* 低电平触发 */
```

### 3.2 引脚编号机制：GET_PIN 宏 + pins[] 映射表

上层不直接写"GPIOB 第 5 脚"，而是用逻辑引脚号。BSP 的 `drv_common.h` 定义（F407 版，寄存器地址步长 0x400）：

```c
#define GET_PIN(PORTx,PIN) (rt_base_t)((16 * ((__STM32_PORT(PORTx) - GPIOA_BASE)/0x0400UL)) + PIN)
/* GET_PIN(B, 5) = 16*1 + 5 = 21 */
```

逻辑号 → 物理引脚的翻译在 `drivers/drv_gpio.c` 的 `pins[]` 映射表里（每个元素含 `GPIO_TypeDef *gpio; rt_uint16_t pin;`）。`stm32_pin_write` 查表拿到 `{GPIOB, GPIO_PIN_5}` 后调 `HAL_GPIO_WritePin` 写寄存器——**上层永远不用知道具体寄存器**。

### 3.3 按键中断实验（星火号）

星火 1 号相关引脚（工程 board 定义）：`LED_R = PF12`、`LED_B = PF11`、`KEY_UP = PC5`（**按下为低电平**）。

**标准流程**（按键控制 LED 翻转）：

```c
#define KEY_UP   GET_PIN(C, 5)     /* PC5，按下为低 */
#define LED_R    GET_PIN(F, 12)

/* 中断回调：只做标记/通知，不做耗时操作 */
static void key_cb(void *args)
{
    rt_sem_release(key_sem);        /* 发信号量通知按键线程 */
}

/* 初始化（INIT_APP_EXPORT 自动执行） */
rt_pin_mode(LED_R, PIN_MODE_OUTPUT);
rt_pin_mode(KEY_UP, PIN_MODE_INPUT_PULLUP);          /* 上拉：松开=高，按下=低 */
rt_pin_attach_irq(KEY_UP, PIN_IRQ_MODE_FALLING, key_cb, RT_NULL);  /* 下降沿触发 */
rt_pin_irq_enable(KEY_UP, PIN_IRQ_ENABLE);

/* 按键线程：等信号量 → 消抖 → 翻转 LED */
while (1)
{
    rt_sem_take(key_sem, RT_WAITING_FOREVER);
    rt_thread_mdelay(20);                            /* ① 消抖延时 */
    if (rt_pin_read(KEY_UP) == PIN_LOW)              /* ② 再读确认确实是低电平 */
    {
        rt_pin_write(LED_R, !rt_pin_read(LED_R));    /* 翻转 LED */
    }
}
```

**中断链路**（对照 drv_gpio.c 源码）：`rt_pin_attach_irq` → BSP 的 `stm32_pin_attach_irq`（L308）把回调存进 `pin_irq_hdr_tab[]` 回调表 + 配置 EXTI 中断线 → 硬件按键按下触发 EXTI 中断 → `stm32_pin_exti_irq` 查表找到该引脚的 `hdr` 回调并调用 → 回到应用回调。

### 3.4 消抖处理（为什么必须做）

机械按键按下/松开的瞬间，簧片会**弹跳 5~20ms**，产生一串高低电平毛刺——如果直接沿触发，一次按下会进好几次中断（LED 会闪好几下或状态错乱）。

| 方案 | 做法 | 适用 |
|---|---|---|
| 硬件消抖 | 按键并联 RC 低通滤波 / 电容，把毛刺滤平 | 电路设计阶段，效果最好 |
| 软件消抖（延时重读） | 中断（或检测到电平变化）后 `mdelay(10~20ms)`，**再读一次电平确认** | 本次实验方案，简单可靠 |
| 软件消抖（状态机/计数） | 定时器周期采样，连续 N 次一致才认为有效 | 需要抗强干扰时 |

### 3.5 中断回调注意事项

1. 回调在**中断上下文**运行：不能 `rt_thread_mdelay`、不能 malloc、不能做重活——只允许发信号量/事件/消息、置标志。
2. 重活（消抖延时、LED 翻转、数据处理）放**线程**里做。
3. 按键按下/松开都可能触发 → 按需选触发沿（本实验只需按下，用下降沿）。

## 4. I2C / SPI 总线外设开发

总线设备的特点是"**总线（Bus）+ 设备（Device）**"两层模型：总线驱动管物理传输，挂在总线上的从设备只管自己的协议逻辑。

### 4.1 I2C 协议基础

- **两根线**：`SCL`（时钟，主机产生）+ `SDA`（数据，双向）
- **寻址**：7 位从机地址（+1 位读写位组成首字节）；一条总线上可挂多个从机，靠地址区分
- **时序**：SCL 高电平时 SDA 产生下降沿 = **起始条件**；SCL 高电平时 SDA 上升沿 = **停止条件**；每个字节 8 位 + 1 位 **ACK/NACK**（从机应答）
- **特点**：半双工、速率标准 100k/400k（快速模式）、线少布线简单
- 典型应用：EEPROM（AT24Cxx）、温湿度传感器（AHT10/SHT30）、OLED（SSD1306 也可走 I2C）

### 4.2 RT-Thread I2C 模型与核心 API（`drivers/i2c.h`）

```c
struct rt_i2c_bus_device {          /* 总线对象：继承 rt_device + 私有字段 */
    struct rt_device parent;
    const struct rt_i2c_bus_device_ops *ops;   /* master_xfer / slave_xfer / control */
    struct rt_mutex lock;           /* 总线自带互斥锁：多线程访问互斥 */
    rt_uint32_t timeout, retries;
    ...
};

struct rt_i2c_msg {                 /* 一次传输单元（消息） */
    rt_uint16_t addr;               /* 7 位从机地址 */
    rt_uint16_t flags;              /* RT_I2C_WR(0) / RT_I2C_RD(1<<0)，可组合 NO_STOP 等 */
    rt_uint16_t len;
    rt_uint8_t  *buf;
};

struct rt_i2c_client {              /* 从设备句柄：绑定总线 + 地址 */
    struct rt_i2c_bus_device *bus;
    rt_uint16_t client_addr;
};
```

**核心 API**（4.1.1 实际存在，可核对 i2c.h）：

| API | 作用 |
|---|---|
| `rt_i2c_bus_device_register(bus, name)` | 注册一条 I2C 总线（BSP 驱动用） |
| `rt_i2c_bus_device_find(name)` | 按名字找总线，如 `"i2c1"` |
| `rt_i2c_transfer(bus, msgs[], num)` | **最底层通用传输**：一组消息数组，可组合"写→读"（如先发寄存器地址再读数据） |
| `rt_i2c_master_send(bus, addr, flags, buf, size)` | 主机发数据（对 transfer 的封装） |
| `rt_i2c_master_recv(bus, addr, flags, buf, size)` | 主机收数据 |
| `rt_i2c_bus_lock/unlock(bus, timeout)` | 手动锁总线（transfer 内部已带锁） |

> 注意：4.1.1 内核**没有** `rt_i2c_read_regs/write_regs`（那是其他版本的 API），读寄存器要靠 `rt_i2c_transfer` 组两条消息：先写寄存器地址（RT_I2C_WR），再读数据（RT_I2C_RD）。

### 4.3 SPI 协议基础

- **四根线**：`SCLK`（时钟）、`MOSI`（主出从入）、`MISO`（主入从出）、`CS`（片选，低有效，一从机一根）
- **全双工**：时钟每个沿同时收发一位——所以 SPI 的"读"其实是"写一个 dummy 字节换回一个字节"
- **模式由 CPOL/CPHA 决定**：CPOL=时钟空闲电平（0/1），CPHA=采样沿（第一个沿/第二个沿）→ 组合出 **Mode 0~3**；配合 MSB/LSB 位序
- **特点**：速率高（几十 MHz）、无寻址（CS 选从机）、线多；典型应用：Flash（W25Qxx）、SD 卡、LCD、传感器

### 4.4 RT-Thread SPI 模型与核心 API（`drivers/spi.h`）

```c
struct rt_spi_device {              /* 从设备对象 */
    struct rt_device parent;        /* 注册后应用层可 rt_device_find 到它 */
    struct rt_spi_bus *bus;         /* 挂在哪条总线上 */
    struct rt_spi_configuration config;   /* mode / data_width / max_hz */
    void *user_data;                /* 私有：如 CS 引脚号 */
};

struct rt_spi_message {             /* 一次传输的要素 */
    const void *send_buf;           /* 要发的数据（NULL = 只收） */
    void *recv_buf;                 /* 接收缓冲区（NULL = 只发） */
    rt_size_t length;
    rt_uint8_t cs_take;             /* 传输前拉低 CS */
    rt_uint8_t cs_release;          /* 传输后拉高 CS */
    struct rt_spi_message *next;    /* 消息链，可一次连续传输多条 */
};
```

**核心 API**：

| API | 作用 |
|---|---|
| `rt_spi_bus_attach_device(dev, name, bus_name, user_data)` | 把从设备挂到总线上并注册（user_data 一般放 CS 引脚） |
| `rt_spi_configure(dev, cfg)` | 配置从设备的模式/位宽/速率 |
| `rt_spi_take_bus / rt_spi_release_bus` | 独占/释放整条总线（多线程保护） |
| `rt_spi_send_then_recv(dev, send_buf, len, recv_buf, len)` | 先发后收（如写命令字再读数据） |
| `rt_spi_send_then_send` | 连续两段发送 |
| `rt_spi_transfer(dev, send_buf, recv_buf, size)` | 全双工收发 |
| `rt_spi_transfer_message(dev, msg)` | 传一条消息（带 CS 控制） |

### 4.5 I2C vs SPI 对比

| 维度 | I2C | SPI |
|---|---|---|
| 线数 | 2 根（SCL/SDA） | 4 根 + 每从机 1 根 CS |
| 速度 | 100k~400k（最高几 M） | 可到几十 MHz |
| 寻址 | 7 位地址，靠地址选从机 | 靠 CS 片选，无地址 |
| 通信方式 | 半双工 | 全双工 |
| 从机数量 | 地址空间大、线共享 | 受 CS 引脚数量限制 |
| 典型器件 | EEPROM / 温湿度 / OLED | Flash / SD / LCD |
| RT-Thread 传输接口 | `rt_i2c_transfer` / `master_send/recv` | `rt_spi_transfer` / `send_then_recv` / `transfer_message` |

## 5. 基于芯片（BSP）与基于 SDK（CubeMX）两种开发模式

### 5.1 基于芯片的 BSP 模式（本项目用的就是这种）

RT-Thread Studio「新建 RT-Thread 项目 → **基于芯片** → STM32F407ZG」：

- 工程里自带 `drivers/` 目录：`board.c`、`board.h`、`drv_gpio.c`、`drv_uart.c`... 这是 **RT-Thread 官方/芯片厂商维护的 BSP 驱动**，随内核一起走
- 引脚/时钟配置写在 `board.h`（如 `BSP_I2C1_SCL_PIN`、`BSP_USART1_TX_PIN`）和 `board.c` 的时钟初始化里，**改配置 = 改源码**
- 编译系统 scons + Kconfig（`.config`/`rtconfig.h`）管组件开关
- **优点**：驱动与 RT-Thread 深度集成、可读可改、能学到框架对接方式；**缺点**：改引脚/外设不如图形化直观

### 5.2 基于 SDK 的 CubeMX 模式

先用 **STM32CubeMX**（ST 官方图形化配置工具）配置时钟树/引脚/外设，**可视化生成初始化代码**，再与 RT-Thread 集成：

- 所有配置保存在 `.ioc` 文件里，**改配置重新生成代码**，不用手写
- 初始化代码是 ST 生成的 HAL 代码（`MX_GPIO_Init()`、`MX_I2C1_Init()`...），RT-Thread 作为"系统层"叠加其上
- 集成方式：CubeMX 工程里加 RT-Thread 包（nano 版做精简内核，完整版带设备框架），或手动移植
- **优点**：图形化、不容易配错时钟/引脚、ST 生态资料多；**缺点**：工程结构由工具生成、定制 RT-Thread 驱动对接要自己处理、版本升级容易出兼容问题

### 5.3 对比与选型

| 维度 | 基于芯片（BSP） | 基于 SDK（CubeMX） |
|---|---|---|
| 初始化代码来源 | RT-Thread BSP 驱动 + 手写/改源码 | CubeMX 自动生成 HAL 初始化 |
| 外设配置方式 | 改 board.h / board.c 源码 | .ioc 图形化配置后重新生成 |
| 时钟/引脚可视化 | 无（看代码） | 有（时钟树/引脚图） |
| 与 RT-Thread 集成度 | 原生集成，驱动即框架 | 需要手动桥接（nano 无设备框架） |
| 学习价值 | **高**：能看到框架对接全过程 | 中：生成代码不易理解底层 |
| 适用场景 | 学习/定制/深度优化 | 快速原型/量产常规开发 |

> 本次夏令营用 BSP 芯片工程，正好能直接看到 `drv_gpio.c` 怎么实现 PIN ops、`board.h` 怎么定义引脚——第四节作业的 test_dev 虚拟驱动，就是模仿这套"驱动实现 ops → 注册 → 应用层调用"的流程。
