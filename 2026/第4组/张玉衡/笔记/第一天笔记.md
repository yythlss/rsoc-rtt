## 二、RT-Thread 生态与三条产品线

RT-Thread 是国产自研的实时操作系统（RTOS），发展近 20 年，GitHub 12.2k+ stars，是国内活跃的开源社区项目，内核已迭代至 V5.x。

### RTOS 为什么需要线程与调度

在裸机程序中，通常是在 `main()` 里循环执行不同任务：

```c
int main(void)
{
    while (1)
    {
        task_a();
        task_b();
        task_c();
    }
}
```

功能简单时够用，但随着系统复杂度提高，会出现「任务周期不同、某个任务阻塞拖垮其他任务、程序耦合越来越严重」等问题。RTOS 的思路是：把不同功能拆成多个线程，交给操作系统调度运行。

几个核心概念：

| 概念          | 含义                                          |
| ------------- | --------------------------------------------- |
| Thread / Task | 系统中的基本运行实体                          |
| Scheduler     | 根据优先级和线程状态决定 CPU 当前运行哪个线程 |
| Tick          | RTOS 的基本时间节拍                           |
| IPC           | 线程之间的通信与同步机制                      |

常见 IPC：信号量（Semaphore）、互斥量（Mutex）、事件（Event）、邮箱（Mailbox）、消息队列（Message Queue）。

### 三条产品线

| 版本                   | 特点                                                         | 适用场景                 |
| ---------------------- | ------------------------------------------------------------ | ------------------------ |
| **Nano**               | 极简内核：线程/调度/时钟/中断/内存管理/IPC，资源占用低，Apache 协议开源 | 资源受限的小型 MCU       |
| **标准版（Standard）** | 内核 + 设备框架 + FinSH/DFS/网络/POSIX/日志/IoT 组件 + 软件包，生态完整 | 通用 MCU、常规嵌入式系统 |
| **Smart**              | 面向带 MMU 的处理器，用户态/内核态隔离，安全性与隔离性更高   | 高性能嵌入式设备         |

> 记忆：**Nano → 小而够用；Standard → 完整 MCU RTOS；Smart → 面向 MMU 的操作系统形态。**

分层模型可以简单理解为：

```text
Application（应用）
    ↓
Components / Packages（组件 / 软件包）
    ↓
RT-Thread Kernel（内核）
    ↓
Device Driver Framework（设备驱动框架）
    ↓
BSP / Hardware（板级支持 / 硬件）
```

## 三、开发环境搭建

### 3.1 环境三要素

RT-Thread 开发环境由三部分组成：

```text
RT-Thread 源码
    +
SDK 开发工具（工具链 / 编译器 / 开发工具）
    +
BSP 板级支持包（启动文件 / 底层驱动 / 工程配置）
    ↓
RT-Thread 开发环境
```

- **RT-Thread Studio**：官方一站式 IDE，集成工程创建、SDK 管理、编译、下载、调试。
- **SDK Manager**：统一管理 RT-Thread 源码、STM32F4 芯片支持包、工具链等开发依赖。
- **BSP（板级支持包）**：适配具体开发板，包含启动文件、底层驱动、工程配置等核心文件。

### 3.2 搭建步骤

1. 安装 RT-Thread Studio 软件，按教程完成配置；
2. 打开 SDK Manager，下载课程指定版本的 RT-Thread 源码（4.1.1）+ STM32F4 芯片支持包；
3. 将 STM32F407 开发板通过 ST-Link 连接电脑，在设备管理器中确认 ST-Link 驱动被正常识别；
4. 新建工程：芯片选 STM32F407ZG，内核选标准版，串口波特率 115200。

创建工程时需同时确认：MCU 型号、RT-Thread 版本、BSP、工具链、调试器、Console/UART 配置。

### 4.2 串口配置

| 参数   | 值     |
| ------ | ------ |
| 波特率 | 115200 |
| 数据位 | 8      |
| 校验位 | None   |
| 停止位 | 1      |
| 流控   | None   |
| 编码   | UTF-8  |

### 4.3 关键代码 `applications/main.c`

```c
#include <rtthread.h>

#define DBG_TAG "main"
#define DBG_LVL DBG_LOG
#include <rtdbg.h>

int main(void)
{
    int count = 1;

    rt_kprintf("rsoc 2026!");

    while (count++)
    {
        LOG_D("Hello RT-Thread!");
        rt_thread_mdelay(1000);
    }

    return RT_EOK;
}
```

- `rt_kprintf()`：通过 RT-Thread 控制台输出字符串；
- `LOG_D()`：输出 Debug 级别日志（配合 `DBG_TAG`、`DBG_LVL`），自动换行；
- `rt_thread_mdelay(1000)`：让当前线程延时 1000 毫秒（约 1 秒）。

### 4.4 终端运行结果

复位开发板后，串口输出启动 banner：

```text
rsoc 2026!
```

主循环每秒打印一次 `[D/main] Hello RT-Thread!`，说明主线程在周期运行。

## 五、Build / Download / Run / Debug 四阶段

这四个概念在嵌入式开发中经常一起出现，但作用不同：

### 5.1 Build（编译）

把源码转换为 MCU 可执行的程序：

```text
Source Code → Preprocess → Compile → Assemble → Link → Executable Image
```

常见输出：`.elf`（含符号与调试信息，Debug 用）与 `.bin`（纯二进制镜像，烧写用）。

### 5.2 Download（下载）

把编译好的程序写入 MCU：`PC → RT-Thread Studio → ST-Link → STM32F407`。

### 5.3 Run（运行）

MCU 正常执行已烧录的程序。

### 5.4 Debug（调试）

通过 ST-Link 在调试器控制下运行：断点、单步、查看变量/寄存器/调用栈。

| 阶段     | 作用                   |
| -------- | ---------------------- |
| Build    | 把源码变成程序         |
| Download | 把程序写入 MCU         |
| Run      | MCU 正常运行程序       |
| Debug    | 在调试器控制下分析程序 |

## 六、RT-Thread 源码目录结构

以 RT-Thread 4.1.1 源码树为例，`rt-thread/` 是一份完整的**内核源码树**，官方分成 6 大目录：

```text
rt-thread/
├── src/         内核核心源码
├── include/     内核头文件
├── libcpu/      芯片/CPU 移植代码
├── components/  组件与中间件
├── examples/    示例代码（纯参考）
├── tools/       构建工具脚本（SCons）
├── Kconfig      内核配置菜单入口
└── SConscript   内核构建脚本入口
```

### 6.1 `src/` —— 内核实现 + `include/` —— 内核接口

`src/` 是内核"心脏"，全部与芯片无关、纯 C 实现：

| 文件                                           | 作用                                                         |
| ---------------------------------------------- | ------------------------------------------------------------ |
| `scheduler.c`                                  | 调度器：就绪队列、优先级调度、时间片轮转，`rt_schedule()` 是线程切换核心 |
| `thread.c`                                     | 线程管理：创建/删除/启动/挂起/恢复/延时                      |
| `timer.c`                                      | 定时器（软件/硬件）                                          |
| `ipc.c`                                        | IPC：信号量/互斥锁/事件/邮箱/消息队列                        |
| `mem.c` / `memheap.c` / `mempool.c` / `slab.c` | 多种内存管理算法                                             |
| `object.c`                                     | 内核对象系统（对象注册、查找，链表管理）                     |
| `device.c`                                     | 设备框架 `rt_device_*`                                       |
| `kservice.c`                                   | 内核基础服务：`rt_kprintf` 等                                |
| `clock.c`                                      | 系统时钟节拍（tick）                                         |
| `cpu.c` / `irq.c`                              | CPU 封装 / 中断管理                                          |
| `idle.c`                                       | 空闲线程（优先级最低）                                       |
| `signal.c`                                     | 信号机制（POSIX）                                            |
| `components.c`                                 | 组件自动初始化 `rt_components_init()`                        |

`include/` 关键头文件：

| 头文件        | 作用                                       |
| ------------- | ------------------------------------------ |
| `rtthread.h`  | 总头文件，`#include <rtthread.h>` 串起其余 |
| `rtdef.h`     | 基础类型、内核对象结构体、通用宏           |
| `rthw.h`      | 硬件抽象接口（移植层必须实现的函数声明）   |
| `rtservice.h` | 双向链表、`container_of` 等容器工具        |
| `rtdbg.h`     | 调试宏 `LOG_D/I/W/E`                       |

> 关键理解：**`src/` 实现内核，`include/` 定义接口**。`rthw.h` 里声明的函数就是给 `libcpu/` 移植层下的"订单"——内核只管调用，具体操作硬件由移植层完成。

### 6.2 `libcpu/` —— 移植层

按芯片架构分目录（arm / risc-v / mips / ia32 / aarch64 等）。STM32F407 使用 Cortex-M4 内核，对应 `libcpu/arm/cortex-m4/`：

| 文件                                                 | 作用                                                    |
| ---------------------------------------------------- | ------------------------------------------------------- |
| `cpuport.c`                                          | CPU 移植实现：SysTick、PendSV、开关中断、启动第一个线程 |
| `context_gcc.S` / `context_iar.S` / `context_rvds.S` | 各编译器的线程上下文切换汇编                            |

> **上下文切换是 RTOS 的"命门"**，必须贴近芯片写汇编，所以放在移植层而不是内核层。换一块 CPU，只需换 `libcpu/` 对应目录。

### 6.3 `components/` —— 组件层

运行在内核之上，可选、可裁剪（由 `rtconfig.h` 的 `RT_USING_*` 宏决定是否编译）：

| 目录         | 作用                                   |
| ------------ | -------------------------------------- |
| `finsh/`     | 命令行组件（FinSH / MSH）              |
| `dfs/`       | 虚拟文件系统框架                       |
| `drivers/`   | 设备驱动框架抽象（串口/SPI/I2C/GPIO…） |
| `net/`       | 网络框架（lwIP、netdev、SAL、AT）      |
| `fal/`       | Flash 抽象层（分区管理）               |
| `utilities/` | 工具（ulog 日志、utest 单元测试等）    |
| `libc/`      | C 库适配层                             |

> 注意：框架源码的存放位置 ≠ 框架名称。例如 GPIO 引脚框架源码在 `components/drivers/misc/pin.c`（头文件 `pin.h`），判断一个框架看 `include/drivers/` 下的头文件即可。

### 6.4 `tools/` —— 构建系统

RT-Thread 用 **SCons** 构建，`tools/` 是构建引擎：`building.py`（递归收集源码）、`gcc.py`/`keil.py`/`iar.py`（适配各编译后端）、`menuconfig.py`/`kconfiglib.py`（图形化配置）、`rt_studio.py`（Studio 专用后端）。

### 6.5 整体关系

```text
        ┌──────────────────────────────┐
        │ 应用层 applications/main.c    │  ← 你写的代码
        └──────────────────────────────┘
                      │ 调用 API
        ┌──────────────────────────────┐
        │ 组件层 components/            │  ← 可选，按 RT_USING_* 裁剪
        └──────────────────────────────┘
                      │
        ┌──────────────────────────────┐
        │ 内核 src/（实现）+ include/（接口）
        └──────────────────────────────┘
                      │ 调用 rthw.h 声明的硬件接口
        ┌──────────────────────────────┐
        │ 移植层 libcpu/arm/cortex-m4/  │  ← 上下文切换汇编 + cpuport.c
        └──────────────────────────────┘
                      │
              STM32F407ZG 硬件
```

> 核心结论：**同一个 `rt-thread/` 源码树，配合不同的 `rtconfig.h`，能产出不同"胖瘦"的系统**——这就是"可裁剪"。

## 七、RT-Thread 启动流程

```text
startup_xx.S（汇编入口）
   ↓ 栈指针配置、Flash 数据拷贝到 SRAM、BSS 段清零
编译器入口（MDK __main / GCC entry）
   ↓
rtthread_startup()
   ↓ 关闭全局中断、板级硬件初始化、打印版本 Logo（rt_show_version）
内核模块初始化（系统时钟 → 调度器 → 信号量等）
   ↓ 组件自动初始化（INIT_*_EXPORT 宏收口，rt_components_init 按顺序执行）
创建主线程 / 定时器线程 / 空闲线程
   ↓
rt_system_scheduler_start()（启动调度器）
   ↓
进入 main() 线程（用户应用程序）
```

与裸机的核心区别：**RT-Thread 不是把 `main()` 当普通函数顺序执行，而是把它放进一个线程里运行**，系统从顺序执行变为多线程调度；只有调度器启动后，多线程才真正开始工作。

线程生命周期：`rt_thread_create()`（动态）或 `rt_thread_init()`（静态）→ `rt_thread_startup()` 进入就绪态 → 调度器按优先级/时间片调度。

## 八、FinSH / MSH 命令行

RT-Thread Standard 的 FinSH 组件提供命令行，开启 `RT_USING_FINSH` + `FINSH_USING_MSH` 后，串口出现 `msh >` 提示符。常用命令：

| 命令                                            | 作用                       |
| ----------------------------------------------- | -------------------------- |
| `help`                                          | 查看命令帮助               |
| `free`                                          | 查看内存使用情况           |
| `list_thread` / `ps`                            | 查看线程                   |
| `list_sem` / `list_mutex`                       | 查看信号量 / 互斥锁        |
| `list_event` / `list_mailbox` / `list_msgqueue` | 查看事件 / 邮箱 / 消息队列 |
| `list_mempool` / `list_timer`                   | 查看内存池 / 定时器        |

优势：**不需要反复修改程序并重新编译，就能直接查看 RTOS 当前的运行状态**，是后续学习线程、IPC、设备驱动时的核心调试工具。

## 十、Git 基础与版本控制

Git 是分布式版本控制系统，用于保存历史、跟踪修改、多人协作、分支开发、代码回退与开源贡献。

### 10.1 四大区域数据流

```text
工作区(Working Tree) --git add--> 暂存区(Staging Area) --git commit--> 本地仓库(Local Repo) --git push--> 远程仓库(Remote Repo)
```

- 工作区：正在编辑的文件；
- 暂存区：`git add` 选择本次 Commit 要包含的修改；
- 本地仓库：`git commit` 生成一次正式版本记录；
- 远程仓库：`git push` 上传到 Gitee 等平台。


| `git restore <file>`                       | 丢弃工作区修改                                     |
| `git restore --staged <file>`              | 取消暂存                                           |
| `git reset --soft/--mixed/--hard <commit>` | 回退（soft 保留暂存与工作区；hard 丢弃全部，慎用） |
| `git revert <commit>`                      | 新增提交来撤销某次提交（不改写历史，推荐）         |
| `git stash` / `git stash pop`              | 临时保存 / 恢复修改                                |

> **reset vs revert**：`reset` 改写历史，适合本地未推送的提交；`revert` 保留历史、新增撤销提交，适合已推送的提交。

## 十一、Fork + PR 开源协作流程

夏令营使用典型的 **Fork + Pull Request** 协作模式：

```text
RT-Thread 官方仓库 (upstream)
        │ Fork（Gitee 平台操作）
        ▼
个人 Gitee Fork (origin)
        │ Clone
        ▼
本地仓库
        │ git add → git commit → git push
        ▼
个人 Fork 功能分支
        │ Pull Request
        ▼
官方仓库 → Review → Merge
```

### 11.1 origin 与 upstream

| 名称       | 含义             |
| ---------- | ---------------- |
| `origin`   | 自己的 Fork 仓库 |
| `upstream` | 官方原始仓库     |

平时 `push → origin`，官方更新时 `git fetch upstream` 获取上游最新状态。

### 11.2 标准 PR 工作流（8 步）

1. Gitee 上 Fork 官方仓库到个人账号，并同步上游；
2. `git switch master` + `git pull origin master`：切回主分支并拉取最新；
3. `git checkout -b day1`：新建当天分支（严禁直接改 master）；
4. 修改 / 新增文件（建 `笔记/`、`作业/` 目录，写 Markdown）；
5. `git add .`：加入暂存区；
6. `git commit -m "说明"`：本地提交；
7. `git push origin day1`：推送到个人 Fork 的 day1 分支；
8. Gitee 网页创建 PR（`你的fork:day1 → 上游:master`），指定 Reviewer。

- **审核职责**：组员 PR 由小组长审核合并，组长 PR 由导师复核。
- **PR 拆分建议**：一次 PR 尽量只解决一个明确问题。Day1 通常拆两次——第一次只建个人目录模板，第二次再交笔记 + 作业。

### 11.3 冲突解决（Merge 与 Rebase）

多人修改同一文件的同一位置时产生冲突，冲突标记如下：

```text
<<<<<<< HEAD
当前分支内容
=======
另一侧内容
>>>>>>> branch
```

解决流程：阅读两侧修改 → 决定最终内容 → 删除冲突标记 → 保存 → `git add` → `git commit`（merge）或 `git rebase --continue`（rebase）。

- **Merge**（`git merge master`）：保留分支合并关系；
- **Rebase**（`git rebase master`）：把当前分支提交"重放"到新基线上，历史更线性；因为改写历史，已共享分支慎用。

```text
原来：  A---B---C
              \
               D---E
Rebase 后： A---B---C---D'---E'
```

## 十二、易混概念辨析

| 易混点                      | 区别                                      |
| --------------------------- | ----------------------------------------- |
| `Commit` vs `Push`          | Commit 是 本地保存；Push 才是 上传远程    |
| `Fetch` vs `Pull`           | Fetch 只取不合并；Pull = fetch + merge    |
| `Fork` vs `Clone`           | Fork 是 远程→远程；Clone 是 远程→本地     |
| `origin` vs `upstream`      | origin = 自己的 Fork；upstream = 官方仓库 |
| `add` vs `commit` vs `push` | 暂存 ≠ 提交 ≠ 推送，三个阶段              |

## 十三、常见问题与踩坑记录

| 问题                                            | 处理                                                         |
| ----------------------------------------------- | ------------------------------------------------------------ |
| ST-Link 固件版本过低、烧录报错                  | 用 ST 官方固件升级工具更新固件（可多换几个工具尝试）         |
| 调试结束后串口出现 `hard fault on thread: main` | 冷启动恢复；若复现，用 `pc`/`lr` 结合 `.map`/调用栈定位，检查栈余量、大数组、空指针、越界、复位方式 |
| Git 不跟踪空文件夹                              | 空目录放 `.gitkeep` 或真实文件（如 README）才能提交          |
| `git push` 提示 `Everything up-to-date`         | 没有新提交，先 `git add` 再 `git commit`                     |
| 命令报 `command not found`                      | 所有命令以 `git` 开头（`git commit` 不是 `commit`），注意 `checkout` 拼写 |
| Windows 带空格路径 `cd` 报 `too many arguments` | 盘符 `D:\` 写成 `/d/`，路径加双引号 `cd "/d/xxx"`            |
| Gitee 禁止命令行暴露邮箱                        | 设置里关闭「禁止命令行推送暴露个人邮箱」，或跳过邮箱配置     |
| 私有仓库 401/认证失败                           | Gitee 私人令牌过期，重新生成；或改用 openssl 后端 + 令牌     |
| LF/CRLF 换行警告                                | 仓库根目录放 `.gitattributes`（内容 `* text=auto`）          |
| `fatal: not a git repository`                   | 当前目录不是仓库，进入项目根目录或 `git init`                |
| `remote origin already exists`                  | 已绑定，用 `git remote set-url origin <url>` 修改            |
