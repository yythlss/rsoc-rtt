# 第四天笔记：RT-Thread IO 设备驱动框架

## 一、IO 设备框架

RT-Thread 用统一的 IO 设备接口隔离应用和硬件。应用层调用 open、read、write、control、close 等标准 API，设备驱动框架层通过 ops 指针完成类型和协议适配，BSP 层再对接 STM32 HAL、寄存器或其他厂商库。

设备对象以 rt_device 为公共基类，包含设备类型、打开标志、回调和操作函数指针等信息。字符设备适合串口、终端、按键等顺序字节流；块设备按块读写并支持随机访问，文件系统通常依赖块设备。

标准设备生命周期：

~~~
create -> register -> find -> open -> read/write/control -> close
~~~

register 会把设备加入 IO 管理链表，因此可以用 list_device 查看。read/write 前必须先 open，否则设备引用计数未增加，操作可能被拒绝。设备未初始化时，open 可能自动调用 init。

## 二、PIN 设备对接

PIN 设备的调用链为：

~~~
应用调用 rt_pin_mode/read/write/attach_irq
  -> IO 管理层统一入口
  -> PIN 框架层
  -> rt_device_pin_ops
  -> BSP PIN 驱动
  -> STM32 HAL 或 GPIO 寄存器
~~~

应用只依赖统一的 PIN API 和引脚编号，框架通过 ops 把请求转发到具体 BSP。更换 MCU 时，主要调整引脚映射、初始化和底层读写，应用层逻辑可以保持不变。

每组 GPIO 有 16 个引脚，PC5 的通用编号计算为 2 * 16 + 5 = 37。实际使用仍要以 BSP 宏、板卡原理图和芯片手册为准。

按键按下为低电平时，可以配置上拉输入和下降沿中断。机械抖动可能使一次按键产生多次中断，应使用软件按键包或其他消抖逻辑。中断上下文不能调用阻塞日志，应该使用异步 ISR 输出或把事件交给线程处理。

## 三、星火一号上的 PIN 对接

### 1. 板卡和环境

本课程板卡为 RT-Spark 星火一号，主控为 STM32F407ZGT6。星火一号工程的 BSP 目录包含 HAL_Drivers、STM32F4xx HAL、board 和 RT-Thread 内核组件。应用层使用 GET_PIN(port, number) 生成引脚编号，具体端口映射由 STM32 PIN 驱动完成。

已核对的星火一号 SDK 例程：

| 板载资源 | MCU 引脚 | 例程中的配置 | 说明 |
| --- | --- | --- | --- |
| 红色 LED | PF12 | PIN_MODE_OUTPUT，输出低电平点亮 | 共阳 LED，低电平有效 |
| 蓝色 LED | PF11 | PIN_MODE_OUTPUT | 由板卡例程使用 |
| KEY1 | PC1 | PIN_MODE_INPUT_PULLUP，下降沿中断 | 按下为低电平 |
| WK_UP | PC5 | PIN_MODE_INPUT_PULLUP，下降沿中断 | 按键例程使用 |

星火一号 SDK 当前已核对并明确使用 PF12、PF11 作为 LED 引脚。PC1、PC5 在本地星火一号 CubeMX 配置中分别显示为以太网 `ETH_MDC`、`ETH_RXD1`，不能仅凭通用 STM32F4 示例直接写成板载按键。课程中按键映射应以当天使用的板卡原理图、BSP 宏和实际连线为准；这也是外设复用冲突排查的一部分。

### 2. 引脚编码

星火一号 BSP 的 STM32 GPIO 驱动使用如下编码：

~~~
PIN_NUM(port, no) = (port << 4) | no
~~~

端口 A、B、C 分别对应 0、1、2。因此：

~~~
PF12 = (5 << 4) | 12 = 92
PC1  = (2 << 4) | 1  = 33
PC5  = (2 << 4) | 5  = 37
~~~

课程中按每组 16 个引脚计算 PC5 = 2 * 16 + 5 = 37，与 BSP 的位移编码结果一致。应用只使用统一编号，BSP 再把高 4 位解释为端口、低 4 位解释为引脚号。

### 3. 从 API 到 HAL 的逐级调用

以红灯控制为例：

~~~
rt_pin_mode(GET_PIN(F, 12), PIN_MODE_OUTPUT)
  -> pin.c 中的 rt_pin_mode()
  -> _hw_pin.ops->pin_mode()
  -> drv_gpio.c 中的 stm32_pin_mode()
  -> HAL_GPIO_Init(GPIOF, GPIO_PIN_12)

rt_pin_write(GET_PIN(F, 12), PIN_LOW)
  -> pin.c 中的 rt_pin_write()
  -> _hw_pin.ops->pin_write()
  -> drv_gpio.c 中的 stm32_pin_write()
  -> HAL_GPIO_WritePin(GPIOF, GPIO_PIN_12, GPIO_PIN_RESET)
~~~

PIN 框架中的 rt_pin_ops 是对接枢纽。星火一号 drv_gpio.c 将 stm32_pin_mode、stm32_pin_write、stm32_pin_read、stm32_pin_attach_irq、stm32_pin_detach_irq、stm32_pin_irq_enable 和 stm32_pin_get 填入 _stm32_pin_ops，最后调用 rt_device_pin_register("pin", &_stm32_pin_ops, RT_NULL) 注册名为 pin 的设备。

因此，list_device 中出现 pin Pin Device 只能证明 PIN 设备已注册；真正控制引脚还必须经过 ops 指针进入 STM32 HAL。

### 4. 按键中断的真实路径

星火一号 SDK 的按键例程对 PC1 和 PC5 执行：

~~~
rt_pin_mode(PIN_KEY1, PIN_MODE_INPUT_PULLUP)
rt_pin_attach_irq(PIN_KEY1, PIN_IRQ_MODE_FALLING, irq_callback, args)
rt_pin_irq_enable(PIN_KEY1, PIN_IRQ_ENABLE)
~~~

在 BSP 中，下降沿模式会配置 GPIO_PULLUP 和 GPIO_MODE_IT_FALLING；驱动根据引脚位号选择 EXTI IRQ，STM32F4 的 EXTI5 至 EXTI9 共用 EXTI9_5_IRQHandler，EXTI10 至 EXTI15 共用 EXTI15_10_IRQHandler。中断处理函数进入 RT-Thread 中断上下文，调用 HAL_GPIO_EXTI_IRQHandler，再由 HAL_GPIO_EXTI_Callback 转到 PIN 驱动保存的回调。

这个链路说明：

1. 应用不需要直接操作 EXTI 寄存器。
2. 同一 IRQ 组内的引脚需要由 BSP 统一分发。
3. 回调运行在中断上下文，不能调用可能阻塞的日志、线程延时或等待型 IPC。

BSP 的 IRQ 注册解决了“如何到达回调”，没有解决机械按键消抖。消抖应在 button 软件包或线程层完成。

### 5. 工程配置与初始化

星火一号例程的 rtconfig.h 开启 RT_USING_PIN。编译时必须同时收集 RT-Thread 的 PIN 框架源文件和 BSP 的 HAL_Drivers/drv_gpio.c；只有开启宏而没有收集 BSP 驱动，应用调用 rt_pin_* 仍可能编译通过，但无法完成正确链接或运行。

PIN 设备初始化依赖 GPIO 时钟开启。星火一号 drv_gpio.c 的 rt_hw_pin_init() 会打开存在的 GPIOA 到 GPIOK 时钟，准备 _stm32_pin_ops 后注册 pin 设备。这个初始化属于板级驱动层，应用层不应重复打开 GPIO 时钟或直接改 HAL 配置。

## 四、RT-Thread 版本和主线源码差异

本次 RSOC 工程和星火一号 SDK 使用的是 RT-Thread 4.1.1 风格的 PIN 接口，本地 pin.h 中可以看到 rt_device_pin_status 和旧式 parent.read/write/control 适配。GitHub 当前 RT-Thread 主线的 dev_pin.h 已演进为 rt_device_pin_value，并增加 PIN 去抖、设备管理和 PIN 控制相关接口。

阅读 GitHub 主线时要区分：

- 统一 API 名称可能保持兼容；
- 结构体字段、返回类型和 ops 成员可能变化；
- 主线的 RT_USING_DM、PINCTRL、pin_debounce 等能力不代表当前课程工程已经开启；
- 作业代码应以当前工程的 rtconfig.h、头文件和实际构建结果为准。

## 五、I2C、SPI 与工具配置

I2C 使用 struct rt_i2c_msg 描述地址、读写标志、长度和缓冲区。多字节事务可组织多个消息结构体后提交。遇到 -5 等错误时，应检查 7 位地址、地址格式、连线、上拉电阻和总线状态。总线被拉死时，可以产生 9 个时钟脉冲尝试释放 SCL/SDA。

SPI 需要先注册总线，再挂载设备。应确认总线名、片选极性、最大频率、MSB/LSB、主从模式和 CPOL/CPHA。发送和接收的底层本质通常是全双工交换。

Qmax/CubeMX 可生成时钟、引脚和外设初始化代码。基于芯片或 SDK 创建的工程一般更容易配置；主线多型号工程可能需要手动打开宏、拷贝初始化代码或调整底层驱动。

## 六、CubeMX 与 RT-Thread Studio 联调外设

### 1. 两个工具的职责边界

CubeMX 负责芯片硬件资源配置，RT-Thread Studio 负责 RT-Thread 工程、组件和驱动的编译运行。联调不能只停留在 CubeMX 生成代码，也不能只以 Studio 编译通过为结束。

| 环节 | CubeMX 负责 | RT-Thread Studio 负责 |
| --- | --- | --- |
| 芯片与时钟 | MCU 型号、HSE/HSI、PLL、APB 时钟 | 检查生成代码是否被工程收集 |
| GPIO 复用 | I2C 的 SCL/SDA、开漏和复用功能 | 检查 BSP 初始化和配置宏 |
| 外设参数 | I2C 速度、地址模式、滤波等 | 使能 RT-Thread I2C 框架和 BSP 驱动 |
| 代码生成 | `MX_I2Cx_Init()`、MSP 初始化 | 加入 SConscript、编译、下载、串口验证 |
| 运行观察 | 保存 `.ioc` 作为硬件配置依据 | 查看 `list_device`、日志和总线波形 |

### 2. 以硬件 I2C 为例的配置流程

以下是 STM32F407 的标准联调流程，实际 I2C 实例、引脚和从设备地址必须按当天板卡和器件原理图替换。

1. 在 CubeMX 中选择准确的 MCU 型号，例如 STM32F407ZGTx，完成系统时钟和调试接口配置。
2. 在 `Pinout & Configuration` 中开启 `I2C1`、`I2C2` 或 `I2C3`，确认 SCL、SDA 使用 Alternate Function Open-Drain。
3. 检查 SCL、SDA 的外部上拉电阻。I2C 由器件主动拉低、靠上拉恢复高电平，不能用普通推挽输出替代完整电气配置。
4. 在 `Parameter Settings` 中设置 7 位地址模式和总线速度。首次联调优先使用 100 kHz，稳定后再按器件手册提高到 400 kHz。
5. 保存 `.ioc`，确认 I2C 外设、GPIO 复用、时钟树和中断配置与板卡一致。
6. 将 `MX_I2Cx_Init()` 及 MSP 初始化代码放入工程实际编译路径，并确认 `stm32f4xx_hal_i2c.c`、对应头文件和 `HAL_I2C_MODULE_ENABLED` 已启用。
7. 在 RT-Thread Studio 的 RT-Thread Settings 中开启 `RT_USING_I2C`、设备框架和对应 BSP 硬件 I2C 驱动。仅开启 `RT_USING_I2C` 而没有 `master_xfer` 实现，应用层无法真正访问硬件。
8. 检查 `SConscript`、工程资源和生成的 `subdir.mk`，确认 CubeMX 文件、HAL I2C、BSP I2C 适配文件和 RT-Thread I2C 核心均进入编译。
9. 构建并下载后执行 `list_device`，确认出现 `i2c1`、`i2c2` 等总线设备，再执行应用层读写测试。

当前星火一号 SDK 的 `rtconfig.h` 已开启 `RT_USING_I2C` 和 `RT_USING_I2C_BITOPS`，其 Kconfig 中的 `BSP_USING_I2C1/2/3` 明确标注为 software simulation；当前 `RSOC2026_IO` 的 `rtconfig.h` 目前只开启 `RT_USING_PIN`，尚未完成 I2C 联调。因此本节是后续移植和验证方案，不是 `test_dev` 已完成的硬件运行结果。

### 3. 星火一号软件 I2C 配置

星火一号 SDK 的软件 I2C 路径为：

~~~
RT_USING_I2C + RT_USING_I2C_BITOPS
    -> rt-thread/components/drivers/i2c/i2c-bit-ops.c
    -> libraries/HAL_Drivers/drv_soft_i2c.c
    -> rt_pin_mode/read/write
    -> 星火一号 drv_gpio.c
    -> STM32 HAL GPIO
~~~

Kconfig 中的默认引脚如下：

| 总线选项 | SCL | SDA | 说明 |
| --- | --- | --- | --- |
| `BSP_USING_I2C1` | PB8，编号 24 | PB9，编号 25 | 软件模拟 I2C1 |
| `BSP_USING_I2C2` | PF1，编号 81 | PF0，编号 80 | 面向 AP3216C、ICM20608、ES8388 等板载设备 |
| `BSP_USING_I2C3` | PE0，编号 64 | PE1，编号 65 | 面向 AHT21 的板载软件 I2C |

软件 I2C 驱动通过 `PIN_MODE_OUTPUT_OD` 设置开漏输出，并将 SDA/SCL 释放为高电平；`i2c-bit-ops.c` 再用 GPIO 高低电平组合出 START、STOP、数据位、ACK 和重复 START。它不需要 STM32 I2C 外设寄存器，但仍依赖 PIN 框架、GPIO 和外部上拉。

### 4. I2C 调用链

硬件 I2C 的调用链为：

~~~
应用层 rt_i2c_transfer()
    -> i2c_core.c
    -> bus->ops->master_xfer()
    -> BSP 硬件 I2C master_xfer
    -> HAL_I2C_Master_Transmit/Receive 或寄存器
    -> SCL/SDA 物理总线
~~~

软件 I2C 的后半段为：

~~~
应用层 rt_i2c_transfer()
    -> i2c-bit-ops.c
    -> set_sda/set_scl/get_sda/get_scl
    -> rt_pin_write/read()
    -> PIN ops
    -> HAL_GPIO_WritePin/ReadPin()
    -> SCL/SDA 物理总线
~~~

`struct rt_i2c_bus_device` 保存总线设备、操作集和互斥锁。`rt_i2c_transfer()` 先获取总线锁，再调用 `master_xfer`，避免多个线程同时改变同一条总线的时序。`struct rt_i2c_msg` 的 `addr` 使用 7 位从设备地址，`flags` 表示读写方向，`len` 是消息长度，`buf` 是数据缓冲区。应用层不要把 7 位地址提前左移。

### 5. I2C 单字节写和寄存器读示例

下面是 RT-Thread 4.1.1 风格的总线 API 示例。`i2c1` 和 `0x68` 只是示例，必须替换为实际总线名和器件 7 位地址；代码未在当前 `test_dev` 工程中执行。

~~~c
#include <rtthread.h>
#include <rtdevice.h>

#define I2C_BUS_NAME "i2c1"
#define I2C_DEV_ADDR 0x68

static int i2c_reg_write(rt_uint8_t reg, rt_uint8_t value)
{
    struct rt_i2c_bus_device *bus;
    struct rt_i2c_msg msg;
    rt_uint8_t data[2] = {reg, value};

    bus = rt_i2c_bus_device_find(I2C_BUS_NAME);
    if (bus == RT_NULL)
        return -RT_ERROR;

    msg.addr = I2C_DEV_ADDR;
    msg.flags = RT_I2C_WR;
    msg.len = sizeof(data);
    msg.buf = data;

    return (rt_i2c_transfer(bus, &msg, 1) == 1) ? RT_EOK : -RT_EIO;
}

static int i2c_reg_read(rt_uint8_t reg, rt_uint8_t *value)
{
    struct rt_i2c_bus_device *bus;
    struct rt_i2c_msg msgs[2];

    if (value == RT_NULL)
        return -RT_EINVAL;

    bus = rt_i2c_bus_device_find(I2C_BUS_NAME);
    if (bus == RT_NULL)
        return -RT_ERROR;

    msgs[0].addr = I2C_DEV_ADDR;
    msgs[0].flags = RT_I2C_WR;
    msgs[0].len = 1;
    msgs[0].buf = &reg;

    msgs[1].addr = I2C_DEV_ADDR;
    msgs[1].flags = RT_I2C_RD;
    msgs[1].len = 1;
    msgs[1].buf = value;

    return (rt_i2c_transfer(bus, msgs, 2) == 2) ? RT_EOK : -RT_EIO;
}
~~~

寄存器读的两个 message 表示“先写寄存器地址，再重复起始读取数据”。调试时检查返回值是否等于 message 数量；只返回 0 或负值时，优先检查总线注册、器件应答、7 位地址、SDA/SCL 接线、上拉和供电。

### 6. CubeMX 与 Studio 的验证顺序

1. CubeMX：保存 `.ioc`，确认 MCU、I2C 实例、SCL/SDA 复用、速度和时钟树。
2. 工程收集：在 Studio 工程树和 `subdir.mk` 中确认生成文件、HAL I2C、BSP 驱动和 I2C 核心已加入。
3. 编译链接：确认 0 errors、0 warnings，生成 ELF/BIN。
4. 设备注册：下载后执行 `list_device`，确认总线名和设备类型出现。
5. 软件读写：执行单字节写、寄存器读和多字节读，打印返回的 message 数和数据。
6. 电气波形：使用逻辑分析仪确认 START、7 位地址、R/W 位、ACK、数据和 STOP。
7. 器件功能：读取芯片 ID 或稳定寄存器，多次复位和重复读写后仍一致，才能记录为真实外设验证。

## 七、硬件 I2C 与软件 I2C 对比

| 项目 | 硬件 I2C | 软件 I2C |
| --- | --- | --- |
| 底层资源 | MCU I2C 外设、状态机和寄存器 | 普通 GPIO，通过 bit-bang 产生时序 |
| RT-Thread 对接 | BSP 实现 `master_xfer`，通常调用 HAL I2C | `rt_i2c_bit_add_bus` + `rt_i2c_bit_ops` + GPIO PIN API |
| 引脚灵活性 | 受芯片 Alternate Function 和外设实例限制 | 可选普通 GPIO，但必须开漏并有外部上拉 |
| CPU 占用 | 通常较低，可使用中断或 DMA | 每个时序位占用 CPU，延时期间不能做复杂工作 |
| 速度稳定性 | 速度较高，硬件处理 ACK、错误和超时 | 受软件延时、线程调度和 GPIO 实现影响 |
| 适用场景 | 量产、高速、多设备或 CPU 负载较高 | 旧 BSP 硬件 I2C 不完整、引脚无 AF、低速板载器件 |
| 常见问题 | 外设时钟未开、AF 错误、HAL 未收集、IRQ/DMA 不匹配 | 无上拉、推挽拉高、延时不准、线程抢占、总线被拉死 |

两者的上层设备驱动可以保持一致，应用都使用 `rt_i2c_bus_device_find()` 和 `rt_i2c_transfer()`；变化的是总线注册和 `master_xfer` 实现。若课程环境的硬件 I2C 支持包较旧，可以先用星火一号已有的软件 I2C 验证协议和器件，再移植硬件 I2C BSP。

## 八、I2C 排错清单

- `list_device` 没有 `i2cX`：检查 `RT_USING_I2C`、对应 `BSP_USING_I2CX`、I2C SConscript 和 BSP 初始化导出。
- 能找到总线但返回 0：检查器件地址、读写 flags、消息数量和 `master_xfer` 返回值。
- 一直 NACK：检查 7 位地址、供电、SDA/SCL 接线、上拉和器件复位状态。
- SCL 被拉低：检查器件是否卡在半帧，必要时用 9 个时钟尝试释放总线。
- SDA/SCL 没有波形：检查 GPIO 时钟、引脚复用、开漏配置、驱动是否编译和是否实际执行读写。
- 有波形但数据错误：降到 100 kHz，确认寄存器地址和读写时序，并逐字节检查 ACK。
