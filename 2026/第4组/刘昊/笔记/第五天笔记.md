## 1. 内容概览

第五天的内容围绕“采集、联网、传输、存储”四个环节展开：使用 AHT10 软件包采集温湿度，通过 RW007 接入网络，利用 MQTT 将数据发布到 Broker，并通过 DFS 将数据记录到外部 Flash 文件系统中。

整个功能链路可以概括为：

```text
AHT10 传感器
    ↓ I2C
传感器采集线程
    ↓ 邮箱传递数据或数据指针
MQTT 发送线程 ──→ RW007 ──→ EMQX Broker
    │
    └────────────→ DFS/POSIX ──→ FatFS ──→ FAL 分区 ──→ W25Qxx Flash
```

这一过程同时涉及 RT-Thread 的软件包生态、线程间通信、网络协议栈、设备驱动框架和文件系统分层。调试时应逐层验证，先确保底层设备可用，再接入上层业务，避免在多个模块同时异常时交叉排查。

## 2. RT-Thread 软件包机制

### 2.1 软件包的作用

RT-Thread 软件包通常封装已经实现的驱动、协议或通用功能。应用层通过配置软件包并调用其公开 API，可以减少重复编写寄存器操作、协议状态机和兼容代码的工作量。

软件包的主要价值包括：

- 复用已有驱动和协议实现，缩短功能验证周期；
- 通过 Kconfig 和 `menuconfig` 按需裁剪，控制 ROM、RAM 和线程资源占用；
- 将公共功能与具体工程分离，便于升级、维护和参与社区协作；
- 通常附带 README、头文件和示例，可作为 API 使用依据。

使用软件包并不等于无需理解底层。出现设备无法初始化、总线传输失败或资源占用异常时，仍需结合数据手册、BSP 配置、软件包源码和硬件连接进行定位。

### 2.2 软件包索引与获取过程

RT-Thread Studio 中的软件包列表由 ENV 下的软件包索引引入，索引内容通过 Kconfig 进入工程配置菜单。软件包仓库与内核仓库相对独立，软件包的下载地址、版本等信息由索引文件维护。

典型过程如下：

```text
打开 RT-Thread Settings/menuconfig
          ↓
选择软件包及版本、配置依赖项
          ↓
保存配置并更新软件包
          ↓
源码下载到工程 packages 目录
          ↓
重新生成工程、编译和下载
```

在 Studio 中保存配置通常会触发软件包更新；使用 ENV 时可执行 `pkgs --update`。软件包下载后，应继续检查其 README、头文件、示例和 Kconfig，不能只依据菜单名称推测调用方法。

![RT-Thread 软件包配置入口](../../RSOC/figures/image-20260821102810090.png)

### 2.3 依赖与版本兼容

软件包可能依赖内核组件或其他软件包。例如 AHT10 驱动依赖 I2C 总线，部分版本还需要 Sensor 框架；MQTT 软件包依赖网络接口和 Socket 能力；文件系统需要块设备、DFS 和具体文件系统实现共同生效。

培训资料中给出的 ENV 兼容关系是：较旧的 RT-Thread 4.x 工程使用 ENV 1.5.x，较新的 5.x 工程使用新版 ENV。实际工程不能只依据这一概括直接替换工具，应以当前 Studio、内核版本和软件包索引的兼容说明为准。版本不匹配时常见现象包括 Kconfig 解析失败、软件包列表缺失、接口声明不同或编译错误。

软件包接入时应记录以下版本信息：

| 项目 | 需要确认的内容 |
| --- | --- |
| RT-Thread 内核 | 主版本、次版本及工程分支 |
| BSP/芯片支持包 | 板卡型号、驱动是否完整 |
| ENV/Studio | 配置工具与软件包索引版本 |
| 软件包 | 选定版本、依赖项和配置选项 |

## 3. AHT10 温湿度采集

### 3.1 设备与总线关系

AHT10 是 I2C 温湿度传感器。应用访问它之前，需要先确认开发板上的 I2C 控制器或软件 I2C 总线已经注册，再将实际总线名称传给驱动。资料示例使用过 `i2c3`，但总线名不是固定值，应以原理图、BSP 配置和 `list_device` 输出为准。

使用软件包和直接操作 I2C 的层次关系如下：

```text
应用线程
  ↓
AHT10 软件包 API
  ↓
RT-Thread I2C 设备框架
  ↓
BSP I2C 驱动
  ↓
AHT10 硬件
```

软件包屏蔽了初始化命令、测量时序和原始数据换算等细节。直接使用 `rt_i2c_transfer()` 则需要自行构造读写消息、检查返回值，并根据数据手册完成初始化和数据换算。

### 3.2 软件包使用流程

基本接入步骤为：

1. 在板级配置中启用 AHT10 所在的 I2C 总线，并确认 SDA、SCL 引脚和上拉条件正确。
2. 在软件包菜单中启用 AHT10；若当前软件包版本依赖 Sensor 框架，应同时启用该组件。
3. 更新软件包并确认工程能够包含 `aht10.h`。
4. 调用 `aht10_init()`，传入实际 I2C 总线名并检查返回句柄。
5. 周期调用温度、湿度读取 API，并检查数值是否处于合理范围。
6. 将采集逻辑放在线程中，通过 MSH 命令或自动初始化方式启动。

核心 API 形式如下：

```c
aht10_device_t dev;
float temperature;
float humidity;

dev = aht10_init("i2c3");
if (dev == RT_NULL)
{
    /* 初始化失败，停止后续访问 */
}

humidity = aht10_read_humidity(dev);
temperature = aht10_read_temperature(dev);
```

总线名称只是示例值，不能直接复制到其他板卡。初始化失败后也不能继续解引用设备句柄。

### 3.3 浮点数输出

嵌入式工程为了减小固件体积，格式化输出可能默认不支持 `%f`。如果直接打印浮点数出现异常，可选择以下方案：

- 启用工程所用版本对应的完整格式化输出组件，例如 `rt_vsnprintf_full` 或相关配置；
- 不启用浮点格式化，将数值拆分为整数和一位小数输出；
- 在业务传输中使用定点数，例如将 `26.1 ℃` 表示为 `261`，由接收端按比例还原。

示例中的拆分方式为：

```c
rt_kprintf("Temp: %d.%d\n",
           (int)temperature,
           (int)(temperature * 10) % 10);
```

对负温度使用这种写法时应单独处理符号和小数部分，否则格式可能不正确。实际记录或上报前还应规定单位和精度，避免发送端与接收端解释不一致。

### 3.4 两种驱动方式的比较

| 对比项 | 使用 AHT10 软件包 | 直接使用 I2C API |
| --- | --- | --- |
| 开发工作量 | 较小，主要完成配置和 API 调用 | 较大，需要实现命令、时序和换算 |
| 可读性 | 业务代码更清晰 | 更容易观察底层通信过程 |
| 调试重点 | 软件包配置、总线名和接口版本 | 地址、消息结构、时序和返回值 |
| 适用场景 | 快速集成和常规应用 | 学习协议、特殊器件适配或驱动缺失 |

工程应用可以优先采用软件包，但应保留通过逻辑分析仪或底层 I2C 返回值定位问题的能力。

## 4. RW007 网络连接

### 4.1 配置要点

RW007 通过 SPI 与主控通信。软件包中的默认引脚不一定与当前开发板一致，必须依据原理图核对 CS、BOOT、INT、RESET 等信号，并按照 RT-Thread 的 PIN 编号规则填写配置。

![RW007 软件包与引脚配置](../../RSOC/figures/rw007-studio-package.png)

需要重点确认：

- RW007 使用的 SPI 总线已经启用并正确初始化；
- SPI 模式、频率和片选引脚符合模块要求；
- INT、RESET、BOOT 等引脚与原理图一致；
- WiFi 与外部 Flash 共用 SPI 控制器时，各设备片选信号保持互斥；
- 模块固件、软件包版本和主控驱动相互兼容。

### 4.2 联网验证顺序

网络层应在接入 MQTT 前单独验证。常用步骤为：

```text
wifi scan
wifi join <ssid> <password>
ifconfig
ping <domain-or-ip>
```

不同 RW007 软件包版本可能使用 `wifi join` 或其他连接命令，应以当前固件的 `help`/MSH 命令列表为准。`ping` 域名失败时，应区分 WiFi 未连接、DHCP 未获取地址、网关不可达和 DNS 解析失败，不能直接判定 MQTT 软件包异常。

## 5. MQTT 发布订阅通信

### 5.1 基本模型

MQTT 是轻量级发布/订阅协议。客户端不直接向另一个客户端发送数据，而是向 Broker 的某个主题发布消息；Broker 再把消息转发给订阅了匹配主题的客户端。

![MQTT 发布与订阅关系](../../RSOC/figures/mqtt-framework.png)

主要概念如下：

| 概念 | 作用 |
| --- | --- |
| Client | 连接 Broker，发布或订阅消息的设备/应用 |
| Broker | 维护连接、接收消息并按主题转发 |
| Topic | 消息的分层名称，区分不同设备和业务 |
| Publish | 向指定主题发送 Payload |
| Subscribe | 注册希望接收的主题或主题过滤器 |
| Keep Alive | 用于检测长连接是否仍然有效 |

发布者与订阅者只需要约定主题和数据格式，因此两者在时间、位置和实现上相对解耦，适合传感器数据上报和设备控制。

### 5.2 QoS 与主题设计

| QoS | 交付语义 | 特点与适用情况 |
| --- | --- | --- |
| 0 | 最多一次 | 开销最小，消息可能丢失，适合周期性环境数据 |
| 1 | 至少一次 | 消息可能重复，应用层需要考虑去重 |
| 2 | 恰好一次 | 交互和资源开销最大，适合少量且不能重复处理的数据 |

QoS 描述的是客户端与 Broker 之间的交付过程，不代表整个应用链路在任何情况下都绝对可靠。

公共 Broker 上应使用不易冲突的客户端 ID 和主题，例如：

```text
板卡发布：rsoc/<唯一标识>/device/up
板卡订阅：rsoc/<唯一标识>/device/down
```

客户端 ID 必须唯一，否则后连接的同名客户端可能使原连接断开。主题区分大小写，发布端和订阅端还必须保持方向一致。公共服务器上的数据可能被其他用户看到，因此不能发送密码、密钥和真实隐私数据。

### 5.3 kawaii-mqtt 配置与验证

培训实操使用 `kawaii-mqtt` 软件包连接 EMQX 公共 Broker。示例参数为：

| 配置项 | 示例值 |
| --- | --- |
| Host | `broker.emqx.io` |
| TCP Port | `1883` |
| MQTT 版本 | 3.1.1 |
| Client ID | 每块板卡使用唯一值 |
| Username/Password | 公共测试连接可留空，以服务当前要求为准 |
| 发布/订阅主题 | 使用带唯一标识的独立主题 |

![kawaii-mqtt 测试参数配置](../../RSOC/figures/kawaii-mqtt-test-config.png)

建议按以下顺序验证：

1. 确认 RW007 已获取 IP，并可以访问 Broker 地址。
2. 启动 MQTT 示例，观察 DNS、TCP 连接和 MQTT CONNACK 日志。
3. 使用 MQTTX 订阅板卡发布主题，验证板卡到电脑的上行消息。
4. 使用 MQTTX 向板卡订阅主题发布消息，验证下行回调。
5. 断开并恢复网络，检查客户端是否能够重新连接并恢复订阅。
6. 基础收发稳定后，再把固定字符串替换为 AHT10 数据。

推荐使用结构明确的 Payload：

```json
{"temperature":26.1,"humidity":45.2}
```

生成 Payload 时必须控制缓冲区长度，并检查格式化函数返回值。接收回调中的 Payload 不一定以 `\0` 结束，应使用回调提供的长度处理，不能直接把它假定为普通 C 字符串。

### 5.4 连接可靠性

MQTT 客户端长期运行时还应考虑：

- DNS 或 TCP 连接失败后的退避重试；
- 心跳超时与网络断开检测；
- 重连后重新订阅主题；
- 发布失败的返回值、日志和有限次数重试；
- 线程栈、收发缓冲区及动态内存是否足够；
- 网络恢复前避免无限堆积待发送数据。

公共 EMQX Broker 适合学习和联调，不适合作为生产系统的服务端。正式项目需要配置身份认证、TLS、主题权限和服务可用性策略。

## 6. DFS、FAL 与 SFUD

### 6.1 分层关系

DFS（Device File System）为应用提供统一的文件路径和 POSIX 风格接口；具体文件系统负责组织文件和目录；FAL 管理 Flash 设备及逻辑分区；SFUD 负责识别和访问具体的 SPI NOR Flash。

```text
应用程序
  ↓ open/read/write/close
DFS 与 POSIX 接口层
  ↓
elm-FatFS
  ↓
FAL 块设备与逻辑分区
  ↓
SFUD 通用 SPI Flash 驱动
  ↓
SPI 设备与 W25Qxx Flash
```

![DFS 文件系统层次](../../RSOC/figures/fs-layer.png)

![FAL 框架](../../RSOC/figures/fal_framework.png)

各层职责不能混淆：

| 层次 | 主要职责 |
| --- | --- |
| DFS | 管理挂载点、文件描述符和统一文件接口 |
| FatFS/elm | 维护 FAT 文件、目录及空间分配结构 |
| FAL | 将 Flash 划分为可独立使用的逻辑分区 |
| SFUD | 屏蔽不同 SPI NOR Flash 的识别、擦除和读写差异 |
| SPI 驱动 | 完成控制器、片选和物理数据传输 |

### 6.2 从 Flash 到挂载点

以外部 W25Qxx 为例，典型设备链路为：

```text
SPI 控制器
  → SPI 从设备
  → SFUD SPI_FLASH 设备
  → FAL 分区
  → 块设备
  → elm-FatFS
  → /flash 或 /fal 挂载点
```

会议材料对 Flash 具体型号和挂载点名称存在不同写法，因此实际工程应以原理图、SFUD 探测日志、FAL 分区表、`list_device` 和 `ls /` 的结果为准。W25Q64、W25Q128 的容量不同，分区表不能直接混用。

### 6.3 配置与验证

配置时通常需要启用：

1. SPI 控制器及对应 SPI Flash 设备；
2. SFUD 驱动；
3. FAL 及正确的 Flash 设备表、分区表；
4. DFS 组件和 elm-FatFS；
5. FAL 分区块设备及自动挂载功能，或自行编写挂载代码。

下载后先确认设备链路：

```text
list_device
fal probe
ls /
ls /flash
```

命令和挂载点需按工程实际情况调整。首次使用且文件系统尚未建立时，可以格式化对应块设备后再挂载。格式化会清除目标分区原有内容，执行前必须确认设备名和分区范围。

### 6.4 POSIX 文件操作

文件操作应遵循“打开、检查、读写、检查结果、关闭”的完整生命周期。追加记录传感器数据时可使用：

```c
int fd;
int length;
int written;
char line[96];

length = rt_snprintf(line, sizeof(line),
                     "temp=%d.%d,humi=%d.%d\n",
                     temp_int, temp_dec,
                     humi_int, humi_dec);

if (length <= 0 || length >= (int)sizeof(line))
{
    /* 格式化失败或数据被截断 */
    return;
}

fd = open("/flash/sensor.log", O_WRONLY | O_CREAT | O_APPEND, 0666);
if (fd < 0)
{
    /* 打开失败 */
    return;
}

written = write(fd, line, length);
close(fd);

if (written != length)
{
    /* 写入不完整 */
}
```

`O_APPEND` 用于在文件尾部增加记录，`O_TRUNC` 会在每次打开时清空原文件，不适合连续日志。所有成功打开的文件都必须在正常和异常路径中关闭，否则文件描述符可能耗尽。

### 6.5 Flash 存储的边界

Flash 擦除次数有限，文件系统写入还可能产生元数据更新和写放大。周期记录数据时应考虑：

- 根据实际需求选择记录周期，避免无意义的高频写入；
- 设置日志文件大小上限，采用轮转或定期导出机制；
- 对掉电一致性有要求时，评估同步策略和断电保护；
- 避免多个线程在没有同步措施时同时操作同一文件；
- 预留空间并监控 `write()` 失败，不能假定 Flash 永远可写。

## 7. 温湿度上报与本地存储方案

### 7.1 线程职责划分

作业要求由 AHT10 采集温湿度，通过邮箱传给 MQTT 线程，并同时记录到 Flash。适合采用职责相对独立的结构：

| 模块 | 职责 |
| --- | --- |
| 采集线程 | 周期读取 AHT10，生成带时间/序号的采样数据 |
| 邮箱 | 传递一个机器字大小的消息或数据对象指针 |
| MQTT 线程 | 维护连接，从邮箱取数据并发布 |
| 存储逻辑 | 将同一份采样数据追加写入日志文件 |

可采用以下数据结构表达一次采样：

```c
struct sensor_sample
{
    rt_int32_t temperature_x10;
    rt_int32_t humidity_x10;
    rt_uint32_t sequence;
};
```

使用定点数可以避免在线程间传递浮点格式差异，`temperature_x10 = 261` 表示 `26.1 ℃`。

### 7.2 邮箱传递的约束

RT-Thread 邮箱的单条消息大小为一个 `rt_ubase_t`，适合传递整数、状态值或对象指针，不能直接复制任意长度的结构体。32 位 MCU 上可通过邮箱传递 `struct sensor_sample *`，但必须保证：

- 不能发送指向采集线程栈变量的指针，因为函数继续执行或下一次循环后内容可能被覆盖；
- 数据对象在 MQTT 线程处理完成前必须一直有效；
- 动态分配对象时要明确由哪个线程释放，避免内存泄漏或重复释放；
- 固定周期任务可使用内存池或预分配缓冲区，降低堆碎片风险；
- 邮箱已满时要明确选择阻塞、丢弃旧数据还是覆盖策略。

如果需要直接复制完整结构体，消息队列通常比邮箱更合适；但在作业明确要求使用邮箱时，可以采用“邮箱传指针 + 内存池管理生命周期”的方式。

### 7.3 数据流与异常策略

推荐的数据处理过程为：

```text
采集 AHT10
   ↓ 检查设备和数值
生成 sample（定点数 + 序号）
   ├─→ 追加写入本地日志
   └─→ 邮箱发送 sample 指针
             ↓
        MQTT 线程取出
             ↓
        组装 JSON 并发布
             ↓
        归还内存池对象
```

网络故障不应阻塞传感器采集和本地记录。MQTT 断线时，可以丢弃非关键的周期数据、只保留最新值，或在容量受控的队列中暂存；不能无限分配内存等待网络恢复。Flash 写入失败也应记录错误并继续执行可用功能，避免一个存储故障使整个采集线程退出。

采样周期可设置为 2～5 秒。使用 `rt_thread_mdelay()` 能满足一般实验要求；对严格周期任务，可使用定时器或基于系统节拍计算下一次唤醒时间，减少循环执行时间带来的累计漂移。

## 8. 配置和调试顺序

将所有功能一次性打开会增加定位难度。建议按依赖关系逐层验证：

1. **基础工程：** 工程能够稳定启动，MSH 和日志输出正常。
2. **I2C 总线：** `list_device` 中能找到目标总线，AHT10 初始化成功。
3. **传感器：** 温湿度能够周期变化，输出格式和单位正确。
4. **RW007：** 能扫描热点、获取 IP，并分别验证网关、IP 和域名连通性。
5. **MQTT：** 先发送固定消息，再验证双向主题收发和断线重连。
6. **Flash/SFUD：** 能识别正确的 Flash 型号和容量。
7. **FAL/DFS：** 分区、块设备、格式化和挂载依次成功。
8. **文件读写：** 固定字符串可以写入、重启后读取和追加。
9. **线程间通信：** 单独验证邮箱满、超时和数据对象生命周期。
10. **业务集成：** 最后接入 AHT10 实际数据，同时验证 MQTT 与文件内容。

每一层都应保留明确的成功标准。例如“MQTT 可用”不能只依据 TCP 已连接，而应同时验证发布、订阅和重连；“文件系统可用”不能只依据挂载成功，还应验证写入、读取、追加和重启后数据保持。

## 9. 常见问题与注意事项

| 现象 | 可能原因 | 建议检查 |
| --- | --- | --- |
| 软件包菜单中找不到目标包 | ENV/索引版本不匹配或索引未更新 | 检查内核与 ENV 版本，更新软件包索引 |
| 编译时出现 AHT10 未定义符号 | 依赖组件未开启或软件包未加入构建 | 检查 Kconfig、Sensor/I2C 依赖及 packages 目录 |
| 找不到 I2C 总线 | 总线未启用、未注册或名称错误 | 查看 `list_device`，核对 BSP 与原理图 |
| 温湿度始终异常 | 设备地址、供电、上拉、初始化或转换等待错误 | 检查返回值并抓取 I2C 波形 |
| `%f` 无法正常显示 | 完整格式化支持未启用 | 启用对应组件或改用定点输出 |
| RW007 无法联网 | SPI/引脚配置错误、固件不匹配或 DHCP 失败 | 先验证模块初始化，再分层检查网络 |
| MQTT 连接后很快断开 | Client ID 冲突、保活失败或网络不稳定 | 使用唯一 ID，检查心跳与重连日志 |
| MQTTX 收不到消息 | 主题方向、大小写或斜杠不一致 | 对照发布主题与订阅主题逐字符检查 |
| 找不到外部 Flash | SPI 模式、片选、设备名或 SFUD 配置错误 | 查看探测日志，核对 JEDEC ID 和原理图 |
| WiFi 与 Flash 互相干扰 | 共用 SPI 时非目标设备 CS 未保持无效 | 初始化引脚并确保同一时刻只选中一个设备 |
| 文件系统挂载失败 | 分区未格式化、类型或设备名不匹配 | 核对 FAL 分区与块设备，必要时首次格式化 |
| 文件每次只剩最后一条 | 使用了 `O_TRUNC` | 改为 `O_APPEND` 并检查写入位置 |
| 日志运行一段时间后失败 | 空间不足、描述符泄漏或 Flash 磨损 | 限制文件大小，检查 `close()` 和返回值 |
| 邮箱数据偶尔错乱 | 发送了栈地址或缓冲区被提前复用 | 使用内存池并明确对象所有权 |

按键中断等异步输入的处理原则同样适用于本次工程：中断回调应尽量短，只记录状态或通知线程，不在中断上下文中执行网络发送、文件写入、长延时或普通阻塞日志。

## 10. 要点总结

1. RT-Thread 软件包通过 ENV/Kconfig 索引进入工程，实际接入时必须同时确认软件包版本、依赖组件和 BSP 能力。
2. AHT10 软件包简化了 I2C 命令和数据换算，但总线注册、硬件连接、返回值检查仍由工程负责。
3. MQTT 采用发布/订阅模型。联调前应先验证网络，使用唯一 Client ID 和主题，并处理断线重连、消息长度和缓冲区边界。
4. DFS、FatFS、FAL、SFUD 和 SPI Flash 分别承担不同层次的职责。应用通过 POSIX 接口访问文件，不等于底层 Flash 配置可以忽略。
5. RW007 与外部 Flash 共用 SPI 控制器时，必须正确管理各自片选，任何时刻只能选中目标设备。
6. 邮箱只能传递一个机器字。传递采样结构体时应发送稳定对象的指针，并通过内存池或明确的所有权规则保证生命周期。
7. 采集、网络和存储应尽量解耦。网络或文件系统暂时故障时，其他模块仍应能够按既定策略继续运行。
8. 完整调试应遵循“配置生效 → 设备注册 → 单模块验证 → 通信链路验证 → 业务集成”的顺序，并对每层设置可观察的成功标准。
