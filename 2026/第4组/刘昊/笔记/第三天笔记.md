## 1. IPC 概述

IPC（Inter-Process Communication）在 RT-Thread 中主要用于解决多线程之间的协作问题。本次课程将 IPC 分为两类：

- **线程同步**：使多个线程按照预期的条件或顺序执行，主要包括信号量、互斥量和事件集。
- **线程通信**：在线程之间传递数据，主要包括消息邮箱和消息队列。

同步解决的是“何时执行”和“谁可以访问”，通信解决的是“线程之间传递什么”。

## 2. 基础概念

### 2.1 临界区与竞态条件

**临界区**是访问共享资源的代码区域。当多个线程可能同时修改同一资源时，如果缺少互斥保护，执行结果将取决于不可预测的调度时序，这种问题称为**竞态条件**。

临界区应尽可能短，其内应避免长时间延时或阻塞操作，以减少其他线程的等待时间。

### 2.2 阻塞、非阻塞与挂起

- **阻塞调用**：资源或条件未满足时，线程暂时无法继续执行。
- **非阻塞调用**：资源不可用时立即返回，线程可处理其他任务。
- **挂起状态**：线程在等待 IPC 对象或延时期间不参与 CPU 调度；条件满足后回到就绪态，等待调度器选中。

阻塞是调用的行为特征，挂起是线程在等待期间的状态，二者不是同一概念。

### 2.3 超时参数

IPC 获取或接收接口通常需要指定等待时间：

- `RT_WAITING_FOREVER`：一直等待，直到条件满足。
- `RT_WAITING_NO`：不等待，无法立即获取时直接返回。
- 正整数：最多等待指定的系统节拍数。

工程中应根据时延上限选择超时值，并对超时、资源已满等返回状态进行处理。

## 3. 信号量

### 3.1 原理与用途

信号量是一个可由线程或中断释放、由线程获取的计数型内核对象。获取成功时计数值减 1，释放时计数值加 1并可能唤醒等待线程。

| 形式 | 典型初值 | 主要用途 |
|---|---:|---|
| 二值信号量 | 0 或 1 | 任务与任务、中断与任务之间的单次事件通知 |
| 计数信号量 | 资源数量 N | 管理同类共享资源的多个实例 |

二值信号量初值为 0 时，表示事件尚未发生；等待线程挂起，另一线程或中断在同步点释放信号量后，等待线程被唤醒。计数信号量的初值 N 表示可用资源数，当计数值为 0 时，后续申请者需要等待资源被释放。

### 3.2 常用 API

| API | 作用 |
|---|---|
| `rt_sem_create()` | 动态创建信号量 |
| `rt_sem_init()` | 静态初始化信号量 |
| `rt_sem_take()` | 获取信号量（P 操作） |
| `rt_sem_release()` | 释放信号量（V 操作） |

创建时的 `flag` 决定有多个等待者时的唤醒顺序：

- `RT_IPC_FLAG_PRIO`：按线程优先级等待，更适合对实时性有要求的场景。
- `RT_IPC_FLAG_FIFO`：按进入等待队列的先后顺序唤醒。

### 3.3 使用要点

- 信号量没有所有权，释放者不一定是获取者，因此适合事件通知和资源计数。
- 中断服务程序可释放信号量通知线程，但不能在中断中执行可能阻塞的获取操作。
- 若需要保护共享临界区，应优先使用具有所有权和优先级继承能力的互斥量。

## 4. 互斥量

### 4.1 核心特性

互斥量专门用于保护临界区，保证同一时刻只有一个线程访问共享资源。它具有以下特性：

- **所有权**：只有持有互斥量的线程才能释放它。
- **递归获取**：同一线程可多次获取同一互斥量，但获取和释放次数必须配对。
- **优先级继承**：用于缓解优先级反转问题。

互斥量只适用于线程上下文，不应在中断服务程序中获取或释放。

### 4.2 优先级反转

假设线程优先级为 A > B > C：

1. 低优先级线程 C 先获取互斥量并进入临界区。
2. 高优先级线程 A 抢占 C，但因无法获取互斥量而挂起。
3. 中优先级线程 B 就绪后抢占 C，导致 C 迟迟无法执行并释放互斥量。
4. 结果是高优先级线程 A 间接地被 B 阻塞，出现优先级反转。

**优先级继承的处理方式**：当 A 等待 C 持有的互斥量时，系统临时将 C 的优先级提升至 A 的优先级，使 C 尽快完成临界区并释放互斥量。释放后，C 恢复原优先级，A 获取互斥量继续执行。

### 4.3 常用 API

| API | 作用 |
|---|---|
| `rt_mutex_create()` | 动态创建互斥量 |
| `rt_mutex_init()` | 静态初始化互斥量 |
| `rt_mutex_take()` | 获取互斥量 |
| `rt_mutex_release()` | 释放互斥量 |

使用时要保证每条退出路径都能释放互斥量，否则容易造成死锁。

## 5. 事件集

### 5.1 原理与特点

事件集使用 32 位无符号整数表示事件标志，每一位对应一类事件，适合一对多或多对多的条件同步。

- `RT_EVENT_FLAG_OR`：监听的任意一个事件发生即满足条件。
- `RT_EVENT_FLAG_AND`：监听的所有事件都发生才满足条件。
- `RT_EVENT_FLAG_CLEAR`：接收成功后自动清除本次满足条件的事件标志。

事件集只表示“某类事件是否已发生”，**不携带具体数据，也不记录同一事件连续发生的次数**。同一标志位在未被清除前多次发送，仍只表现为该位置 1。

### 5.2 常用 API

| API | 作用 |
|---|---|
| `rt_event_create()` / `rt_event_init()` | 创建或初始化事件集 |
| `rt_event_send()` | 发送事件标志 |
| `rt_event_recv()` | 按 AND/OR 条件接收事件 |

如果业务既需要事件通知又需要传递参数，应结合消息队列，或直接使用消息队列对事件和数据进行封装。

## 6. 消息邮箱

### 6.1 原理与特点

消息邮箱以 `rt_ubase_t` 为一封邮件的存储单元。在本次使用的 32 位平台上，每封邮件为 4 字节，适合传递整型值或指针，具有开销小、效率高的特点。

邮箱中传递指针时，必须确保指针指向的数据在接收者处理完成前一直有效，并明确该内存由谁管理和释放。不能将即将失效的局部变量地址作为邮件发送。

### 6.2 常用 API

| API | 作用 |
|---|---|
| `rt_mb_create()` / `rt_mb_init()` | 创建或初始化邮箱 |
| `rt_mb_send()` | 发送邮件 |
| `rt_mb_recv()` | 接收邮件，可指定超时时间 |
| `rt_mb_urgent()` | 将紧急邮件放到待接收邮件的前端 |

`rt_mb_send()` 不会因等待空闲邮箱位置而挂起；邮箱已满时应检查错误返回值。因其发送路径不阻塞，可用于中断向线程发送简短通知。

## 7. 消息队列

### 7.1 原理与特点

消息队列用于在线程之间传递一段数据，比邮箱更适合传递结构体、数据帧等复合消息。消息队列在创建时需指定单条消息的最大长度 `msg_size` 和队列容量，内核使用消息块管理待接收数据。

与邮箱相比，队列不只能传递一个机器字，但它并非无上限地接收任意长度数据；发送长度不应超过创建时设定的 `msg_size`。

### 7.2 常用 API

| API | 作用 |
|---|---|
| `rt_mq_create()` / `rt_mq_init()` | 创建或初始化消息队列 |
| `rt_mq_send()` | 将普通消息放入队尾 |
| `rt_mq_urgent()` | 将紧急消息放入队首 |
| `rt_mq_recv()` | 从队首接收消息，可指定超时时间 |

普通消息按先进先出顺序处理，`rt_mq_urgent()` 可将紧急消息插入队首，使其先于已排队的普通消息被接收。该能力应谨慎使用：持续插入紧急消息可能使普通消息长时间得不到处理。

发送和接收时都应检查返回值。使用基础发送接口时，队列已满并不意味着可以无限等待，应根据所用 RT-Thread 版本和接口语义处理队列满的情况。

## 8. IPC 选型与对比

| 机制 | 是否传递数据 | 核心用途 | 关键特性 | 典型场景 |
|---|---|---|---|---|
| 信号量 | 否 | 单事件同步、资源计数 | 无所有权，可由中断释放 | 按键中断通知处理线程 |
| 互斥量 | 否 | 保护临界区 | 有所有权、递归获取、优先级继承 | 多线程访问同一设备或共享数据 |
| 事件集 | 否 | 多条件组合同步 | 32 位标志，支持 AND/OR | 等待多个模块就绪 |
| 消息邮箱 | 是 | 传递一个机器字 | 开销小，适合整型或指针 | 传感器采样值或缓冲区指针通知 |
| 消息队列 | 是 | 传递数据块 | 支持结构化消息和紧急插队 | 串口数据帧、命令和状态消息 |

可按以下思路选型：

1. 只需要一次事件通知，优先考虑二值信号量。
2. 需要统计可用资源数量，使用计数信号量。
3. 需要保护共享资源，使用互斥量。
4. 需要等待多个条件的 AND/OR 组合，使用事件集。
5. 只需要传递整型或指针，优先考虑消息邮箱。
6. 需要传递结构化数据或数据帧，使用消息队列。

## 9. 实验现象与结论

### 9.1 信号量实验

线程 1 每计数 10 次释放一次信号量，线程 2 以永久等待方式获取信号量，成功后对 `number` 自增。最终 `number` 为 10，说明信号量能够将生产者的同步信号可靠地传递给等待线程。

### 9.2 互斥量实验

两个线程分别修改 `number1` 和 `number2`：

- 使用互斥量保护时，两个变量始终保持一致。
- 去掉互斥保护后，线程 1 在两次修改之间因 `rt_thread_mdelay()` 挂起，线程 2 插入执行，导致数据不一致。

该实验说明：单条 C 语句看似简单，但一组业务操作并非必然具有原子性。正确的临界区边界应覆盖整个需要保持一致性的操作序列。

### 9.3 事件集实验

线程 1 先以 OR 模式等待事件 3 或事件 5，线程 2 发送事件 3 后线程 1 立即被唤醒。之后改为 AND 模式，仅发送事件 3 不会唤醒，待事件 5 也到达后才满足条件。实验验证了 OR 与 AND 的条件判定差异。

### 9.4 消息邮箱实验

发送线程交替发送 `"string1"` 和 `"string2"` 的指针，最后发送 `"over"`；接收线程永久等待邮件，收到 `"over"` 后退出。实验说明，邮箱传递的是指针数值，而不是将整个字符串拷贝到邮箱中。

### 9.5 消息队列实验

普通消息按 `a` 至 `h` 的顺序入队，之后使用 `rt_mq_urgent()` 发送 `i`。接收顺序为 `a` 、`i` 、`b` 至 `h`。`a` 在紧急消息发送前已经被取出，`i` 则被插入剩余待处理消息的队首，因此第二个被接收。

## 10. 易错点与学习收获

### 10.1 易错点

- 信号量适合“通知/计数”，互斥量适合“保护”，二者不应只因计数值都可以是 1 就混用。
- 事件集不能记录事件发生次数，需要逐条保留的事件应放入队列。
- 邮箱在 32 位平台上传递 4 字节数值；传递大数据时实际传的是指针，需要特别注意对象生命周期。
- 消息队列的单条消息长度受 `msg_size` 限制，应在容量、内存占用和峰值消息量之间做设计。
- 不能忽略 IPC API 的返回值；超时、队列满、对象不可用都应有明确的处理策略。
- 中断中不能执行可能导致挂起的操作，实际开发时应确认当前 RT-Thread 版本对具体 API 的中断上下文约束。

### 10.2 学习收获

本次学习的重点不是记忆 API 名称，而是先分析线程间关系：是需要等待条件、保护共享资源，还是传递数据；再根据是否需要计数、组合事件、所有权或数据缓冲能力选择 IPC 对象。

代码实现时还需同时考虑临界区范围、超时策略、返回值、中断上下文限制及数据生命周期。只有把 IPC 机制的语义与实际调度过程联系起来，才能避免竞态、死锁、数据丢失和不确定延时等问题。
