## 一、设备驱动框架：分层架构与设计思想

### 1. 为什么需要设备驱动框架

#### 1.1 不同厂家 API 不一致导致代码复用率低

嵌入式开发中，SPI / I2C 等总线的**协议标准是统一的**（如 W25Q128 Flash 芯片的 SPI 时序各厂商一致），但**不同 MCU 厂商提供的操作接口（API）各不相同**。由此带来两个现实问题：

- **重复开发**：A 同事用 STM32 写了 W25Q128 的 Flash 驱动并挂上文件系统；B 同事换了另一颗芯片，SPI 驱动必须重新写一遍——尽管 W25Q128 的驱动逻辑完全相同。
- **重复学习**：换厂家就要重新学习一套新的 API 设计，学习成本高、碎片化开发多、反复"造轮子"。

> 类比：SPI 总线好比"普通话"（标准统一），而各厂商的 API 好比"方言"（实现各异）。上层业务只想说普通话，而不想每种方言都学一遍。

#### 1.2 解决思路：把设备抽象出一层

核心思想是**在应用与具体硬件驱动之间插入一层抽象**：

```
┌─────────────────────────────────────────────┐
│  上层应用（业务代码，与具体 MCU 无关）          │
├─────────────────────────────────────────────┤
│  设备驱动框架层（统一 API：open/write/read/close）│
├─────────────────────────────────────────────┤
│  具体厂商底层驱动（STM32 / 其他厂家 各自实现）    │
├─────────────────────────────────────────────┤
│             硬件外设（SPI/I2C/GPIO/串口…）      │
└─────────────────────────────────────────────┘
```

上层应用统一通过 RT-Thread 提供的 API 调用设备，底层由各家驱动负责对接具体硬件。RT-Thread 对大部分常见外设的驱动都已适配完成，因此应用代码可以在不同 MCU 之间无缝迁移。

#### 1.3 分层的优劣势对比

| 维度 | 优势 | 劣势 |
|---|---|---|
| 驱动与应用 | 驱动与设备分离，更换硬件只改底层驱动 | 框架代码更复杂 |
| 代码复用 | 应用可跨 MCU 快速迁移，无需重写 | Flash 占用相对更大 |
| 学习成本 | 应用工程师只接触一套 API，学习成本低 | — |
| 开发效率 | 减少碎片化开发，避免反复造轮子 | — |

> 结论：尽管框架更复杂、占用稍多 Flash，但相比四项优势，这一点代价完全可以接受。

### 2. 设备驱动框架的演进与分层架构

#### 2.1 演进路线

RT-Thread 设备框架经历了从"外设各自为政"到"统一 IO 层"的演进：

1. **早期**：SPI 一套 API、I2C 一套 API，各自独立。
2. **中期**：演进为统一的 **IO 设备层**，通过 `open / write / read / close` 等通用函数接口操作硬件。
3. **现在**：保留统一 IO 层的同时，**并行保留特定接口层**（如 SPI 设备框架的读写/传输函数、I2C 设备框架等）——两类层**并行共存**，特定设备框架既可通过专用接口调用，也可经由统一 IO 层访问。

```
            ┌────────────────────────────────┐
            │       统一 IO 设备层            │
            │   open / write / read / close  │
            └───────────────┬────────────────┘
                            │（并行）
            ┌───────────────┴────────────────┐
            │  SPI 设备框架 / I2C 设备框架 …    │
            │  特定读写与传输函数               │
            └───────────────┬────────────────┘
                            │
            ┌───────────────┴────────────────┐
            │  BSP 底层驱动（对接具体芯片）      │
            └────────────────────────────────┘
```

#### 2.2 驱动开发的两类角色

- **BSP（板级支持包）工程师**：负责把底层驱动对接到 RT-Thread 的统一 IO 层以及 SPI / I2C 等设备驱动框架层。
- **RT-Thread 应用开发工程师**：只通过统一 IO 接口读写设备，无需关心底层实现。

### 3. rt_device 核心结构与设备分类

#### 3.1 面向对象：一切皆继承

RT-Thread 采用**面向对象**的编程思路，整个框架都建立在"继承"之上：所有设备驱动框架层都继承自 `rt_device`（设备基类）。下层设备驱动层再对接到设备驱动框架层的具体 API（ops），完成逐层对接。

#### 3.2 rt_device 结构体关键字段

| 字段 | 作用 |
|---|---|
| 继承的内核对象基类 | 设备也是内核对象，纳入对象管理 |
| 设备类型（`type`） | 区分字符/块/网络/SPI/I2C 等类型，有对应枚举 |
| 设备参数 | 记录设备特有信息，如波特率、读写模式等 |
| 打开标志（`open_flag`） | 记录设备是否被打开、以何种模式打开；不同线程打开时**打开次数累加** |
| 接收回调（`rx_indicate`） | 数据可读时通知上层 |
| 发送完成回调（`tx_complete`） | 数据发送完成时通知上层 |
| 设备操作方法集（`ops`） | 驱动对接的关键：封装 init/open/close/read/write/control 等函数指针 |

#### 3.3 设备分类

RT-Thread 派生出的设备类型很多，常见的有：串口、Pin、SPI、I2C、块设备、网络设备、显示设备、音频设备、RTC、图形设备、USB（host/device）、SDIO、杂类设备等。

**字符设备与块设备的区别**（本次重点讲解）：

| 对比项 | 字符设备 | 块设备 |
|---|---|---|
| 数据访问 | 提供**连续数据流**，只能**顺序读取** | 支持**随机访问**，可自行指定读取位置 |
| 读写单位 | 以字节/字符为单位 | 以**块**为单位（如 512 字节，取决于具体设备） |
| 寻址能力 | 不支持随机寻址 | 通过寻址在任意位置读取 |
| 典型设备 | 键盘、串口、调制解调器 | 硬盘、软盘、ROM 驱动器、Flash、SD 卡 |

> 判断本质：**是否可以被随机访问**。串口只能一个字节一个字节顺序接收，而 RAM/Flash 可以跳到任意地址去读写。

#### 3.4 为什么要对设备分类

- **重定向支持**：设备分类后，可以通过 NSH（`msh`）终端把输出**重定向到任意字符设备**。例如把 LCD 模拟成字符设备，即可把 log 打印到 LCD 上；也可以实现一个空字符设备接收重定向。
- **文件系统依赖块设备**：Flash 文件系统依赖块设备来存储数据。将 SD 卡的读写实现成块设备，或用 RAM 模拟块设备，文件系统即可统一管理 SD 卡与 RAM。
- **统一控制**：不同组件/应用依赖不同设备，对设备分类后可将它们抽象成同一套东西，对外提供统一的 API 接口，对内实现由驱动负责，应用层不关心。

> 常见设备归类示例：串口→字符设备；网卡→以太网设备；音频→音频设备；GPIO→Pin 设备；LCD→显示设备；录音→音频设备。相关类型枚举可查阅 RT-Thread 头文件。

### 4. 设备驱动分层对接模型（ops）

#### 4.1 为什么是 ops

上层应用通过 `open / read / write / close` 调用设备，**具体怎么调用到底层，都是通过 `ops`（操作集）实现**：设备驱动层为每个设备实现对应的 `ops`（init/open/close/read/write/control 函数指针），上层应用通过 ops **间接调用**底层驱动。

```
上层应用 ──open/read/write──▶ rt_device 框架 ──ops──▶ 底层设备驱动 ──▶ 硬件
```

#### 4.2 调试技巧

源码难以读懂时，**用调试器单步跟踪**：从上层 API 跳入框架函数，看它如何通过 ops 调到我们自己实现的函数，即可验证对接是否正确（本次课程即用此方法验证了 init/control 的对接）。**理解驱动框架对接，只需重点关注 ops 的具体实现。**

### 5. 官方手册补充：设备对象继承与面向对象设计

#### 5.1 设备对象继承关系：rt_device 也是内核对象

结合官方《I/O 设备模型》手册：RT-Thread 的设备模型建立在内核对象模型之上，**设备是一类对象，被纳入对象管理器范畴**。每个设备对象都由基对象派生而来。`struct rt_device` 的关键字段如下：

```c
struct rt_device
{
    struct rt_object          parent;      // 继承的内核对象基类 → 纳入对象管理器
    enum rt_device_class_type type;        // 设备类型（字符/块/SPI/I2C...）
    rt_uint16_t               flag;        // 设备标志（含 ACTIVATED 等）
    rt_uint16_t               open_flag;   // 打开标志
    rt_uint8_t                ref_count;   // 打开引用计数
    rt_err_t (*rx_indicate)(rt_device_t dev, rt_size_t size);   // 接收回调
    rt_err_t (*tx_complete)(rt_device_t dev, void *buffer);     // 发送完成回调
    const struct rt_device_ops *ops;       // 操作方法集
    void *user_data;                       // 用户数据
    ...
};
```

要点：
- 结构体第一个成员就是 `parent`（rt_object），这是 C 语言中"继承"的落地方式：**把父类对象放在结构体首部，即可通过指针强转实现父子类型转换**。
- 正因为设备本身是内核对象，才能被对象管理器统一管理、被 `rt_device_find()` 按名称查找。

#### 5.2 新增 BSP 驱动只需写驱动层

官方手册明确：**新增 BSP 设备驱动到 I/O 设备模型框架时，开发者只需开发驱动层**；设备驱动框架层和 I/O 设备管理层 RT-Thread 已写好，无需改动（除非发现 BUG 或新增设备类别）。

#### 5.3 横向分层 / 纵向派生：面向对象抽象贯穿

官方手册对 I/O 设备模型框架补充图做了系统解读：

- **横向看是分层思想**：驱动层 → 驱动框架层 → I/O 管理层，从下到上不断抽象、屏蔽下层差异。
- **纵向看是各类派生继承关系**：子类受父类接口约束、各自实现父类提供的统一接口，体现**面向接口编程**。
- **多对一对接**：以串口为例，不管下层是 STM32、GD32 还是其他平台，只要是串口设备，都对接到 RT-Thread 的串口设备类——多个硬件对象对接同一个父类接口，体现面向对象抽象的威力。
- **框架层公共类已备好**：设备驱动框架层的各类在源码 `components/drivers` 目录下（serial / i2c / spi / sensor / can 等）；驱动层的各 BSP 实现则在 `bsp/` 目录下（如 STM32 的 `drv_uart.c`，实际路径在 `libraries/HAL_Drivers` 下，各版本可能不同）。

## 二、IO 设备管理：API 与设备生命周期

### 1. 设备生命周期总览

一个设备从创建到销毁的完整流程：

```tex
创建(create) → 注册(register) → 查找(find) → 打开(open) → 读写/控制(read/write/control) → 关闭(close) → 注销(unregister) → 销毁(destroy)
```

- 设备驱动层先 `rt_device_create` 创建设备并 `rt_device_register` 注册进 IO 设备管理器（挂入链表）。
- 上层应用 `rt_device_find` 按名称查找设备，`rt_device_open` 打开后即可 `read / write / control`。
- IO 管理层调用 `read` 时会进一步调用底层设备驱动，最后 `rt_device_close` 关闭设备。

### 2. 创建与注册 API

#### 2.1 创建 / 销毁

| API | 参数说明 | 返回值 |
|---|---|---|
| `rt_device_t rt_device_create(int type, int attach_size)` | `type`：设备类型（取自设备类型枚举）；`attach_size`：用户数据大小 | 设备句柄 `rt_device_t`；失败返回 `RT_NULL` |
| `rt_err_t rt_device_destroy(rt_device_t dev)` | `dev`：设备句柄 | `RT_EOK` 成功，负值失败 |

> 说明：RT-Thread 中名称带 `_t` 后缀的类型通常是**指针（句柄）**（通过 `typedef` 重定义）。如 `rt_device_t` 本质是指针，返回 `RT_NULL` 代表创建失败。

#### 2.2 注册 / 注销

| API | 参数说明 | 返回值 |
|---|---|---|
| `rt_err_t rt_device_register(rt_device_t dev, const char *name, rt_uint16_t flags)` | `dev`：创建的设备句柄；`name`：设备名称（长度受宏 `RT_NAME_MAX` 限制，主仓实现会在名称后补 `\0`）；`flags`：设备打开模式 | 成功返回 `RT_EOK`（值为 0）；失败返回**负值** |
| `rt_err_t rt_device_unregister(rt_device_t dev)` | `dev`：设备句柄 | `RT_EOK` 成功 |

注册的本质：把设备结构体**塞入 IO 管理层的链表中**进行统一管理；注册成功后即可通过 `list device` 命令在 `msh` 终端查看。

#### 2.3 设备打开模式（flags）

| 模式 | 说明 |
|---|---|
| `RT_DEVICE_FLAG_RDONLY` / `RT_DEVICE_FLAG_WRONLY` | 只读 / 只写方式打开 |
| `RT_DEVICE_FLAG_RDWR` | 读写方式打开 |
| `RT_DEVICE_FLAG_STREAM` | 流模式（阻塞方式）打开 |
| `RT_DEVICE_FLAG_INT_RX` / `RT_DEVICE_FLAG_DMA_RX` | 中断接收 / DMA 接收 |
| `RT_DEVICE_FLAG_INT_TX` / `RT_DEVICE_FLAG_DMA_TX` | 中断发送 / DMA 发送 |

> 例：串口可以用中断模式接收、DMA 模式接收，发送同理。**若上层应用需要使用接收回调，必须以中断或 DMA 模式打开设备**；流模式是阻塞方式，无需回调。

### 3. 查找 / 初始化 / 打开 / 关闭 API

| API | 参数说明 | 返回值 / 行为 |
|---|---|---|
| `rt_device_t rt_device_find(const char *name)` | `name`：设备名称 | 返回设备句柄；无对应设备返回 `RT_NULL` |
| `rt_err_t rt_device_init(rt_device_t dev)` | `dev`：设备句柄 | `RT_EOK` 初始化成功；负值为具体错误码 |
| `rt_err_t rt_device_open(rt_device_t dev, rt_uint16_t oflag)` | `dev`：句柄；`oflag`：打开模式 | 成功返回 `RT_EOK`；不允许重复打开时可能返回总线忙等错误码 |
| `rt_err_t rt_device_close(rt_device_t dev)` | `dev`：句柄 | 关闭成功返回 `RT_EOK`，否则返回对应错误 |

> 所有 API 均返回 `rt_err_t` 错误码，具体含义在 RT-Thread 头文件中有定义：**正数或 0 表示成功，负数为各类错误码**。
>
> **引用计数**：设备被不同线程打开时，打开次数会累加；`close` 逐次递减，直到引用计数归零才真正关闭设备。实验中终端使用的串口设备会显示打开次数为 2（终端本身占用一次）。
>
> **补充（实验验证 · 4.x 引用计数不对称语义）**：通过 Day4 作业 `test_dev` 虚拟设备实测发现，4.x 中 `open` / `close` 的引用计数是**不对称**的：
>
> - `rt_device_open`：**每次调用都会进入驱动 `open`**，同时系统引用计数 `ref_count++`；
> - `rt_device_close`：每次调用把 `ref_count--`，但**只有当 `ref_count` 归零那一次，才会真正调用驱动 `close`**。
>
> 因此驱动私有计数与系统 `ref_count` 并不严格配对：例如 open 两次再 close 两次，驱动 `open` 被调用 2 次、驱动 `close` 只被调用 1 次（归零那一次），驱动内部计数最终停在 1 而不是 0。**要想看到"计数归零 → 驱动 `close` → 真正关闭"的闭环，必须单开单关**；多次 open/close 的计数演示需单独观察。这正是作业里 `test_dev_app`（单开单关）与 `test_dev_ref`（open×3 / close×3）两条 msh 命令分别演示的内容。
>
> **open 时的自动初始化**：若设备尚未初始化（无初始化标志），`open` 内部会先自动调用一次 `init`，初始化成功后将标志置为"已初始化"，避免重复初始化。

### 4. 读写与控制 API

| API | 参数说明 | 说明 |
|---|---|---|
| `rt_size_t rt_device_read(rt_device_t dev, rt_off_t pos, void *buffer, rt_size_t size)` | `pos`：偏移量；`buffer`：读缓冲地址；`size`：读取大小 | 对**字符设备偏移量无效**（顺序读）；对**块设备会按偏移定位读取** |
| `rt_size_t rt_device_write(rt_device_t dev, rt_off_t pos, const void *buffer, rt_size_t size)` | 同上 | 同理，块设备按偏移写入 |
| `rt_err_t rt_device_control(rt_device_t dev, int cmd, void *arg)` | `cmd`：控制命令；`arg`：控制参数 | 命令随设备类型而定：串口可设置波特率、I2C 可设置速率、SPI 可设置模式与速率等 |

> 实验教训：**设备未成功打开时，`read` / `write` 不会被执行**（返回不允许操作）。实验中现象是 init 与 control 正常打印、read/write 未执行——原因就是遗漏了 `open` 步骤，补上 `open` 后读写正常。可结合调试器验证。

### 5. 回调机制

#### 5.1 接收 / 发送回调设置

| API | 作用 |
|---|---|
| `rt_err_t rt_device_set_rx_indicate(rt_device_t dev, rt_err_t (*rx_ind)(rt_device_t dev, rt_size_t size))` | 设置**接收回调**：硬件设备接收到数据时通知上层（传入设备句柄与本次接收数据大小） |
| `rt_err_t rt_device_set_tx_complete(rt_device_t dev, rt_err_t (*tx_done)(rt_device_t dev, void *buffer))` | 设置**发送完成回调**：DMA 等非阻塞发送完成后通知上层 |

#### 5.2 回调链的传递过程

硬件中断触发 → **底层驱动回调**（如 STM32 HAL 库回调）→ 调用 **RT-Thread 框架层回调** → 最终通知**上层应用**。

```
硬件中断 → STM32 HAL 回调 → RT-Thread 设备框架回调(rx_indicate/tx_complete) → 上层应用
```

> 例：串口以 DMA + 空闲中断方式接收时，回调函数携带本次接收的数据大小，上层应用据此取走数据；DMA 发送是非阻塞的，上层通过发送完成回调获知"这段数据已发送成功"。
>
> 注意：RT-Thread 的回调本质上仍依赖具体硬件实现（如串口需支持空闲中断回调），流程是先进入厂商回调，再进一步转到 RT-Thread 的回调。

#### 5.3 IO 框架调用关系小结

无论 init/open/close/read/write/control，最终都通过 **ops** 实现。上层 `rt_device_init` → IO 管理层 init → ops 中的 init → 底层硬件。**研究设备框架对接，只需关注 ops 的具体实现。**

### 6. 实战：字符设备注册实验 与 ops 对接实验

#### 6.1 实验一：创建一个字符设备并注册

**实验目标**：创建一个字符类型设备并注册到设备链表，在 `msh` 终端用 `list device` 查看。

**实验步骤**（核心代码要点，非源码全文）：
1. 调用 `rt_device_create(RT_Device_Class_Char, 0)` 创建字符设备句柄；
2. 判断返回句柄非空，否则打印错误并返回；
3. 调用 `rt_device_register(dev, "test_dv", RT_DEVICE_FLAG_RDWR)` 注册；
4. 校验返回值，非 `RT_EOK` 说明注册失败；
5. 通过**自动初始化机制**（`INIT_APP_EXPORT` 等宏）在系统启动流程中自动执行；
6. 烧录后在终端敲 `list device`，可见 `test_dv` 设备出现在设备列表。

**实验现象**：`list device` 中显示 `test_dv`，且其打开次数字段可见（本实验终端占用串口设备，故串口显示打开 2 次）。

> 本实验仅演示创建/注册 API 的调用方式，暂未实现具体 ops。RT-Thread 大部分真实驱动已写好，此处只是为了理解 IO 设备管理机制。

#### 6.2 实验二：为 test 设备实现 ops 对接

**实验目标**：为上面的 test 设备实现一套自定义 `ops`，通过 ulog 打印模拟各操作，理解上下层如何通过 ops 对接。

**实验步骤**（核心代码要点）：
1. 新建一个驱动文件并包含对应头文件；
2. 实现 `init / open / close / read / write / control` 各函数，内部用 `ulog`（注意用 `LOG_I` 调试级别打印，`LOG_E` 会显示为红色错误信息）打印日志模拟真实操作；
3. 将各函数指针**赋值给设备的 ops 结构体对应成员**（init → ops->init，open → ops->open，…）；
4. 在应用层通过 `rt_device_find("test_dv")` 找到设备、判空，依次调用 `init / open / read / write / control / close`；
5. 编译烧录，观察日志输出顺序。

**实验现象与调试分析**：
- 调用 `rt_device_init` 后，调试单步进入 `device_init`，确认跳到了我们自己实现的 init——**对接成功**；control 同理。
- 最初 read/write 未执行：原因是**未先 open 设备**，设备处于未打开状态，读写被拒绝；补上 `open` 后正常。
- open 时若设备未初始化，会**自动先调用 init** 并置初始化标志，避免重复初始化——这与「引用计数」「自动初始化」机制呼应。

> 通过单步调试（打断点、跳入函数内部）可以直观看到：`rt_device_init` → 判断 ops 非空 → 调用 ops 中的 init（即我们赋值的函数）。理解本实验后，再去读真实驱动的源码会顺畅很多。

### 7. 官方手册补充：ops 语义、flags 与块设备写回

#### 7.1 rt_device_ops 六方法详细语义

结合官方手册对六个操作方法更精确的语义说明（与实验二对照）：

| 方法 | 官方语义要点 |
|---|---|
| `init` | 初始化完成后把设备控制块 `flag` 置为已激活（`RT_DEVICE_FLAG_ACTIVATED`）；若已激活则再次调用**立即返回、不重复初始化** |
| `open` | 建议在调用 open 时才使能设备（设备不因系统启动就默认开始收数据，需等上层应用准备好） |
| `close` | 维护打开计数：open 时 +1、close 时 -1，**计数归 0 才真正关闭** |
| `read` | 返回 `rt_ssize_t`：字符设备以**字节**为单位、块设备以**块**为单位；`<0` 表示错误，正常情况下返回 size 值，**返回 0 需设置对应 errno**。对块设备 pos/size 均以块大小为单位（如块 512B，pos=10、size=2 表示从第 10 块起共 2 块） |
| `write` | 同 read，返回真实写入的字节数或块数，`<0` 错误，返回 0 设 errno |
| `control` | 按 cmd 命令控制设备，命令多由各类设备驱动自定义（如 `RT_DEVICE_CTRL_BLK_GETGEOME` 获取块设备大小） |

#### 7.2 注册 flags 完整宏

官方手册完整列出注册 flags（可用 `|` 组合）：

```
RT_DEVICE_FLAG_RDONLY      0x001   只读
RT_DEVICE_FLAG_WRONLY      0x002   只写
RT_DEVICE_FLAG_RDWR        0x003   读写
RT_DEVICE_FLAG_REMOVABLE   0x004   可移除（如可插拔存储）
RT_DEVICE_FLAG_STANDALONE  0x008   独立设备：不允许重复打开
RT_DEVICE_FLAG_SUSPENDED   0x020   挂起
RT_DEVICE_FLAG_STREAM      0x040   流模式：输出 "\n" 时自动补 "\r"
RT_DEVICE_FLAG_INT_RX      0x100   中断接收
RT_DEVICE_FLAG_DMA_RX      0x200   DMA 接收
RT_DEVICE_FLAG_INT_TX      0x400   中断发送
RT_DEVICE_FLAG_DMA_TX      0x800   DMA 发送
```

要点补充：
- `RT_DEVICE_FLAG_STANDALONE` 设备**不允许重复打开**（重复 open 会返回 `-RT_EBUSY`）。
- `RT_DEVICE_FLAG_STREAM` 用于向串口终端输出字符串：输出字符 `"\n"` 时自动在前面补一个 `"\r"` 做分行。

#### 7.3 通用控制命令宏

`rt_device_control` 的 cmd 通用命令：

```
RT_DEVICE_CTRL_RESUME   0x01   恢复设备
RT_DEVICE_CTRL_SUSPEND  0x02   挂起设备
RT_DEVICE_CTRL_CONFIG   0x03   配置设备
RT_DEVICE_CTRL_SET_INT  0x10   设置中断
RT_DEVICE_CTRL_CLR_INT  0x11   清除中断
RT_DEVICE_CTRL_GET_INT  0x12   获取中断
```

#### 7.4 块设备写不足一块："先读-覆盖-再写回"

官方手册指出：块设备的数据块大小是**硬件强制**的。当一次写操作的最后一部分数据小于设备块尺寸时，驱动必须先**读**出该设备块 → 把写入数据**覆盖**到读出数据上 → 再作为完整一块**写回**。例如每块 512B，前 3 块直接写，第 4 块不足一块就按"先读-覆盖-再写回"合成新块处理。

#### 7.5 attach_size：动态创建设备的附加用户数据

`rt_device_create(int type, int attach_size)` 中 `attach_size` 为**用户数据大小**：系统从动态堆内存中分配 `struct rt_device + attach_size` 大小的设备控制块，设备类型由 `type` 设定。设备被创建后需实现访问硬件的操作方法（ops），不再需要时可调用 `rt_device_destroy()` 销毁。

#### 7.6 看门狗设备：经框架层向 IO 层注册 + 完整使用示例

看门狗设备是官方手册给出的"先注册到设备驱动框架、再由框架注册到 IO 管理器"的典型例子：

1. 看门狗驱动按模型创建具备硬件访问能力的实例，用 `rt_hw_watchdog_register()` 注册到看门狗设备驱动框架；
2. 框架内部通过 `rt_device_register()` 将设备注册进 I/O 设备管理器；
3. 应用程序通过 I/O 设备管理接口访问看门狗硬件。

框架层注册代码要点（看门狗无 read/write，故 ops 对应位为 `RT_NULL`）：

```c
const static struct rt_device_ops wdt_ops =
{
    rt_watchdog_init, rt_watchdog_open, rt_watchdog_close,
    RT_NULL, RT_NULL, rt_watchdog_control,
};

rt_err_t rt_hw_watchdog_register(rt_watchdog_t *wdt, const char *name,
                                 rt_uint32_t flag, void *data)
{
    struct rt_device *device = &(wdt->parent);   // 继承基类取设备
    device->type      = RT_Device_Class_Miscellaneous;
    device->ops       = &wdt_ops;
    device->user_data = data;
    return rt_device_register(device, name, flag);  // 注册到 IO 管理器
}
```

应用侧完整使用示例（find → init → control → 空闲钩子喂狗）：

```c
#define IWDG_DEVICE_NAME "wdt"
static rt_device_t wdg_dev;

static void idle_hook(void)   // 空闲钩子中喂狗
{
    rt_device_control(wdg_dev, RT_DEVICE_CTRL_WDT_KEEPALIVE, NULL);
    rt_kprintf("feed the dog!\n");
}

int main(void)
{
    rt_uint32_t timeout = 10;                      // 溢出时间（秒）
    wdg_dev = rt_device_find(IWDG_DEVICE_NAME);    // 1. 查找设备
    if (!wdg_dev) { /* 打印失败并返回 */ }
    res = rt_device_init(wdg_dev);                 // 2. 初始化设备
    if (res != RT_EOK) return res;
    res = rt_device_control(wdg_dev, RT_DEVICE_CTRL_WDT_SET_TIMEOUT, &timeout);
    if (res != RT_EOK) return res;
    rt_thread_idle_sethook(idle_hook);             // 3. 空闲钩子周期喂狗
    return res;
}
```

## 三、GPIO(Pin) 外设开发

### 1. GPIO 基础

#### 1.1 引脚分类

MCU 芯片上的引脚大致分为四类：

| 类别 | 说明 |
|---|---|
| 电源引脚 | 芯片电源域供电 |
| 时钟引脚 | 时钟输入，本质上是晶振（低速晶振 / 高速晶振） |
| 控制引脚 | 复位、使能等控制信号 |
| IO 引脚 | 通用输入输出，或功能复用（如 SPI 的 MOSI/MISO/片选/时钟、I2C 的 SCL/SDA、串口的 TX/RX） |

大多数 MCU 引脚**不止一个功能**：不同引脚内部结构不同、拥有的功能也不同，可以通过不同配置切换引脚的**实际功能**（即引脚复用）。

#### 1.2 通用 IO 特性

- **可编程控制**：由软件配置方向、模式、电平。
- **中断能力**：支持多种触发模式，可通过外部高/低电平或边沿触发中断。
- **五种中断触发模式**：上升沿触发、下降沿触发、高电平触发、低电平触发、双边沿触发（上升沿+下降沿都触发）。

#### 1.3 引脚编号规律（以 STM32 为例）

STM32 GPIO 按组（PA/PB/PC…）组织，每组 16 个引脚（0~15）。RT-Thread Pin 驱动把引脚统一编号：`PA 0~15` 为 0~15，`PB 0~15` 为 16~31，`PC 0~15` 为 32~47…… 因此 `PC5` 对应引脚编号 = 32 + 5 = **37**。

> 推导：`引脚编号 = 组序号 × 16 + 组内序号`（PA=0, PB=1, PC=2 …）。

### 2. RT-Thread Pin 设备管理接口

RT-Thread 提供统一的 Pin 设备管理接口来访问 GPIO：

| API | 作用 |
|---|---|
| `rt_err_t rt_pin_mode(rt_base_t pin, rt_base_t mode)` | 设置引脚模式（五类模式见下） |
| `rt_err_t rt_pin_write(rt_base_t pin, rt_base_t value)` | 设置引脚电平（`PIN_LOW` / `PIN_HIGH`） |
| `rt_base_t rt_pin_read(rt_base_t pin)` | 读取引脚电平（返回低/高电平） |
| `rt_err_t rt_pin_attach_irq(rt_base_t pin, rt_uint32_t mode, void (*hdr)(void *args), void *args)` | 绑定引脚中断回调函数（指定触发模式） |
| `rt_err_t rt_pin_detach_irq(rt_base_t pin)` | 脱离引脚中断回调（不再使用中断） |
| `rt_err_t rt_pin_irq_enable(rt_base_t pin, rt_bool_t enabled)` | 使能 / 失能引脚中断 |

#### 2.1 引脚模式（mode）

| 模式 | 说明 |
|---|---|
| 输出模式 | 普通推挽输出 |
| 输入模式（上拉输入） | 内部上拉，默认高电平 |
| 输入模式（下拉输入） | 内部下拉，默认低电平 |
| 开漏输出模式 | 集电极开路输出，常配合外部上拉 |

#### 2.2 中断触发模式（mode）

| 触发模式 | 触发时机 |
|---|---|
| 上升沿触发 | 电平从低到高 |
| 下降沿触发 | 电平从高到低 |
| 高电平触发 | 维持高电平 |
| 低电平触发 | 维持低电平 |
| 双边沿触发 | 上升沿或下降沿均触发 |

### 3. 实战：按键中断实验

#### 3.1 硬件与原理

开发板上有 4 个可编程按键（丝印标有 up / down 的方向键），按键按下时为**低电平**。使用**上拉输入**模式：未按下时读到高电平，按下后引脚被拉低，触发中断。

**按键与引脚对应**：

| 按键 | 引脚 |
|---|---|
| 上（UP） | PC5 |
| 下（DOWN） | PC1 |
| 右（RIGHT） | PC0 |
| 左（LEFT） | PC4 |

#### 3.2 实验步骤（核心代码要点）

1. **设置引脚模式**：对 4 个按键引脚分别调用 `rt_pin_mode(pin, PIN_MODE_INPUT_PULLUP)`（上拉输入，对应按下为低电平的原理图设计）；
2. **绑定中断回调**：调用 `rt_pin_attach_irq(pin, PIN_IRQ_MODE_FALLING, callback, args)`，触发模式选**下降沿**（按下瞬间电平从高拉低）；
3. **实现回调函数**：在回调中调用 `rt_pin_read(pin)` 读取并打印电平值，区分是哪个按键（如打印 "up/down/left/right"）；
4. **使能中断**：对每个按键调用 `rt_pin_irq_enable(pin, PIN_IRQ_ENABLE)`；
5. 编译下载，**确保 ulog 已开启输出**，否则终端无打印。

#### 3.3 实验现象与问题

- 按键按下后触发中断回调，终端打印对应按键信息。
- **问题现象**：按键一次按下却触发了**两次中断**。

### 4. 调试：Pin 驱动分层源码分析

#### 4.1 从 API 到 HAL 库的完整调用栈

通过单步调试可以验证 Pin 驱动的完整对接链路：

```
上层应用 → rt_pin_mode(...)
        → Pin 设备驱动框架层 ops（drv_pin 层）
        → 具体设备驱动层（如 stm32_pin）
        → STM32 HAL 库 GPIO 接口
        → 硬件寄存器
```

- `rt_pin_mode` 调用的是一个 **ops**，随后跳转到 STM32 的具体 GPIO 实现，最终由 HAL 库 API 完成硬件操作。
- 引脚编号 37（PC5）经公式推导得到，不同厂家的引脚编号规则不同，但 **RT-Thread 已把这些适配做好**，上层只需使用通用 API。

#### 4.2 关键结论

上层应用全部使用 RT-Thread 通用 API 时，**迁移到另一颗 MCU 只需把上层应用迁移过去，底层驱动完全不用管**——这正是设备驱动框架分层设计的最终价值。

### 5. 按键消抖问题与解决

#### 5.1 为什么会出现两次触发

机械按键存在**机械抖动**：按下/松开瞬间，触点接触不稳定，会在极短时间内产生多次电平跳变，导致一次按压触发多次中断。

#### 5.2 常用消抖方案

| 方案 | 说明 |
|---|---|
| **软件包消抖（推荐）** | 使用 RT-Thread 软件包（如 **button 库**）封装按键状态机，自动处理抖动与长按/短按逻辑 |
| 延时消抖 | 在回调中延时（如 10~20ms）再读取电平确认，简单但会占用中断时间 |
| 状态机消抖 | 自行实现按键状态机，用定时器周期扫描代替中断触发 |

> 尝试使用软件包（如 button 库）解决按键消抖问题。

### 6. 官方手册补充：引脚编号、模式/中断宏与蜂鸣器按键示例

#### 6.1 引脚编号的 3 种获取方式

官方手册明确：**RT-Thread 的引脚编号 ≠ 芯片引脚号**，引脚编号由 PIN 设备驱动程序定义、和具体芯片相关。有 3 种获取方式：

| 方式 | 说明 | 示例 |
|---|---|---|
| API 获取 | `rt_pin_get("PF.9")` 按名获取 | `pin_number = rt_pin_get("PF.9");` |
| 宏定义 | STM32 BSP 提供 `GET_PIN(port, pin)` | `#define LED0_PIN GET_PIN(F, 9)` |
| 查看 PIN 驱动 | 非 STM32 BSP 查 `drv_gpio.c` 的 `pins[]` 数组 | `__STM32_PIN(2, A, 15)` → 编号 2 = PA15 |

`drv_gpio.c` 的数组示例：

```c
static const rt_uint16_t pins[] =
{
    __STM32_PIN_DEFAULT,
    __STM32_PIN(2, A, 15),   // 2 是 RT-Thread 引脚编号，A 为端口，15 为引脚号
    __STM32_PIN(3, B, 5),
    ...
};
```

> 与笔记 1.3 的"编号 = 组号×16 + 组内号"公式互补：STM32 用 `GET_PIN` / `pins[]` 数组直查；其他 BSP 编号规则可能不满足该公式，**务必以各 BSP 的 `pins[]` 数组为准**。

#### 6.2 5 种引脚模式宏

官方宏定义（与笔记 2.1 表格对应上宏名）：

```
PIN_MODE_OUTPUT         0x00   输出
PIN_MODE_INPUT          0x01   输入
PIN_MODE_INPUT_PULLUP   0x02   输入上拉
PIN_MODE_INPUT_PULLDOWN 0x03   输入下拉
PIN_MODE_OUTPUT_OD      0x04   开漏输出
```

#### 6.3 5 种中断触发模式宏

```
PIN_IRQ_MODE_RISING          0x00   上升沿
PIN_IRQ_MODE_FALLING         0x01   下降沿
PIN_IRQ_MODE_RISING_FALLING  0x02   双边沿
PIN_IRQ_MODE_HIGH_LEVEL      0x03   高电平
PIN_IRQ_MODE_LOW_LEVEL       0x04   低电平
```

#### 6.4 detach_irq：脱离后中断未关闭，可再绑定

官方手册强调：`rt_pin_detach_irq()` 只是**脱离中断回调函数**，**中断并没有关闭**，之后仍可再次调用 `rt_pin_attach_irq()` 绑定其他回调函数。若要彻底关闭中断，需配合 `rt_pin_irq_enable(pin, PIN_IRQ_DISABLE)`。

#### 6.5 官方蜂鸣器 + 按键示例（与实验三呼应）

官方示例流程与笔记实验三呼应，差异在于官方用按键控制蜂鸣器开关而非仅打印按键名：

1. 蜂鸣器引脚设为输出，默认低电平；
2. 按键 0 / 按键 1 设为上拉输入，绑定中断回调并使能；
3. 按 KEY0 → 蜂鸣器响，按 KEY1 → 蜂鸣器停。

```c
#define BEEP_PIN_NUM  35
#define KEY0_PIN_NUM  55
#define KEY1_PIN_NUM  56

void beep_on(void *args)  { rt_pin_write(BEEP_PIN_NUM, PIN_HIGH); }  // 响
void beep_off(void *args) { rt_pin_write(BEEP_PIN_NUM, PIN_LOW); }   // 停

static void pin_beep_sample(void)
{
    rt_pin_mode(BEEP_PIN_NUM, PIN_MODE_OUTPUT);
    rt_pin_write(BEEP_PIN_NUM, PIN_LOW);

    rt_pin_mode(KEY0_PIN_NUM, PIN_MODE_INPUT_PULLUP);
    rt_pin_attach_irq(KEY0_PIN_NUM, PIN_IRQ_MODE_FALLING, beep_on, RT_NULL);
    rt_pin_irq_enable(KEY0_PIN_NUM, PIN_IRQ_ENABLE);

    rt_pin_mode(KEY1_PIN_NUM, PIN_MODE_INPUT_PULLUP);
    rt_pin_attach_irq(KEY1_PIN_NUM, PIN_IRQ_MODE_FALLING, beep_off, RT_NULL);
    rt_pin_irq_enable(KEY1_PIN_NUM, PIN_IRQ_ENABLE);
}
MSH_CMD_EXPORT(pin_beep_sample, pin beep sample);
```

#### 7.2 对接链路逐层解析：应用层 → ops → BSP → HAL → 寄存器

第 4.1 节的调用栈可以展开为完整的五层链路，**引脚编号在这条链路上逐层传递并最终"翻译"成硬件能懂的端口+引脚**：

```
应用层  rt_pin_mode / rt_pin_read / rt_pin_attach_irq ...（传入「RT-Thread 引脚编号」）
   │
   ▼
框架层  PIN 设备驱动（pin.c 通用层：通过设备 ops 分发，屏蔽芯片差异）
   │   device->ops 指向 stm32_pin_ops
   ▼
BSP 层  drv_gpio.c（stm32_pin_mode / stm32_pin_read / stm32_pin_attach_irq ...）
   │   用 GET_PIN / pins[] 把「编号」换算成 端口 + 引脚号
   ▼
HAL 库  HAL_GPIO_Init / HAL_GPIO_ReadPin / HAL_GPIO_EXTI_IRQHandler ...
   │   GPIO_TypeDef*（如 GPIOA）+ GPIO_PIN_x（如 GPIO_PIN_9）
   ▼
寄存器 GPIOx->MODER / ODR / IDR / EXTI 相关寄存器（最终物理控制）
```

各层职责：

| 层 | 代表文件/接口 | 职责 |
|---|---|---|
| 应用层 | `main.c` / 业务代码 | 只调通用 API，不关心芯片型号 |
| 框架层 | `pin.c`（ops 分发） | 提供统一接口，把通用调用路由到具体驱动 |
| BSP 驱动层 | `drv_gpio.c` | 实现各芯片的 pin ops，**负责"编号 → 端口/引脚"的映射**，是对接核心 |
| HAL 库 | 厂商库 | 封装寄存器操作（初始化、读/写电平、外部中断回调） |
| 寄存器 | GPIOx 寄存器 | 最终控制引脚电平与中断行为 |

> 用第 4.1 节的实验验证：单步进入 `rt_pin_mode` → 跳到 `stm32_pin_mode`（BSP）→ 再进 `HAL_GPIO_Init`（HAL）→ 最终写寄存器。每一层都只是在"把编号往硬件方向翻译"。

#### 7.3 引脚编号：贯穿对接链路的"软件与硬件桥梁"

官方手册强调：**RT-Thread 的引脚编号 ≠ 芯片引脚号，引脚编号由 PIN 设备驱动程序定义、与具体芯片相关**。它在对接链路中的作用可以这样理解：

- **获取端（上层）**：3 种方式（`rt_pin_get("PF.9")` 按名解析 / `GET_PIN(F,9)` 编译期计算 / 查 `drv_gpio.c` 的 `pins[]` 数组）得到的是同一个东西——**驱动定义的统一编号**；
- **使用端（BSP 驱动）**：驱动拿到编号后，通过 `GET_PIN` 宏或 `pins[]` 数组**把编号换算成端口 + 引脚号**，再进一步落到 `GPIOx + GPIO_PIN_x`，最终操作寄存器；
- **为什么上层不直接用芯片引脚号**：不同芯片的端口/引脚命名千差万别（STM32 的 PA9、瑞萨/GD32 等各不相同），统一编号让**应用层代码跨芯片复用**——换 MCU 只需换 BSP 驱动，上层 `rt_pin_*` 调用一行不用改。

一句话总结：**编号是应用层与硬件之间的"约定"，获取方式（rt_pin_get / GET_PIN / pins[]）决定怎么得到它，BSP 驱动决定怎么把它翻译成硬件操作——两者共同完成"对接"。**

## 四、I2C 与 SPI 总线外设开发

### 1. I2C 总线外设开发

#### 1.1 I2C 协议基础

| 概念 | 说明 |
|---|---|
| 起始位 / 结束位 | 总线空闲为高电平；SCL 高时 SDA 由高变低为起始，由低变高为结束 |
| 应答（ACK） | 接收方拉低 SDA 表示应答 |
| 7 位设备地址 | I2C 设备通常为 7 位地址；传输时**左移一位**，末尾补**读写位**（0 写 / 1 读），即地址字节 = 设备地址 << 1 \| R/W |
| 总线锁死恢复 | I2C 总线锁死时，可通过**产生 9 个时钟脉冲（SCL）** 恢复总线 |

#### 1.2 总线-设备模型

I2C 采用**总线-设备模型**：先创建一个 I2C 总线（总线控制器），再将具体设备挂载到总线上。`list device` 可查看已注册的 I2C 设备。

#### 1.3 核心 API：消息结构体

I2C 通信通过构建 `struct rt_i2c_msg` 结构体进行：

| 字段 | 说明 |
|---|---|
| `addr` | 设备地址 |
| `flags` | 读写标志 |
| `buf` | 缓冲区指针 |
| `len` | 数据长度 |

使用 `rt_i2c_transfer` 等接口把消息发到总线上完成读写。

> 配置并实操 I2C 外设，熟悉相关 API 的使用。

### 2. SPI 总线外设开发

#### 2.1 SPI 总线特点

| 特点 | 说明 |
|---|---|
| 高速 | 速率远高于 I2C |
| 全双工 | 同时收发数据 |
| 同步 | 由主机时钟驱动，从机被动接收 |
| 多从机 | 通过片选（CS）选择从设备 |

#### 2.2 总线-设备模型与命名规则

- SPI 同样采用**总线-设备模型**：先注册 SPI 总线控制器，再将具体设备（如 Flash W25Q128）挂载到总线上。
- 设备命名遵循 **`spixy`** 格式：`x` 为总线号，`y` 为设备序号。例如 `spi10` 表示**总线 1 上的 0 号设备**。

#### 2.3 SPI 配置参数

| 配置项 | 说明 |
|---|---|
| 时钟频率 | 传输速率，需匹配从设备能力 |
| 数据宽度 | 8 位 / 16 位 |
| 传输模式（CPOL / CPHA） | 决定时钟极性（空闲电平）与相位（采样时刻），共 4 种模式 |
| 数据位序（MSB / LSB） | 高位在前或低位在前传输 |

#### 2.4 驱动启用方法

通过 ENV 配置工具或 RT-Thread Studio 配置引脚后即可启用 SPI 驱动。

> 配置并实操 SPI 外设，熟悉相关 API 的使用。

### 3. 开发环境：基于芯片（BSP） vs 基于 SDK（CubeMX）

#### 3.1 两种开发模式对比

| 对比项 | 基于芯片（BSP） | 基于 SDK（CubeMX / 主线） |
|---|---|---|
| 适用范围 | 多种芯片适配 | 特定芯片型号 |
| 引脚/时钟配置 | 手动在 `board.h` / `board.c` 配置，流程繁琐 | 直接利用 CubeMX 生成的配置文件，自动化程度高 |

当前**部分芯片支持包仅支持软件模拟 I2C（Soft I2C）**；若需使用硬件 I2C，需**手动更新驱动**或改用**主线版本**支持包。

### 4. 官方手册补充：I2C / SPI 协议细节与 API 详解

#### 4.1 I2C：总线原理

官方手册定义：I2C（Inter Integrated Circuit）由 **PHILIPS** 开发，是**半双工、双向、二线制同步串行总线**。只用两根线：**SDA**（双向数据线）+ **SCL**（双向时钟线）。与 SPI 双线收发不同，I2C 用**一根线**分时收发。

- 以主从方式工作，但**不同于 SPI 的一主多从，I2C 允许多个主设备同时存在**；
- 每个连接到总线上的器件都有**唯一地址**；
- 主设备启动数据传输并产生时钟信号，从设备被主设备寻址，**同一时刻只允许一个主设备**。

#### 4.2 I2C：传输格式

官方时序（总线空闲时 SDA、SCL 均为高电平）：

```
开始条件 → 从机地址+读写位 → 数据（逐字节 ACK 应答）→ ... → 停止条件
```

| 名词 | 说明 |
|---|---|
| 开始条件 | SCL 为高电平时主机把 SDA 拉低，表示传输即将开始 |
| 从机地址 | 第一个字节：高 7 位为地址，最低位为 R/W（1 读 0 写）。分 7 位 / 10 位地址模式：10 位模式首字节头 7 位为 `11110XX`（XX 是 10 位地址的最高两位），第二个字节是 10 位地址剩余 8 位 |
| 应答 ACK | 每传完一个字节接收方回 ACK；写数据时从机发 ACK，读数据时主机发 ACK；主机读到最后一个字节可发 NACK 后跟停止条件 |
| 数据 | 每字节 8 位，**高位在前**，字节数不限 |
| 重复开始条件 | 需与不同从机通信或切换读写时，主机可再发一个开始条件（典型"写寄存器地址 → 重复开始 → 读数据"） |
| 停止条件 | SDA 为低时主机把 SCL 拉高并保持，再把 SDA 拉高，表示传输结束 |

#### 4.3 I2C：rt_i2c_msg 与 flags 宏

```c
struct rt_i2c_msg
{
    rt_uint16_t addr;    // 从机地址（不含读写位！读写位由 flags 控制）
    rt_uint16_t flags;   // 消息标志
    rt_uint16_t len;     // 数据长度
    rt_uint8_t  *buf;    // 数据缓冲区
};
```

**重要**：RT-Thread I2C 接口使用的从机地址**不包含读写位**，读写控制通过 flags 实现：

```
RT_I2C_WR           0x0000      写
RT_I2C_RD           (1u << 0)   读
RT_I2C_ADDR_10BIT   (1u << 2)   10 位地址
RT_I2C_NO_START     (1u << 4)   不发送开始条件
RT_I2C_IGNORE_NACK  (1u << 5)   忽略 NACK
RT_I2C_NO_READ_ACK  (1u << 6)   读数据时不发 ACK
RT_I2C_NO_STOP      (1u << 7)   不发送停止条件
```

flags 可用位运算 `|` 组合。

#### 4.4 I2C：transfer 与推荐封装、拼接发送

- `rt_i2c_transfer(bus, msgs[], num)`：传输**消息数组**；若主设备需发送重复开始条件，则使用 **2 个消息**。返回成功传输的消息个数，失败返回错误码。
- **推荐封装**：`rt_i2c_master_send()` / `rt_i2c_master_recv()` 封装自 `rt_i2c_transfer()`，读写从设备更简单易用。
- **拼接发送技巧**：把"寄存器地址（前缀）"和"数据"拼成一条 I2C 数据：

```c
rt_i2c_master_send(bus, addr, RT_I2C_NO_STOP, prefix_buffer, prefix_len);  // 先发前缀，不停
rt_i2c_master_send(bus, addr, RT_I2C_NO_START, buffer, len);               // 再发数据，不重复开始
```

- **注意**：`rt_i2c_transfer()` 内部会调用 `rt_mutex_take()`，**不能在中断服务程序里调用**（会 assertion 报错）。

#### 4.5 I2C：AHT10 温湿度传感器示例要点

官方 AHT10 示例核心流程：
1. `rt_device_find("i2c1")` 获取 I2C 总线句柄；
2. 初始化：发 `NORMAL_CMD(0xA8)` → 延时 → 发 `CALIBRATION_CMD(0xE1)` 校准；
3. 读数据：发 `GET_DATA(0xAC)` → 延时 400ms → `read_regs()` 读 6 字节；
4. 从 6 字节原始数据按位拼接计算温湿度（湿度、温度各 20 bit，乘以比例系数换算成百分数与摄氏度）。

#### 4.6 SPI：4 线定义与一主多从

官方手册四根线：

| 线 | 全称 | 作用 |
|---|---|---|
| MOSI | Master Output / Slave Input | 主机输出、从机输入数据线 |
| MISO | Master Input / Slave Output | 主机输入、从机输出数据线 |
| SCLK | Serial Clock | 串行时钟线，主设备输出时钟至从设备 |
| CS | Chip Select（也叫 SS/CSB/CSN/EN） | 片选线，主设备输出，**低电平有效** |

- 一个 SPI 控制器（主设备）可连接多个从设备：挂载在**同一控制器上的从设备共享 SCK/MISO/MOSI，但每个从设备的 CS 引脚独立**。
- 同一时刻一个 SPI 主设备上**只有一个 CS 处于有效状态**，只有与该有效 CS 相连的从设备能与主设备通信。
- 扩展知识：SPI Flash 有标准 / Dual / Quad 三种，Dual/Quad 把 MOSI、MISO 复用作 SIO0~SIO3，一个时钟周期传 2/4 bit 提高速率；QSPI（Queued SPI）是 Motorola 对 SPI 的增强，以 80 字节 RAM 代替收发寄存器、支持队列传输，传输期间无需 CPU 干预。

#### 4.7 SPI：CPOL / CPHA 与 4 种模式

- **CPOL**（时钟极性）：时钟信号的**初始电平**，0=初始低电平，1=初始高电平。
- **CPHA**（时钟相位）：在**哪个时钟沿采样数据**，0=第一个变化沿采样，1=第二个变化沿采样。

CPOL 与 CPHA 组合出 4 种时序模式：

| 模式 | CPOL | CPHA | 说明 |
|---|---|---|---|
| MODE_0 | 0 | 0 | 空闲低电平，首个时钟沿采样 |
| MODE_1 | 0 | 1 | 空闲低电平，第二个时钟沿采样 |
| MODE_2 | 1 | 0 | 空闲高电平，首个时钟沿采样 |
| MODE_3 | 1 | 1 | 空闲高电平，第二个时钟沿采样 |

#### 4.8 SPI：挂载 API（cspin 新接口 / 旧版 user_data）

- **新版（RT-Thread 5.0.0 新增）**：`rt_spi_bus_attach_device_cspin(device, name, bus_name, cs_pin, user_data)`——**基于 PIN 框架**绑定片选引脚，避免不同 BSP 对片选引脚操作不统一：

```c
rt_spi_bus_attach_device_cspin(spi_device, "spi10", "spi1", GET_PIN(B, 14), RT_NULL);
rt_spi_bus_attach_device_cspin(spi_device, "spi10", "spi1", rt_pin_get("PB.14"), RT_NULL);
```

- **旧版（5.0.0 前）**：`rt_spi_bus_attach_device(device, name, bus_name, user_data)`——片选引脚通过 `user_data` 传入（一般为 CS 引脚指针），传输时 SPI 控制器操作该引脚完成片选。官方建议今后尽量使用 cspin 新接口。
- 命名规则：总线 `spix`、设备 `spixy`（`spi10` = 挂载在 spi1 总线上的 0 号设备）。
- 卸载接口：`rt_spi_bus_detach_device()`（应用层优先，内部调用 `rt_spi_bus_detach_device_cspin()`），卸载成功后动态申请的设备可 `rt_free` 释放。

#### 4.9 SPI：rt_spi_configure 与配置结构体

```c
struct rt_spi_configuration
{
    rt_uint8_t  mode;        // 主从/时序/位序等组合
    rt_uint8_t  data_width;  // 数据宽度：8 / 16 / 32 位
    rt_uint16_t reserved;
    rt_uint32_t max_hz;      // 最大频率（波特率）
};
```

mode 常用宏：

```
RT_SPI_MASTER / RT_SPI_SLAVE    主从模式
RT_SPI_MODE_0 ~ RT_SPI_MODE_3   四种时序模式
RT_SPI_MSB / RT_SPI_LSB         数据位序（高位/低位在前）
RT_SPI_CS_HIGH / RT_SPI_NO_CS / RT_SPI_3WIRE / RT_SPI_READY
```

配置示例：

```c
struct rt_spi_configuration cfg;
cfg.data_width = 8;
cfg.mode = RT_SPI_MASTER | RT_SPI_MODE_0 | RT_SPI_MSB;
cfg.max_hz = 20 * 1000 * 1000;      // 20MHz
rt_spi_configure(spi_dev, &cfg);
```

#### 4.10 SPI：传输 API 族

| API | 说明 |
|---|---|
| `rt_spi_transfer_message()` | 传输一连串消息（单向链表，`next` 连接）；`cs_take`=1 表示传输前片选有效、`cs_release`=1 表示结束后释放；首条消息 cs_take=1、末条 cs_release=1 |
| `rt_spi_transfer()` | 传输一次数据（等效单条消息：开始选中片选、返回时释放） |
| `rt_spi_send()` / `rt_spi_recv()` | 只发送 / 只接收（接收时主设备发 0xFF 提供时钟） |
| `rt_spi_send_then_send()` | 连续发送两段数据，中间**不释放片选**（先发命令/地址再发数据，写 Flash 常用） |
| `rt_spi_send_then_recv()` | 先发送后接收，中间不释放片选（先发命令/地址再读数据，读 Flash 常用） |
| `rt_spi_sendrecv8() / 16()` | 发送 1/2 字节的同时接收 1/2 字节 |
| `rt_spi_take_bus / take / release / release_bus` | 多线程下获取/释放总线与片选（独占总线场景） |

消息结构体要点：

```c
struct rt_spi_message
{
    const void *send_buf;          // RT_NULL 表示本次只接收
    void *recv_buf;                // RT_NULL 表示本次只发送
    rt_size_t length;              // 数据长度（8 位时即字节数）
    struct rt_spi_message *next;   // 下一条消息，单向链表连接
    unsigned cs_take : 1;          // 传输前拉低 CS（选中从设备）
    unsigned cs_release : 1;       // 传输结束后释放 CS
};
```

- **注意**：所有 SPI 传输接口内部调用 `rt_mutex_take()`，**不能在中断服务程序里调用**（会 assertion 报错），与 I2C 一致。

#### 4.11 W25Q128 读 ID 示例要点

官方示例核心流程：
1. `rt_device_find("qspi10")` 获取 SPI 设备句柄；
2. `rt_spi_send_then_recv(spi_dev, &cmd_0x90, 1, id, 5)`：先发读 ID 命令字节 `0x90`，再接收 5 字节 ID；
3. 或改用 `rt_spi_transfer_message()`：构建 msg1（发命令，cs_take=1）/ msg2（收 ID，cs_release=1）两条消息组成消息链传输。

## 总结

RT-Thread **设备驱动框架与 IO 外设开发**：

1. **分层思想**：通过统一 IO 设备层 + 特定设备框架层，把应用与具体 MCU 驱动解耦，实现代码跨芯片复用，降低学习成本。
2. **rt_device 生命周期**：`create → register → find → open → read/write/control → close → unregister → destroy`，配套引用计数、自动初始化与回调机制。
3. **GPIO(Pin) 开发**：掌握引脚模式与五种中断触发模式，通过按键中断实验理解从 API 到 HAL 库的 ops 逐层对接，并解决按键机械抖动问题。
4. **总线外设开发**：I2C（`rt_i2c_msg`、7 位地址 + 读写位、总线锁死恢复）与 SPI（总线-设备模型、`spixy` 命名、CPOL/CPHA 配置）。
5. **开发模式**：基于芯片（BSP）与基于 SDK（CubeMX）两种模式各有适用场景，硬件 I2C 支持需关注支持包版本。

核心结论：**上层应用用统一 API 开发，底层驱动交给 BSP 适配，即可在不同 MCU 间无缝迁移。**
