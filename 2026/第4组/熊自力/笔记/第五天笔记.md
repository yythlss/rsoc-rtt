## 一、软件包生态与索引机制

### 1. 什么是 RT-Thread 软件包

软件包是 RT-Thread 生态中**可复用的功能模块**（传感器驱动、网络协议、工具库等），通过简单的菜单配置即可拉取到工程中使用，无需自己手写底层驱动。主线上已有 **800+ 个软件包**，覆盖外设、工具、系统等类型，例如：

| 类别     | 示例                                                     |
| -------- | -------------------------------------------------------- |
| 传感器   | AHT10、MPU6050 及其同系列陀螺仪                          |
| 网络连接 | kawaii-mqtt、阿里云飞燕平台（IoT）连接包、TCP/UDP server |
| 系统兼容 | FreeRTOS 兼容层（可把 RT-Thread 应用无感迁移到其他系统） |
| 工具     | 浮点数打印（rt_vsnprintf_full）等                        |

> 类比：软件包相当于嵌入式界的"应用商店"——别人写好的模块，配置即用。

### 2. 软件包索引与配置路径

软件包在 menuconfig / Studio 中使能后会被索引到。关键点：

- **索引来源**：软件包的 Kconfig 配置路径在 **env 工具目录下**，通过 `packages` 目录引入。具体路径为 `studio安装目录/env/packages`。
- **env 版本兼容**：RT-Thread Studio 针对不同内核版本维护了**两份 env 配置**——内核 **5.1.0 以上**使用新版 env（2.0），**5.1.0 以下**只能使用 1.5.x 版本，确保软件包与内核版本兼容匹配。

```
studio安装目录/env/
        ├── 新版本 env（2.0）     → 内核 5.1.0 以上
        └── 旧版本 env（1.5.x）   → 内核 5.1.0 以下
                └── packages/     ← 软件包索引目录（Kconfig 在此）
```

> 工程最外层 Kconfig 中：第一个 include 引入内核的 Kconfig（rtconfig 目录），第二个值由 env 传入——即**软件包的 Kconfig 路径来自 env 环境**。

### 3. 软件包仓库维护与贡献流程

- 软件包仓库**独立维护**在 RT-Thread 官方仓库中，索引（Kconfig 内容）一致。
- 想共建软件包，需向仓库提交 **PR**，PR 内容通过 **package.json** 文件记录软件包的位置（仓库地址），例如某贡献者（逐字稿提及"王顺"）贡献的软件包即通过 package.json 登记地址。
- 在 env / Studio 中使能该软件包并保存后，系统会**自动拉取对应软件包源码**到工程目录。

```
贡献者 → 提交 PR（package.json 记录仓库地址）→ 合并进软件包仓库 → 用户 menuconfig 使能 → 自动拉取源码
```

### 4. 软件包集成流程与依赖管理

1. **配置使能**：在 menuconfig / Studio 的"添加软件包"中搜索并勾选目标软件包（如 AHT10、RW007），`Ctrl+S` 保存后自动拉取源码至工程 `packages/` 目录。
2. **依赖管理**：部分软件包依赖底层框架，需**手动开启相关依赖项**，否则编译报错。典型例子：AHT10 依赖 **Sensor 设备框架**，若未使能会出现 `undefined reference to sensor ops`（详见第二大章）。

### 5. 熟悉其它软件包

| 软件包              | 作用                | 本次实战的用法                                               |
| ------------------- | ------------------- | ------------------------------------------------------------ |
| `AHT10`             | 温湿度传感器驱动    | `aht10_init("i2c3")` + `aht10_read_temperature/humidity` 采集数据 |
| `kawaii-mqtt`       | MQTT 客户端         | `mqtt_lease` 建实例、`mqtt_set_host/port/client_id` 配置、`mqtt_connect`/`mqtt_subscribe`/`mqtt_publish` 收发 |
| `RW007`             | SPI WiFi 模块驱动   | `wifi join` 连接热点联网，作为 MQTT 的底层网卡               |
| `rt_vsnprintf_full` | 浮点数打印支持      | 默认 libc 不支持 `%f`，使能后 `Temp: %.2f` 才能正常输出      |
| `SFUD`              | 串行 Flash 通用驱动 | 屏蔽 W25Q64 差异，配合 FAL 分区供 DFS 挂载                   |

> 软件包不是"死代码"，它们各自承担一类能力（传感器 / 网络协议 / 存储），组合起来就能快速搭出"采集 → 上云 → 落盘"的完整链路。后续可继续尝试 button（按键消抖）、cjson（JSON 解析）等常用包。

## 二、传感器驱动与网络配置实战（AHT10 + RW007）

### 1. AHT10 温湿度传感器：手写驱动 vs 软件包

#### 1.1 对比

| 对比项 | 手写驱动                                  | 软件包驱动                  |
| ------ | ----------------------------------------- | --------------------------- |
| 流程   | 查数据手册 → 找寄存器 → 配寄存器 → 读数据 | 使能软件包 → 调封装好的 API |
| 复用性 | 每换传感器都要重写                        | 别人已写好，可直接复用      |
| 工作量 | 大                                        | 小                          |

AHT10 是板载温湿度传感器，通过 **I2C** 通信，使用 **sensor device 框架**。板载外设在工程里已声明，因此在"添加软件包"中直接搜索 **AHT10** 并使能即可，`Ctrl+S` 后自动拉取源码。

#### 1.2 软件包核心 API

在软件包头文件中可看到三个关键接口（软件包本质上是把 I2C 寄存器操作封装了一层）：

| API                           | 作用                                                         |
| ----------------------------- | ------------------------------------------------------------ |
| `aht10_init(bus_name)`        | 初始化，传入 **I2C 总线名称**（本板为 `"i2c3"`），返回 AHT10 设备句柄 |
| `aht10_read_temperature(dev)` | 读取温度                                                     |
| `aht10_read_humidity(dev)`    | 读取湿度                                                     |

```c
#include <aht10.h>

aht10_device_t dev = aht10_init("i2c3");   // 传入 I2C 总线名，返回设备句柄
if (dev == RT_NULL) { /* 初始化失败处理 */ }

float temp = aht10_read_temperature(dev);   // 读取温度
float humi = aht10_read_humidity(dev);      // 读取湿度
```

> 关键理解：软件包内部仍是通过 RT-Thread 的 I2C 设备框架 API 去读写 AHT10 寄存器，只是把寄存器操作封装成易用的接口——这也是"复用"的意义。

#### 1.3 线程封装与 MSH 导出

建议把读取逻辑封装在**独立线程**中，并导出为 MSH 命令便于终端调试：

```c
static void aht10_thread_entry(void *param)
{
    aht10_device_t dev = aht10_init("i2c3");
    if (dev == RT_NULL) { LOG_E("aht10 init failed"); return; }
    while (1)
    {
        rt_kprintf("temp: %.1f C, humi: %.1f %%\n",
                   aht10_read_temperature(dev), aht10_read_humidity(dev));
        rt_thread_mdelay(500);               // 每 500ms 读一次
    }
}

static void aht10_sample(void)
{
    rt_thread_t tid = rt_thread_create("aht10", aht10_thread_entry, RT_NULL,
                                       1024, 10, 20);   // 栈 1024、优先级 10
    if (tid) rt_thread_startup(tid);
    else     LOG_E("thread create failed");
}
MSH_CMD_EXPORT(aht10_sample, aht10 sample);  // 终端敲 aht10_sample 启动
```

#### 1.4 两个典型编译/运行问题

| 问题       | 现象                                | 解决                                                         |
| ---------- | ----------------------------------- | ------------------------------------------------------------ |
| 依赖缺失   | `undefined reference to sensor ops` | AHT10 软件包依赖 **Sensor 框架**未使能。原因是软件包 scons 文件把所有源码都编译了，需在 menuconfig 手动打开 Sensor 框架后重新编译 |
| 浮点数打印 | 温度湿度打印不出来 / 输出异常       | 默认 libc **不支持浮点数打印**，需使能浮点数打印软件包（`rt_vsnprintf_full`），重新配置编译后即可正常打印 |

#### 1.5 实验现象

- 烧录后终端敲 `aht10_sample`，复位后能持续打印温湿度数值；
- 用手捂热传感器，读数随之上升——验证读取功能正确。

### 2. RW007 WiFi 模块配置

#### 2.1 使能软件包

在 menuconfig 的"硬件板载设备驱动"中找到 **RW007** 并勾选使能，保存后自动拉取软件包。

#### 2.2 引脚修正

RW007 默认引脚配置与**开发板原理图不符**，必须对照原理图修正以下引脚：

| 引脚          | 说明                                           |
| ------------- | ---------------------------------------------- |
| 片选 CS       | 用于 SPI 通信选择模块（本板为 PD5 对应编号等） |
| Boot0 / Boot1 | 启动模式选择                                   |
| 中断 INT      | WiFi 中断引脚（本板为 PG11，编号 107）         |
| Reset         | 复位引脚                                       |

> 判断方法：看原理图的网络标签（如 `wifi INT`），找到对应 MCU 引脚后，把默认配置替换为正确引脚编号（可用 `GET_PIN` 宏或 msh 计算）。这一步不改会导致模块无法工作。

#### 2.3 联网验证

烧录后通过终端 `wifi` 命令系列操作：

```

wifi join <热点名> <密码>   连接手机热点，自动分配 IP
```

`ping` 通百度即代表 RW007 联网成功，为下一步 MQTT 通信打基础。

## 三、MQTT 协议通信：软件包实战

### 1. MQTT 协议基础

MQTT 是嵌入式物联网常用的协议，核心特点：

- **轻量化**：报文开销小，适用于**资源受限设备**；
- **发布 / 订阅模型**：客户端订阅某个主题，发布者向主题发消息，订阅者即可收到，松耦合；
- 消息按主题路由，支持 QoS 等级（QoS0 开销最小、相对不可靠，QoS1/2 递增）。

```
发布者 --发布(主题/数据)--> Broker(消息代理) --推送--> 订阅者
```

### 2. 免费服务器：EMQX + MQTTX 客户端

- **服务端**：使用开源 **EMQX** 提供的**免费公共服务器**，TCP 端口 **1883**；
- **客户端验证**：使用 **MQTTX** 桌面客户端连接同一个服务器，验证收发。

连接要点（免费服务器）：

| 配置项          | 说明                                                     |
| --------------- | -------------------------------------------------------- |
| 服务器地址      | EMQX 免费服务器域名 + 端口 1883                          |
| 客户端 ID       | 每台客户端**必须唯一**（相同 ID 会互相顶掉线）           |
| 用户名 / 密码   | 免费服务器**不做校验**，随便填即可；自有服务器则必须校验 |
| 订阅 / 发布主题 | 公共服务器上尽量**错开**，避免互相干扰定位               |

### 3. kawaii-mqtt 软件包示例

#### 3.1 配置

1. 添加 **kawaii-mqtt** 软件包（社区大佬作品，作者同时也是 sensor 维护者）；
2. 使能 **示例代码**（enable kawaii-mqtt test）；
3. 填写配置：
   - **host**：免费服务器地址（broker.emqx.io）；
   - **port**：1883（TCP）；
   - **client id**：唯一；
   - **订阅主题 / 发布主题**：自定义且错开。

`Ctrl+S` 后自动拉取软件包。

#### 3.2 示例执行流程

1. 先连接 WiFi（上一步的 RW007）；
2. 终端敲 msh 导出的 **`kawaii-mqtt`** 命令发起连接；
3. 观察日志出现"连接成功"，随后示例自动向发布主题发送消息；
4. 在 MQTTX 中订阅该主题，即可看到板端发送的数据；MQTTX 向板端订阅主题发消息，板端也能收到并回调。

示例代码的核心流程（提炼，非全文）：

```c
// 创建 demo 线程 → 延迟稳定 → 创建客户端实例
mqtt_client_t client = mqtt_lease();              // 新建客户端实例
mqtt_set_host(client, HOST);                      // 服务端地址
mqtt_set_port(client, PORT);                      // 端口号
mqtt_set_user_passwd(client, USER, PASSWD);       // 认证用户名密码
mqtt_set_client_id(client, CLIENT_ID);            // 连接 ID
mqtt_connect(client);                             // 发起连接
mqtt_subscribe(client, SUB_TOPIC, QOS0, cb);      // 订阅主题，回调接收
mqtt_publish(client, PUB_TOPIC, msg, QOS0);       // 发布主题，QoS0 开销最小
```

> 接收是**回调驱动**：订阅主题收到消息会唤醒回调函数处理；发送示例默认用 **QoS0**（资源占用小）。

#### 3.3 分层抽象的收益

RT-Thread 把网卡（WiFi）抽象成统一的网络接口，**MQTT 应用层不关心底层是哪种 WiFi/网卡**，只要有联网能力即可跑同一套 MQTT 代码——这正是设备驱动框架分层设计的价值：上层应用只面对统一 API，底层差异被屏蔽，可快速移植到不同 MCU。

### 4. MSH 自定义命令封装（argc/argv）

不想每次改源码发送时，可封装一条 MSH 命令，通过命令行参数控制发送：

```c
static void mqtt_send(int argc, char *argv[])
{
    if (argc < 2) { rt_kprintf("usage: mqtt_send <msg>\n"); return; }
    if (mqtt_client_connected(client))          // 等连接成功后
        mqtt_publish(client, PUB_TOPIC, argv[1], QOS0);
}
MSH_CMD_EXPORT(mqtt_send, send mqtt message);
```

**argc / argv 语义**（与 Linux 命令行一致）：

| 命令行输入         | argc | argv                           |
| ------------------ | ---- | ------------------------------ |
| `mqtt_send`        | 1    | `["mqtt_send"]`                |
| `mqtt_send 123456` | 2    | `["mqtt_send", "123456"]`      |
| `mqtt_send a b c`  | 3    | `["mqtt_send", "a", "b", "c"]` |

> 第一个参数是命令本身；`argc` 即参数个数。MSH 命令本质原型与此相同。

### 5. 调试提示

- 连不上：确认 WiFi 已连接、host/端口/主题拼写一致、客户端 ID 唯一；
- 改完配置**必须重新保存编译**，未使能示例时提示找不到命令需检查示例是否编入。

## 四、DFS 文件系统与外部 Flash 实战

### 1. DFS：设备虚拟文件系统

**DFS（Device File System）** 是 RT-Thread 提供的**虚拟文件系统**，使用类 Linux 的文件/文件夹风格：

- 系统有**唯一根目录**，用 `/` 表示；根目录下文件写作 `/file`；
- 提供统一的 **POSIX 标准接口**：`open / read / write / close`，与应用平时用的 C 语言文件 API 一致；
- 支持目录管理（`mkdir` 等）；
- 支持多种底层介质：SD 卡、SPI Flash（NOR Flash）等。

```
应用程序
   │  POSIX 标准接口（open/write/read/close/mkdir...）
   ▼
DFS 虚拟文件系统层（统一根目录 /）
   ▼
块设备 / Flash 介质（SD、SPI NOR Flash...）
```

### 2. 文件系统使能配置

menuconfig 依次使能：

| 配置项              | 说明                                                         |
| ------------------- | ------------------------------------------------------------ |
| 硬件 → 使能 Flash   | 使能 Flash 组件（含**自动挂载**），其依赖会自动使能          |
| 组件 → DFS          | 使能虚拟文件系统，打开旧版本兼容性支持                       |
| 组件 → elm 文件系统 | 使能 **elm**（FATFS 兼容层）文件系统。本工程 Flash 最大扇区 **4096** |

保存、重新编译、下载后，终端 `list device` 可见文件系统设备已注册。

### 3. 分区表与外部 Flash（W25Q64）

#### 3.1 分区表

外部 Flash（W25Q64）通过**分区表**划分多个区域（分区表定义在 `library/board.h` 中，用 `11` 等数字标识分区偏移）：

| 分区           | 用途                                                |
| -------------- | --------------------------------------------------- |
| app            | 固件存放区                                          |
| 下载区         | WiFi 固件管理（wifi 固件存在外部 Flash 比片内合理） |
| 字库区         | 字库存放                                            |
| **文件系统区** | 挂载为文件系统，挂载到根目录 `/flash`               |

```
W25Q64 外部 Flash
├── app（固件区）
├── 下载区（WiFi 固件）
├── 字库区
└── 文件系统区 ──挂载──▶ /flash（DFS 根目录下的 flash 文件夹）
```

#### 3.2 SFUD 通用驱动

- **SFUD**（串行 Flash 通用驱动库）屏蔽了市面上不同 Flash 型号的差异（SPI 模式、读写时序、页大小不同等）；
- 只要告诉它 Flash 型号，即可用**统一接口**读写，无需关心具体芯片配置；
- 分区表读写即通过 SFUD 组件实现：一次操作最多 **4096 字节**（W25Q64 的特性）。

#### 3.3 挂载流程（board 驱动初始化）

`board.c / drv_*.c` 中完成对接（提炼流程）：

```
1. 初始化 Flash，把 SPI 设备注册到 SPI 总线上
2. 对 Flash 兼容层初始化，创建块设备
3. 通过 DFS 把块设备挂载到根目录 /flash 下（文件系统类型 elm）
4. 挂载成功 → ls 可见 /flash
```

> 挂载失败需要先**格式化**文件系统（`mkfs` 命令），格式化后该分区原有内容会被清空。

### 4. SPI 总线冲突解决（关键坑）

**WiFi 与 W25Q64 共用同一条 SPI 总线**。若不处理片选信号，两者会**互相干扰**，导致找不到 W25Q64（典型报错：w25q64 not found）。解决：**初始化时把 WiFi 的片选引脚上拉**，避免干扰 Flash 读写。

```c
// 例：wifi 片选引脚（GPIO10 等）上拉，避免与 Flash 抢总线
rt_pin_mode(WIFI_CS_PIN, PIN_MODE_OUTPUT);
rt_pin_write(WIFI_CS_PIN, PIN_HIGH);
```

### 5. POSIX 读写示例（open / write / close）

用标准 POSIX 接口在 `/flash` 下创建并写入文件：

```c
#include <dfs_posix.h>

int fd = open("/flash/test.txt", O_RDWR | O_CREAT);   // 读写方式打开，不存在则创建
if (fd >= 0)
{
    write(fd, "HelloDay5", 9);                        // 写入内容与长度
    close(fd);                                        // 关闭文件
}
```

> 注意：文件描述符 `fd` 为 **0 也代表成功**（不是负值），判断失败应看 `fd < 0`。

写入后终端 `ls /flash` 可见 `test.txt`，`cat /flash/test.txt` 可查看内容。App 侧通过这一套 POSIX 接口，就能把数据持久化到外部 Flash 的指定分区。

### 6. 综合实战作业

**作业要求**：通过 AHT10 软件包读取温湿度，**每 2 秒**通过 MQTT 发布一次（电脑端 MQTTX 可见），同时把数据**记录（追加）到 Flash 文件**中。

- 融合点：温湿度采集与读取 → 第二、三大章内容；MQTT 发送 → 第三章；文件记录 → 第四章。
- 示例（参考）：每 5 秒读取一次温湿度，追加写入文件一次；上电几次后，文件系统中即累积了每次的记录数据——即"边记录到 Flash，边发布到 MQTT"。

```
AHT10 读取（每 2s）
   ├──▶ MQTT 发布主题 ──▶ EMQX ──▶ MQTTX 电脑端可见
   └──▶ open/write 追加写入 /flash 文件 ──▶ 数据持久化
```

### 7. 实战：三线程 + 双消息队列解耦

把任务拆成**三个线程 + 两条消息队列**，实现采集、上传、落盘三者解耦：

```
AHT10 采集线程（每 3s 读数，Count 自增）
   │ rt_mq_send（同一份数据发两份）
   ├──▶ sensor_mqtt_mq ──▶ MQTT 上传线程 ──▶ EMQX 上行
   └──▶ sensor_file_mq ──▶ 文件保存线程 ──▶ /fal/Data.txt 落盘
```

- **采集线程 `AHT10_read`**：`aht10_init("i2c3")` 后每 3 秒读温湿度，`Count++`，把数据同时发往两条消息队列；
- **MQTT 线程 `MQTT_auto`**：`rt_mq_recv` 用 **500ms 短超时**取队列，拼装 `Temp: %.2f; Humi: %.2f; Count: %d` 后 `mqtt_publish`；取完必调 `mqtt_sleep_ms(500)` 保活；
- **文件线程 `File_save`**：`rt_mq_recv` 死等取队列，维护**最近 10 条滚动缓存**，`open(O_TRUNC)` 整份重写后 `close` 落盘。

**本次挂载的是 `/fal` 分区**（FAL 分区表里文件系统分区的挂载点），而不是`/flash`——挂载点由分区表决定，用 `list device` 和 `ls /` 即可确认当前板子的真实挂载点。

```c
/* Data.txt 落盘格式（Count 为自上电起采集次数） */
snprintf(cache[count], sizeof(cache[count]),
         "Temp: %.2f; Humi: %.2f; Count: %d\r\n", data.temp, data.humi, data.Count);
```

**云端控灯**：下行走**订阅回调**而非线程——`sub_topic_handle1` 收到 `rtt-sub12138` 主题消息后，用 `strstr(payload, "led_toggle")` 做包含匹配（兼容 JSON 包裹 `{"msg":"led_toggle"}`），匹配到就 `rt_pin_write` 翻转板载 LED（F12），实现"云端指令 → 开发板小灯翻转"。

### 8. 本次实战排错经验

| 问题                      | 现象                                       | 解决                                                         |
| ------------------------- | ------------------------------------------ | ------------------------------------------------------------ |
| `/fal` 目录 BAD file 乱码 | `ls /fal` 出现大量 `BAD file: ▒▒▒▒▒.▒▒▒`   | FAT 目录项损坏（写一半断电 / 旧代码写垃圾块），`mkfs -t elm filesystem` 格式化（**设备名是 filesystem，不是 fal**；fal 只是挂载目录名），格式化后分区内容清空 |
| DFS 写缓存未落盘          | `write` 返回成功但 `cat Data.txt` 是空文件 | DFS 写入带缓存，`write()` 只进内存；**`close(fd)` 触发 flush 才真正写进介质**。可靠写法：循环内每次 open/write/close |
| RTC 警告刷屏              | `Cannot find a RTC device!`                | FAT 取时间戳调 `time()` 找不到 RTC 设备；在 **`ffconf.h` 中把 `FF_FS_NORTC` 设为 1** 即可关闭（比改 rtconfig 的 `DFS_ELM_USE_TIMESTAMP` 更直接有效） |

> 三条经验本质都是"文件系统 / 介质层面的时序与缓存"问题：格式化治标（清脏数据）、close 落盘治本（保证数据落地）、RTC 警告是无伤大雅的时钟缺失，按需关闭即可。

## 总结

RT-Thread **软件包生态与文件系统实战**：

1. **软件包生态**：Kconfig 索引位于 `env/packages`，Studio 按内核版本维护两份 env；贡献软件包走 PR + package.json；使能后自动拉取源码，注意依赖框架（如 Sensor）要手动开启。
2. **传感器与网络**：AHT10 用软件包封装 I2C 寄存器操作（init/read_temp/read_humi + 线程封装 + MSH 导出），需解决浮点打印；RW007 需对照原理图修正 CS/Boot/INT 引脚，wifi scan/connect/ping 验证联网。
3. **MQTT 通信**：MQTT 是轻量发布/订阅协议；用 EMQX 免费服务器（1883）+ MQTTX 验证；kawaii-mqtt 软件包使能示例即可收发；MSH 命令通过 argc/argv 解析参数；分层抽象让 MQTT 应用与底层网卡解耦。
4. **DFS 文件系统**：虚拟文件系统统一 POSIX 接口与根目录 `/`；使能 DFS + elm + Flash 自动挂载；W25Q64 按分区表划分后文件系统区挂载到 `/flash`；SFUD 屏蔽 Flash 差异；WiFi 与 Flash 共用 SPI 总线需上拉 WiFi 片选；用 open/write/close 即可持久化文件。
5. **作业闭环**：AHT10 每 2 秒读温湿度 → MQTT 发布 → 同时追加写入 Flash 文件，串起 Day5 全部知识点。

核心结论：**软件包让外设驱动"配置即用"，DFS 让外部 Flash"像文件一样读写"，两者结合即可低成本实现"传感器采集 → 网络上报 → 本地持久化"的完整物联网数据链路。**
