# RT-Thread夏令营学习笔记

## 一、Markdown基础学习

### 1.Markdown基本语法

Markdown是一种轻量级标记语言，常用于编写学习笔记、项目说明以及README文档。本次主要学习了标题、列表、粗体、代码块、链接和图片等基础语法。

常用写法如下：

```markdown
# 一级标题
## 二级标题
### 三级标题
#### .....
- 无序列表
1. 有序列表

**粗体**
`行内代码`
***斜体***
```

Markdown语法简单，编写完成后也能够保持比较清晰的文档结构，非常适合用于整理后续RT-Thread学习内容。

### 2.代码块和文档编写

在嵌入式学习过程中，经常需要记录命令、程序代码以及操作步骤，因此代码块是Markdown中比较常用的功能。

例如记录Git命令：

```bash
git status
git add .
git commit -m "完成学习任务"
```

使用代码块可以将程序、命令和普通说明文字区分开，使学习笔记更加清晰，也方便后续查找和复制命令。

### 3.Markdown的实际用途

在RT-Thread和开源项目的学习过程中，Markdown可以用于：

- 编写每天的学习笔记；
- 编写Git仓库中的README.md；
- 记录程序编译、运行以及实验过程；
- 编写Pull Request中的说明内容。

因此，Markdown不仅可以用来整理笔记，也是参与开源项目开发需要掌握的一项基础技能。

## 二、RT-Thread基础环境配置

### 1.下载SDK和板级文件包

本次首先完成了RT-Thread基础开发环境的配置，包括下载SDK和对应的板级文件包。

SDK主要提供程序编译所需要的工具链、编译器以及相关开发工具。板级支持包BSP则与具体芯片和开发板相关，其中通常包含启动文件、驱动程序以及工程配置等内容。

整个环境可以简单理解为：

```text
RT-Thread源码
    +
SDK开发工具
    +
BSP板级支持
    ↓
RT-Thread开发环境
```

只有正确配置SDK和BSP，后续才能正常创建、编译和运行RT-Thread工程。

### 2.创建工程并进行编译

完成基础环境配置后，需要创建RT-Thread工程，并通过编译来检查环境是否配置正确。

本次学习中使用了`qemu-vexpress-a9`工程。QEMU可以模拟ARM硬件环境，因此即使没有实际开发板，也可以运行RT-Thread进行学习和测试。

基本操作流程为：

```text
创建qemu-vexpress-a9工程
        ↓
检查工程配置
        ↓
编译RT-Thread工程
        ↓
检查编译结果
```

如果工程能够顺利完成编译，并且没有出现工具链或文件缺失等错误，说明基础开发环境已经配置成功。

### 3.运行工程并检查msh

完成工程编译后，可以通过QEMU运行RT-Thread。

程序正常启动后，会显示RT-Thread的启动信息，并进入msh命令行。

整体检查过程可以总结为：

```text
创建工程
   ↓
成功编译
   ↓
QEMU运行
   ↓
RT-Thread启动
   ↓
进入msh
```

msh是RT-Thread提供的命令行Shell，可以通过输入命令查看系统状态和执行相关功能。

因此，当工程能够成功编译并进入msh时，就说明RT-Thread的基础开发环境已经基本搭建完成。

## 三、Git仓库和Pull Request

### 1.Git基本操作

本次学习完成了Git环境配置，并创建了个人代码仓库，同时学习了常见的Git版本管理命令。

常用命令包括：

```bash
git clone <仓库地址>
git status
git add .
git commit -m "提交信息"
git pull
git push
```

这些命令分别用于克隆仓库、查看修改、添加文件、提交修改、拉取代码以及推送代码。

基本工作流程可以理解为：

```text
修改文件
   ↓
git status
   ↓
git add .
   ↓
git commit
   ↓
git push
   ↓
远程仓库
```

通过Git可以记录每一次代码和文档修改，方便后续查看历史版本以及进行多人协作。

### 2.分支和仓库同步

在进行新的学习任务之前，需要先保证本地仓库和远程主分支保持同步。

第一次PR提交，可以执行：

```bash
git switch master
git pull origin master
git checkout -b day1
```

其中：

```bash
git switch master
```

用于切换回主分支。

```bash
git pull origin master
```

用于拉取远程主分支中的最新内容。

```bash
git checkout -b day1
```

用于基于最新主分支创建一个新的`day1`分支。

因此比较规范的操作顺序为：

```text
同步上游仓库
    ↓
切换master
    ↓
拉取最新代码
    ↓
创建新分支
    ↓
开始新的任务
```

这样可以避免不同学习任务之间的修改混在一起。

### 3.Pull Request基本流程

Pull Request通常简称PR，主要用于请求将自己分支中的代码或文档修改合并到目标仓库。

在开源项目中，一般先Fork目标仓库到自己的账号，再将仓库Clone到本地，然后创建新的开发分支。

基本流程为：

```text
Fork上游仓库
    ↓
Clone个人仓库
    ↓
创建新分支
    ↓
修改代码或文档
    ↓
git add .
    ↓
git commit
    ↓
git push
    ↓
创建Pull Request
```

例如第二天完成学习任务后，可以执行：

```bash
git add .
git commit -m "完成Day1学习任务"
git push origin day2
```

随后进入远程仓库，在`day2`分支下创建新的PR。

如果后续只是修改当前PR中的问题，可以继续在原来的分支上修改并再次提交：

```bash
git add .
git commit -m "修改PR内容"
git push origin day2
```

新的提交会继续更新到当前PR中。

如果开始的是一个新的学习任务，则应该先同步主分支，再创建新的分支和新的PR。

通过本次学习，我基本掌握了从本地修改代码到提交PR的完整流程：

```text
同步代码
   ↓
创建分支
   ↓
完成修改
   ↓
git add
   ↓
git commit
   ↓
git push
   ↓
创建PR
```

这也是后续参与RT-Thread开源项目和管理个人学习代码时需要经常使用的基本工作流程。
