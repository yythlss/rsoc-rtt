# RT-Thread线程间同步与通信学习随笔

今天继续往RT-Thread的内核机制里走。

前面学习线程时，我更多关注的是每个线程自身的状态、优先级、时间片以及挂起和恢复。但真正写一个稍微复杂一点的嵌入式程序后，很快就会遇到一个问题：线程不是各跑各的，它们一定会共享硬件、共享数据，也需要互相通知。

比如一个线程采集传感器，一个线程负责显示，一个线程负责通信。如果没有同步机制，几个线程可能同时修改同一份数据；如果没有通信机制，采集线程得到了数据以后，显示线程甚至不知道新数据已经来了。

所以今天学完以后，我对RTOS里线程间同步和线程间通信的理解开始清晰了一些：

> **同步解决的是什么时候可以做、谁先做、谁能访问资源的问题；通信解决的是线程之间要传什么信息的问题。**

虽然两者经常混在一起使用，但它们关注的重点其实不同。

---

# 一、线程间同步：重点不是一起运行，而是有秩序地运行

## 1.信号量：最容易理解的资源计数器和通知器

RT-Thread里的信号量可以看成一个带计数值的同步对象。

一个线程通过`rt_sem_take()`获取信号量，通过`rt_sem_release()`释放信号量。如果信号量当前还有资源，线程就可以继续运行；如果信号量已经为0，那么等待线程可以进入挂起状态，直到其他线程或者中断释放信号量。

我觉得用停车场来理解信号量很直观。假设停车场有3个位置，那么信号量初始值就是3：

```text
初始值 = 3

线程A获取 → 2
线程B获取 → 1
线程C获取 → 0
线程D再获取 → 没有资源，等待

线程A释放 → 线程D获得机会继续运行
```

所以信号量其实可以做两件事。一种是**资源计数**，比如系统只有3个可用缓冲区，就把信号量初始值设为3。另一种是**线程同步**，例如采集线程完成ADC采样以后释放一个信号量，处理线程一直等待这个信号量。

```text
采集线程
   ↓
ADC完成
   ↓
rt_sem_release()
   ↓
处理线程被唤醒
   ↓
处理采样数据
```

这一点和我以前使用FreeRTOS时的Binary Semaphore、Counting Semaphore非常接近。FreeRTOS也把二值信号量用于任务之间或者ISR到任务的同步，把计数信号量用于资源计数。

ChibiOS的Semaphore思路也类似，同样属于计数型同步原语，而且还提供超时等待、Reset等操作。

Linux里也有POSIX Semaphore：

```c
sem_wait();
sem_post();
```

从概念上看，四个系统其实非常接近。真正让我感觉不同的地方是，RT-Thread把线程、信号量、互斥量、事件、邮箱、消息队列统一放在“内核对象”这一套体系里，所以学习的时候会比较容易从整体上理解这些IPC对象之间的关系。

## 2.互斥量：和信号量很像，但真正重点是“所有权”

刚开始看互斥量时，很容易产生一个疑问：信号量初始值设成1，不也能保证同一时间只有一个线程进入临界区吗？为什么还需要Mutex？

今天重新理解以后，我觉得最重要的区别不是“值是不是1”，而是**互斥量有所有者，而信号量没有真正意义上的所有者**。

例如两个线程都会访问同一个I2C总线：

```text
thread_sensor
       \
        → I2C总线
       /
thread_display
```

如果两个线程同时开始操作I2C，就可能把一次完整传输打断。因此需要先获得互斥量，完成访问以后再释放。

```c
rt_mutex_take(&i2c_lock, RT_WAITING_FOREVER);

/* 临界区 */
read_sensor();

rt_mutex_release(&i2c_lock);
```

这里还有一个非常重要的问题：**优先级反转**。

假设：

```text
高优先级线程H
中优先级线程M
低优先级线程L
```

L先拿到了Mutex，然后H需要这个Mutex，于是H只能等待。如果这时M不断抢占L，那么真正高优先级的H反而会因为L迟迟得不到CPU而一直被卡住。

RT-Thread的互斥量使用优先级继承机制来减轻这种情况：低优先级线程持有Mutex并阻塞了高优先级线程时，可以临时提升持有者的优先级，让它尽快完成临界区并释放Mutex。

这一点和FreeRTOS很像。FreeRTOS的Mutex也带优先级继承机制，而Binary Semaphore不带，因此更适合把Semaphore用于同步，把Mutex用于保护共享资源。

ChibiOS在这一点上也很明确：Mutex具有Owner属性，实现Priority Inheritance，而且还能配置Recursive Mutex。

Linux的`pthread_mutex_t`则更加通用。普通Mutex默认并不一定采用优先级继承，但POSIX提供`PTHREAD_PRIO_INHERIT`、`PTHREAD_PRIO_PROTECT`等协议，可以针对实时线程配置。

所以我现在会这样区分：

```text
Semaphore：
更像“有几个资源”或者“某件事发生了”

Mutex：
更像“这个资源现在属于谁”
```

这个区别比单纯记API更重要。

## 3.事件集：当一个线程需要同时关心很多条件时特别好用

事件集是今天我觉得很有意思的一部分。

RT-Thread用一个32位无符号整数表示事件集合，每一位代表一个事件：

```text
bit0 → ADC完成
bit1 → UART收到数据
bit2 → 网络连接成功
bit3 → 按键触发
...
```

例如：

```c
#define EVENT_ADC  (1 << 0)
#define EVENT_UART (1 << 1)
```

等待线程可以选择OR模式或者AND模式。OR模式表示任意一个感兴趣的事件发生都可以唤醒线程；AND模式表示多个条件全部满足以后才唤醒。RT-Thread还可以配合`RT_EVENT_FLAG_CLEAR`，在线程成功接收到事件以后自动清除对应标志。

我现在觉得信号量比较像“有人敲门了”，而事件集更像“ADC完成了、UART有数据了、网络连接了、按键按下了”，而且可以决定满足其中一个就处理，还是所有条件满足以后再处理。

这里还有一个很关键的特性：**事件本身不负责传输数据，而且同一个事件重复发送不会像计数信号量一样不断累积。**

FreeRTOS里对应的是Event Group，也可以通过bit等待多个条件，并选择等待任意bit还是全部bit。因此从使用体验上，RT-Thread Event和FreeRTOS Event Group很接近。

ChibiOS也有完整的Events机制，而且支持Event Source、Listener、Event Flags以及waitOne、waitAny、waitAll。在我看来，ChibiOS的事件系统更偏“事件发布/订阅”的感觉，而RT-Thread的Event Set结构更直接。

Linux线程里没有一个完全等价于RTOS Event Group的单一POSIX线程API。实际开发中可能使用Condition Variable、eventfd、信号或者epoll等组合来实现类似需求。Linux的能力明显更强，但同时抽象层次也更复杂。

# 二、线程间通信：线程不只是要互相等，还要真正交换数据

## 1.邮箱：轻量级的消息传递方式

如果说同步主要解决数据准备好了没有，那么通信解决的就是准备好的数据到底是什么？

RT-Thread的Mailbox就是一个比较轻量的通信机制。按照RT-Thread文档里的设计，邮箱一次传递一个4字节大小的消息，因此可以直接发送整数、状态值、地址或者指针。

例如：

```text
按键线程
   ↓
检测KEY1按下
   ↓
发送消息1
   ↓
LED线程收到1
   ↓
LED翻转
```

如果需要传递一个较大的结构体，也可以把结构体放在缓冲区里，然后通过Mailbox传递指针。

这让我想到FreeRTOS的Task Notification。Task Notification可以把任务内部的通知值当作轻量级Semaphore、Event甚至Mailbox来使用，而且不需要单独创建Queue对象，在一对一通知场景下开销很小。

ChibiOS也有Mailbox，底层是一个消息的Circular Queue，可以在线程和ISR上下文中Post和Fetch。从这个角度看，ChibiOS Mailbox和RT-Thread Mailbox的思想非常接近。

但Linux里我反而很少会把“Mailbox”作为线程通信的第一选择。Linux同一个进程中的线程本身共享地址空间，所以很多情况下直接使用“共享数据+Mutex+Condition Variable”就能完成线程通信。

这体现出了MCU RTOS和Linux思维上的一个区别：

> **RTOS更倾向于使用显式的内核通信对象组织线程关系，而Linux线程天然共享进程内存，通信和同步往往是组合起来设计的。**

## 2.消息队列：比邮箱更适合真正的数据传递

如果需要传递的不只是一个状态或者一个指针，Message Queue就更合适。

RT-Thread的消息队列允许消息在设定的最大消息长度内携带不同长度的数据，而且消息会被缓存起来。

```text
Producer
   ↓
Message1
Message2
Message3
   ↓
Message Queue
   ↓
Consumer
```

如果队列为空，接收线程可以等待；新消息到达后再被唤醒。这是一种典型的异步通信方式，也就是说发送方不需要等接收方马上处理。

例如串口接收：

```text
UART中断
   ↓
得到一段数据
   ↓
rt_mq_send()
   ↓
消息进入队列
   ↓
协议处理线程被唤醒
   ↓
解析数据
```

这样中断只负责快速搬运数据，而耗时的协议解析放在线程里完成，非常符合RTOS里“中断尽量短，把工作推迟到线程”的思路。

RT-Thread还有`rt_mq_urgent()`，普通消息放到队尾，而Urgent Message放到队头，可以优先处理。

FreeRTOS里Queue是非常核心的通信机制，消息默认按值复制，也可以传递指针。

ChibiOS除了Mailbox以外，还有很有特色的Synchronous Messages，更像一个轻量级Client/Server调用模型。这个设计和RT-Thread的异步Mailbox/Message Queue思路明显不同。

Linux里则有POSIX Message Queue：

```c
mq_send();
mq_receive();
```

它允许消息带Priority，而且不仅能在线程之间使用，也可以用于进程间通信。因此Linux的消息队列进入了更完整的系统资源管理体系。

## 3.Signal：让我第一次明显感觉到RT-Thread和Linux之间的联系

RT-Thread的Signal让我感觉很像Linux。

RT-Thread把Signal描述为一种“软中断”，用于通知线程发生了异步事件。线程可以安装Signal Handler，可以屏蔽或者解除屏蔽，其他线程则可以通过`rt_thread_kill()`向目标线程发送Signal。

```c
rt_signal_install();
rt_signal_mask();
rt_signal_unmask();
rt_thread_kill();
```

这种设计和Linux里的：

```c
pthread_kill();
sigaction();
pthread_sigmask();
```

在概念上非常接近。

Linux中`pthread_kill()`可以把一个Signal定向发送给同一进程中的指定线程；RT-Thread则把这种思想放到了嵌入式线程环境中。

FreeRTOS内核本身没有POSIX Signal这种完全对应的核心机制。类似“通知某个任务发生了某个异步事件”的需求，通常会用Task Notification、Event Group、Queue或者Semaphore。

ChibiOS也更倾向于使用Event、Synchronous Message等机制完成异步通知，没有必要完全照搬POSIX Signal模型。

所以如果之前接触过Linux，我觉得RT-Thread的Signal会显得比较亲切。

# 三、把RT-Thread、FreeRTOS、ChibiOS和Linux放在一起以后，我的一些发现

## 1.四个系统解决的问题很像，但它们的“性格”不一样

|需求|RT-Thread|FreeRTOS|ChibiOS|Linux/POSIX|
|---|---|---|---|---|
|资源计数/同步|Semaphore|Binary/Counting Semaphore|Semaphore|POSIX Semaphore|
|临界区互斥|Mutex|Mutex|Mutex|pthread_mutex|
|等待多个事件|Event Set|Event Group|Events|Condition/Eventfd等组合|
|轻量通知|Mailbox/Signal|Task Notification|Events/Synchronous Message|Signal/Eventfd|
|消息传递|Mailbox/Message Queue|Queue/Message Buffer|Mailbox/Synchronous Message|POSIX Message Queue|
|优先级反转处理|Mutex优先级继承|Mutex优先级继承|Mutex优先级继承|可配置PRIO_INHERIT等协议|

FreeRTOS给我的感觉一直是**Kernel味最浓**。Task、Queue、Semaphore、Mutex、Event Group这些东西很直接，尤其Task Notification很有自己的特色，很多简单IPC可以不创建额外内核对象。

ChibiOS给我的感觉是**非常强调结构和效率**。Mutex、Condition Variable、Event Source、Listener、Synchronous Message这些设计都有比较清晰的体系，而且能看出它很重视小开销和确定性。

Linux则是**通用操作系统思维**。同步和通信不只服务于几个MCU线程，还要面对多进程、权限、文件描述符、命名空间等问题，所以工具非常多，但系统复杂度也高得多。

RT-Thread在这几个里面给我的感觉比较居中。它既有Semaphore、Mutex、Event、Mailbox、Message Queue这些典型RTOS机制，又加入了Signal、POSIX接口、FinSH、设备框架、文件系统、网络组件和软件包等更接近完整操作系统的能力。

所以RT-Thread不像FreeRTOS那样只给我一种“实时内核”的感觉，而更像是：

> **从MCU RTOS向完整嵌入式操作系统延伸的一套系统。**

## 2.我开始发现：IPC选择其实是在选择“线程之间的关系”

以前刚学RTOS的时候，我比较容易把这些东西当成API表：Semaphore怎么创建、Mutex怎么Take、Queue怎么Send。

但今天学完以后，我觉得真正重要的是先问：

> 这两个线程到底是什么关系？

如果只是线程A告诉线程B“事情做完了”，Semaphore或者Notification就够了。

如果线程A和线程B都要访问I2C，应该优先想到Mutex。

如果线程需要同时等待网络连接完成、时间同步完成、传感器初始化完成，Event Set会更自然。

如果UART线程要把一帧数据交给协议线程，Message Queue明显更适合。

如果只是通知一个异步异常事件，Signal或者轻量通知机制可能更合适。

所以我觉得IPC不是“哪个API更高级”，而是一个选择过程：

```text
线程关系
   ↓
数据量
   ↓
是否需要缓存
   ↓
是否允许阻塞
   ↓
是否来自ISR
   ↓
是否涉及共享资源
   ↓
选择合适的IPC
```

这个思维方式比直接背API更接近真正做系统设计。

## 3.今天最大的感受：RTOS的核心不是多线程，而是可控的并发

刚开始接触RTOS时，我会把它理解成：

```text
裸机只能while(1)
RTOS可以创建很多线程
```

但现在慢慢感觉这个理解太浅了。

真正复杂的地方不是“创建很多线程”，而是多个线程什么时候运行、谁先运行、共享资源怎么保护、一个线程怎么通知另一个线程、数据应该放在哪里、线程等待时能不能让出CPU、中断和线程之间怎么配合、优先级反转怎么办。

也就是说：

> **多线程本身并不是目标，把并发行为控制在一个可以预测、可以维护的范围内才是RTOS真正的价值。**

之前使用FreeRTOS时，我更多是在用API完成任务；使用ChibiOS时，我会明显感觉到它的内核设计很紧凑；接触Linux线程以后，又会看到一个成熟通用操作系统里同步、通信和进程模型是怎么结合的。

现在再回来看RT-Thread，我会发现它刚好处在一个很有意思的位置：

```text
比FreeRTOS更像一个完整OS
比Linux更轻量、更贴近MCU
API和概念又保留了很多传统RTOS的直观性
```

对我来说，这次学习最大的收获已经不只是知道`rt_sem_take()`、`rt_mutex_take()`、`rt_event_recv()`、`rt_mb_send()`、`rt_mq_send()`这些函数怎么调用，而是开始能够从系统角度理解：

```text
线程为什么需要同步
线程为什么需要通信
不同IPC为什么会同时存在
以及什么时候应该选哪一个
```

我觉得这才是今天这部分内容真正值得记下来的地方。
