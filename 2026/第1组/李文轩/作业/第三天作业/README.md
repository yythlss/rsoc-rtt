# RT-Thread 线程间同步与通信 实验报告（Day3）

> 实验环境：RT-Thread 4.1.1 + STM32F407ZG（RSOC2026_ipc 工程，GCC/scons 编译）
> 运行方式：烧录后在 MSH 终端输入对应命令，如 `parking_demo`

| 练习 | 文件 | MSH 命令 | 核心机制 |
| --- | --- | --- | --- |
| 一、停车场车位管理 | `01_parking.c` | `parking_demo` | 计数信号量 |
| 二、多窗口售票系统 | `02_ticket.c` | `ticket_demo` | 互斥量 |
| 三、系统启动条件检查 | `03_startup.c` | `startup_demo` | 事件集（AND 模式） |
| 四、快递分拣中心 | `04_package.c` | `package_demo` | 消息队列 |

## 练习一：停车场车位管理（计数信号量）

- 3 个车位 → 计数信号量初值 3；5 辆车线程申请车位，2 秒内未获得则打印
  `carN waiting for a space` 并稍后重试；停留后释放车位。
- 信号量计数值即剩余资源数，从机制上保证同时占用车位 ≤ 3。
- 思考题：互斥量是"单持有者排他锁"，而车位是允许最多 3 个持有者的有限资源，
  计数信号量的计数值天然表示剩余资源量，适合资源池场景。

## 练习二：多窗口售票系统（互斥量）

- 窗口 A/B 共享全局余票变量，互斥量保护"检查余票 → 读票号 → 减一"完整临界区；
  售完自动退出，保证 20 张票不重号、余票不为负。
- 对比实验：将 `02_ticket.c` 中 `TICKET_USE_MUTEX` 改为 0 重新编译，
  会在读余票与减一之间出现竞争窗口，可观察到重复票号 / 余票为负。
- 思考题：只锁 `ticket_count--` 不够，因为"检查余票 > 0"与"减一"不是原子的，
  两个线程可能同时通过检查后各自减一，同一张票卖出两次、余票变 -1。

## 练习三：系统启动条件检查（事件集）

- 网络(1s)/传感器(2s)/存储(5s)三个初始化线程各自发送就绪事件位；
  主业务线程用 `RT_EVENT_FLAG_AND` 等三个位齐备。
- 超时测试：业务线程每次最多等 3s，超时后按未置位的事件位打印
  `wait modules timeout, storage is not ready`，再继续等待，直到全部就绪。
- 思考题：三个独立信号量只能分别 take，无法原子地表达"多条件同时满足"，
  且查询"哪些已完成"要逐个探测；事件集一个对象即可 AND/OR 组合 + 查询子集。

## 练习四：快递分拣中心（消息队列）

- 消息队列容量 5；send_a / send_b 各产生 5 条快递（编号 1001~1005 / 2001~2005），
  区域按 1/2/3 循环（east/south/north）；
  队列满时 `rt_mq_send` 返回失败，发送线程只计数不崩溃。
- 两个发送线程全部完成后，命令线程发送一条结束消息（region=0 标记），
  分拣线程收到后打印总数、各区域数量、总重量并退出。
- 输出示例：`package 1001 -> south, weight: 537 g`；结尾统计
  `total packages: N`、`east/south/north 计数`、`total weight: N g`、`send failed: N`。
  注：队列满会导致部分快递发送失败（不送达），因此 `total packages` 可能小于 10，
  `send failed` 反映实际失败次数（与本机调度时序有关）。

## 设计说明

- 每个命令可重复执行：任务结束后命令线程等待全部子线程完成，
  再删除 IPC 对象；运行期间重复输入命令会被拒绝（防重入标志）。
- 所有线程与 IPC 对象均检查创建结果，失败时回收已创建资源。
