# 线程间的同步与通讯

> **版本依据**：RT-Thread **4.1.1**（星火 1 号 `stm32f407-rtspark`，`RT_TICK_PER_SECOND = 1000`，1 tick = 1 ms）。
---

## 概述：同步与通讯

**同步**是指按指定的先后次序运行。**线程同步**指多个线程通过特定机制（如互斥量、事件集、临界区等）控制线程间的执行顺序；若没有同步，线程将乱序执行。

**临界区**：多个线程操作/访问的同一块区域（代码），这块代码称为临界区。**线程互斥**指对临界区资源访问的排他性——多个线程使用临界区资源时，每次只允许一个线程使用，其他线程必须等到占用者释放资源。

一个直观的例子：两个线程协作——线程 1 从传感器收数据写入共享内存，线程 2 周期性读出并显示。若不互斥，线程 2 可能在线程 1 写了一半时去读，显示的数据就是不同时刻采样值的混合，数据错乱。

RT-Thread 提供两类机制，本笔记逐一介绍：

| 类别 | 机制 | 数据能力 | 典型场景 |
| --- | --- | --- | --- |
| 同步 | 信号量 | 无（计数器） | 资源计数、锁、线程/中断同步 |
| 同步 | 互斥量 | 无（二值 + 所有权） | 保护共享资源临界区、防优先级翻转 |
| 同步 | 事件集 | 无（32 位事件标志） | 一对多 / 多对多同步、多条件汇合 |
| 通讯 | 邮箱 | 固定 4 字节（可传指针） | 少量数据、指针传递 |
| 通讯 | 消息队列 | 可变长度数据块（拷贝） | 结构化数据流 |
| 通讯 | 信号 | 异步事件通知 | 异常 / 紧急事件通知 |

进入/退出临界区除了使用上面的同步机制，还有两种最原始的手段，先介绍它们。

---

## 1. 关闭中断

进入临界区最简单的方式是**关闭中断**。当临界区可能被**中断服务程序（ISR）访问**（即线程与中断共享资源）时，必须使用关中断来互斥——因为调度机制管不住中断，中断随时会打断线程执行。

```c
/*
 * 关闭中断：进入临界区时关中断，退出时按 level 恢复原先的中断状态。
 * level 保存的是关闭中断前的中断状态值（rt_base_t），恢复时原样写回。
 */
rt_base_t level;
level = rt_hw_interrupt_disable(); /* 关闭中断，保存中断状态 */
/* 临界区代码 */
rt_hw_interrupt_enable(level);     /* 恢复中断状态 */
```

**注意**：`level` 指中断状态的保存值（关中断前的状态），必须传入 `rt_hw_interrupt_enable()` 原样恢复，不能直接"无条件开中断"（否则会破坏外层嵌套关中断的状态）。关中断期间不能长时间执行——中断被屏蔽会直接影响系统实时性（如串口接收中断延迟）。

---

## 2. 禁止调度（调度器上锁）

若临界区**只被线程访问、不会被中断服务程序访问**，则不必关中断，只需禁止线程调度即可——用 `rt_enter_critical()` 进入临界区（调度器上锁），`rt_exit_critical()` 退出临界区（调度器解锁）。

```c
/*
 * 禁止调度（调度器上锁）：进入临界区时给调度器上锁，退出时解锁。
 * 当前线程不会被其他线程抢占（禁止线程切换），但中断仍然可以响应！
 */
rt_enter_critical();  /* 调度器上锁 */
/* 临界区代码 */
rt_exit_critical();   /* 调度器解锁 */
```

## 3. 信号量（Semaphore）

### 3.1 概念介绍

用**停车场**来理解信号量：

① 停车场空位多时，管理员放行外面的车进入；
② 车位满时，管理员禁止车辆进入，车辆在外面排队等待；
③ 有车离开腾出空位后，管理员再放行等待的车辆。

在这个例子里：**管理员 = 信号量**，管理员管理的**空位数 = 信号量的 value**（非负、动态变化），**车位 = 共享资源（临界区）**，**车辆 = 线程**。车辆通过获得管理员的许可来使用车位，正如线程通过获取信号量来访问公共资源。

**工作机制**：信号量是一种轻量型内核对象，用于解决线程间的同步问题。每个信号量对象有一个**信号量值**和一个**线程等待队列**：
- 信号量值 = 资源实例的个数（值 = 5 表示有 5 个可用资源）；
- 获取（take）：值 > 0 时立即获得，值减 1；值 = 0 时，申请线程按 `time` 参数决定直接返回、挂起一段时间或永久等待，并挂到等待队列上；
- 释放（release）：有等待线程时唤醒等待队列中的第一个线程；没有等待线程时值加 1。
- 信号量最大值 **65535**（控制块中 `value` 是 `rt_uint16_t`）。

**信号量控制块**：

```c
struct rt_semaphore
{
   struct rt_ipc_object parent;  /* 继承自 IPC 对象类 */
   rt_uint16_t value;            /* 信号量值，最大 65535 */
};
typedef struct rt_semaphore *rt_sem_t;
```

**使用场合**：

1. **线程同步**：初值 0，作为"工作完成标志"——等待线程 take 挂起，完成工作的线程 release 唤醒它继续下一步；
2. **锁**：初值 1，多个线程访问同一共享资源时充当锁（值只在 0/1 间变化，故称**二值信号量**）；
3. **中断与线程的同步**：初值 0，线程 take 挂起，ISR 处理硬件后 release 唤醒线程（如 FinSH 串口中断唤醒 shell 线程）。> 注意：**中断与线程之间的互斥不能靠信号量锁，只能靠开关中断**；
4. **资源计数**：初值 N，表示 N 份资源。

### 3.2 相关 API（v4.1.1 签名，已核对源码）

| 操作 | 函数 | 说明 |
| --- | --- | --- |
| 动态创建 | `rt_sem_t rt_sem_create(const char *name, rt_uint32_t value, rt_uint8_t flag)` | 内核从堆分配对象；失败返回 `RT_NULL` |
| 静态初始化 | `rt_err_t rt_sem_init(rt_sem_t sem, const char *name, rt_uint32_t value, rt_uint8_t flag)` | 对象内存由编译器分配，使用前先初始化 |
| 获取 | `rt_err_t rt_sem_take(rt_sem_t sem, rt_int32_t time)` | time 单位是 OS Tick；`RT_WAITING_FOREVER`(-1) 永久等待，0 不等待；超时返回 `-RT_ETIMEOUT` |
| 无等待获取 | `rt_err_t rt_sem_trytake(rt_sem_t sem)` | 等价于 `rt_sem_take(sem, 0)` |
| 释放 | `rt_err_t rt_sem_release(rt_sem_t sem)` | 无等待者值加 1；有等待者唤醒队列第一个 |
| 删除 | `rt_err_t rt_sem_delete(rt_sem_t sem)` | 只用于**动态创建**的信号量，唤醒所有等待者（返回 `-RT_ERROR`） |
| 脱离 | `rt_err_t rt_sem_detach(rt_sem_t sem)` | 只用于**静态初始化**的信号量 |

`flag` 决定等待线程的排队方式：`RT_IPC_FLAG_FIFO`(0x00) 先进先出；`RT_IPC_FLAG_PRIO`(0x01) 按优先级排队。

### 3.3 两种创建方式核对（4.1.1）

- ✅ **动态**：`rt_sem_create(name, value, flag)` 正确。
- ❌ **静态**：`rt_sem_create_static(name, value, flag, sem_mem)` **在 4.1.1 中不存在**（没有这个函数）。静态信号量的正确做法是：先定义一个控制块变量（内存由编译器分配在数据段），再用 `rt_sem_init` 初始化：

```c
static struct rt_semaphore sem;                  /* ① 定义静态控制块 */
rt_sem_init(&sem, "ssem", 1, RT_IPC_FLAG_FIFO);  /* ② 初始化（对应动态版的 rt_sem_create） */
```

### 3.4 例子讲解：sem_sample（双线程乒乓同步）

```c
/* 例子：使用信号量实现线程同步——两个线程"你一步、我一步"交替执行 */
#include <rtthread.h>
static rt_thread_t tid1, tid2;
static struct rt_semaphore sem;       /* 静态信号量（控制块在数据段） */
static rt_sem_t dynamic_sem;          /* 动态信号量句柄 */

static void thread1_entry(void *parameter)
{
    while (1)
    {
        if (rt_sem_take(&sem, RT_WAITING_FOREVER) == RT_EOK) /* 等待 thread2 放行 */
        {
            rt_kprintf("thread1 take a static semaphore\n");
            rt_thread_mdelay(1000);
            rt_sem_release(&dynamic_sem);   /* 放行 thread2 */
        }
    }
}
static void thread2_entry(void *parameter)
{
    while (1)
    {
        if (rt_sem_take(&dynamic_sem, RT_WAITING_FOREVER) == RT_EOK) /* 等待 thread1 放行 */
        {
            rt_kprintf("thread2 take a dynamic semaphore\n");
            rt_thread_mdelay(1000);
            rt_sem_release(&sem);           /* 放行 thread1 */
        }
    }
}

int sem_sample(void)
{
    tid1 = rt_thread_create("thread1", thread1_entry, RT_NULL, 1024, 25, 5);
    tid2 = rt_thread_create("thread2", thread2_entry, RT_NULL, 1024, 24, 5);
    rt_sem_init(&sem, "ssem", 1, RT_IPC_FLAG_FIFO);        /* 静态信号量，初值 1 */
    dynamic_sem = rt_sem_create("dsem", 1, RT_IPC_FLAG_FIFO); /* 动态信号量，初值 1 */
    if (tid1 != RT_NULL)
        rt_thread_startup(tid1);
    if (tid2 != RT_NULL)
        rt_thread_startup(tid2);
    return RT_EOK;
}
MSH_CMD_EXPORT(sem_sample, sem sample);
```

**讲解**：

- 一个**静态**信号量 `sem`（`struct rt_semaphore` + `rt_sem_init`）和一个**动态**信号量 `dynamic_sem`（`rt_sem_create`），初值都是 1；
- 初值都为 1，所以第一轮两个线程都能拿到；之后 thread1 拿的 `sem` **只有 thread2 会释放**，thread2 拿的 `dynamic_sem` **只有 thread1 会释放**——于是两个线程被强制交替执行（乒乓同步）；
- **教学点 1**：信号量**没有所有权**——thread1 可以释放 thread2 拿走的信号量、反之亦然。这正是信号量与互斥量（第 4 节）最本质的区别；
- **教学点 2**：如果把两个初值都改成 0，双方都会在第一次 take 时永久挂起 → 死锁。用信号量做同步时，初值必须保证"先有货可拿"（要么初值 1 双方都能起步，要么一方先 release）；
- 运行输出：每秒一对、严格交替（首次先打印哪个由调度决定）：

```
thread2 take a dynamic semaphore
thread1 take a static semaphore
thread2 take a dynamic semaphore
thread1 take a static semaphore
...
```

## 4. 互斥量（Mutex）

### 4.1 概念介绍

互斥量又称**互斥型信号量**，是一种**特殊的二值信号量**。可以比喻为：**只有一个车位的停车场**——一辆车进入，闸门锁上，其他车在外面等；里面的车出来，闸门打开，下一辆车进入。

互斥量与信号量的区别：

1. **所有权（ownership）**：拥有互斥量的线程拥有它的所有权，**只能由持有它的线程释放**；而信号量可以由任意线程释放；
2. **递归持有**：同一线程可以再次获得自己已持有的互斥量而不会被挂起（持有计数 `hold` 加 1）；二值信号量递归持有会因"没有实例"而挂起，最终死锁——这是必须用互斥量而不是二值信号量的重要场景；
3. **防止优先级翻转**：互斥量通过**优先级继承**算法解决优先级反转问题。

**优先级翻转**（优先级 A > B > C 的场景）：线程 C 正在使用共享资源 M，线程 A 到来想要 M 被挂起（A 等 C）；此时线程 B 到来，因 B > C 抢占 C 一直运行——结果 A 被"更低优先级"的 B 一直阻塞，高优先级线程反而最后运行，实时性无法保证。

**优先级继承**：A 等待期间，把占用资源 M 的 C 的优先级**临时提升到 A 的优先级**（所有等待者中的最高优先级），防止 C（间接防止 A）被 B 抢占；C 释放 M 后优先级恢复原值。

**互斥量控制块**：

```c
struct rt_mutex
{
    struct rt_ipc_object parent;   /* 继承自 IPC 对象类 */
    rt_uint16_t value;             /* 互斥量值（0 锁定 / 1 未锁） */
    rt_uint8_t  original_priority; /* 持有线程的原始优先级（用于释放后恢复） */
    rt_uint8_t  hold;              /* 持有计数（递归持有次数） */
    struct rt_thread *owner;       /* 当前持有互斥量的线程 */
};
typedef struct rt_mutex *rt_mutex_t;
```

**注意事项**：

- ⚠️ **互斥量不能在中断服务程序中使用**（4.1.1 源码明确检查：`this function must not be used in interrupt even if time = 0`）；
- 获得互斥量后应尽快释放；
- 持有互斥量期间，不能修改持有线程的优先级。

### 4.2 相关 API（v4.1.1 签名，已核对源码）

| 操作 | 函数 | 说明 |
| --- | --- | --- |
| 动态创建 | `rt_mutex_t rt_mutex_create(const char *name, rt_uint8_t flag)` | 失败返回 `RT_NULL` |
| 静态初始化 | `rt_err_t rt_mutex_init(rt_mutex_t mutex, const char *name, rt_uint8_t flag)` | 对象内存由编译器分配 |
| 获取 | `rt_err_t rt_mutex_take(rt_mutex_t mutex, rt_int32_t time)` | 未占用则获得（记录 owner、original_priority）；自己已持有则 hold+1 不挂起；他人持有则挂起并触发优先级继承；超时返回 `-RT_ETIMEOUT` |
| 无等待获取 | `rt_err_t rt_mutex_trytake(rt_mutex_t mutex)` | 等价于 `rt_mutex_take(mutex, 0)` |
| 释放 | `rt_err_t rt_mutex_release(rt_mutex_t mutex)` | **只有持有者能释放**（否则返回 `-RT_ERROR`）；hold 减到 0 时先恢复持有者原优先级，再唤醒等待线程 |
| 删除 | `rt_err_t rt_mutex_delete(rt_mutex_t mutex)` | 只用于**动态创建**的互斥量 |
| 脱离 | `rt_err_t rt_mutex_detach(rt_mutex_t mutex)` | 只用于**静态初始化**的互斥量 |

> 📌 **4.1.1 特性**：`rt_mutex_init` / `rt_mutex_create` 的 `flag` 参数**已废弃**（源码中 `RT_UNUSED(flag)`，传入的值不再起作用），等待队列被**强制设为 `RT_IPC_FLAG_PRIO`**——源码注释：FIFO 排队无法解决无界优先级翻转问题。所以互斥量的等待线程**始终按优先级排队**。

### 4.3 两种创建方式核对（4.1.1）

- ✅ **动态**：`rt_mutex_create(name, flag)` 正确。
- ✅ **静态**：`rt_mutex_init(mutex, name, flag)` 正确。
- 📌 补充两点：① 4.1.1 中 flag 已废弃（见上）；② 还需注意"不能在中断中使用"的限制，这是互斥量与信号量的重要区别（信号量的 release 可在 ISR 中唤醒线程，互斥量 take/release 都不行）。

### 4.4 例子讲解：mutex_sample（优先级继承验证）

```c
/* 例子：使用互斥量演示优先级继承——低优先级线程持锁期间被提升到等待者的优先级 */
#include <rtthread.h>
static rt_thread_t tid1, tid2, tid3;
static rt_mutex_t mutex;

void thread1_entry(void *parameter)
{
    rt_kprintf("the priority of thread1 is %d\n", tid1->current_priority);
    rt_thread_mdelay(100);   /* 让低优先级线程先运行并持锁 */
    rt_kprintf("the priority of thread2 is %d\n", tid2->current_priority);
    rt_kprintf("the priority of thread3 is %d\n", tid3->current_priority); /* 应已被提升 */
    rt_kprintf("thread1 exit!\n");
}
void thread2_entry(void *parameter)
{
    rt_err_t result;
    rt_kprintf("the priority of thread2 is %d\n", tid2->current_priority);
    rt_thread_mdelay(50);    /* 让 thread3 先拿到互斥量 */
    result = rt_mutex_take(mutex, RT_WAITING_FOREVER); /* 挂起 → 触发优先级继承 */
    if (result == RT_EOK)
    {
        rt_kprintf("thread2 take a mutex\n");
        rt_mutex_release(mutex);
    }
    rt_kprintf("thread2 exit!\n");
}
void thread3_entry(void *parameter)
{
    rt_err_t res;
    rt_kprintf("the priority of thread3 is %d\n", tid3->current_priority);
    res = rt_mutex_take(mutex, RT_WAITING_FOREVER); /* 低优先级线程先拿到锁 */
    if (res == RT_EOK)
    {
        rt_kprintf("thread3 take a mutex\n");
        rt_thread_mdelay(500);  /* 长时间持锁 */
    }
    rt_mutex_release(mutex);    /* 释放时优先级被恢复 */
    rt_kprintf("the priority of thread3 is %d\n", tid3->current_priority); /* 已恢复原值 */
    rt_kprintf("thread3 exit!\n");
}

int mutex_sample(void)
{
    mutex = rt_mutex_create("mutex", RT_IPC_FLAG_FIFO);
    tid1 = rt_thread_create("thread1", thread1_entry, RT_NULL, 1024, 9, 10);  /* 最高 */
    tid2 = rt_thread_create("thread2", thread2_entry, RT_NULL, 1024, 10, 10);
    tid3 = rt_thread_create("thread3", thread3_entry, RT_NULL, 1024, 11, 10); /* 最低 */
    if (tid1 != RT_NULL) rt_thread_startup(tid1);
    if (tid2 != RT_NULL) rt_thread_startup(tid2);
    if (tid3 != RT_NULL) rt_thread_startup(tid3);
    return RT_EOK;
}
MSH_CMD_EXPORT(mutex_sample, mutex sample);
```

**讲解**（这个例子就是优先级继承的验证思路）：

- 三个线程优先级 9 / 10 / 11（数字越小优先级越高），各自用 `mdelay` 错开，让**最低优先级的 thread3 先拿到锁**；
- 时序推演：
  - t=0：thread1 运行（9 最高）→ 打印自己 9 → `mdelay(100)` 让位；
  - t=0：thread2 运行 → 打印 10 → `mdelay(50)` 让位；
  - t=0：thread3 运行 → 打印 11 → **take 成功持锁** → `mdelay(500)`；
  - t=50：thread2 醒来 take → 挂起等待 → **优先级继承生效：thread3 的 `current_priority` 被提升到 10**；
  - t=100：thread1 醒来，打印 thread2 / thread3 的优先级 → **两个都是 10** → 继承验证成功，退出；
  - t=500：thread3 醒来 release → **释放时先恢复原优先级 11**、再唤醒 thread2 → thread2 拿到锁打印、释放、退出；
  - thread3 最后打印自己的优先级 → **11（已恢复）** → 退出。
- 预期输出：

```
the priority of thread1 is 9
the priority of thread2 is 10
the priority of thread3 is 11
thread3 take a mutex
the priority of thread2 is 10
the priority of thread3 is 10        ← 优先级继承：被提升到 thread2 的优先级
thread1 exit!
thread2 take a mutex
thread2 exit!
the priority of thread3 is 11        ← 释放锁后恢复原始优先级
thread3 exit!
```

## 5. 事件集（Event）

### 5.1 概念介绍

用**等公交车**来理解事件集（P1 出行看作线程，"车到站""P2 到站"看作事件发生）：

1. **特定事件唤醒**：只有某一路公交车能到目的地，P1 等那一辆车；
2. **任一事件唤醒（OR）**：3 路公交车都能到，任一到达即可出发；
3. **多个事件同时发生才唤醒（AND）**：P1 要等"P2 到站"**且**"车到站"两个条件都满足。

**工作机制**：事件集主要用于**一对多、多对多**的线程同步。一个 32 位无符号整数表示事件集合，**每一位代表一个事件**；线程通过"逻辑与"或"逻辑或"关联多个事件——逻辑或又称独立型同步（线程与任一事件同步），逻辑与又称关联型同步（线程与若干事件同步）。

**事件集的三大特点**：

1. 事件只与线程相关、事件之间相互独立：每个线程可拥有 32 个事件标志（32 位无符号整数，每位一个事件）；
2. **事件仅用于同步，不提供数据传输功能**；
3. **事件不排队**：同一事件被多次发送（线程还没来得及读取），等效于只发送一次。

**事件信息标记**（三个属性，可组合）：

| 宏 | 值（v4.1.1 rtdef.h） | 语义 |
| --- | --- | --- |
| `RT_EVENT_FLAG_AND` | 0x01 | 逻辑与：所有等待的事件位都置位才唤醒 |
| `RT_EVENT_FLAG_OR` | 0x02 | 逻辑或：任一等待的事件位置位即唤醒 |
| `RT_EVENT_FLAG_CLEAR` | 0x04 | 唤醒后自动清除已满足的事件位（一次性消费） |

**事件集控制块**：

```c
struct rt_event
{
    struct rt_ipc_object parent;   /* 继承自 IPC 对象类 */
    rt_uint32_t set;               /* 事件集合：每一位代表一个事件 */
};
typedef struct rt_event *rt_event_t;
```

**与信号量的本质区别**：事件的**发送不可累积**（清除前重复发送无效），而信号量的**释放可累积**；但事件集可以**一次等待多个事件**（AND 模式），信号量只能识别单次释放、无法同时等待多种释放。

### 5.2 相关 API（v4.1.1 签名，已核对源码）

| 操作 | 函数 | 说明 |
| --- | --- | --- |
| 动态创建 | `rt_event_t rt_event_create(const char *name, rt_uint8_t flag)` | 失败返回 `RT_NULL` |
| 静态初始化 | `rt_err_t rt_event_init(rt_event_t event, const char *name, rt_uint8_t flag)` | 对象内存由编译器分配 |
| 发送 | `rt_err_t rt_event_send(rt_event_t event, rt_uint32_t set)` | 置位 set 中指定的事件位，唤醒条件匹配的等待线程 |
| 接收 | `rt_err_t rt_event_recv(rt_event_t event, rt_uint32_t set, rt_uint8_t option, rt_int32_t timeout, rt_uint32_t *recved)` | 按 option 等待 set 中的事件；`recved` 返回满足条件时的事件位；超时返回 `-RT_ETIMEOUT`；timeout = 0 不等待 |

`option` 常用组合：`RT_EVENT_FLAG_OR | RT_EVENT_FLAG_CLEAR`（来一个处理一个）、`RT_EVENT_FLAG_AND | RT_EVENT_FLAG_CLEAR`（全部到齐才继续）。

- ✅ **动态**：`rt_event_create(name, flag)` 正确。
- ✅ **静态**：`rt_event_init(event, name, flag)` 正确。
- ✅ `rt_event_recv(event, EVENT_SET_3 | EVENT_SET_5, RT_EVENT_FLAG_OR | RT_EVENT_FLAG_CLEAR, ...)` 的组合合法（0x02 | 0x04 = 0x06），4.1.1 中有效。

### 5.4 例子讲解：event_sample（OR 收单、AND 收全）

```c
/* 例子：使用事件集——thread1/thread2 分别发送事件 3/5，thread3 先 OR 收任一、再 AND 收全部 */
#include <rtthread.h>
#define EVENT_SET_3 (1 << 3)
#define EVENT_SET_5 (1 << 5)
rt_event_t event;
rt_thread_t tid1, tid2, tid3;

void thread1_entry(void *parameter)
{
    while (1)
    {
        rt_thread_mdelay(1000);
        rt_kprintf("thread1 send event set 3\n");
        rt_event_send(event, EVENT_SET_3);  /* 每 1s 发送事件 3 */
    }
}
void thread2_entry(void *parameter)
{
    while (1)
    {
        rt_thread_mdelay(2500);
        rt_kprintf("thread2 send event set 5\n");
        rt_event_send(event, EVENT_SET_5);  /* 每 2.5s 发送事件 5 */
    }
}
void thread3_entry(void *parameter)
{
    rt_uint32_t recved;
    while (1)
    {
        if (rt_event_recv(event, EVENT_SET_3 | EVENT_SET_5,
                          RT_EVENT_FLAG_OR | RT_EVENT_FLAG_CLEAR,
                          RT_WAITING_FOREVER, &recved) == RT_EOK)   /* 任一事件 → 返回并清除 */
        {
            rt_kprintf("thread3 : OR recv event 0x%08x\n", recved);
        }
        if (rt_event_recv(event, EVENT_SET_3 | EVENT_SET_5,
                          RT_EVENT_FLAG_AND | RT_EVENT_FLAG_CLEAR,
                          RT_WAITING_FOREVER, &recved) == RT_EOK)   /* 两个都要 → 返回并清除 */
        {
            rt_kprintf("thread3 : AND recv event 0x%08x\n", recved);
        }
    }
}

int event_sample(void)
{
    event = rt_event_create("event", RT_IPC_FLAG_PRIORITY);
    tid1 = rt_thread_create("thread1", thread1_entry, RT_NULL, 1024, 20, 10);
    tid2 = rt_thread_create("thread2", thread2_entry, RT_NULL, 1024, 21, 10);
    tid3 = rt_thread_create("thread3", thread3_entry, RT_NULL, 1024, 22, 10);
    if (tid1 != RT_NULL) rt_thread_startup(tid1);
    if (tid2 != RT_NULL) rt_thread_startup(tid2);
    if (tid3 != RT_NULL) rt_thread_startup(tid3);
    return RT_EOK;
}
MSH_CMD_EXPORT(event_sample, event sample);
```

**讲解**：

- thread1 每 1s 发事件 3，thread2 每 2.5s 发事件 5；thread3 先 **OR|CLEAR** 等"任一事件"，再 **AND|CLEAR** 等"两个都到齐"；
- 时序推演：t=1s 事件 3 → OR 命中（打印 `0x00000008`，位 3 被清除）；随后 AND 等待 → t=2s 事件 3 再置位（缺事件 5，不满足）→ t=2.5s 事件 5 → **AND 命中（打印 `0x00000028` = 位 3 + 位 5，两位都被清除）**；之后每轮循环重复此节奏；
- **教学点 1**：OR 模式"来一个处理一个"，AND 模式"全部到齐才继续"，对应等公交车例子的 ②③ 场景；
- **教学点 2**：CLEAR 的"一次性消费"语义——若不清除，t=2s 置位的事件 3 会一直保留，AND 条件可能被"历史事件"提前满足；
- **教学点 3**：事件不排队——thread1 每隔 1s 发送的事件 3 在两次接收之间多次置位，等效只置位一次，与信号量"release 累积计数"形成对比。

## 6. 邮箱（Mailbox）

### 6.1 概念介绍

典型例子：线程 1 检测按键状态发"邮件"，线程 2 读邮件根据按键状态控制 LED；发送方还可以扩展多个（线程 1 发按键状态、线程 2 发 ADC 信息，接收线程按信息类型分别处理）。

**工作机制**：邮箱是 RT-Thread 用于线程间通信的机制，特点是**开销低、效率高**。每封邮件**固定 4 字节**（32 位系统上 4 字节正好放一个指针，因此一封邮件可承载一个指针）：

- 线程或中断服务程序都可以发邮件；**非阻塞发送模式可安全地在 ISR 中使用**（中断、定时器向线程发消息的有效方式）；
- 接收一般可阻塞：邮箱空且 timeout 不为 0 时，接收线程挂起等待；
- **邮箱满**时，发送方可选择挂起等待（带超时）或直接返回 `-RT_EFULL`；邮箱空时接收方同样可挂起等待或超时返回 `-RT_ETIMEOUT`。

**邮箱控制块**：

```c
struct rt_mailbox
{
    struct rt_ipc_object parent;
    rt_uint32_t *msg_pool;            /* 邮箱缓冲区起始地址 */
    rt_uint16_t size;                 /* 邮箱容量（邮件条数） */
    rt_uint16_t entry;                /* 邮箱中已有的邮件数 */
    rt_uint16_t in_offset, out_offset;/* 缓冲区入/出指针 */
    rt_list_t suspend_sender_thread;  /* 发送线程的挂起等待队列 */
};
typedef struct rt_mailbox *rt_mailbox_t;
```

**传递大数据**：4 字节装不下大块数据时，把**指向缓冲区的指针**当邮件发送（示例）：

```c
struct msg
{
    rt_uint8_t *data_ptr;    /* 数据块起始地址 */
    rt_uint32_t data_size;   /* 数据块大小 */
};
/* 发送端：malloc 一块内存，把指针发出去 */
msg_ptr = (struct msg *)rt_malloc(sizeof(struct msg));
rt_mb_send(mb, (rt_uint32_t)msg_ptr);
/* 接收端：收到指针，处理完后释放内存 */
if (rt_mb_recv(mb, (rt_uint32_t *)&msg_ptr, RT_WAITING_FOREVER) == RT_EOK)
    rt_free(msg_ptr);
```

### 6.2 相关 API（v4.1.1 签名，已核对源码）

| 操作 | 函数 | 说明 |
| --- | --- | --- |
| 动态创建 | `rt_mailbox_t rt_mb_create(const char *name, rt_size_t size, rt_uint8_t flag)` | `size` = 邮件条数；内核自动分配 `4 × size` 字节缓冲 |
| 静态初始化 | `rt_err_t rt_mb_init(rt_mailbox_t mb, const char *name, void *msgpool, rt_size_t size, rt_uint8_t flag)` | 缓冲由用户提供；**msgpool 为 N 字节时，容量 size 应为 N/4** |
| 发送（非阻塞） | `rt_err_t rt_mb_send(rt_mailbox_t mb, rt_ubase_t value)` | 可在 ISR 中使用；邮箱满返回 `-RT_EFULL` |
| 发送（可等待） | `rt_err_t rt_mb_send_wait(rt_mailbox_t mb, rt_ubase_t value, rt_int32_t timeout)` | 邮箱满时挂起等待空位，超时返回 `-RT_ETIMEOUT` |
| 接收 | `rt_err_t rt_mb_recv(rt_mailbox_t mb, rt_ubase_t *value, rt_int32_t timeout)` | 邮箱空时挂起 / 超时返回 `-RT_ETIMEOUT` |
| 删除 | `rt_err_t rt_mb_delete(rt_mailbox_t mb)` | 只用于**动态创建**的邮箱 |
| 脱离 | `rt_err_t rt_mb_detach(rt_mailbox_t mb)` | 只用于**静态初始化**的邮箱 |

> 📌 4.1.1 中邮件内容类型为 `rt_ubase_t`（早期文档写作 `rt_uint32_t`，两者在 32 位平台上等价，但以 4.1.1 头文件为准）。

### 6.3 两种创建方式核对（4.1.1）

- ✅ **动态**：`rt_mb_create(name, size, flag)` 正确。
- ✅ **静态**：`rt_mb_init(mb, name, msgpool, size, flag)` —— 函数名与参数顺序正确，但注意参数类型应为 **`rt_mailbox_t mb`**（而不是 `rt_mailbox`）（`struct rt_mailbox` 的句柄 typedef 是 `rt_mailbox_t`，源码签名统一用它）。`rt_mb_send`/`rt_mb_recv`/`rt_mb_detach` 同理。
- ⚠️ **例子代码里的容量 bug**：`char mailbox_pool[MAILBOX_SIZE]` 只有 **5 字节**，而 `sizeof(mailbox_pool)/4 = 5/4 = 1` → 邮箱实际容量是 **1 封**，不是 `MAILBOX_SIZE` 本意的 5 封。按邮箱容量规则（缓冲 N 字节 → 容量 N/4），应改为：

```c
char mailbox_pool[MAILBOX_SIZE * 4];   /* 20 字节 → 容量 5 封 */
```

（修正前的代码能跑通纯属巧合：发送方每 1s 才发一封、接收方一直阻塞等待，永远追得上；若发送变密集，容量为 1 的邮箱会立刻 `-RT_EFULL`。）

### 6.4 例子讲解：mailbox_sample（指针邮件）

```c
/* 例子：使用邮箱通信——发送方把字符串的"指针"当邮件发出，接收方按指针打印内容 */
#include <rtthread.h>
#include <string.h>
#define MAILBOX_SIZE 5
struct rt_mailbox test_mb;
char mailbox_pool[MAILBOX_SIZE * 4];    /* 修正：20 字节，容量 5 封 */
rt_thread_t tid1, tid2;

char test_str1[] = "this is a first mail!";
char test_str2[] = "this is a second mail!";
char test_str3[] = "over!";

void thread1_entry(void *parameter)
{
    rt_thread_mdelay(1000);
    rt_mb_send(&test_mb, (rt_ubase_t)test_str1);   /* 发的"邮件"是字符串的地址 */
    rt_thread_mdelay(1000);
    rt_mb_send(&test_mb, (rt_ubase_t)test_str2);
    rt_thread_mdelay(1000);
    rt_mb_send(&test_mb, (rt_ubase_t)test_str3);   /* 结束标志 */
}
void thread2_entry(void *parameter)
{
    rt_err_t result;
    char *recv_str;
    while (1)
    {
        result = rt_mb_recv(&test_mb, (rt_ubase_t *)&recv_str, RT_WAITING_FOREVER);
        if (result == RT_EOK)
        {
            rt_kprintf("thread2 : recv mail %s\n", recv_str);
            if (strcmp(recv_str, test_str3) == 0)
            {
                rt_kprintf("thread2 : recv mail over!\n");
                break;
            }
        }
        else
        {
            rt_kprintf("thread2 : recv mail failed!\n");
        }
    }
    rt_mb_detach(&test_mb);    /* 静态邮箱用 detach 脱离 */
}

int mailbox_sample(void)
{
    rt_mb_init(&test_mb, "test_mb", mailbox_pool,
               sizeof(mailbox_pool) / 4, RT_IPC_FLAG_FIFO);  /* 静态初始化，容量 = 字节数/4 */
    tid1 = rt_thread_create("thread1", thread1_entry, RT_NULL, 1024, 20, 10);
    tid2 = rt_thread_create("thread2", thread2_entry, RT_NULL, 1024, 21, 10);
    if (tid1 != RT_NULL) rt_thread_startup(tid1);
    if (tid2 != RT_NULL) rt_thread_startup(tid2);
    return RT_EOK;
}
MSH_CMD_EXPORT(mailbox_sample, mailbox sample);
```

**讲解**：

- 邮箱控制块 `test_mb` 是**静态对象**（`struct rt_mailbox` + `rt_mb_init`），缓冲区 `mailbox_pool` 由用户定义，容量 = 字节数/4；
- 三封"邮件"实际上是三个字符串的**指针**（`(rt_ubase_t)test_str1` 强转）——正是邮箱"4 字节放指针"的用法。本例指针指向全局字符串数组（永远有效），所以接收方不需要释放；更高级的用法是发 `rt_malloc` 的缓冲区指针，**接收方处理完必须 `rt_free`**；
- thread2 阻塞接收，收到 `"over!"` 后退出并 `rt_mb_detach`——静态对象用 detach、动态对象用 delete，两者不要混用；
- **与消息队列的分工**：邮箱每封只有 4 字节，只能传指针（大块数据要另开内存，还要操心谁释放）；消息队列直接拷贝整个数据块，省掉内存管理负担——见下一节。

## 7. 消息队列（Message Queue）

### 7.1 概念介绍

**消息队列是邮箱的扩展**，用于线程间交换**不定长度**的消息，是一种**异步通信**方式：线程或 ISR 把消息放入队列缓存，其他线程从队列读出；队列空时读线程挂起，新消息到达后被唤醒。多个消息先入先出（**FIFO**）。

**内部结构**：创建消息队列时分配一块内存，组织成消息链表——`msg_queue_head` / `msg_queue_tail` 是消息链表头尾，`msg_queue_free` 是**空闲消息块链表**。发送时从空闲链表取一块、**拷贝**消息内容、挂到队列尾；接收时把队首消息转回空闲链表。总消息块数 = 队列长度（创建时指定）。

**消息队列控制块**：

```c
struct rt_messagequeue
{
    struct rt_ipc_object parent;
    void *msg_pool;            /* 存放消息的缓冲区指针 */
    rt_uint16_t msg_size;      /* 每条消息的长度（字节） */
    rt_uint16_t max_msgs;      /* 最大可容纳的消息条数 */
    rt_uint16_t entry;         /* 队列中已有的消息数 */
    void *msg_queue_head;      /* 消息链表头 */
    void *msg_queue_tail;      /* 消息链表尾 */
    void *msg_queue_free;      /* 空闲消息链表 */
};
typedef struct rt_messagequeue *rt_mq_t;
```

**数据拷贝语义**（与邮箱的本质区别）：消息队列**直接拷贝数据内容**，接收线程把消息收进自己的局部变量即可，**无需动态内存分配、也无需操心释放**；而邮箱传指针时，数据内存要留给接收线程释放。对比两种写法：同样一个 `struct msg`，邮箱只能发"指向该结构的指针"（接收方处理完要 `rt_free`），消息队列直接 `rt_mq_send(mq, &msg_ptr, sizeof(struct msg))` 把结构体整个拷进去。

**其他要点**：

- **紧急消息** `rt_mq_urgent`：与普通发送唯一区别是插入**队首**（而不是队尾），接收方优先收到，用于需要及时处理的消息；
- 队列满：发送返回 `-RT_EFULL`（**不会崩溃**，由调用方决定重试或丢弃）；发送长度超过 `msg_size`：返回 `-RT_ERROR`；
- **同步消息**用法：在消息结构里内嵌一个邮箱或信号量做"确认"标志，实现"发送后等待确认"；
- 当所有消息长度都是 4 字节时，消息队列退化为邮箱。

### 7.2 相关 API（v4.1.1 签名，已核对源码）

| 操作 | 函数 | 说明 |
| --- | --- | --- |
| 动态创建 | `rt_mq_t rt_mq_create(const char *name, rt_size_t msg_size, rt_size_t max_msgs, rt_uint8_t flag)` | 给**每条消息长度 + 最大条数**，内核自动分配内存 |
| 静态初始化 | `rt_err_t rt_mq_init(rt_mq_t mq, const char *name, void *msgpool, rt_size_t msg_size, rt_size_t pool_size, rt_uint8_t flag)` | 内存由用户提供；第 5 参数是**缓冲区字节数** `pool_size` |
| 发送 | `rt_err_t rt_mq_send(rt_mq_t mq, const void *buffer, rt_size_t size)` | 队满返回 `-RT_EFULL`；`size` 大于 `msg_size` 返回 `-RT_ERROR` |
| 发送（可等待） | `rt_err_t rt_mq_send_wait(rt_mq_t mq, const void *buffer, rt_size_t size, rt_int32_t timeout)` | 队满时挂起等待 |
| 紧急发送 | `rt_err_t rt_mq_urgent(rt_mq_t mq, const void *buffer, rt_size_t size)` | 插到队首，优先被接收 |
| 接收 | `rt_err_t rt_mq_recv(rt_mq_t mq, void *buffer, rt_size_t size, rt_int32_t timeout)` | 队空挂起；超时返回 `-RT_ETIMEOUT` |
| 删除 | `rt_err_t rt_mq_delete(rt_mq_t mq)` | 只用于**动态创建**的消息队列 |
| 脱离 | `rt_err_t rt_mq_detach(rt_mq_t mq)` | 只用于**静态初始化**的消息队列 |

> 📌 4.1.1 中 `rt_mq_send` / `rt_mq_urgent` 的 buffer 参数是 `const void *buffer`（发送不改源数据）。

### 7.3 两种创建方式核对（4.1.1）

- ✅ **动态**：`rt_mq_create(name, msg_size, max_msgs, flag)` 正确。
- ❌ **静态**：`rt_mq_init(mq, name, start, msg_size, max_msgs, flag)` 的**第 5 参数错了**。4.1.1 源码签名是：

```c
rt_err_t rt_mq_init(rt_mq_t     mq,
                    const char *name,
                    void       *msgpool,
                    rt_size_t   msg_size,
                    rt_size_t   pool_size,   /* ← 内存池字节数，不是消息条数！ */
                    rt_uint8_t  flag)
```

  动态创建时给"条数"（内核自己算内存 = (msg_size + 链表头) × max_msgs），静态初始化时给"缓冲区字节数"（内存是用户分配的）。
- ✅ 例子核对：`rt_mq_create("mq", sizeof(struct msg), 2, RT_IPC_FLAG_FIFO)`（msg_size = 101、max_msgs = 2）正确；`rt_mq_send(mq, &send_msg, sizeof(struct msg))` 发送长度必须与创建时的 `msg_size` 一致（101 == 101）正确。

### 7.4 例子讲解：mq_sample（结构化消息收发）

```c
/* 例子：使用消息队列传递结构化数据——字符串消息与二进制消息都能搬 */
#include <rtthread.h>
#include <string.h>
rt_mq_t mq;
rt_thread_t tid1, tid2;

char test_str1[] = "this is a first message!";
rt_uint8_t test_str2[] = {0x11, 0x22, 0x33, 0x44};

struct msg
{
    rt_uint8_t data[100];
    rt_uint8_t len;
};

void thread1_entry(void *parameter)
{
    struct msg send_msg;
    send_msg.len = strlen(test_str1);
    strcpy((char *)send_msg.data, test_str1);
    rt_mq_send(mq, &send_msg, sizeof(struct msg));  /* 第一条：字符串消息（101 字节整体拷贝） */
    rt_thread_mdelay(1000);
    send_msg.len = sizeof(test_str2);
    memcpy(send_msg.data, test_str2, send_msg.len);
    rt_mq_send(mq, &send_msg, sizeof(struct msg));  /* 第二条：二进制消息 */
}
void thread2_entry(void *parameter)
{
    struct msg recv_msg;
    rt_err_t result;
    char flag = 0;
    while (1)
    {
        result = rt_mq_recv(mq, &recv_msg, sizeof(struct msg), RT_WAITING_FOREVER);
        if (result == RT_EOK)
        {
            if (flag == 0)
            {
                rt_kprintf("thread2 : recv message %s\n", recv_msg.data);
                rt_kprintf("thread2 : recv message length %d\n", recv_msg.len);
                flag = 1;
            }
            else
            {
                rt_kprintf("thread2 : recv message ");
                for (rt_uint8_t i = 0; i < recv_msg.len; i++)
                    rt_kprintf("0x%02x ", recv_msg.data[i]);
                rt_kprintf("\n");
                rt_kprintf("thread2 : recv message length %d\n", recv_msg.len);
                flag = 0;
                break;
            }
        }
        else
        {
            rt_kprintf("thread2 : recv message failed!\n");
        }
    }
}

int mq_sample(void)
{
    mq = rt_mq_create("mq", sizeof(struct msg), 2, RT_IPC_FLAG_FIFO);  /* 每条 101 字节 × 2 条 */
    tid1 = rt_thread_create("thread1", thread1_entry, RT_NULL, 1024, 20, 5);
    tid2 = rt_thread_create("thread2", thread2_entry, RT_NULL, 1024, 21, 5);
    if (tid1 != RT_NULL) rt_thread_startup(tid1);
    if (tid2 != RT_NULL) rt_thread_startup(tid2);
    return RT_EOK;
}
MSH_CMD_EXPORT(mq_sample, message queue sample);
```

**讲解**：

- `struct msg` 共 101 字节（data[100] + len），队列容量 2 条。发送时 `sizeof(struct msg)` 与创建时的 `msg_size` 一致，接收同理——不一致会返回 `-RT_ERROR`；
- 第一条消息用 `strcpy`/`strlen` 装字符串、按 `%s` 打印；第二条用 `memcpy` 装 `0x11 0x22 0x33 0x44`、按 `0x%02x` 逐字节打印——展示消息队列**能传递任意二进制数据**（不依赖 `'\0'` 结尾，也不要求可打印）；
- **拷贝语义**：thread2 的 `recv_msg` 是普通局部变量，消息从队列**拷进**局部变量，不需要 `rt_free`——与邮箱"传指针、接收方释放"形成对比；
- 预期输出：

```
thread2 : recv message this is a first message!
thread2 : recv message length 25
thread2 : recv message 0x11 0x22 0x33 0x44
thread2 : recv message length 4
```

## 8. 附：信号（Signal）

作为通讯机制的补充，RT-Thread 还提供**信号**：

**什么是信号**：信号又称**软中断信号**，从软件上模拟中断机制——线程收到信号，如同处理器收到中断请求。用于线程间**异步通知**（异常、紧急事件）；线程无需专门等待信号的到来，具有异步性。RT-Thread 中 `rt_sigset_t` 定义为 `unsigned long`，应用可用的信号为 `SIGUSR1(10)` 和 `SIGUSR2(12)`。

**处理方式**（三类）：

1. 类似中断处理程序——安装用户自定义处理函数，信号到来时调用；
2. `SIG_IGN`——忽略该信号，当它没发生；
3. `SIG_DFL`——使用系统默认处理。

**工作流程**：线程先 `rt_signal_install` 安装信号处理函数并 `rt_signal_unmask` 解除屏蔽；其他线程用 `rt_thread_kill` 向它发送信号。信号送达时：若线程挂起则转为就绪去处理；若正在运行，则在**当前线程栈上新建栈帧**处理（线程栈占用会相应增加）。

| 操作 | 函数 | 说明 |
| --- | --- | --- |
| 安装信号 | `rt_sighandler_t rt_signal_install(int signo, rt_sighandler_t handler)` | handler 可为自定义函数 / `SIG_IGN` / `SIG_DFL`；返回安装前的处理函数 |
| 屏蔽信号 | `void rt_signal_mask(int signo)` | 被屏蔽的信号不会送达，不产生软中断 |
| 解除屏蔽 | `void rt_signal_unmask(int signo)` | 解除屏蔽后信号才会送达线程 |
| 发送信号 | `int rt_thread_kill(rt_thread_t tid, int sig)` | 向指定线程发送信号 |
| 等待信号 | `int rt_signal_wait(const rt_sigset_t *set, rt_siginfo_t *si, rt_int32_t timeout)` | 信号未到时挂起，超时返回 `-RT_ETIMEOUT` |

## 9. 小结：六种 IPC 机制选型对照

| 机制 | 类别 | 数据能力 | 关键语义 | 动态 / 静态 | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| 信号量 | 同步 | 无（计数 0~65535） | 无所有权，任意线程可释放；release 可累积 | `rt_sem_create` / `rt_sem_init` | 资源计数（停车场）、事件计数、线程/中断同步 |
| 互斥量 | 同步 | 无（二值 + 所有权） | 只有持有者可释放；支持递归持有；优先级继承防翻转；**不能用于中断**；4.1.1 中 flag 废弃、等待队列固定按优先级 | `rt_mutex_create` / `rt_mutex_init` | 保护共享变量临界区（售票）、防优先级翻转 |
| 事件集 | 同步 | 无（32 位标志） | 一对多 / 多对多；AND / OR / CLEAR；发送不累积（不排队） | `rt_event_create` / `rt_event_init` | 多条件汇合（三模块就绪）、可超时诊断缺失项 |
| 邮箱 | 通讯 | 固定 4 字节（可传指针） | 开销低；非阻塞发送可在中断中使用；队满 `-RT_EFULL`；传指针时接收方负责释放 | `rt_mb_create` / `rt_mb_init` | 少量数据 / 指针传递（按键状态、缓冲地址） |
| 消息队列 | 通讯 | 可变长度数据块（拷贝） | 数据整体拷贝，接收方无需释放；FIFO；支持紧急消息插队首；队满 `-RT_EFULL` | `rt_mq_create` / `rt_mq_init` | 结构化数据流（快递分拣）、可变长度数据 |
| 信号 | 通讯 | 异步事件通知 | 软中断；安装 / 屏蔽 / 发送 / 等待 | — | 异常、紧急事件异步通知 |

**选型口诀**：

- 保护共享资源 / 锁 → **互斥量**（要所有权、要防优先级翻转）；
- 数 N 份资源 / 事件计数 → **计数信号量**（无所有权要求）；
- 同时等多个条件、想知道"缺哪个" → **事件集**（AND/OR + 读位诊断）；
- 传 4 字节小数据或指针 → **邮箱**（开销最低）；
- 传结构化 / 变长数据 → **消息队列**（拷贝语义省内存管理）；
- 线程间异步"打断"通知 → **信号**。

**静态与动态的统一规律**（本笔记所有核对项的核心）：

```
动态：rt_xxx_create(...) 创建（内核从堆分配内存）  →  用完 rt_xxx_delete()
静态：定义控制块变量（编译器分配内存）→ rt_xxx_init(...) 初始化  →  用完 rt_xxx_detach()
```

（互斥量 4.1.1 例外：flag 参数已废弃；消息队列静态初始化第 5 参数是 `pool_size` 字节数，与动态版的 `max_msgs` 条数不同。）

### 10.2 思考题解答

**思考题一（练习一）：为什么停车场使用计数信号量，而不是互斥量？**

1. **计数能力**：互斥量是二值对象（锁定/未锁定），只能表示"一个资源可用"；停车场有 3 个车位，需要 0~3 的计数状态，信号量初值 3 天然表达"剩余车位"，每 take/release 一次就是车位减一/加一；
2. **所有权语义不匹配**：互斥量要求"谁持有谁释放"，而车位场景中"占位"与"释放"可以来自任意车辆（任何一辆车离开都让出一个车位），信号量无所有权限制，语义完全匹配；
3. **开销与误用风险**：互斥量附带优先级继承、递归计数等机制，解决的是"锁"场景的问题；资源计数用不上这些特性，反而增加开销，且若误用（车辆释放了不属于自己的"锁"）会破坏语义。

**思考题二（练习二）：为什么只给 `ticket_count--` 加锁仍可能不安全？**

售票的完整过程是"检查余票 → 记录票号 → 修改余票"三步。只锁 `ticket_count--`：

1. **检查与修改分离（check-then-act 竞态）**：两个窗口可能同时在锁外读到余票 = 1，都认为"有票"，进入临界区后都售出同一张票（重复售票），随后两次 `ticket_count--` 使余票变成 -1；
2. **锁保护不了"基于过期读值的判断"**：`ticket_count--` 加锁只保证减操作本身原子，但"该不该减"的判断发生在锁外——锁不能保证减的操作对象是合法的。

结论：互斥的粒度必须覆盖整个事务（判断 + 修改），这就是把互斥量放在 while 循环里包裹完整售票过程的原因。

**思考题三（练习三）：如果用三个独立信号量实现这个功能，与使用事件集相比有什么区别？**

1. **等待顺序问题**：三个信号量下业务线程必须按固定顺序 take（先 net 再 sensor 再 storage），无法"同时等待三个条件"；而模块就绪顺序不定，要么被迫等待不必要的串行延迟，要么为每种顺序写分支；
2. **无法诊断缺失项**：信号量 take 超时只返回"超时"，无法得知"到底哪个模块没就绪"（无法区分 value=0 的到底是哪一个）；事件集超时后可用 OR 非清除模式读位，精确报告 `storage is not ready`；
3. **广播语义**：事件一次 `rt_event_send` 可同时唤醒多个等待者，而一个信号量 release 只唤醒一个等待者；多业务线程等待同一条件时事件集更自然；
4. **事件集的代价**：事件位只有置位/清除、没有计数——同一事件连续发生 N 次无法区分 N 次；若条件需要"计数 N 次"语义，信号量仍是正确选择。本场景是"全部就绪"的布尔条件，事件集语义完全匹配。
