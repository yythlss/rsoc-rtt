# RT-Thread 夏令营第四天学习笔记

## 1. 本日学习目标

1. 理解 RT-Thread 设备框架为什么要提供统一的设备模型；
2. 掌握 GPIO/PIN 设备从应用 API 到芯片 HAL 的分层调用链；
3. 区分字符设备和块设备的访问特征；
4. 理解设备注册、查找、打开、读写、控制和关闭的生命周期；
5. 认识回调函数、操作函数表和中断通知在驱动框架中的作用；
6. 自主设计一个不依赖真实硬件的虚拟设备框架层 `test_dev`；
7. 使用 Shell 自测命令验证设备边界、统计和清空行为。

## 2. 设备驱动框架的意义

### 2.1 厂商 API 差异

STM32、NXP、TI 和其他 MCU 对 GPIO、SPI、I2C、UART 的寄存器和 HAL API 都不相同。如果业务代码直接调用厂商库，代码会同时承担设备逻辑和芯片适配工作，复用性很低。

设备框架的基本思路是：

```text
应用层统一 API
  -> RT-Thread 设备模型
  -> BSP/总线适配层
  -> 厂商 HAL 或寄存器
  -> 具体硬件
```

上层只关心“打开哪个设备、读写什么数据、发送什么控制命令”，底层负责把统一操作转换成具体芯片动作。迁移到另一款 MCU 时，主要替换 BSP 和驱动适配层。

### 2.2 RT-Thread 的设备模型

设备对象通常包含：

- 设备类型和名称；
- 打开标志、引用计数和用户数据；
- `init/open/close/read/write/control` 操作回调；
- 可选的接收通知和发送完成回调；
- 面向总线设备的配置参数和操作函数表。

设备通过 `rt_device_register()` 加入 I/O 管理系统链表，应用通过 `rt_device_find()` 按名称查找。标准生命周期可以概括为：

```text
创建或静态定义
  -> 初始化
  -> rt_device_register
  -> rt_device_find
  -> rt_device_open
  -> read/write/control
  -> rt_device_close
```

`open` 和 `close` 通常配合引用计数使用。驱动不能在第一次关闭前释放仍被其他调用者使用的资源。

## 3. 字符设备与块设备

| 类型 | 访问特征 | 示例 |
| --- | --- | --- |
| 字符设备 | 按字节流或顺序数据访问，通常不强调随机寻址 | 串口、键盘、传感器、终端 |
| 块设备 | 按固定块或扇区随机寻址，常带容量和擦除约束 | SD 卡、Flash、硬盘 |

本次 `test_dev` 使用字符设备注册方式，但在逻辑上模拟了一段可按偏移读写的内存。这样既能练习 RT-Thread 字符设备接口，又能观察 `pos`、容量和越界截断等块式访问特征。

## 4. GPIO/PIN 设备访问

### 4.1 引脚配置与电平操作

```c
rt_pin_mode(pin, PIN_MODE_OUTPUT);
rt_pin_write(pin, PIN_HIGH);
rt_base_t level = rt_pin_read(pin);
```

输入引脚需要根据电路选择浮空、上拉或下拉模式；输出引脚需要区分推挽和开漏。开漏输出只能主动拉低，释放高电平依赖外部上拉，适合 I2C 等共享线场景。

### 4.2 PIN API 的分层调用

```text
用户程序
  -> rt_pin_mode / rt_pin_write / rt_pin_read
  -> pin_device 统一接口
  -> pin_ops 操作函数表
  -> STM32 GPIO/EXTI 驱动
  -> HAL_GPIO_WritePin 等底层实现
```

这种调用链的价值在于，上层不需要知道 GPIOA、GPIOB 的寄存器地址，也不需要处理每个芯片独有的时钟使能细节。

### 4.3 PIN 中断

按键中断的典型配置过程：

```c
rt_pin_mode(key_pin, PIN_MODE_INPUT_PULLUP);
rt_pin_attach_irq(key_pin,
                  PIN_IRQ_MODE_FALLING,
                  key_irq_callback,
                  RT_NULL);
rt_pin_irq_enable(key_pin, PIN_IRQ_ENABLE);
```

回调中不应执行复杂业务，不应长时间阻塞，也不应无条件连续打印。更稳妥的做法是：

```text
中断回调
  -> 记录按键事件/释放信号量
  -> 工作线程等待并消抖
  -> 读取稳定电平
  -> 执行 LED、菜单或设备控制
```

### 4.4 按键消抖

机械触点在切换时会产生数毫秒的抖动。若不消抖，下降沿中断可能连续触发多次。延时消抖、软件定时器消抖和 button 软件包都可以解决这一问题，但中断本身应保持轻量。

## 5. `test_dev` 虚拟设备框架

### 5.1 设计动机

真实硬件驱动需要板卡、引脚和外设才能验证。为了先验证设备框架逻辑，`test_dev` 用数组模拟设备存储区，不依赖任何外部硬件：

```text
容量 256 字节
支持按偏移读写
支持清空和状态查询
支持统计读写次数与字节数
支持越界截断
```

这使得设备注册、生命周期、错误处理和并发保护可以在没有传感器或 Flash 芯片的情况下单独测试。

### 5.2 文件职责

```text
test_dev.h
  -> 对外常量、结构体和函数声明

test_dev.c
  -> 虚拟设备对象、RAM 后端、互斥锁、统计
  -> RT-Thread 回调适配和 INIT_DEVICE_EXPORT

test_dev_demo.c
  -> MSH 命令 test_dev_run
  -> 自动化读写、边界和清空验证

SConscript
  -> 将 test_dev 源码加入工程构建
```

当前实现把核心和内存后端放在同一 C 文件中，便于阅读；接口已经按设备层和后端行为分开，后续可以拆成多个文件。

### 5.3 统一接口

```c
int test_dev_start(void);
rt_err_t test_dev_open(void);
rt_err_t test_dev_close(void);
rt_int32_t test_dev_read(rt_off_t pos, void *buffer, rt_size_t size);
rt_int32_t test_dev_write(rt_off_t pos, const void *buffer, rt_size_t size);
rt_err_t test_dev_control(int command, void *args);
```

RT-Thread 回调只做适配：

```text
rt_device_read
  -> test_dev_rtt_read
  -> test_dev_read
  -> RAM 数据区
```

这样以后把 RAM 换成 SPI Flash，应用层仍可以使用 `rt_device_read()` 和 `rt_device_write()`。

### 5.4 互斥量保护

设备内部共享以下数据：

- 256 字节内存；
- `used` 有效长度；
- 打开次数；
- 读写次数和累计字节数。

每次打开、关闭、读、写和控制操作都先获取互斥量，完成状态更新后释放。锁的范围覆盖完整的“检查-修改-统计”逻辑，避免出现读写数据和统计数据不一致。

### 5.5 控制命令

```c
TEST_DEV_CMD_CLEAR
TEST_DEV_CMD_INFO
TEST_DEV_CMD_RESET_STATS
```

清空命令改变数据状态，信息命令把当前状态复制到 `struct test_dev_info`，复位统计命令只影响计数器。控制命令统一使用整数编号，便于未来继续增加擦除、只读模式或后端切换操作。

## 6. 自测流程

启动后执行：

```text
list_device
test_dev_run
```

`test_dev_run` 的验证路径：

```text
open
  -> clear
  -> write(pos=12, size=4)
  -> read(pos=12, size=4)
  -> compare
  -> write(pos=254, size=4)
  -> info(used == 256)
  -> clear
  -> info(used == 0)
  -> empty read == 0
  -> close
```

预期输出：

```text
test_dev_run: PASS
```

这里的 `PASS` 只代表自测条件通过，不代表已经验证真实 SPI、I2C 或 GPIO 电气特性。

## 7. 驱动设计中的错误处理

本次代码重点处理了以下错误：

| 情况 | 处理 |
| --- | --- |
| 负偏移 | 返回 `-RT_EINVAL` |
| 空缓冲区 | 返回 `-RT_EINVAL` |
| 零长度 | 返回 `-RT_EINVAL` |
| 未打开设备 | 读写返回 0 |
| 偏移达到容量 | 不访问数组，返回 0 |
| 写入超过末尾 | 截断并返回实际长度 |
| 空控制参数 | 返回 `-RT_EINVAL` |
| 未知控制命令 | 返回 `-RT_ENOSYS` |
| 未匹配的 close | 返回错误 |

驱动接口不能只关心成功路径。调用者需要通过返回值判断设备是否存在、是否打开成功、是否完整完成传输以及是否需要重试。

## 8. 本日总结

今天的重点是把“调用一个 GPIO API”提升为“理解一套设备框架”：

- PIN API 屏蔽了芯片 GPIO 寄存器和 HAL 差异；
- `rt_device` 用统一生命周期管理不同类别的设备；
- 操作函数指针把框架和具体硬件实现连接起来；
- 中断回调负责快速通知，复杂业务交给线程处理；
- 虚拟设备可以在没有真实硬件时验证驱动接口和边界；
- 互斥量、返回值检查和生命周期管理决定了驱动是否可靠。
