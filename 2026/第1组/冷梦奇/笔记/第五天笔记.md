## 一、 软件包生态与索引机制

### 1.1 什么是软件包生态
软件包（Software Package）是 RT-Thread 官方及社区开发者贡献的功能模块集合，涵盖了传感器驱动、网络协议栈、安全组件、多媒体 GUI、AI 算法等诸多领域。
- **避免重复造轮子**：开发者无需从零编写芯片时序和复杂协议；
- **配置即引入**：在 Studio 或 `menuconfig` 图形界面中勾选后即可自动拉取源码并完成工程工程化集成。

### 1.2 软件包索引与 Kconfig 机制
- **配置路径**：软件包的 Kconfig 描述文件维护在 `RT-Thread Studio/env/packages` 路径下；
- **版本隔离机制**：针对内核版本 5.1.0 以上和以下分别维护独立配置，保证依赖兼容性；
- **更新索引**：执行 `pkgs --upgrade` 可从官方镜像同步最新软件包索引，执行 `pkgs --update` 可下载选中的软件包源码到 `packages/` 目录。

### 1.3 软件包集成两步法
1. **配置使能**：在图形配置中勾选目标软件包及其版本；
2. **依赖管理**：关注软件包的依赖关系（例如：`aht10` 依赖 Sensor 框架；`kawaii-mqtt` 依赖 SAL / Socket 网络层）。

## 二、 AHT10 传感器驱动与避坑实战

### 2.1 标准 API 调用流程
```c
/* 1. 初始化传感器：指定挂载的 I2C 总线名称 (如 "i2c3") */
aht10_device_t dev = aht10_init("i2c3");
if (dev == RT_NULL) {
    LOG_E("AHT10 初始化失败!");
}

/* 2. 读取温湿度数值 */
float temp = aht10_read_temperature(dev); // 获取温度 (℃)
float humi = aht10_read_humidity(dev);    // 获取湿度 (%RH)
```

### 2.2 浮点格式化打印避坑 (`rt_vsnprintf_full`)
- **踩坑现象**：使用 `rt_kprintf("%.2f", temp)` 出现乱码、异常字符或无输出；
- **原因剖析**：RT-Thread 默认的轻量级 libc 为了节省 ROM/RAM 资源，裁剪了对浮点格式化的支持；
- **解决方案**：在软件包菜单中启用 **`rt_vsnprintf_full`** 软件包，开启完整的 `printf` 格式化引擎，即可原生支持 `%f`、`%.2f` 输出。

### 2.3 线程封装与 MSH 命令导出
将周期性采集封装为独立后台线程，并通过 `MSH_CMD_EXPORT` 导出命令行入口，既可后台常驻运行，又方便串口调试：
```c
MSH_CMD_EXPORT(day5_start, Start Day5 AHT10 + MQTT + FileSystem task);
```

## 三、 RW007 SPI WiFi 模块网络接入

### 3.1 引脚配置与硬件对齐
RW007 是一款基于 SPI 总线的高速 WiFi 模块：
- **引脚对齐**：必须对照开发板原理图仔细核对 CS（片选）、BOOT0、BOOT1、INT/BUSY、RST 引脚的 GPIO 编号；
- **星火一号配置**：SPI2 总线，CS: `PG10` (90), BOOT0: `PB13` (29), INT: `PG11` (107), RST: `PG15` (111)。

### 3.2 常用网络诊断命令
```bash
# 扫描周围 WiFi 热点
wifi scan

# 连接无线路由器
wifi connect SSID PASSWORD

# 查看网卡 IP 与网关信息
ifconfig

# 测试外网连通性
ping broker.emqx.io
```

## 四、 MQTT 协议与设备上云通信

### 4.1 MQTT 通信模型与核心概念
MQTT（Message Queuing Telemetry Transport）是一种基于 TCP/IP 的轻量级发布/订阅模式消息传输协议：
- **Broker（消息代理）**：服务端核心，负责路由分发报文（本实验使用开源公共 Broker `broker.emqx.io:1883`）；
- **Client（客户端）**：星火一号开发板与 PC 端调试助手（如 MQTTX）；
- **Topic（主题）**：消息路由通道，如 `rtt-pub0721`（板卡上报）与 `rtt-sub0721`（云端控制）。

### 4.2 QoS 等级与应用选型
| QoS 等级 | 语义 | 特点 | 适用场景 |
|---|---|---|---|
| **QoS 0** | 最多交付一次 | 无确认、开销极低、可能丢包 | 高频环境温湿度上报 |
| **QoS 1** | 至少交付一次 | 需 ACK 确认、可能重复 | 远程控制指令、告警通知 |
| **QoS 2** | 恰好交付一次 | 四次握手、开销最高、绝不重复 | 计费交易、固件升级包 |

### 4.3 `kawaii-mqtt` 客户端实战
`kawaii-mqtt` 是专为嵌入式环境打造的高稳定性 MQTT 客户端库：
```c
/* 1. 申请客户端句柄并配置连接参数 */
mqtt_client_t *client = mqtt_lease();
mqtt_set_host(client, "broker.emqx.io");
mqtt_set_port(client, "1883");
mqtt_set_client_id(client, "spark_rsoc_day5_lmq");
mqtt_set_clean_session(client, 1);

/* 2. 建立连接并订阅主题 */
mqtt_connect(client);
mqtt_subscribe(client, "rtt-sub0721", QOS0, cloud_msg_callback);

/* 3. 构造报文并发布 */
mqtt_message_t msg;
msg.qos = QOS0;
msg.payload = "{\"temperature\":26.35,\"humidity\":54.20,\"count\":1}";
mqtt_publish(client, "rtt-pub0721", &msg);
```

## 五、 DFS 虚拟文件系统与 Flash 管理

### 5.1 存储体系架构 (POSIX - DFS - FatFS - FAL - SFUD)
```text
应用层 POSIX API (open / read / write / close)
      │
      ▼
RT-Thread DFS 虚拟文件系统 (统一 VFS 目录树)
      │
      ▼
具体文件系统 (Elm-FatFS / RomFS)
      │
      ▼
FAL Flash 抽象层 (font / filesystem 分区)
      │
      ▼
SFUD 通用驱动 (读写擦除指令统一)
      │
      ▼
物理硬件 (板载 W25Q64 Nor Flash)
```

### 5.2 SFUD 与 FAL 的职责划分
- **SFUD（Serial Flash Universal Driver）**：解决“**如何与具体 Flash 芯片物理通信**”的问题，自动探测芯片参数；
- **FAL（Flash Abstraction Layer）**：解决“**如何将物理 Flash 划分为逻辑分区**”的问题，向文件系统提供标准的块设备视图。

### 5.3 分区表配置与自动挂载流程
1. `FAL_PART_TABLE` 中定义分区大小与偏移（如 `font` 分区 3MB，`filesystem` 分区 3MB）；
2. 根目录挂载 `romfs`，建立 `/font` 静态节点；
3. 调用 `fal_blk_device_create("font")` 在 `font` 分区上注册块设备；
4. 调用 `dfs_mount("font", "/font", "elm", 0, 0)` 完成挂载；若未格式化则自动触发 `dfs_mkfs`。

### 5.4 SPI 总线多从机片选冲突避坑
- **痛点现象**：挂载文件系统后 WiFi 无法联网，或 WiFi 工作时 Flash 读写超时；
- **根本原因**：W25Q64 与 RW007 **共用 SPI2 硬件总线**，当某从机的片选（CS）引脚处于浮空或低电平时，会非法占用总线；
- **黄金法则**：多从机共用 SPI 总线时，未使用的设备片选引脚在初始化阶段**必须显式拉高**（高电平表示未选中）。

### 5.5 POSIX 标准文件操作接口
```c
/* 打开文件：追加写入模式 */
int fd = open("/font/Data.txt", O_WRONLY | O_CREAT | O_APPEND, 0666);
if (fd >= 0) {
    write(fd, buf, len);
    close(fd);
}
```

## 六、 疑难问题与排错心得总结

1. **环境版本匹配**：
   RT-Thread 内核版本、env 工具版本与 Studio 插件版本需保持一致，避免因构建脚本不匹配导致宏定义丢失；
2. **Flash 挂载开箱自愈机制**：
   在应用代码中加入“挂载失败 $\rightarrow$ 自动格式化 $\rightarrow$ 重新挂载”的状态机逻辑，能够避免全新板卡因未格式化而启动失败；
3. **云端指令健壮性处理**：
   在 MQTT 消息回调中，解析 payload 时务必根据 `payloadlen` 显式补充 `\0` 字符串结束符，避免发生数组越界访问。
