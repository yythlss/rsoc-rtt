## 一、 线程同步底层基础概念

在进入各类 IPC 对象之前，必须牢固建立以下四个底层核心概念：

| 核心概念 | 机制与工作原理 | 关键注意事项 |
| :--- | :--- | :--- |
| **临界区（Critical Section）** | 一段访问独占共享资源的代码，任何时刻最多只能有一个执行流进入。进入前上锁/关中断，离开后解锁/开中断。 | 必须保持简短，严禁在临界区内长时间延时或执行高耗时 I/O。 |
| **阻塞（Blocking）** | 线程因等待 IPC 资源不可用而主动让出 CPU 控制权，内核将其移出就绪队列并加入该 IPC 对象的挂起等待队列。 | **零浪费 CPU 时间片**，是 RTOS 高效运行的基石。 |
| **非阻塞（Non-blocking）** | 调用 API 时若资源不可用立即返回错误码（如 `-RT_ETIMEOUT`），线程不挂起。 | **中断服务程序（ISR）中必须强制使用非阻塞调用**。 |
| **挂起（Suspend）** | 线程处于暂停执行状态，等待特定事件、信号量、消息到达或定时器到期后由内核唤醒。 | 唤醒后重新按优先级排入系统就绪队列。 |

> 💡 **核心精髓**：IPC 的本质就是利用内核的 **“阻塞 + 唤醒”** 机制，让多线程安全、有序地协调对共享资源与事件的访问，彻底替代裸机系统中低效消耗 CPU 的“忙等轮询（Busy-Waiting）”。

## 二、 信号量（Semaphore）

### 2.1 概念与分类

信号量是内核维护的一个非负整数计数值 `value` 与挂起等待队列。`take`（获取）时计数值减 1，`release`（释放）时计数值加 1；当计数值为 0 时，`take` 操作将导致线程阻塞。

```text
               ┌───────────────────────────────────────────┐
               │         Semaphore (内部计数 value)         │
               └─────────────────────┬─────────────────────┘
                                     │
         ┌───────────────────────────┴───────────────────────────┐
         ▼                                                       ▼
   【二值信号量】 (初值 0 或 1)                               【计数信号量】 (初值 N)
 典型用途: 单一事件通知 / 中断到线程同步                   典型用途: 有限共享资源池配额管理
 (初始 0 -> 等待阻塞; 触发 1 -> 唤醒处理)                  (如 3 个车位、5 个动态缓冲区)
```

### 2.2 核心 API

```c
/* 动态创建 / 删除 */
rt_sem_t rt_sem_create(const char *name, rt_uint32_t value, rt_uint8_t flag);
rt_err_t rt_sem_delete(rt_sem_t sem);

/* 静态初始化 / 脱离 */
rt_err_t rt_sem_init(rt_sem_t sem, const char *name, rt_uint32_t value, rt_uint8_t flag);
rt_err_t rt_sem_detach(rt_sem_t sem);

/* 获取 / 释放 */
rt_err_t rt_sem_take(rt_sem_t sem, rt_int32_t time);  /* time: RT_WAITING_FOREVER / 0 / 超时(ms) */
rt_err_t rt_sem_trytake(rt_sem_t sem);                /* 尝试获取（非阻塞，等同于 time = 0） */
rt_err_t rt_sem_release(rt_sem_t sem);                /* 释放信号量，value+1 并唤醒阻塞线程 */
```

## 三、 互斥量（Mutex）

### 3.1 概念与核心特性

互斥量是一种特殊的二值信号量，专用于保护临界区数据的一致性。与普通二值信号量相比，互斥量具备两大杀手级特性：

1. **严格所有权（Ownership）与递归嵌套**：
   - 互斥量记录持有者线程（`owner`）；只有持锁的线程才能释放锁。
   - 支持同一线程**递归加锁**（内部计数 `hold` 递增），不会引起自身死锁，退出时需成对释放。
2. **优先级继承机制（Priority Inheritance）**：
   - **优先级反转（Priority Inversion）隐患**：低优先级线程持有锁 $\rightarrow$ 中优先级线程抢占 CPU $\rightarrow$ 高优先级线程因等待锁被无限期拖延。
   - **优先级继承解决之道**：当高优先级线程等待低优先级线程持有的锁时，内核**动态临时提升**低优先级线程的优先级至高优先级线程的水平；待其释放锁后，立即恢复原初始优先级。

```text
【优先级反转与优先级继承对比时序】：
普通信号量 (发生反转):
高优先级 (H) :  ───────────────[等待锁阻塞]──────────────────────> [被严重推迟]
中优先级 (M) :         ┌───────────抢占 CPU 运行──────────┐
低优先级 (L) :  ──[拿锁]┴─────────────────────────────────┴──[放锁]──>

互斥量 (优先级继承):
高优先级 (H) :  ──────────[等锁]───────[唤醒执行]───────>
低优先级 (L) :  ──[拿锁]──[临时升至H级]──[放锁并降级]───────>
中优先级 (M) :                          └─[此时才轮到M运行]─>
```

### 3.2 核心 API

```c
rt_mutex_t rt_mutex_create(const char *name, rt_uint8_t flag);
rt_err_t   rt_mutex_delete(rt_mutex_t mutex);

rt_err_t   rt_mutex_take(rt_mutex_t mutex, rt_int32_t time);
rt_err_t   rt_mutex_release(rt_mutex_t mutex);
```

## 四、 事件集（Event Set）

### 4.1 概念与位图掩码

事件集使用一个 **32 位无符号整型（`rt_uint32_t`）** 记录事件标志，每一位代表一个二值事件（`1U << 0` ~ `1U << 31`）。支持**一对多**与**多对多**的多条件逻辑同步。

### 4.2 接收模式与选项

| 模式宏定义 | 功能说明 | 适用场景 |
| :--- | :--- | :--- |
| `RT_EVENT_FLAG_OR` | 关心的事件位中**任意一个**置 1 即被唤醒（逻辑或） | 多个中断/事件任意触发处理 |
| `RT_EVENT_FLAG_AND` | 关心的事件位**全部同时置 1** 才被唤醒（逻辑与） | 多模块协同就绪、系统启动前置条件检查 |
| `RT_EVENT_FLAG_CLEAR` | 成功被唤醒后，自动将匹配到的事件位清零 | 防止重复触发 |

### 4.3 核心 API

```c
rt_event_t rt_event_create(const char *name, rt_uint8_t flag);
rt_err_t   rt_event_delete(rt_event_t event);

rt_err_t   rt_event_send(rt_event_t event, rt_uint32_t set);
rt_err_t   rt_event_recv(rt_event_t event,
                         rt_uint32_t set,
                         rt_uint8_t  option,
                         rt_int32_t  timeout,
                         rt_uint32_t *recved);
```

## 五、 数据传递：消息邮箱 vs 消息队列

信号量、互斥量、事件集解决的是**同步**与**控制**；要在线程间传递**具体数据载荷**，则使用邮箱或消息队列。

### 5.1 消息邮箱（Mailbox）
- **特点**：传递**固定 4 字节**消息（传递指针或数值），内存占用极低、开销极小。
- **ISR 友好**：`rt_mb_send` 通常无阻塞，特别适合在中断服务程序中向后台工作线程发送数据指针。

### 5.2 消息队列（Message Queue）
- **特点**：接收**不定长**消息（创建时指定单条消息最大字节数 `msg_size`），内部通过环形缓冲区或链表管理。
- **值拷贝（Copy-by-Value）**：发送时将整个结构体内容拷贝进内核缓冲区，接收时拷贝出，发送方局部变量在发送完成后可立即安全释放或复用。
- **紧急消息插队（`rt_mq_urgent`）**：支持将高优先级/紧急消息直接插入队列头部，实现优先分拣与应急响应。

### 5.3 邮箱 vs 消息队列对比矩阵

| 比较维度 | 消息邮箱 (Mailbox) | 消息队列 (Message Queue) |
| :--- | :--- | :--- |
| **消息载荷长度** | 固定 4 字节（通常为指针/数值） | 不定长（由 `msg_size` 决定，如结构体） |
| **内存机制** | 4 字节简单环形数组 | 缓冲池链表 / 环形内存区 |
| **数据传递方式** | 引用传递（指针）或单字数值 | 值拷贝（Copy-by-Value） |
| **紧急消息插队** | ❌ 不支持 | ✅ 支持（`rt_mq_urgent` 插入队头） |
| **典型适用场景** | ISR $\rightarrow$ 线程指针通知、状态码传递 | 结构化报文、传感器数据包、生产者-消费者模型 |

## 七、 嵌入式实战避坑指南

1. **ISR（中断上下文）黄金禁忌**：
   - 中断不是线程，无法被挂起，**严禁在 ISR 中调用带有阻塞等待的 API**（如 `rt_thread_mdelay`、`rt_sem_take(sem, timeout > 0)`、`rt_mutex_take` 等）；
   - ISR 中只能调用**非阻塞版本**的发送 API（如 `rt_sem_release`、`rt_event_send`、`rt_mb_send`、`rt_mq_send` 且 timeout 为 0）。
2. **Check-then-Act 复合原子性**：
   - 保护共享变量时，必须将“读取检查 + 修改数据 + 业务处理”整体圈入同一把 Mutex 临界区中，切忌只对 `count--` 局部加锁。
3. **资源生命周期与防重入**：
   - 在 MSH 导出的测试命令中，应建立运行态互斥标志并在演示结束时显式调用 `delete` 销毁 IPC 对象，确保反复执行命令时系统稳定可靠。
