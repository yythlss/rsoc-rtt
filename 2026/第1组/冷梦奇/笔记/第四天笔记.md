## 一、 为什么需要设备驱动框架？

### 1. 传统单片机开发的烦恼
以前我们写 51 单片机或 STM32 裸机时：
- 要点个灯，直接去操作 `GPIO_SetBits(GPIOA, GPIO_Pin_5)`；
- 要发个串口数据，直接调用 `HAL_UART_Transmit(...)`。

这种写法虽然直观，但有一个致命缺点：**代码写死在某一家芯片上了**。假如老板突然说：“STM32 涨价了，我们改用 GD32 或者国产芯片”，那我们之前写的所有点灯、串口、传感器代码，全部都要推倒重写！

### 2. 生动的比喻：Type-C 接口与万能遥控器
RT-Thread 的解决办法就是建立一套**统一的设备管理标准**：
- **就像手机统一用 Type-C 充电口**：不管是华为、小米还是苹果，充电线插头都是标准的 Type-C（统一的 API：`open / read / write / close`）。手机内部具体的充电电路（底层硬件驱动）由各个手机厂商自己去搞定。
- **就像万能电视遥控器**：遥控器上面只有“开机、关机、加音量、减音量”几个固定按键（统一的 `ops` 接口）。索尼电视和海信电视各自去响应这些按键。

在 RT-Thread 看来，**所有的硬件外设都是一个“设备对象（`rt_device`）”**：
- 想操作串口？`rt_device_find("uart1")` $\rightarrow$ `rt_device_write(...)`
- 想操作自己写的设备？`rt_device_find("test_dev")` $\rightarrow$ `rt_device_write(...)`

无论底层是什么芯片，**上层应用代码一模一样，100% 轻松复用！**

## 二、 设备框架的 3 层结构

RT-Thread 把设备操作分成了清清爽爽的 3 层：

```text
┌─────────────────────────────────────────────────────────────┐
│                 1. 应用层 (Application Layer)               │
│   我们写业务逻辑的地方，调用通用的 rt_device_open / read / write  │
└──────────────────────────────┬──────────────────────────────┘
                               │ 统一接口
┌──────────────────────────────▼──────────────────────────────┐
│             2. I/O 设备管理层 (I/O Device Manager)          │
│   系统的大管家：负责根据名字找设备、记录设备打开次数、把命令分发下去│
└──────────────────────────────┬──────────────────────────────┘
                               │ 驱动操作集 (ops)
┌──────────────────────────────▼──────────────────────────────┐
│                3. 底层驱动层 (Hardware Driver Layer)        │
│   直接跟具体芯片打交道，负责操作 STM32 的 HAL 库和硬件寄存器     │
└─────────────────────────────────────────────────────────────┘
```

## 三、 PIN 设备驱动是如何一层层对接的？

PIN 设备就是我们最常用的 **GPIO 引脚设备**。

### 1. 形象的比喻：点餐与后厨
- **顾客（应用层）**：跟前台说“我要一份 5 号引脚输出低电平”（调用 `rt_pin_write(pin, PIN_LOW)`）；
- **前台管家（PIN 框架层 `pin.c`）**：在菜单里查到点菜对应的后厨厨师（调用 `_hw_pin.ops->pin_write`）；
- **主厨（驱动层 `drv_gpio.c`）**：计算出这是 GPIOF 端口的第 9 号引脚，动手炒菜（调用 `HAL_GPIO_WritePin` 写入寄存器）。

---

### 2. 详细调用链跟踪

```text
第 1 步：应用层调用
rt_pin_write(pin, PIN_LOW)
  │
  ▼
第 2 步：框架层转接 (components/drivers/misc/pin.c)
_hw_pin.ops->pin_write(&_hw_pin.parent, pin, PIN_LOW)
  │
  ▼
第 3 步：驱动层实现 (drivers/drv_gpio.c)
stm32_pin_write(...)
  ├── PIN_STPORT(pin) -> 算出对应的是 GPIOF 端口
  └── PIN_STPIN(pin)  -> 算出对应的是 GPIO_PIN_9 引脚
  调用 STM32 HAL 库: HAL_GPIO_WritePin(GPIOF, GPIO_PIN_9, GPIO_PIN_RESET)
  │
  ▼
第 4 步：硬件生效
芯片内部向 GPIOF->BSRR 寄存器写入数据，引脚电平瞬间变低！
```

### 3. 按键中断是怎样工作的？

平时我们用按键有两种方法：
1. **轮询法（死等）**：在 `while(1)` 里不停地读引脚电平，非常浪费 CPU；
2. **中断法（推荐）**：平时不管，当按键被按下的那一瞬间，硬件自动触发中断，系统立刻去执行我们写好的**回调函数**。

```c
/* 按键中断回调函数 */
static void key_callback(void *args)
{
    rt_kprintf(">> 按键被按下了! <<\n");
}

int key_init(void)
{
    /* 1. 设置引脚为上拉输入 (平时高电平，按下变低电平) */
    rt_pin_mode(KEY_PIN, PIN_MODE_INPUT_PULLUP);

    /* 2. 绑定下降沿中断 (高电平变低电平的瞬间触发) */
    rt_pin_attach_irq(KEY_PIN, PIN_IRQ_MODE_FALLING, key_callback, RT_NULL);

    /* 3. 开启中断 */
    rt_pin_irq_enable(KEY_PIN, PIN_IRQ_ENABLE);
    return 0;
}
```

## 四、 动手实操：自制虚拟设备 `test_dev`

为了彻底掌握设备框架，我们亲自动手实现了一个名叫 **`test_dev`** 的虚拟内存字符设备：

### 1. 核心原理
我们在内存中定义一个数组 `char s_buffer[64]`，用户向 `test_dev` 写入数据时就存进数组，从 `test_dev` 读取数据时就从数组拷贝出来。

### 2. 只需要实现 6 个基础函数：
1. **`test_dev_init`**：初始化设备，清空缓冲区；
2. **`test_dev_open`**：打开设备；
3. **`test_dev_close`**：关闭设备；
4. **`test_dev_read`**：读数据；
5. **`test_dev_write`**：写数据；
6. **`test_dev_control`**：控制设备（如清空缓冲区）。

### 3. 注册设备：
```c
int test_dev_register(void)
{
    s_test_dev.type    = RT_Device_Class_Char;
    s_test_dev.init    = test_dev_init;
    s_test_dev.open    = test_dev_open;
    s_test_dev.close   = test_dev_close;
    s_test_dev.read    = test_dev_read;
    s_test_dev.write   = test_dev_write;
    s_test_dev.control = test_dev_control;

    /* 注册为 "test_dev" */
    return rt_device_register(&s_test_dev, "test_dev", RT_DEVICE_FLAG_RDWR);
}
INIT_DEVICE_EXPORT(test_dev_register);
```

### 4. 运行验证效果：
在串口终端输入 `test_dev_sample`：
```text
msh >test_dev_sample

--- 开始测试 test_dev 设备 ---
[test_dev] 2. 设备已打开 (open)
[test_dev] 3. 写入数据 16 字节
[test_dev] 4. 读出数据 16 字节
>> 从设备中读出的字符串: [hello rt-thread] <<
[test_dev] 5. 设备已关闭 (close)
--- test_dev 测试成功! ---
```

## 五、 今日学习收获

1. **不再害怕操作系统设备驱动**：原来设备驱动框架就是定义好统一的结构体和函数指针，并不神秘；
2. **理解了 C 语言的面向对象**：通过 `struct rt_device` 和函数指针表，纯 C 语言也能实现漂亮的面向对象多态；
3. **打通了从上层应用到硬件底层的全过程**：以后遇到任何外设问题，都能顺着调用链一层层单步排查！
