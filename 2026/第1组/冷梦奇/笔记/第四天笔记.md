## 一、 为什么要做设备驱动框架（分层抽象的设计哲学）

### 1.1 传统裸机驱动的痛点
在传统的嵌入式开发中，应用层往往直接调用芯片厂商的固件库（如 STM32 HAL 库的 `HAL_GPIO_WritePin` / `HAL_UART_Transmit`）。这会导致以下三大严重缺陷：
1. **代码复用率极低**：应用程序与特定硬件紧密耦合，牵一发而动全身；
2. **跨平台移植成本高昂**：当项目更换 MCU 选型（例如由 STM32 切换为 GD32、NXP 或 ESP32）时，所有外设读写代码必须全盘重写；
3. **系统碎片化严重**：团队协作中不同模块开发者对外设的操作习惯各异，缺乏统一的标准规范。

### 1.2 RT-Thread 三层设备驱动抽象架构
RT-Thread 的解法是引入**分层抽象模型**，由上至下划分为三层：

```text
┌─────────────────────────────────────────────────────────────┐
│                 应用层 (Application Layer)                  │
│   使用统一的标准 API (open / read / write / control / close)  │
└──────────────────────────────┬──────────────────────────────┘
                               │ 统一标准 I/O 接口 (rt_device_*)
┌──────────────────────────────▼──────────────────────────────┐
│             I/O 设备管理层 (I/O Device Manager)              │
│   提供设备注册、统一查找、引用计数管理及 ops 虚函数指针分发     │
└──────────────────────────────┬──────────────────────────────┘
                               │ 面向对象 ops 操作集 (struct rt_xxx_ops)
┌──────────────────────────────▼──────────────────────────────┐
│                底层驱动层 (Hardware Driver Layer)            │
│   实现具体硬件外设的 ops 函数集 (STM32 HAL / 寄存器 / 中断)   │
└─────────────────────────────────────────────────────────────┘
```

- **架构演进历程**：RT-Thread 设备框架最早从 SPI 统一 API 起步，逐步演化为完备的统一 **I/O 设备管理层**，将类 Unix 的标准抽象理念引入实时操作系统。
- **核心收益**：**应用层代码 100% 保持不变**，换芯片只需编写底层驱动并挂接 `ops` 函数指针，大幅降低学习与移植成本。

## 二、 设备分类与面向对象核心数据结构

### 2.1 设备类型划分

RT-Thread 内核将硬件设备归纳为两大主要流派及专用总线/网络设备：

| 设备类型 | 数据流特征 | 随机寻址 | 典型设备 |
| :--- | :--- | :--- | :--- |
| **字符设备 (Char Device)** | 按**字节流**顺序读写，数据不可回溯 | ❌ 不支持 | 串口 (UART)、GPIO (PIN)、按键、各类传感器、I2C/SPI 从机 |
| **块设备 (Block Device)** | 以**固定块 (Block/Sector)** 为单位传输 | ✅ 支持 | SD 卡、SPI Flash (W25Qxx)、NAND/NOR Flash、eMMC |

### 2.2 设备基类结构体 `struct rt_device`

在 RT-Thread 内核中，所有设备都是一个 `rt_device` 对象，采用 C 语言结构体内嵌实现“面向对象继承”：

```c
struct rt_device
{
    struct rt_object          parent;        /* 继承内核基类 (name, type, flag, list) */
    enum rt_device_class_type type;          /* 设备类型 (字符、块、网络、PIN、I2C 等) */
    rt_uint16_t               flag;          /* 设备标志 (RDWR/INT_RX/DMA_TX 等) */
    rt_uint16_t               open_flag;     /* 打开模式 (RT_DEVICE_OFLAG_RDWR 等) */
    rt_uint8_t                ref_count;     /* 引用计数 (只有归零 close 才会真正释放硬件) */
    rt_uint8_t                device_id;     /* 设备 ID */

    /* 异步通信回调函数指针 */
    rt_err_t (*rx_indicate)(rt_device_t dev, rt_size_t size);
    rt_err_t (*tx_complete)(rt_device_t dev, void *buffer);

#ifdef RT_USING_DEVICE_OPS
    const struct rt_device_ops *ops;         /* 驱动操作函数指针集合 (新版规范) */
#else
    /* 经典模式的操作函数指针 */
    rt_err_t  (*init)   (rt_device_t dev);
    rt_err_t  (*open)   (rt_device_t dev, rt_uint16_t oflag);
    rt_err_t  (*close)  (rt_device_t dev);
    rt_size_t (*read)   (rt_device_t dev, rt_off_t pos, void *buffer, rt_size_t size);
    rt_size_t (*write)  (rt_device_t dev, rt_off_t pos, const void *buffer, rt_size_t size);
    rt_err_t  (*control)(rt_device_t dev, int cmd, void *args);
#endif

    void                     *user_data;     /* 驱动私有数据指针 (指向硬件状态上下文) */
};
```

## 三、 I/O 设备生命周期与异步回调机制

### 3.1 设备的完整生命周期

```text
┌─────────────────┐      rt_device_register()     ┌─────────────────┐
│ 创建/静态初始化 ├──────────────────────────────>│   挂载已注册    │
└─────────────────┘                               └────────┬────────┘
                                                           │
                                            rt_device_open() (ref_count++)
                                                           │
                                                           ▼
┌─────────────────┐      rt_device_close()        ┌─────────────────┐
│  完全关闭释放   │<──────────────────────────────┤   打开就绪态    │
└─────────────────┘      (当且仅当 ref_count==0)   │  (read / write) │
                                                  └─────────────────┘
```

1. **注册与查找**：
   - 驱动层调用 `rt_device_register(dev, "name", flags)` 将设备挂载进系统对象容器；
   - 注册成功后，可在 FinSH 控制台运行 **`list_device`** 实时查看系统中所有已注册设备及其引用计数；
   - 应用层调用 `rt_device_find("name")` 按名称检索并获取设备句柄。
2. **引用计数管理（Reference Counting）**：
   - 多任务并发环境下，多个线程可同时 `open` 同一设备，每次 `open` 内部 `ref_count + 1`；
   - 每次 `close` 时 `ref_count - 1`，**只有当引用计数降至 0 时，才会真正调用底层 `ops->close` 关闭物理硬件**。

### 3.2 异步回调与中断通知链（自底向上）

在中断接收或 DMA 发送完成等非阻塞异步场景下，为避免上层线程忙等轮询浪费 CPU，采用**事件驱动回调链**：

```text
【底层硬件中断触发】 (如 EXTI 下降沿 / 串口 RXNE)
        │
        ▼
【硬件中断服务程序 (ISR)】 清除中断标志，提取暂存数据
        │
        ▼
【触发上层注册的回调函数】 dev->rx_indicate(dev, size)
        │
        ▼
【回调函数执行 (如释放二值信号量 / 发送邮箱)】
        │
        ▼
【内核调度器唤醒阻塞的工作线程】 线程安全调用 rt_device_read() 提取数据处理
```

- **中断上下文核心禁忌**：**严禁在中断服务函数（ISR）或 `rx_indicate` 回调中调用任何可能导致线程挂起阻塞的 API（如 `rt_thread_mdelay()`、`rt_mutex_take()` 等）**。

## 四、 GPIO / PIN 设备驱动对接全景剖析

GPIO 外设在 RT-Thread 中被提炼为专用的 **PIN 设备框架**（`components/drivers/misc/pin.c`）。

### 4.1 数据结构映射体系

```text
┌─────────────────────────────────────────────────────────────┐
│                    struct rt_device_pin                     │
│ ┌───────────────────────────┬─────────────────────────────┐ │
│ │ struct rt_device parent;  │ const struct rt_pin_ops *ops│ │
│ └───────────────────────────┴─────────────────────────────┘ │
└──────────────────────────────────────────┬──────────────────┘
                                           │ 指向底层 BSP 实现
                                           ▼
                            ┌──────────────────────────────┐
                            │ static const struct          │
                            │   rt_pin_ops _stm32_pin_ops  │
                            ├──────────────────────────────┤
                            │ .pin_mode       = stm32_mode │
                            │ .pin_write      = stm32_write│
                            │ .pin_read       = stm32_read │
                            │ .pin_attach_irq = ...        │
                            │ .pin_irq_enable = ...        │
                            │ .pin_get        = ...        │
                            └──────────────────────────────┘
```

### 4.2 核心 API 链路跟踪

1. **电平写入 (`rt_pin_write`)**：
   - 应用层 `rt_pin_write(pin, val)` $\rightarrow$ 框架层 `_hw_pin.ops->pin_write(&_hw_pin.parent, pin, val)` $\rightarrow$ 驱动层 `stm32_pin_write`（计算端口与引脚号） $\rightarrow$ STM32 HAL 库 `HAL_GPIO_WritePin` $\rightarrow$ 操作硬件 `BSRR` 寄存器。
2. **中断绑定与分发 (`rt_pin_attach_irq` / `rt_pin_irq_enable`)**：
   - 绑定回调：`rt_pin_attach_irq` 将用户函数保存至 `pin_irq_hdr_tab[irqno]` 中断分发表；
   - 使能通道：`rt_pin_irq_enable` 调用 `HAL_NVIC_EnableIRQ`；
   - 物理触发：硬件触发 `EXTIx_IRQHandler` $\rightarrow$ `HAL_GPIO_EXTI_IRQHandler`（清除 Pending 标志） $\rightarrow$ `HAL_GPIO_EXTI_Callback` $\rightarrow$ `pin_irq_hdr` $\rightarrow$ 执行用户回调函数。

### 4.3 实操按键消抖深度对比

物理按键在闭合与释放瞬间会产生 5~20ms 的弹性机械抖动，导致一次按压触发多次中断。

| 消抖方案 | 工作原理 | 优点 | 缺点 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **软件延时消抖** | 检测到边沿后延时等待稳定 | 简单直观 | **严禁在 ISR 中延时**（会锁死调度器） | 仅限主循环轮询 |
| **软件时间戳消抖** | 中断发生时对比 `rt_tick_get() - last_tick` | 极轻量、非阻塞、ISR 安全 | 无法识别长按/双击 | 简单边沿触发 |
| **状态机消抖 (`button` 库)** | 定时器（20ms）周期采样电平并驱动 FSM | **支持单击/双击/长按/释放**，工业级健壮 | 占用微量定时器资源 | 复杂人机交互 |

- **星火一号 4 方向按键引脚**：`KEY_UP` (PC5), `KEY_DOWN` (PC1), `KEY_LEFT` (PC0), `KEY_RIGHT` (PC4)。

### 4.4 驱动排查与单步调试黄金法则
1. **确认设备注册**：通过 `list_device` 查看 `pin` 设备是否存在；
2. **排查 `ops` 虚表指针**：单步跟踪 `_hw_pin.ops` 确保函数指针不为空且正确挂接；
3. **排查时钟与引脚计算**：确认 `__HAL_RCC_GPIOx_CLK_ENABLE()` 是否开启，`GET_PIN` 宏计算的端口基地址是否准确。

## 五、 I2C 与 SPI 总线驱动开发体系

### 5.1 I2C 总线模型与传输机制

I2C 是半双工两线制（SCL + SDA）串行总线。RT-Thread 采用 **`struct rt_i2c_msg` 消息包** 统一调度：

```c
struct rt_i2c_msg
{
    rt_uint16_t addr;   /* 7 位从机物理地址 (框架会自动左移 1 位补齐读写位，应用无需左移) */
    rt_uint16_t flags;  /* 标志位: RT_I2C_WR (写) / RT_I2C_RD (读) / RT_I2C_NO_START */
    rt_uint16_t len;    /* 传输字节数 */
    rt_uint8_t  *buf;   /* 数据缓冲区首地址 */
};
```

- **组合时序读取**：调用 `rt_i2c_transfer(bus, msgs, 2)`，其中 `msgs[0]` 负责写入寄存器地址，`msgs[1]` 负责读取返回数据，底层自动产生 Repeated START 信号，避免总线仲裁丢失。
- **I2C 9-Pulse 总线锁死恢复机制**：
  - **产生机理**：当主控发生异常复位，而从机正处于向 SDA 发送低电平（ACK 态）时，SDA 会被从机持续拉死，主控无法再发出 START 信号。
  - **解法**：主控将 SCL 切换为 GPIO 输出，**连续向 SCL 发送 9 个时钟脉冲**，迫使从机移位寄存器走完并释放 SDA，随后发送一个 STOP 信号复位总线。
- **Soft-I2C vs 硬件 I2C**：当前多数 BSP 默认采用 GPIO 软件模拟 I2C（Soft I2C），兼容性与容错性极高；对高速传输需求可切至硬件 I2C 驱动。

### 5.2 SPI 总线-设备模型（Bus-Device Model）

SPI 总线采用“总线控制器（Bus）挂载多个从设备（Device）”的拓扑架构：

```text
┌─────────────────────────────────────────────────────────────┐
│                 SPI 总线控制器 (SPI Bus: spi2)               │
└──────────────┬──────────────────────────────┬───────────────┘
               │ 片选 CS (PB12)               │ 片选 CS (PB14)
┌──────────────▼──────────────┐┌──────────────▼──────────────┐
│  SPI Device (spi20: Flash)  ││  SPI Device (spi21: LCD 屏)  │
└─────────────────────────────┘└─────────────────────────────┘
```

1. **设备命名规范**：`spixy` —— `x` 代表 SPI 总线号（如 `spi2`），`y` 代表挂载在各片选引脚上的设备号（如 `spi20`）。
2. **动态挂载 API**：`rt_hw_spi_device_attach("spi2", "spi20", GPIOB, GPIO_PIN_12)`。
3. **SPI 配置参数 (`struct rt_spi_configuration`)**：
   - `mode`：CPOL（时钟极性）与 CPHA（时钟相位）组合出的 4 种 SPI 模式（模式 0~3）；
   - `max_hz`：最大时钟频率（如 1MHz ~ 20MHz）；
   - `data_width`：数据位宽（8 位 / 16 位）；
   - `bit_order`：位序（MSB First / LSB First）。
4. **传输 API 族**：
   - `rt_spi_transfer()`：全双工同时收发；
   - `rt_spi_send()` / `rt_spi_recv()`：单向发送/接收；
   - `rt_spi_send_then_send()` / `rt_spi_send_then_recv()`：组合指令时序。

## 六、 开发模式对比：基于芯片(BSP) vs 基于 SDK(CubeMX)

| 对比维度 | 基于芯片 (BSP 纯手动模式) | 基于 SDK (CubeMX 图形化模式) |
| :--- | :--- | :--- |
| **配置文件** | 手动编写 `board.h` / `board.c` | CubeMX 图形化生成 HAL 初始化配置 |
| **时钟树配置** | 在代码中手动计算并配置 PLL 寄存器 | 图形化时钟树自动生成，直观防错 |
| **引脚复用分配** | 手动查阅芯片手册并在驱动中宏定义 | 图形化点击引脚分配并自动处理冲突 |
| **适用场景** | 多芯片通用 BSP 移植、跨平台标准化适配 | 特定芯片快速原型验证、产品功能开发 |

## 七、 从简易 `test_drv` 到自研 `test_dev` 框架的进阶思考

在 Day4 课堂中，老师演示了通过 `rt_device_create()` 注册简易字符设备 `test_drv` 的基本语法。

在本次作业中，我们将其升华重构为**工业级三层虚拟设备框架 `test_dev`**：
1. **框架层抽象 (`test_dev.h` / `test_dev.c`)**：封装 `struct rt_test_device` 与 `struct rt_test_ops`，向上导出 `rt_test_dev_*` 专用 API 和 FinSH 调试命令，向下对齐标准 `rt_device` 调度；
2. **驱动层实现 (`drv_vtest.c`)**：实现 256 字节 FIFO 环形缓冲区，引入 `rt_mutex_t` 互斥锁保障多线程并发安全，支持 `NORMAL`、`LOOPBACK`、`ECHO`、`PATTERN` 4 种工作模式，并模拟中断触发 `rx_indicate`；
3. **应用测试验证 (`test_dev_sample.c`)**：包含标准 I/O 接口测试、高阶专用接口测试及生产者-消费者异步回调 IPC 闭环验证。

## 八、 总结与今日收获

1. **深刻领会了 C 语言面向对象设计思想**：通过 `rt_device` + `ops` 虚函数指针表，用纯 C 实现了与 C++ 虚基类媲美的多态机制；
2. **彻底打通了外设驱动调用链**：从上层 API、I/O 管理层、驱动层到 HAL 库及底层外设寄存器，建立了完整、透明的调用认知；
3. **掌握了主流总线通信范式**：深刻理解了 I2C 消息包组合传输机制与 9-Pulse 恢复原理，以及 SPI 总线-设备树模型。
