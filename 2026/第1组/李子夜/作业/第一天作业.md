## 一、Git 协作环境搭建（已完成）

### 1.1 确认上游仓库的约束

动手前先确认权限边界，避免走错路径：

```bash
# 查看自己对上游仓库的权限
curl "https://gitee.com/api/v5/repos/rtthread/rsoc-rtt?access_token=<token>"
# → pull: True   push: False   admin: False

# 查看 master 分支保护状态
curl "https://gitee.com/api/v5/repos/rtthread/rsoc-rtt/branches/master?access_token=<token>"
# → protected: True
```

**结论**：`push: False` + `master` 受保护 → 不存在直接推送通道，唯一路径是 **Fork → 分支 → PR**。

### 1.2 Fork 与克隆

```bash
# Fork（通过 API，等价于网页点 Fork）
curl -X POST "https://gitee.com/api/v5/repos/rtthread/rsoc-rtt/forks" -d "access_token=<token>"
# → HTTP 201，得到 https://gitee.com/CyberSprout/rsoc-rtt

# 克隆自己的 Fork（不是上游）

cd rsoc-rtt

# 挂载上游，用于后续同步
git remote add upstream https://gitee.com/rtthread/rsoc-rtt.git

```

**修复**：

```bash

```


### 1.4 Windows + 中文路径配置（实测）

本仓库路径全为中文（`2026/第1组/李子夜/笔记/`），需要额外配置。

**① `core.quotepath` —— 中文文件名显示为八进制转义**

```bash
# 默认（未设置，等效 true）
$ git status --short
?? "\347\254\2541\347\273\204/"

# 设为 false 后
$ git status --short
?? 第1组/
```

修复：

```bash
git config --global core.quotepath false
git config --global i18n.logOutputEncoding utf-8
```

**② `core.autocrlf` —— 换行符转换**

```bash
$ git config --show-origin --get-all core.autocrlf
file:C:/Program Files/Git/etc/gitconfig    true
```

Git for Windows 安装默认值为 `true`（入库转 LF、签出转 CRLF）。本次每次 `git add` 都出现提示，属预期行为：

```
warning: in the working copy of '2026/第1组/李子夜/笔记/第一天笔记.md',
LF will be replaced by CRLF the next time Git touches it
```

**③ `core.longpaths`** —— 本机已为 `true`，中文长路径未触发 260 字符限制。

## 三、过程中排查的一个编码问题

通过 API 创建 PR 时，标题与正文中的中文在 Gitee 上存成了乱码。

**错误做法**：

```bash
curl -X POST ".../pulls" --data-urlencode "title=【RSOC26】..."
```

`--data-urlencode` 发送的是 `application/x-www-form-urlencoded` 且未声明 charset，服务端按非 UTF-8 解码。

**验证手段**（关键：不能只看终端，终端本身可能是编码问题）：把 API 返回写入 UTF-8 文件再读回，确认服务端存储的确实是乱码，而非本地显示问题。

**修复做法**：改用 JSON + 显式声明字符集，请求体从文件读入以绕开 shell 编码：

```bash
curl -X PATCH ".../pulls/104" \
  -H "Content-Type: application/json; charset=utf-8" \
  --data-binary "@body.json"
```

修复后读回确认：

```
TITLE : 【RSOC26】第1组 李子夜 - 第一课笔记：如何使用 Git 去管理你的工程
```

对照组：同一 shell 下 `git commit -m "docs(第1组/李子夜): ..."` 的中文全程正常，说明问题不在 Git 也不在终端，仅在 curl 的表单编码路径上。

### 4.3 本机实际环境

RT-Thread Studio 已安装并成功创建、编译工程：

| 项 | 实际值 |
|---|---|
| Studio 安装路径 | `C:\RT-ThreadStudio\` |
| 工程路径 | `C:\RT-ThreadStudio\workspace\qemu-a9\` |
| 内核版本 | **4.1.1**（`RT_VERSION 4` / `RT_SUBVERSION 1` / `RT_REVISION 1`） |
| SOC | `SOC_STM32F407ZG`，`ARCH_ARM_CORTEX_M4` |
| 板级配置 | `BOARD_STM32F407_SPARK`（星火一号） |
| 调试接口 | SWD / ST-Link |
| 编译产物 | `Debug/rtthread.elf`（545,880 B）、`Debug/rtthread.bin`（70,680 B） |

**一个值得记录的坑**：工程目录名为 `qemu-a9`，但 `rtconfig.h` 中实际配置是 STM32F407ZG + STM32 HAL 驱动 + CubeMX，调试配置文件为 `qemu-a9.STLink.Debug.rttlaunch`（SWD 接口）。即目录名与实际目标平台不一致，**不能按 QEMU 方式运行**，需通过 ST-Link 下载到实体开发板。

> 这类"名字与内容不符"的问题正是工程管理要防的：后续接手的人（包括自己）会按目录名做出错误假设。规范做法是工程名如实反映目标平台，或在 `README.md` 中显式说明。

```c
#define RT_TICK_PER_SECOND         1000   /* 1 tick = 1 ms */
#define RT_ALIGN_SIZE              4
#define RT_USING_OVERFLOW_CHECK           /* 栈溢出检查已开启 */
#define RT_USING_HOOK
```
