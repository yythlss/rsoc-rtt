## 二、线程创建与启动（静态初始化路径）

### 2.1 内核自带线程的创建方式

本工程中运行时存在的三个线程全部使用 **静态初始化**（`rt_thread_init`）创建：

#### tidle0 —— idle 线程

**源码位置**：`rt-thread/src/idle.c`，第 316–330 行

```c
rt_thread_init(&idle[i],
               tidle_name,
               rt_thread_entry,
               RT_NULL,
               &rt_thread_stack[i][0],
               sizeof(rt_thread_stack[i]),
               RT_THREAD_PRIORITY_MAX - 1,  /* 31 */
               32);                         /* 时间片 */
rt_thread_startup(&idle[i]);
```

- 初始化时**不分配内存**，`idle[]` 和 `rt_thread_stack[][]` 已经在 BSS 段声明
- 优先级 31（最低），时间片 32 tick
- 名字格式为 `tidle0`（第 i 个 CPU 对应 `tidle{i}`）

#### main —— 用户主线程

**源码位置**：`rt-thread/src/components.c`

```c
tid = rt_thread_create("main", main_thread_entry, RT_NULL,
                       RT_MAIN_THREAD_STACK_SIZE,    /* 2048 */
                       RT_MAIN_THREAD_PRIORITY,       /* 10 */
                       20);                           /* 时间片 */
rt_thread_startup(tid);
```

- 使用 **动态创建**（堆上分配）
- 优先级 10，高于 tshell(20)，在当前线程中优先级最高
- 时间片 20 tick

#### tshell —— finsh 命令行线程

- 由 finsh 组件初始化时创建（优先级 20，栈 4096）
- 等待 UART 输入，解析后启动了对应线程执行

### 2.2 静态 vs 动态初始化对比

| 维度 | 静态 `rt_thread_init` | 动态 `rt_thread_create` |
|---|---|---|
| 内存来源 | 外部传入（BSS/数据段） | 堆分配 |
| 创建后状态 | `INIT` | `INIT` |
| 启动方式 | `rt_thread_startup()` | `rt_thread_startup()` |
| 适合场景 | 内核线程（idle、system） | 应用线程 |
| 失败模式 | 传入 NULL 时断言 | 返回 `RT_NULL` |

## 三、线程休眠与延迟

### 3.1 三种延时 API

| 函数 | 单位 | 本质 |
|---|---|---|
| `rt_thread_delay(ms)` | 毫秒 | `sleep(ms * RT_TICK_PER_SECOND / 1000)` |
| `rt_thread_mdelay(ms)` | 毫秒 | 循环调用 `rt_hw_us_delay`（阻塞 CPU） |
| `rt_thread_delay_until(previous_tick, ms)` | 毫秒 | 绝对时间唤醒，消除累积误差 |

### 3.2 本工程中的实际使用

用户代码（`applications/main.c`）：

```c
rt_pin_write(PIN_LED_R, PIN_LOW);
rt_thread_mdelay(500);
rt_pin_write(PIN_LED_R, PIN_HIGH);
rt_thread_mdelay(500);
count++;
```

- LED 亮/灭各 500ms，周期 1s
- 低电平亮（`PIN_LOW`），高电平灭
- `rt_thread_mdelay` 忙等待，期间 CPU 不释放给其他线程

> **问题**：用 `rt_thread_delay(500)` 替代 `rt_thread_mdelay(500)` 可以释放 CPU 给 tshell 和 idle，但当前代码用了忙等待版本。

## 四、线程挂起与恢复

### 4.1 本工程中的 `rt_thread_suspend`

**调用位置**：`thread.c` 第 840 行

**关键约束**（4.1.1）：

```c
RT_ASSERT(thread == rt_thread_self());
```

即：**当前版本的 RT-Thread 只允许挂起自身**。不能跨线程挂起。

恢复操作无此限制：

```c
rt_thread_resume(thread);   /* 任何线程/ISR 都可以调用 */
```

### 4.2 场景推导

如果用户代码中调用：

```c
rt_thread_suspend(rt_thread_self());
```

- 当前线程状态变为 `SUSPEND`
- 触发调度，最高优先级的 READY 线程获得 CPU
- 必须在另一个线程或 ISR 中调用 `rt_thread_resume()` 才能恢复，否则线程休眠
- `remaining_tick > 0` 时，超时也会自动恢复

## 五、线程删除与延迟回收

### 5.1 删除流程源码

`rt_thread_delete(rt_thread_self())` 执行以下步骤：

```c
/* thread.c 第 499 行附近 */
RT_ASSERT(thread == rt_thread_self());

thread->stat = RT_THREAD_CLOSE;
/* 挂入 defunct 链表 */
rt_list_insert_after(&_rt_thread_defunct, &thread->tlist);
/* 触发调度 */
rt_schedule();
```

**实际内存释放**不在此刻发生，而是由 idle 线程代为执行：

```c
/* idle.c 第 160-170 行 */
while (1) {
    thread = rt_list_entry(_rt_thread_defunct.next, struct rt_thread, tlist);
    if (&thread->tlist == &_rt_thread_defunct) break;
    rt_list_remove(&thread->tlist);
    if (rt_object_is_systemobject((rt_object_t)thread))
        rt_memset(thread, 0, sizeof(struct rt_thread));
    else
        rt_free(thread->stack_addr);
}
```

### 5.2 实践要点

1. `rt_thread_delete` 后线程**不会立刻消失**，在 `list_thread` 中仍然可见（状态 `close`）
2. 真实释放等 idle 线程调度时执行
3. 若高优先级线程持续占用 CPU，idle 永远得不到时间片，defunct 队列堆积，堆内存泄漏

## 七、思考题

### Q1：为什么 `rt_thread_suspend` 只能挂起自己？

从源码看，`thread.c` 第 840 行有硬性断言：

```c
RT_ASSERT(thread == rt_thread_self());
```

**分析**：
- RT-Thread 4.x 的设计目标之一是轻量，跨线程挂起需要额外的同步机制（如 mutex）来避免竞态
- 如果线程 A 挂起线程 B，而 B 正好持有一个 mutex，A 也会被阻塞，形成死锁
- 限制为自挂起是最安全的做法，用户代码应在自身逻辑中控制流程
- RT-Thread 5.x 起放宽了此限制，但 4.1.1 保留此约束

### Q2：`rt_thread_mdelay` 和 `rt_thread_delay` 的区别对系统的影响

- `rt_thread_mdelay`：忙等待，不释放 CPU。在整个延时期间当前线程持续占用 CPU，其他同优先级的线程无法运行
- `rt_thread_delay`：挂起当前线程，让出 CPU。调度器切换到最高优先级的 ready 线程
- 在本工程 main 线程（优先级 10）中使用 `rt_thread_mdelay` 没有问题，因为它是用户线程中优先级最高的，不释放 CPU 不会饿死其他用户线程
- 但如果在优先级低于 tshell(20) 的线程中使用 `rt_thread_mdelay`，tshell 依然可以运行

### Q3：栈溢出时为什么系统 hang 而不复位？

源码 `scheduler.c` `_scheduler_stack_check`：

```c
rt_base_t level = rt_hw_interrupt_disable();
while (level);   // 死循环
```

- 关中断后进入 `while(1)`，不调用任何 fault handler
- Bootloader 没有被触发，因为程序仍在运行——只是停了
- 原因：RT-Thread 设计者认为栈溢出是**严重错误**，停止比继续运行更安全；且 HardFault 可能在栈溢出时已损坏异常栈，进入 fault handler 本身也会崩溃
- 但对于开发者来说，调试时现象是系统完全无响应，必须通过 J-Link / ST-Link 抓取 SP 和 PC 判断
