# 【RSOC26】第一课：如何使用 Git 去管理你的工程

> 本课目标：掌握在一个**多人协作、主干受保护**的仓库里提交自己成果的完整流程，以及出问题时的排查与责任界定方法。
>
> 全部示例以夏令营笔记仓库 `gitee.com/rtthread/rsoc-rtt` 为对象，作者身份为**第 1 组 李子夜**。

---

## 一、先看清约束：为什么必须走 Fork + PR

打开夏令营仓库 `gitee.com/rtthread/rsoc-rtt`，`README.md` 规定了目录结构：

```
└─2026
    ├─第1组
    │  └─李子夜
    │      └─笔记
    │          └─第一天笔记.md
    │      └─作业
    │          └─第一天作业.md
    ├─第2组
    ...
    └─第6组
```

再查一下这个仓库的分支状态：

```bash
curl "https://gitee.com/api/v5/repos/rtthread/rsoc-rtt/branches"
```

返回中有两个关键信息：

- 整个仓库**只有 `master` 一个分支**
- `"protected": true` —— **`master` 是受保护分支**

**结论：任何人都无法直接 `git push` 到这个仓库。**

这不是配置疏漏，而是所有正规工程的标准做法：主干只能通过**可审查、可追溯、可回退**的路径接收变更。因此唯一的提交路径是：

```
Fork（复制到自己账号） → 在自己仓库改 → 发 Pull Request → 维护者审查后合并
```

本课就是把这条路径拆开讲。

## 二、心智模型：你要同时管三个仓库

大部分 Git 混乱源于脑子里只有"一个仓库"。实际上有三个：

```
        ┌──────────────────────────────────────┐
        │  upstream                            │
        │  gitee.com/rtthread/rsoc-rtt         │  官方仓库
        │  只读 + 可发 PR，不可写               │
        └──────────────────────────────────────┘
              ▲                    │
              │ ③ Pull Request     │ ① git fetch upstream
              │                    ▼
        ┌──────────────────────────────────────┐
        │  origin                              │
        │  gitee.com/<你的用户名>/rsoc-rtt      │  你 Fork 出来的，有全部权限
        └──────────────────────────────────────┘
              ▲                    │
              │ ② git push origin  │ git clone
              │                    ▼
        ┌──────────────────────────────────────┐
        │  local                               │
        │  C:\Users\llwxy\Documents\RTT\...    │  本地工作区
        └──────────────────────────────────────┘
```

三个方向，记住即可：

| 动作 | 方向 | 手段 |
|---|---|---|
| 获取他人最新进展 | upstream → local | `git fetch upstream` |
| 上传自己的成果 | local → origin | `git push origin <分支>` |
| 请求合入官方 | origin → upstream | 网页开 Pull Request |

**注意：Pull Request 不是 Git 命令，是 Gitee 平台功能。** Git 负责版本，平台负责协作流程，二者分工不同。

## 三、环境准备

### 3.1 身份配置（决定提交归属，必须先做）

每个 Git 提交记录 `author name` 和 `author email`。**Gitee 依靠 email 把提交与账号关联。**

如果 email 与 Gitee 绑定邮箱不一致，你的提交在网页上会显示为一个无头像、无法点击的陌生用户 —— 贡献统计里没有你，也无法通过账号追溯到你。

```bash
# 查看当前配置
git config --global user.name
git config --global user.email

# 设置（name 建议直接用 Gitee 用户名）
git config --global user.name  "你的Gitee用户名"
git config --global user.email "你注册Gitee的邮箱"
```

如果这台机器上有多个身份，在仓库内做局部覆盖（去掉 `--global`）：

```bash
cd rsoc-rtt
git config user.email "你注册Gitee的邮箱"    # 仅对本仓库生效
```

**首次提交后立即验证：**

```bash
git log -1 --format='作者：%an <%ae>'
```

> 补救：如果邮箱写错且**尚未推送**，可用 `git commit --amend --reset-author --no-edit` 修正。已推送则不要改（原因见第九节）。

### 3.2 Windows + 中文路径的四项配置

本仓库路径全部为中文（`2026/第1组/李子夜/笔记/`），在 Windows 下有几个必须提前处理的问题。以下均为本机实测。

**① `git status` 显示为八进制转义**

```bash
# core.quotepath 未设置（默认 true）时：
$ git status --short
?? "\347\254\2541\347\273\204/"

# 设置为 false 后：
$ git status --short
?? 第1组/
```

修复：

```bash
git config --global core.quotepath false
git config --global i18n.logOutputEncoding utf-8
```

**② 换行符（CRLF / LF）**

查看本机来源：

```bash
$ git config --show-origin --get-all core.autocrlf
file:C:/Program Files/Git/etc/gitconfig    true
```

`core.autocrlf=true` 是 Git for Windows 的安装默认值：提交时把 CRLF 转为 LF 入库，签出时转回 CRLF。**单机自洽，但团队不一致时会出问题** —— 若有人设为 `false` 并用 CRLF 编辑器提交，你再改这个文件，Git 会判定**每一行都变了**，PR diff 全红，`git blame` 也会把整个文件的记录指向你。

根治方式是让规则跟着仓库走，在仓库放 `.gitattributes`：

```gitattributes
* text=auto eol=lf
*.md text eol=lf
*.png binary
*.jpg binary
```

> 但这是公共文件，**不要自己加了直接提 PR**，先在 Issue 或群里与维护者确认（见第十一节）。

**③ 路径长度**

中文目录加上本地前缀容易触及 Windows 260 字符上限：

```bash
git config --global core.longpaths true
```

同时建议本地克隆路径尽量短，不要放在层层嵌套的中文目录里。

**④ PowerShell 不支持 `&&`**

Windows PowerShell 5.1 **没有** `&&` 和 `||`，从教程抄的 `git add . && git commit -m "x"` 会直接语法报错：

```powershell
# PowerShell 写法
git add . ; git commit -m "docs: 第一天笔记"
git add . ; if ($?) { git commit -m "docs: 第一天笔记" }
```

```bash
# Git Bash 写法，&& 可用
git add . && git commit -m "docs: 第一天笔记"
```

**建议：Git 操作统一在 Git Bash 里执行**，命令兼容性和路径处理都更省事。

## 四、完整流程

### 步骤 1：Fork

浏览器打开 `https://gitee.com/rtthread/rsoc-rtt`，点击 **Fork**，复制到自己账号下。

此步无命令行等价操作（除调用 API）。完成后得到 `https://gitee.com/<你的用户名>/rsoc-rtt`。

### 步骤 2：Clone **自己的 Fork**

```bash
cd ~/Documents/RTT
git clone https://gitee.com/<你的用户名>/rsoc-rtt.git
cd rsoc-rtt
```

**常见错误：clone 了官方仓库。** 那样 `origin` 指向你没有写权限的地址，push 必然失败。验证：

```bash
git remote -v
# origin  https://gitee.com/<你的用户名>/rsoc-rtt.git (fetch)
# origin  https://gitee.com/<你的用户名>/rsoc-rtt.git (push)
```

必须是**你的用户名**。

> **关于登录**：本机 `credential.helper = manager`（Git for Windows 自带的 Git Credential Manager）。首次 push 会弹窗登录 Gitee，凭证随后存入 Windows 凭据管理器，无需重复输入。若使用私人令牌，用户名填 Gitee 用户名，密码位置填令牌。

### 步骤 3：挂载 upstream

```bash
git remote add upstream https://gitee.com/rtthread/rsoc-rtt.git
git remote -v      # 应同时出现 origin 与 upstream
```

**为什么必须加**：Fork 是**一次性快照，不会自动跟随官方更新**。夏令营几十人每天往官方仓提交，没有 `upstream`，你几天后就在一个过时的仓库上工作，PR 一提就冲突。

### 步骤 4：创建分支

```bash
git fetch upstream                           # 先取官方最新
git switch -c day1/notes upstream/master     # 基于官方最新创建分支
```

**铁律：不在 `master` 上写任何东西。**

理由是实用的：**本地 `master` 应始终是官方 `master` 的干净镜像。** 一旦在上面写了自己的内容，它就"脏"了，之后每次同步官方进展都会打架。保持干净，同步就永远无痛。

分支命名约定：

```
day1/notes        第一天笔记
day1/homework     第一天作业
day2/notes
fix/typo-day1     修错别字
```

**一件事一分支。** 因为 PR 的粒度等于分支的粒度 —— 笔记和作业混在一个分支里，审查者就得一次看两件不相干的事，且只能一起合并或一起打回。

### 步骤 5：写内容

```bash
mkdir -p "2026/第1组/李子夜/笔记"
mkdir -p "2026/第1组/李子夜/作业"
```

严格遵守 README 的目录结构。**目录约定就是这个项目的接口**，自己发明一套会导致维护者手工搬文件，或直接被打回。

### 步骤 6：提交前必做的三条检查

```bash
git status                       # 哪些文件变动了
git diff                         # 未暂存的改动内容
git add "2026/第1组/李子夜"        # 明确指定路径，不用 git add .
git diff --cached                # ★ 确认即将提交的内容
```

第四条最常被跳过，也最重要。它回答唯一要紧的问题：**我即将写入历史的，就是我想写的吗？**

> **`git add .` 是最主要的事故来源。** 它会把目录下所有内容 —— 编译产物、临时文件、误存的截图 —— 一并纳入。

### 步骤 7：提交与推送

```bash
git commit -m "docs(第1组/李子夜): 添加第一天笔记"
git push -u origin day1/notes
```

`-u` 只需首次使用，它绑定本地与远程分支，之后 `git push` 即可。

### 步骤 8：开 Pull Request

回到浏览器打开你的 Fork 页面，刚 push 完通常会有创建 Pull Request 的提示，也可从 Pull Requests 入口手动新建。

四个字段不能填错：

```
源：    <你的用户名>/rsoc-rtt : day1/notes
目标：  rtthread/rsoc-rtt    : master
```

> Gitee 页面布局与按钮文案会随版本调整，以你打开的页面为准。**逻辑不变：从我的分支，合入官方的 master。**

## 五、Commit Message 规范

### 格式

```
<类型>(<范围>): <一句话说明做了什么>

（空行）
（可选：为什么这么改）
```

常用类型：

| 类型 | 用途 |
|---|---|
| `docs` | 笔记、作业、README（夏令营中绝大多数提交属于此类） |
| `feat` | 新增功能 |
| `fix` | 修 bug、修笔误 |
| `refactor` | 重构，行为不变 |
| `chore` | 杂务：`.gitignore`、目录调整 |
| `style` | 只改格式排版 |

### 对照

| ❌ | ✅ |
|---|---|
| `update` | `docs(第1组/李子夜): 添加第一天笔记` |
| `修改` | `fix(第1组/李子夜): 修正笔记中优先级数值笔误` |
| `1` | `docs(第1组/李子夜): 补充线程调度器一节` |
| `最终版` / `最终版2` / `真的最终版` | 不应存在 |

### 为什么规范 message 是实际收益，不是形式主义

设想排查场景：某文件出了问题，用 `git blame` 定位到一个提交。

- **提交 A**：message 为 `update`，改动 47 个文件、涉及 5 个人的目录 → 无法分辨哪部分是有意为之、哪部分是误伤，**这 47 个文件的问题默认全归此人**。
- **提交 B**：message 为 `docs(第1组/李子夜): 添加第一天笔记`，只动 1 个文件 → 一眼即可关联或排除。

**提交是日志，不是存档。** 写完一小块就提一次，不要攒一整天。

### 多行 message 的写法

```bash
# Git Bash
git commit -F - <<'EOF'
docs(第1组/李子夜): 添加第一天笔记

补充 Git 协作流程一节，记录 master 受保护、
必须走 Fork + PR 的原因。
EOF
```

```powershell
# PowerShell 5.1：结尾的 '@ 必须顶格在行首，不能缩进
git commit -m @'
docs(第1组/李子夜): 添加第一天笔记

补充 Git 协作流程一节。
'@
```

或直接执行 `git commit`（不带 `-m`），由编辑器输入。

## 六、同步 upstream：rebase 与 merge

官方 `master` 每天都在变。你昨天开的分支，今天可能已落后几十个提交。

标准四步：

```bash
git fetch upstream                                # 1. 下载官方最新（不动工作区，安全）
git switch day1/notes                             # 2. 回到自己分支
git rebase upstream/master                        # 3. 把自己的提交移到官方最新之后
git push --force-with-lease origin day1/notes     # 4. 更新 Fork 上的分支
```

### 两者区别

```
merge（有分叉与合并节点）：
  官方 ──A──B──C─────────M──
              \         /
   你的         D──E───┘

rebase（线性）：
  官方 ──A──B──C──D'──E'──
```

**个人分支推荐 rebase**，唯一理由：**线性历史大幅降低溯源难度。** `git log` 是一条干净时间线，`git bisect` 二分查找不会在合并节点上迷路，"往前数三个提交"有明确含义。

### 红线

> **不要 rebase 已被他人拉取过的公共分支。**

rebase 的本质是**重写历史**：丢弃原提交，生成内容相同但 SHA 全新的提交。自己独占的分支无所谓；若他人已基于该分支工作，rebase 会让他的本地与远程彻底分叉。

同理，注意上面第 4 步用的是 `--force-with-lease` 而非 `--force`：

- `--force`：无条件覆盖远程
- `--force-with-lease`：**先检查远程是否仍是你上次看到的状态**，若他人期间推送过则拒绝执行

**始终使用 `--force-with-lease`。**

## 七、冲突处理

**本仓库的目录设计天然防冲突**：每人在 `2026/第N组/自己的名字/` 下活动，Git 按文件按行判定冲突，各改各的文件不会撞上。README 的目录规范本质上是一个**冲突隔离设计**。

真正会冲突的是**共享文件**：根 `README.md`、`2026/第N组/README.md`，以及未来可能出现的索引页。

### 解决步骤

rebase 中途冲突时，Git 会停下并指出冲突文件。打开后会看到：

```
<<<<<<< HEAD
（upstream/master 上当前的内容）
=======
（你的提交想写入的内容）
>>>>>>> docs(第1组/李子夜): 更新组内索引
```

1. 人工决定最终内容（索引类文件通常两边都要保留）
2. **删除 `<<<<<<<`、`=======`、`>>>>>>>` 三行标记** —— 漏删并提交上去是常见翻车点
3. 告知 Git 已解决：

```bash
git add "冲突的文件"
git rebase --continue
```

### 随时可以中止

```bash
git rebase --abort      # 完全取消本次 rebase，回到操作前
git merge --abort       # merge 版本
```

`--abort` 是完整回滚，安全。**看不懂就 abort 重来，好过硬着头皮乱敲。**

## 八、溯源：查历史的核心命令

Git 的核心能力是精确回答「什么时候、谁、为什么改了这一行」。

### 8.1 看全局

```bash
git log --oneline --graph --decorate --all
```

`--oneline` 一行一提交、`--graph` 画分支拓扑、`--decorate` 标出分支标签、`--all` 含所有分支。建议做成别名：

```bash
git config --global alias.lg "log --oneline --graph --decorate --all"
```

### 8.2 追踪单个文件的完整历史

```bash
git log --follow -p -- "2026/第1组/李子夜/笔记/第一天笔记.md"
```

- `--follow`：**文件被改名或移动后仍继续往前追**
- `-p`：显示每次提交的具体改动行

### 8.3 逐行定位：`git blame`

```bash
git blame "2026/第1组/李子夜/笔记/第一天笔记.md"
git blame -L 40,60 "2026/第1组/李子夜/笔记/第一天笔记.md"    # 只看 40-60 行
```

每行前显示**最后修改该行的提交 SHA、作者、日期**。

### 8.4 查看某次提交

```bash
git show <SHA>                         # 改了什么
git show <SHA> --stat                  # 只看文件清单与增删统计
git show <SHA>:"路径/文件.md"           # 查看该时刻此文件的完整内容
```

### 8.5 定位某段内容的引入者：`git log -S`

```bash
git log -S "rt_thread_mdelay" --oneline
```

`-S` 搜索**哪次提交改变了该字符串的出现次数** —— 即谁添加的、谁删除的。排查"这个配置从哪来的"时效率远高于肉眼翻 log。

### 8.6 二分定位故障：`git bisect`

```bash
git bisect start
git bisect bad                   # 当前版本是坏的
git bisect good <某个正常的SHA>   # 该版本是好的
# Git 自动签出中间提交，测试后告知结果：
git bisect good                  # 或 git bisect bad
# 重复几次后，Git 指出第一个出问题的提交
git bisect reset                 # 结束
```

**对数复杂度**：100 个提交中定位，约需 7 次测试。

### 8.7 本地恢复：`git reflog`

```bash
git reflog
```

记录本地 HEAD 的每次移动（切分支、commit、rebase、`reset --hard`）。**即使 `reset --hard` 删掉了提交，只要是本地操作过的，基本都能找回：**

```bash
git reflog                        # 找到目标状态，如 HEAD@{5}
git reset --hard HEAD@{5}
```

> `reflog` 默认保留 90 天，且**仅存在于本地** —— 未推送的内容换台机器就没有了。

### 8.8 汇总

| 需求 | 命令 |
|---|---|
| 整体历史与分支形状 | `git log --oneline --graph --decorate --all` |
| 某文件完整变更史（含改名） | `git log --follow -p -- <文件>` |
| 某一行是谁写的 | `git blame <文件>` / `git blame -L a,b <文件>` |
| 某次提交的内容 | `git show <SHA>` |
| 某段内容的引入者 | `git log -S "关键字"` |
| 哪个提交导致故障 | `git bisect` |
| 恢复本地误操作 | `git reflog` + `git reset --hard HEAD@{n}` |
| 某人某时间段的提交 | `git log --author="名字" --since="2026-08-17"` |

## 九、责任边界：五条自保规则

多人协作中，"文件被覆盖了""内容不见了"是客观会发生的。区别只在于它是**可查证的事实**，还是靠猜和争论。以下五条本质上是在保护你自己。

### 1. 身份必须真实

见 3.1 节。email 配错的后果：你的产出可能算到别人头上，且**你没有任何证据链证明哪些提交是你的、哪些不是**。

### 2. 提交要小，message 要准

见第五节。这是你的证据链 —— 每个提交只动一个文件、意图明确，任何问题都能被精确关联或排除。

### 3. 不代人提交，不共用账号

帮同学"我给你推上去"会导致提交作者是你、内容是他的，记录从此错误且极难更正。正确做法是教他自己发 PR。确实需要代提时用正规机制：

```bash
git commit --author="他的名字 <他的邮箱>" -m "..."
```

或在 message 末尾添加：

```
Co-authored-by: 某某 <某某的邮箱>
```

### 4. 不对公共分支 force push

**`git push --force` 到他人也在使用的分支，会永久销毁"谁改了什么"的记录。** 原提交从远程消失，历史被替换。这一操作的性质不是失误，而是篡改记录。

- 自己的 PR 分支需要改历史：可以，**但用 `--force-with-lease`**
- `master` 或任何他人在用的分支：**不要**

本仓库 `master` 受保护，平台层面就会拒绝 —— **这个保护是在帮你，不要设法绕过。**

### 5. 撤销已推送的提交用 `revert`，不用 `reset`

| | `git revert <SHA>` | `git reset --hard <SHA>` |
|---|---|---|
| 做法 | **新增**一个反向提交 | **删除**后续提交 |
| 历史 | 错误与修正都保留 | 抹去错误发生的痕迹 |
| 已推送的提交 | ✅ 唯一正确选择 | ❌ 需 force push，见规则 4 |

```bash
git revert <出问题的SHA>
```

`revert` 留下的是一条负责任的记录：出错 → 发现 → 修正。而抹掉痕迹的人，在旁人看来反而是第一嫌疑人。

### 如何证明"不是我"

```bash
# 1. 这几行最后是谁改的
git blame -L 30,40 "路径/文件.md"

# 2. 我在这段时间内的全部提交（范围外的都不是我）
git log --author="你的Gitee用户名" --since="2026-08-17" --oneline --stat

# 3. 该文件的完整变更史
git log --follow --format="%h %an %ad %s" -- "路径/文件.md"
```

> **规范的最终目的不是在追责时自保，而是让追责不必发生。** 当提交都小而清晰、身份真实、历史从不篡改，出问题时看一眼 log 即知原委，改掉继续 —— 没有人需要猜，也就没有人需要背锅。

> `*.uvguix.*` 存的是**个人窗口布局**，一旦提交，每个打开工程的人都会看到它变化并互相覆盖，天天冲突且毫无意义。

注意：根目录 `.gitignore` 是公共文件，修改前先沟通。

### 已误提交的处理

```bash
git rm --cached -r build/                     # 停止跟踪，保留本地文件
git commit -m "chore: 停止跟踪构建产物"
```

**这只是从此不再跟踪，历史中那份仍在。** 彻底清除需重写历史，而重写公共仓库历史违反规则 4 —— **所以一开始就不要提上去。**

### 大文件

- 截图先压缩，一张配图不需要 5MB
- 不提交视频、固件包、完整工具链
- 需分享大文件用网盘链接

Git 对二进制文件是**每个版本存一整份**，一个反复修改的 10MB 图片能把仓库撑到几百 MB，所有人 clone 都要等。

## 十一、协作约定

### PR 描述模板

PR 是你与维护者之间唯一的沟通界面：

```markdown
### 内容
第 1 组 李子夜 第一天笔记 + 第一天作业

### 变更文件
- `2026/第1组/李子夜/笔记/第一天笔记.md`（新增）
- `2026/第1组/李子夜/作业/第一天作业.md`（新增）

### 自查
- [x] 目录结构符合 README 规范
- [x] 仅改动自己名下目录，未触碰他人文件
- [x] 已 rebase 到最新 upstream/master，无冲突
- [x] 无构建产物、无大文件
```

其中「仅改动自己名下目录」最关键 —— 它明确划定了本次 PR 的责任边界，维护者一眼即知风险范围。

### Issue 的使用

- 想改公共文件（根 `README.md`、`.gitignore`、`.gitattributes`）→ **先开 Issue，不要直接 PR**
- 发现仓库结构或模板有歧义 → 开 Issue
- 求助 → 开 Issue，**贴完整报错**，不要只说"跑不起来"

**判断标准：改自己的东西直接 PR，改公用的东西先商量。**

### 组内索引文件

`2026/第N组/README.md` 是唯一会频繁冲突的文件。两种做法：

1. **由一人统一维护**，其他人不动 —— 冲突源归零
2. 约定**只在文件末尾追加**，不插入中间 —— Git 对同一行附近的并发修改最易冲突，对追加到不同位置相对宽容

## 十二、每日操作清单

```bash
# ① 同步（每天第一件事）
git switch master
git fetch upstream
git reset --hard upstream/master     # ⚠ 有破坏性，仅在 master 保持干净时安全
git push origin master

# ② 开当天分支
git switch -c day2/notes

# ③ 在 2026/第1组/李子夜/ 下写内容

# ④ 提交前四连
git status
git diff
git add "2026/第1组/李子夜"
git diff --cached

# ⑤ 提交推送
git commit -m "docs(第1组/李子夜): 添加第二天笔记"
git push -u origin day2/notes

# ⑥ 浏览器开 PR，按模板写描述

# ⑦ 合并后清理
git switch master
git branch -d day2/notes
git push origin --delete day2/notes
```

### 救命指令速查

| 情况 | 命令 |
|---|---|
| 改错了还没 `add`，想丢弃 | `git restore <文件>` |
| 已 `add`，想取消暂存（保留内容） | `git restore --staged <文件>` |
| 刚提交发现 message 写错（**未推送**） | `git commit --amend` |
| 撤销提交但保留改动 | `git reset --soft HEAD~1` |
| 活没做完要紧急切分支 | `git stash` → 回来 `git stash pop` |
| 撤销**已推送**的提交 | `git revert <SHA>` |
| 把本地搞坏了 | `git reflog` → `git reset --hard HEAD@{n}` |
| rebase / merge 中途乱了 | `git rebase --abort` / `git merge --abort` |
| 确认当前在哪个分支 | `git status` / `git branch -vv` |

## 本课要点

1. **`master` 受保护 → 唯一路径是 Fork + PR**，这是所有正规工程的标准做法
2. **三个仓库**：upstream 只读、origin 是你的 Fork、local 是工作区；必须挂 `upstream` 才能同步
3. **`user.email` 决定提交归属**，配错等于放弃了自己的署名权与举证能力
4. **不在 `master` 上写东西**，保持它是官方的干净镜像
5. **提交前必看 `git diff --cached`**，不要用 `git add .`
6. **提交小、message 准**，这既是可读的历史，也是可查的责任边界
7. **不对公共分支 force push**，撤销已推送的提交用 `revert`
